# 结构化业务规则 — 文档优化设计

## 背景

优化 `training_doc/知识点/需求代码化.md`，基于以下认知迭代：

1. 需要结构化的不是所有"需求"，而是 **强规则/强逻辑的业务规则**
2. PRD 作为增量/变更描述是 PM 工作性质决定的终态，不会被替代
3. 结构化业务规则 / SPEC / 测试用例三者描述同一对象，当前通过 ID 引用联动，未来可能合并
4. PM 可直接维护结构化文档，Agent 辅助只是更便捷的选项

## 各章内容要点

### 第 1 章：Agent 为什么读不懂 PRD

保留当前三个问题（找不到全貌、边界模糊、AC 无法自动验证），目标句改写为：

> **结构化业务规则的目标**：把为人准备的增量描述，改造成 Agent 能直接消费的结构化资产——让每个业务概念有且只有一个唯一事实来源（Single Source of Truth）。

### 第 2 章：哪种需求需要结构化？（新增）

**核心论断：**

不是所有产品知识都需要结构化。探索性想法不需要，流程性描述不需要，UI 交互细节不需要。真正需要结构化管理的，是"业务规则"——那些逻辑密度高、边界清晰、错了就是线上事故的内容。这类规则有两个共同特征：**无法通过使用产品直观穷举，以及恰好是测试的重心。** 当你没法在页面上"点一圈"就看清所有分支，当 QA 的测试用例天然在覆盖这些边界——这就是该结构化的信号。

**四象限分类表：**

| 类型 | 特征 | 需要结构化？ | 举例 |
|------|------|-------------|------|
| 业务规则 | 边界清晰，逻辑密集，可穷举，错过就是 bug | 是 | 登录校验、权限矩阵、定价规则、状态机 |
| 策略探索 | 方向未定，还在讨论，随时可能推翻 | 否 | "要不要做社交？""积分或会员？" |
| 流程总览 | 在 PRD 文本中已有完整表达，易理解 | 否 | 用户路径："打开 App → 首页 → 点短剧 → 播放" |
| 感官约定 | 设计稿/代码里已有全貌，PM 描述的是增量改哪里 | 否 | 按钮位置、间距、动效 |

**为什么只有 PM 需要这个？**

其他角色的产出天然是"全貌"：UX 交付完整设计稿、开发维护完整代码库、测试维护完整用例集、运维维护完整配置。唯独 PM 的产出天然是"增量"（PRD）。这不是 PM 做得不够，而是 PM 与下游的协作模式决定的——下游消费增量信息最有效。因此"结构化业务规则"只针对 PM 工作中那部分天然需要全貌视角的强规则内容，而不是试图把 PRD 本身变成全貌文档。

**测试视角呼应：**

QA 的测试用例本质上就是在校验业务规则。一个场景有多少个 AC，测试就应该有多少条用例。结构化业务规则把"规则是什么"显式化之后，AC 可以被测试框架直接消费——这不仅是 PM 和开发的对齐，也是 PM 和测试的对齐。

### 第 3 章：PRD + 结构化业务规则如何协同（新增）

**核心模型：双轨并存，Agent 为枢纽**

```
PM 写 PRD（变更叙事）
    │
    ├─→ Agent 提取规则变更 → 更新 business-rules/login.md（规则全貌）
    │                                    │
    │                              git commit + diff
    │                                    │
    └────────────────────────────────────┘
                    │
              PRD 引用规则全貌链接 + 变更 diff
```

**三条要点：**

1. **PM 可直接维护，也可 Agent 辅助**：PM 可直接编辑结构化业务规则文档（Markdown 文本），也可通过 Agent 辅助——用自然语言描述变更，由 Agent 负责格式化、提交 git、生成 diff。两种方式无优劣之分，取决于团队偏好和 PM 对工具的熟悉度。

2. **PRD 中引用规则的两种方式**：
   - 全貌链接：`详见 [登录规则](business-rules/auth/login.md)` —— 让读者在 PRD 中一键跳到当前完整规则
   - 变更 diff：`本次变更：新增账号锁定规则（连续失败 5 次 → 锁定 30 分钟）` —— 让读者知道这次 PRD 到底改了哪条规则

3. **核心原则**：结构化业务规则与 PRD 各司其职，互不替代。PRD 提供动机、背景、影响面；结构化规则提供精确、无歧义的当前事实。

### 第 7 章：与下游的关系

展开为三方 ID 引用联动：

```
业务规则文档（PM）                SPEC.md（开发）
  id: RULE-AUTH-001               references:
                                    rule: RULE-AUTH-001
  描述：登录规则的全貌               测试用例:
                                    AC-2 → TC-AUTH-002
                    ↘           ↙
                  测试用例（QA）
                    tc_id: TC-AUTH-002
                    covers: RULE-AUTH-001 / SPEC.md#AC-2
```

**为什么不是三合一？** 三家各自独立的原因是维护责任不同：PM 对规则正确性负责、开发对实现边界负责、QA 对覆盖充分性负责。合并为一份文档意味着这三个角色的改动互相干扰。ID 引用保留了各方的自治权，同时通过链接建立了可追溯的关联。

末尾加一句：**三者描述的内容有重叠，未来可能走向某种形式的合并。**
