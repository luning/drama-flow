# DramaFlow 技术决策审计报告

> 本文档列出项目骨架搭建过程中所做的微观技术选择，说明选型理由、备选方案及差异分析，并从专业 App 厂商视角提出潜在顾虑和建议。

## 一、后端 (Python FastAPI)

### 1.1 SQLAlchemy 2.0 ORM

| 项目 | 内容 |
|------|------|
| **选择** | SQLAlchemy 2.0 (`declarative_base` + `sessionmaker` + relationship) |
| **大纲依据** | 未明确指定，仅说"SQLite + Pydantic" |
| **理由** | 教学演示 ORM 映射 + 关系加载（lazy loading），AI 生成代码质量高 |
| **备选** | raw SQL / dataset / peewee / SQLModel |

**差异对比**：

| 方案 | 类型安全 | AI 友好度 | 学习曲线 | 生产适用 |
|------|---------|----------|---------|---------|
| **SQLAlchemy 2.0** | ✅ 强类型 | ✅ 生成质量高 | 中等 | ✅ 工业级 |
| raw SQL | ❌ 易错 | ❌ AI 易写错 | 低 | ✅ 可接受 |
| SQLModel | ✅ | ✅✅ 最佳 | 低 | ⚠️ 仍缺部分特性 |
| peewee | ⚠️ 部分 | ✅ | 低 | ⚠️ 功能有限 |

**专业厂商顾虑**：
- SQLAlchemy 在全 SQLite 场景下过于重型，多数中小项目用 raw SQL + dataclasses 更轻量
- 对于演示培训项目，引入 ORM 增加了认知负担，学员需要在有限时间内理解两层抽象（Pydantic + SQLAlchemy）
- **推荐调整**：可考虑替换为 SQLModel（FastAPI 作者出品，Pydantic + SQLAlchemy 合一），减少概念数量

### 1.2 python-jose + passlib 认证栈

| 项目 | 内容 |
|------|------|
| **选择** | `python-jose` 做 JWT 签名/验签 + `passlib[bcrypt]` 做密码哈希 |
| **大纲依据** | 仅说"JWT"，未指定具体库 |
| **理由** | 生态成熟，passlib 自动管理 bcrypt salt round |
| **备选** | PyJWT / Authlib / fastapi-jwt-auth / `hashlib` + `hmac` |

**差异对比**：

| 方案 | 维护状态 | API 复杂度 | 功能覆盖 |
|------|---------|-----------|---------|
| python-jose | ⚠️ 2023 年起更新缓慢 | 中 | JWT 基础功能 |
| **PyJWT** | ✅ 活跃 | 低 | 基础，更轻量 |
| Authlib | ✅ 活跃 | 高 | OAuth + JWT 全套 |

**专业厂商顾虑**：
- `python-jose` 已进入低维护模式（last release 2023），安全问题响应可能延迟
- 生产环境建议换用 **PyJWT**（更轻量、更活跃）或 **Authlib**（如需 OAuth）
- passlib 的 bcrypt deprecated warning 在新版本常见，需固定版本

### 1.3 三层架构：API → Service → Model

| 项目 | 内容 |
|------|------|
| **选择** | API 路由（薄） → Service 层（业务逻辑） → ORM Model |
| **大纲依据** | 未提及 |
| **理由** | 关注点分离，AC 可独立测试 |
| **备选** | Fat Controller / Repository 模式 / CQRS |

**差异对比**：

| 方案 | 适合项目 | 测试性 | 复杂度 |
|------|---------|-------|-------|
| API→Service→Model | 中小型 | ✅ 各层可测 | 中等 |
| Fat Controller | 快速原型 | ❌ 难以测试 | 低 |
| Repository + Service | 大型 | ✅✅ | 高 |
| CQRS | 复杂业务 | ✅✅ | 最高 |

**专业厂商顾虑**：
- 培训项目的规模（5 个模型，~/20 个接口）完全不需要 Service 层，控制器直接用 ORM 即可
- 多一层抽象 = 多一层 AI 幻觉的风险（Schema 变更时 Service 层不同步更新）
- **推荐调整**：保留 Service 层作为教学演示"什么是关注点分离"，但迭代 1 中可以直接走 API → Model

## 二、Android (Kotlin)

### 2.1 Retrofit + OkHttp (vs Ktor vs Volley)

| 项目 | 内容 |
|------|------|
| **选择** | Retrofit 2.9 + OkHttp + logging-interceptor |
| **大纲依据** | 未指定 |

**差异对比**：

| 方案 | Kotlin 原生 | 协程 | 拦截器 | 学习曲线 |
|------|-----------|------|--------|---------|
| **Retrofit + OkHttp** | ⚠️ Java 库 | ✅ 2.6+ 支持 | ✅ 丰富 | 中 |
| Ktor Client | ✅ 纯 Kotlin | ✅ 原生 | ✅ 自定义 | 高（DSL） |
| Volley | ❌ 老旧 | ❌ | ⚠️ 有限 | 低 |

**专业厂商顾虑**：
- Retrofit 是 Java 库，Kotlin 项目现在更多选 **Ktor Client** 或 **OkHttp 直接调用**
- 不过 Retrofit + Gson 的搭配在国内 Android 生态仍然是绝对主流，对求职更实用
- `logging-interceptor` 在生产环境应只在 debug 构建启用——这个约束需要在 CLAUDE.md 中明确，否则 AI 可能生成 release 日志泄露 Token

### 2.2 Gson (vs Moshi vs Kotlinx Serialization)

| 项目 | 内容 |
|------|------|
| **选择** | Gson 2.10 |
| **大纲依据** | 未指定 |

**差异对比**：

| 方案 | Kotlin 兼容 | 编译期安全 | 性能 | 版本 |
|------|-----------|-----------|------|------|
| Gson | ❌ 需 @SerializedName | ❌ 反射 | 中 | 成熟 |
| **Moshi** | ✅ 更好 | ✅ 编译期 adapter | ✅ 高 | 活跃 |
| Kotlinx Serialization | ✅✅ 原生 | ✅✅ 编译器插件 | ✅ 高 | 官方 |

**专业厂商顾虑**：
- Gson 对 Kotlin 的支持需要额外处理（`null` 安全、默认参数、data class），容易踩坑
- **Moshi** 是 Square 出品（与 Retrofit 一家），配合 Retrofit 更自然
- **Kotlinx Serialization** 是 JetBrains 官方方案，但需要编译器插件，Retrofit 需要额外 converter
- 建议改用 **Moshi 或 Kotlinx Serialization**，Gson 在此场景中属于"技术债"

### 3.1 TypeScript (vs JavaScript)

| 项目 | 内容 |

## 四、架构与设计模式

### 4.1 WebView 承载内容页

| 项目 | 内容 |
|------|------|
| **选择** | 首页（HomeFragment）和详情页用 WebView 加载 Vue3 H5 |
| **大纲依据** | 已说明，这是课程核心设计 |

**差异对比**：

| 方案 | 更新无需发版 | 交互性能 | 离线能力 | AI 开发效率 |
|------|-------------|---------|---------|-----------|
| **WebView + H5** | ✅ | ❌ 一般 | ❌ | ✅✅ |
| 原生渲染 | ❌ 需发版 | ✅ 优秀 | ✅ | ⚠️ 慢 |
| React Native / Flutter | ✅ OTA 更新 | ✅ 好 | ✅ 部分 | ❌ 调试困难 |

**专业厂商看法**：
- WebView + H5 的混合架构在海外短剧类 APP 中很常见（DramaBox 等也是类似架构）
- 但 JSBridge 通信的稳定性是常见问题（Android 版本碎片化、WebView 内核差异大）
- 中国大陆 Android 生态中 WebView 内核由各家厂商定制，兼容性测试需要大量 coverage
- 数据密集型场景（如拖拽进度条上报连续位置）在 JSBridge 桥接下容易出现性能瓶颈 → 建议在 CLAUDE.md 中注明"高频调用走 Native，低频调用走 JSBridge"

### 4.2 Token 刷新 + 记住我

| 项目 | 内容 |
|------|------|
| **选择** | Access Token 2h + Refresh Token 7d，勾选"记住我"后持久化 |
| **大纲依据** | 未指定细节 |

**专业厂商顾虑**：
- Refresh Token 轮换（Rotation）机制未实现：每次刷新应签发新的 Refresh Token，旧的失效
- EncryptedSharedPreferences 在 API 26+ 可用，但 `minSdk = 26` 排除了约 5% 的设备
- 没有实现 Token 注入拦截器（OkHttp interceptor）——每次请求都需要手动拼接 Authorization header
- **建议**：最少需要 OkHttp interceptor 统一注入 Token，否则每个 API call 都重复 set header

### 4.3 Upsert 模式

| 项目 | 内容 |
|------|------|
| **选择** | WatchRecord 使用 upsert（INSERT ... ON CONFLICT UPDATE） |
| **大纲依据** | 未指定 |

**专业厂商看法**：WatchRecord 的 upsert 选择是对的。但目前的实现是在代码中先 SELECT 再 INSERT/UPDATE，不是真正的数据库级 `INSERT ... ON CONFLICT DO UPDATE`。在 WebView 上报频繁的场景，可能产生竞态条件（两次 SELECT 同时为 null → 创建两条记录）。建议用原生 SQLite `UPSERT`。

### 4.4 ViewModel 生命周期与协程

| 项目 | 内容 |
|------|------|
| **选择** | `viewModelScope.launch` + `LiveData` |
| **大纲依据** | 列出 ViewModel + LiveData |

**专业厂商看法**：标准做法，但需要说明 `viewModelScope` 的自动取消机制。如果学员不理解协程作用域，可能在播放器 Activity 中产生内存泄漏或重复请求。

## 五、SQL & 数据

### 5.1 SQLite + check_same_thread=False

| 项目 | 内容 |
|------|------|
| **选择** | SQLite with `check_same_thread=False` |
| **大纲依据** | 列出 SQLite |

**专业厂商顾虑**：
- `check_same_thread=False` 允许多线程访问同一个 SQLite 连接，但 SQLite 本身不是为高并发设计的
- 在 FastAPI 异步场景下，多个协程可能共享同一个 Session，导致 `Database is locked` 错误
- **建议**：使用 `aiosqlite` + `SQLAlchemy async`，或者在每个请求中创建独立的同步 Session（当前已这样做，但需确保配置正确）

### 5.2 Seed 数据

| 项目 | 内容 |
|------|------|
| **选择** | 幂等导入（先 `query().count()` 检查，＞0 则跳过） |
| **大纲依据** | 未指定细节 |

**专业厂商看法**：幂等策略合理。但当前实现只检查 Drama 数量，如果 ID 冲突但 count 不准确（如手动删除了数据），重新 seed 会失败。SQL 脚本中使用了 `INSERT OR IGNORE`，这是更好的保证。

## 八、对培训场景的建议

1. **明确标注"演示级"与"生产级"**：在 CLAUDE.md 或 README 中对每个可能引起争议的决策标注 `[Demo-only]` 或 `[Production-ready]`，避免学员/客户认为这是生产最佳实践

2. **保留决策痕迹**：在 `docs/` 下添加 `ADR-*.md`（Architecture Decision Records），记录为什么选 A 不选 B，这本身就是培训大纲中"Architecture as Code"的知识点

3. **技术债清单**：每次迭代结束后运行 `cr-refactor` Skill 时，将上述风险项纳入检查清单，让学员亲身体会"AI 生成速度快，技术债积累更快"的课程要点

4. **学员课前准备的第四项"七牛云"需要在代码中有对应配置留空**：目前七牛云的配置在 `config.py` 中已有占位，但未实现签名 URL 生成逻辑——迭代 2 才补全，需在迭代 1 标注 `TODO(iter2)`
