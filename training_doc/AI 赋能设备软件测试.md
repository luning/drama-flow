# AI 赋能设备软件测试：构建 Agent 驱动的测试能力体系

## 内容简介

设备软件测试难在"状态机 × 时序 × 异常"的组合爆炸，且错误成本极高。AI 在这一领域的价值是知识驱动的自主测试能力——覆盖组合空间、跨源诊断根因；代价是"可信但错"的幻觉在设备领域识别难度最高，必须有工程化对策。

本课程目标不是教一组 Prompt 技巧，而是建立 Agent 驱动的测试能力体系：以 **"生成可溯源、把关有制度、经验进资产"** 为主线，把测试依据、设备专有知识、场景方法与团队经验沉淀为可版本化的测试 Harness；在此之上构建功能/边界/异常/时序四类用例生成、Windows（Qt/MFC）与 Linux（VNC）桌面测试 Agent、日志诊断等能力，通过 Skills/MCP/SDD 走向多 Agent 规模化，并让 Harness 随软件版本持续进化。

## 目标学员

1. **测试工程师**：掌握需求规格化、分场景用例生成与 AI 输出评审方法
2. **自动化测试开发**：掌握 Windows（Qt/MFC）与 Linux（VNC）桌面测试 Agent 的实现与自愈架构
3. **测试负责人**：建立 AI 测试的质量管控制度、工具体系与落地路线图
4. **设备软件开发工程师**：理解可测性设计与日志规范如何放大 AI 测试效能

## 课程收益

1. **测试规格工程**：基于测试依据与可验证 AC 生成可溯源的用例集，掌握分场景用例设计、评审制度与资产增量维护
2. **测试项目空间**：把方法论资产编码进团队级 Harness，从"会用方法"升级为"一次编码、持续生效"
3. **工具体系**：掌握测试 Skill/MCP 设计方法论与受控测试流水线的构建
4. **分场景用例生成**：功能/边界/异常的业务场景技法 + 状态机/时序/通信/长流程的设备特色方法论
5. **测试 Agent 工程能力**：在 Windows / Linux 双平台实现桌面测试 Agent
6. **日志诊断与规模化**："先结构化、再推理"的缺陷定位流水线 + 多 Agent 协作编排与测试资产持续进化

## 课程大纲

### 第一部分：认知地图 — AI 用在哪里、靠什么用好（约 1h）

> **目标**：建立"什么该用 AI、什么不该"的判断框架，理解设备软件测试的特殊性以及释放 AI 能力的思路，明确测试工程师在 AI 时代的角色重心。

**1.1 AI 赋能设备软件测试的全景**

- Agent 可串联测试全链路：需求解读 → 用例设计 → 自动化执行与自愈 → 日志诊断 → 归档；无人值守跑批、多模块并行
- AI 辅助 vs Agent 驱动的核心差距：前者人触发 AI 干一件事，后者测试依据、知识、规则、经验持久存在于 Harness，Agent 自主流转
- 三类判断永远以人为主：测试策略（风险权衡）、AC 最终确认（意图守护）、版本放行（责任归属）
- [演示] 裸提问 vs 注入规格/领域知识/流程约束后生成，对比覆盖深度与幻觉

**1.3 洞察一：AI 的价值是知识驱动的自主测试能力**

- 不只是覆盖组合爆炸，而是能基于领域知识自主规划、执行与诊断
- 面对多状态机叠加，AI 做的是知识引导的风险路径采样，而非穷举
- 在可测试性与可观察性支持下，实现长程自主执行与异常自愈，突破 GUI 局限

**1.4 洞察二：AI 用例的质量由领域知识管理决定**

- 缺少领域知识时只能产出"通用软件"用例（格式正确、术语像样，工程上意义有限）
- 领域知识来源于规格文档、约束标准与历史缺陷，而非通用软件知识
- 四个维度决定用例生成重心：状态模型、时序与控制约束、互锁与安全逻辑、调度与资源模型
- 领域知识版本化沉淀，Agent 通过 Harness 渐进披露而非人工决定注入内容

**1.5 洞察三：设备领域幻觉"可信但错"，识别有难度**

- 都有格式正确、术语专业的外观：编造报警代码、虚构协议状态转换、捏造参数范围、合理但不存在的界面元素
- [演示] 四类幻觉现场复现与识别要点
- 工程化对策的本质是让输出可溯源：输入规格化 + 文档锚定 + 强制溯源 + 约束 Hooks

**1.6 洞察四：执行与诊断的分工铁律——确定性手段负责可靠执行，大模型负责推理与修复**

- GUI 自动化三层降级（控件识别 → 图像匹配/OCR → 多模态视觉自愈）保障执行稳定性；优先走测试接口绕过 GUI 不稳定性
- 日志诊断：脚本先结构化（时间对齐、事件抽取），大模型只在压缩后事件序列上做因果推理
- 两者共同铁律：确定性手段保底执行，大模型专注推理与修复等高价值环节

**1.7 测试工程师在 AI 时代的角色重心**

- 不可让渡的四项能力：测试策略、AC 最终确认、版本放行、失败分类（真 Bug 不能被自愈掩盖）
- 新增核心能力：**Harness 设计**——把测试依据、知识、规则、经验编码成持续生效的测试项目空间；角色从"执行测试用例的人"转型为"质量体系的设计者"

### 第二部分：需求解读 — 评审需求质量，提炼可被 AI 消费的测试素材（约 1h）

> **目标**：在不依赖需求格式改造的前提下，先评审原始需求的质量与完整性，澄清或标记问题后，再用五段式提炼结构化测试素材；建立可版本管理的 `test-basis/` 基线，支撑后续用例生成（第五部分）与增量需求的影响分析。

**2.1 需求诊断与 Agent 辅助评审——在提炼前找出问题**

- 典型缺陷：描述实现路径而非行为结果、异常处理一笔带过、预期结果缺乏可观测性——"温度异常时应妥善处理"容易产出无法核验的用例
- AI 放大缺陷的机制：模糊输入 → AI 自信生成"看起来合理但无从验证"的用例
- Agent 辅助找遗漏：基于原始需求 + 同类功能/设备场景知识，分析遗漏
- **[待确认] 标记法**：无法当场澄清的缺口主动标记，推动澄清；未关闭的缺口不进入后续提炼
- 封装为 `/review-req` Skill：输入原始需求文档，输出缺口清单 + [待确认] 条目

**2.2 五段式——在评审后的需求上提炼测试素材**

- 五段式是阅读需求时的提炼框架：识别**领域名词**（→ 等价类候选）、**前置条件**（→ 边界场景）、**主流程**（→ 功能用例）、**异常处理**（→ 异常用例）、**隐含验收点**（→ 可观测预期）
- 流程型需求用五段式解读，组合型需求（状态转换、时序约束、互锁关系）补充形式化表
- 产出测试素材笔记，存入 `test-basis/`，是增量比对的基线和用例生成的上游

**2.3 增量需求分析——找原始、判影响、定动作**

- 日常场景：收到一段增量描述，不清楚是新功能还是对已有行为的修改，也不知道影响哪些已有用例
- Agent 操作流程：
  1. 对增量需求先走 `/review-req`，找出新缺口与 [待确认] 项
  2. 用 Agent 对比增量描述与 `test-basis/` 对应条目，输出"新增 / 修改 / 删除"分类
  3. 受影响的已有用例自动标记待评估（标记而非自动修改，人决定怎么改）
  4. 新增部分重走五段式，产出新的 `test-basis/` 条目；修改部分更新对应条目并记录变更历史
- **[待确认] 继承处理**：确认原有未关闭的缺口是否被增量需求覆盖，未覆盖则继续挂起

**2.4 AI 时代的需求规格化趋势**

- 行业趋势：结构化需求规格正在普及，Agent 消费结构化输入效率远高于散文；测试的五段式解读产出（可观测 AC、边界条件）可反向贡献给需求文档，让研发在实现阶段考虑可测性（日志事件、状态输出、测试接口）

**2.5 [练习] 需求解读全流程**

- 对一份样本需求运行 `/review-req`，产出缺口清单 + [待确认] 条目，讨论哪些需要澄清
- 澄清后对同一需求做五段式提炼，产出 `test-basis/` 首条条目
- 给出一段增量需求，对比原始条目完成影响分析，标记受影响用例范围
- 产出：`test-basis/` 条目 + 需求缺口清单 + 增量影响分析报告

### 第三部分：项目测试空间 — 结构化组织测试 Harness（约 1.5h）

> **目标**：理解"Prompt 工程 → Context 工程 → Harness 工程"的范式演进，搭建团队级"项目测试空间"骨架——这是后续所有用例生成、工具设计和 Agent 执行的持久基座。

**3.1 为什么"复制粘贴 Prompt 模板"难以为继**

- Prompt 模板的四个退化点：散落无版本管理、约束在新会话中遗失、新人不知用哪个、知识与模板耦合处处过时
- 三层范式演进：Prompt 工程（怎么问）→ Context 工程（给模型看什么）→ Harness 工程（模型在什么机制里干活）——答案从"每次拼 Prompt"升级为"持久存在、按需加载的项目空间"

**3.2 项目测试空间的设计 — 知识、能力与约束的持久基座**

- **索引**：`CLAUDE.md` 告知 Agent 哪类任务加载哪些知识，渐进披露避免上下文冗余
- **测试依据**：`test-basis/` 存放五段式 AC 条目，按功能模块归档，是功能用例溯源的根基
- **设备专有知识**：`device-knowledge/` 存放各类测试的结构化原材料——边界测试的参数规格表（每行含唯一编号）、异常测试的报警代码表与异常处理规格、时序/状态机测试的状态转换表与时序约束清单
- **生成规则**：`test-knowledge/` 存放各类测试的颗粒度约束、枚举框架与溯源格式
- **经验沉淀**：`test-patterns/` 积累样本用例、驳回案例和故障模式，按需写入，避免膨胀
- **能力封装**：`skills/` 封装生成类、评审类、执行类、诊断类 Skill；MCP 工具提供连接外部系统的确定性执行手脚
- **约束执行**：`hooks/` 将不同测试类型各自的机器可查 DoD 规则固化为自动拦截关卡，人只在拦截时处理语义决策
- **输出归档**：`cases/` 存放评审通过的用例，带双向追溯链
- **自动化经验**：`automation/` 存放自动化测试指引

**3.3 四层视图与设计原则**

- 四层从软到硬：文档层 → 经验层 → 约束层 → 执行层
- 渐进披露原则，知识与经验经 INDEX 按需加载
- 经验层引入时机：真的反复犯同类错误再沉淀；人写资产（预防规章）vs Agent Memory（工作笔记），验证普适后再提炼进经验层

**3.4 团队治理**

- Git 提交边界：代表团队共识的全部提交（测试依据、设备知识、测试模式、模板、Skills、Hooks），个人偏好不纳入
- Review 分级：CLAUDE.md / Hooks / Skill 必须 PR 严审；经验文件少而精，防止"越来越长被忽略"

**3.5 [演示 + 练习] 搭建测试项目空间骨架**

- [演示] 空白环境 vs 完善项目空间：同一生成任务对比输出对齐度、幻觉率、人工纠正轮数
- [练习] 用 Claude Code 初始化骨架：含四条铁律的 CLAUDE.md + 目录结构；把第二部分产出的 `test-basis/` 条目放入对应目录，验证 Agent 能否基于它生成用例
- 产出：每组 1 个可版本化的测试项目空间骨架

### 第四部分：Skills、MCP 与受控工作流 — 为测试 Agent 构建工具体系（约 1.5h）

> **目标**：掌握测试专用 Skill 的封装方法和 MCP 的外部系统接入方法，理解两者分工；掌握自定义受控测试工作流的设计——从"有工具"升级为"工具在受控流程里运行"。

**4.1 Skill 设计 — 测试工作流的封装单元**

- Skill 的本质：把"怎么干这件测试活"固化为可复用、可版本化的作业指导书；固定逻辑剥离到确定性脚本，Skill 只负责调用与结果解读
- 测试 Skill 四类：生成类、评审类、执行类、诊断类，举例说明
- Skill 设计原则：单职责、输入输出有明确 Schema、幂等、可组合；[演示] 编写一个 /gen-cases Skill：注入点设计 → 颗粒度约束 → 溯源强制 → 输出模板

**4.2 MCP 工程设计 — 连接测试外部系统**

- 测试域 MCP 典型接入（Agent 直接读取外部系统，无需人肉传递）：测试管理系统（读取/写入用例与执行状态）、日志与设备遥测（按时间窗口拉取）、仿真器与设备控制接口（触发场景、注入故障）、CI 集成（拉取构建结果、触发回归包）
- MCP 设计原则：只读账号优先、工具描述精确、敏感字段脱敏、审计日志
- Skills vs MCP 选型：Skill = 封装 AI 的工作流程；MCP = 连接外部工具与数据源；Skill 调用 MCP 工具完成有状态的外部操作

**4.3 受控测试流水线 — SDD 工具生态**

散点式使用 AI 的三个瓶颈：约束靠口头与记忆、阶段靠自觉（未评审用例被拿去执行）、过程无审计痕迹。

- SDD 本质是流程状态机：阶段间靠结构化制品传递；三个核心机制：**新鲜上下文隔离**（每阶段起干净 Session）、**工件结构管理**（测试依据/用例/评审报告作为阶段合同）、**变更隔离**（每变更独立目录，支持并行与审计）
- 以 OpenSpec 为例：工具原理；工作流 Propose → Apply → Archive，与设备行业 ECN 变更文化天然契合，[演示] 从测试依据变更触发走完全流程

**4.4 自定义测试流水线 — 场景与实践**

- 自定义 SDD 四要素 — 阶段命令：/analyze-requirements → /gen-cases → /review-cases → /run-mission → /diagnose → /archive
- 上下文加载策略：评审阶段只读用例 + checklist，刻意不读生成过程上下文——**新鲜上下文隔离防自评估污染**
- 验证关卡（机器可查 DoD）：溯源不完整不得进评审、评审未通过不得执行
- 归档与追溯：测试依据-用例-评审-执行-缺陷的完整工件链，直接服务审计合规

**4.5 [演示 + 练习] 构建最小受控测试流水线**

- [演示] 从零搭两阶段流水线：/gen-cases（带溯源关卡）→ /review-cases（新鲜上下文执行），用小需求跑通
- [练习] 为本组流水线增加一个关卡（如"[待确认] 项未处理不得进评审"）并验证拦截生效
- 产出：最小测试 SDD 流水线（阶段命令 + 关卡 Hook + MCP 接入设计草案）

### 第五部分：测试规格工程 — 用例设计、管理与资产化（约 3.5h）

> **目标**：测试规格 = 可溯源、可版本化的用例集。以 Harness 知识基座（`device-knowledge/`、`test-knowledge/`、`hooks/`）为燃料，以 `/gen-cases` Skill 和 SDD 流水线为引擎，展开功能/边界/异常/时序四类设备场景的用例设计实践——从具体生成方法到串联 SDD 工作流，再到评审归档与知识演进。

**5.1 功能测试用例生成**

- **测试重点**：三类对象侧重不同——UI 类覆盖控件状态与交互路径，作业类覆盖状态流转与资源绑定，脚本类覆盖接口契约与数据流；三种输入驱动：AC → 正向覆盖、历史 Bug → 补回归盲区、截图 → 多模态
- **前置知识**：`test-basis/` AC 条目；截图直接作为上下文注入，控件树是防幻觉的硬锚点
- **幻觉抑制 & 拦截**：编造不存在的界面元素；截图注入 + 生成时强制输出控件名溯源字段；Hook 拦截：溯源字段为空不得进评审，[待确认] 项计数输出评审报告
- **人工审查**：机器只查"有溯源"，人判断"溯源是否对应 AC 真实意图"；[待确认] 项是需求澄清还是可关闭

**5.2 边界测试用例生成**

- **测试重点**：三类边界系统化识别——参数边界（量程/步进精度）、容量边界（满载/空载）、时间边界（超时阈值前后）；多参数组合矩阵覆盖参数交互缺陷
- **幻觉抑制 & 拦截**：最典型幻觉：捏造"看起来合理"的数值——[演示] 无规格表 vs 注入后对比；注入 `device-knowledge/params.md`（每行有唯一编号），强制引用行号，无出处标 [待确认]；Hook 拦截：数值未引用规格表行号不得进评审
- **人工审查**：组合矩阵优先级裁剪；参数规格本身正确性（AI 不能判断规格对错）

**5.3 异常测试用例生成**

- **测试重点**：异常枚举框架（硬件/通信/操作/数据/环境）；**设备测试最大差异点**："异常注入时机矩阵"——同一异常在流程不同阶段注入预期行为不同
- **Agent 流程**：生成"异常类型 × 注入阶段"二维矩阵；通信异常进一步扩展为"通信状态 × 业务阶段"矩阵（断链/半开连接/超时/消息乱序/非法报文）；环境异常延伸为跑批长流程的资源泄漏观测（内存/句柄/磁盘）与中途恢复检查点
- **幻觉抑制 & 拦截**：虚构报警代码或异常处理逻辑；Hook 拦截：报警代码不在 `device-knowledge/alarms.md` 中则拦截；预期结果字段空则拦截
- **人工审查**：注入时机矩阵覆盖优先级（哪个阶段注入风险最高）；破坏性测试（断电/急停）执行时机是风险决策，不能由 Agent 自主判断

**5.4 时序与状态机测试**

- **测试重点**：状态机——N×N 矩阵三层覆盖（合法转换逐一验证 + 非法转换逐一拒绝 + 转换中触发事件的嵌套场景）；时序——形式化"A 之后 X ms 内必须 B"约束，生成"正常/临界/违例"三档用例，日志时间戳断言优于界面观察
- **前置知识（先提取再生成）**：两类测试都需先由 Agent 从需求/代码提取结构化知识（状态转换表 → `state-machines/`，时序约束清单 → `timing-constraints.md`），人审确认后再投喂生成——提取质量直接决定覆盖质量；[演示] 投喂状态转换表 → 批量生成覆盖矩阵与用例
- **幻觉抑制 & 拦截**：编造状态名/事件名/时间阈值；Hook 拦截：状态名/事件名不在知识库则拦截；时间数值未引用约束清单出处则拦截
- **人工审查**：提取出的状态转换表语义正确性；竞态场景可观测性（不可观测的必须重新设计验证方式）

**5.5 串联流水线与跨类型覆盖检查**

- 四类生成阶段由 SDD 流水线串联，各阶段产出结构化工件后经对应 Hook 关卡；拦截触发时人处理知识缺口并回写，当轮重新生成——知识库越完善，关卡通过率越高
- 四类 Hook 对应关卡：溯源字段完整性（functional）、数值引用规格表行号（boundary）、报警代码合法性（abnormal）、状态名/时序约束引用出处（timing）
- `/cross-check-coverage` 跨类型覆盖检查：同一功能模块的功能用例与状态机矩阵是否覆盖同一对象，遗漏的 AC 条目跨类型报告
- `/review-cases` 新鲜上下文隔离评审：只读用例集 + checklist，不加载任何生成上下文，防止生成阶段的自我说服污染评审判断；评审通过后 `/archive-cases` 归档
- **人工介入节点**：Hook 拦截时处理知识缺口并回写；跨类型遗漏由人确认是否补充；评审驳回列表由人归因到 Harness 层

**5.6 评审、归档与知识演进**

- 三级评审分工：AI 自检（新鲜上下文对照原文档）→ 同行快评（查溯源与 [待确认] 项）→ 模块负责人抽检；Hook 已拦截的项不再出现在人工评审视野中
- 驳回归因到 Harness 层：太泛→收紧生成规则，遗漏→补枚举框架，错误→补知识缺口，反复犯同类错→固化为 Hook；"生成→评审→归因→回写资产"闭环，每轮迭代幻觉率下降；度量：采纳率、驳回原因分布（知识缺口/Skill 规则/需求模糊）
- `/archive-cases` 归档：评审通过用例进 `cases/`，分配稳定编号；双向追溯：正向查"AC 无用例覆盖"，反向查"无依据/依据已变更的用例"——Hook 自动检测，人只处理语义判断
- 知识资产归位：本部分提取的结构化知识（状态转换表/时序约束清单/参数规格/报警代码表）→ `device-knowledge/`；场景枚举框架 → 场景 Skills；已验证用例模板 → `templates/`；驳回案例 → `experience/`

### 第六部分：Windows 桌面测试 Agent（Qt/MFC）（约 1.5h）

> **目标**：在测试项目空间之上实现第一个端到端测试 Agent，跑通"读用例 → 执行 → 观察 → 判定 → 留痕"的完整循环。

**6.1 自动化驱动层与三档降级**

- 主力工具：pywinauto（UIA backend）封装点击、输入、等待、截图、控件树 dump；自绘控件用 inspect.exe 诊断后降级图像模板
- 测试接口优先：推动开发侧提供 CLI/Socket/内部 API 用于状态构造与故障注入，比 GUI 稳定且无需截图；危险操作设白名单 + 人工确认卡口
- 三档降级——第一档：UIA 属性精确定位 + 测试接口，零 AI 成本；第二档：知识库查找（已知路径直接执行，已验证序列固化为回归脚本）；第三档：多模态兜底，仅在前两档失效时介入——知识库越积越厚，大模型调用越来越少

**6.2 利于自动化消费的用例设计**

- **步骤写意图，不写坐标**：用例不随坐标失效，Agent 自行定位
- **前置条件明确**：描述起始系统状态，便于 Agent 自动构造或校验环境
- **预期结果可判定**：每条预期映射具体断言手段——控件属性 / 截图区域 / 日志关键字 / 报文字段，避免"界面正常"等模糊描述
- **执行范围指定**：按用例 ID、标签（@regression/@smoke）或套件文件告知 Agent，无需特殊目录；第五部分用例按此格式写，可直接消费

**6.3 三构件架构与 Agent 执行循环**

- 三构件：Agent 定义（角色、工具白名单，常驻且稳）→ 测试 Skill（执行循环、定位策略，按需加载可迭代）→ 驱动层（确定性脚本）
- 执行循环：加载用例 → 查知识库规划路径 → 按三档降级执行 → 观察控件/截图状态 → 对照预期判定 → 结构化留痕
- 分工：回归跑固定脚本（快、稳、便宜），探索性验收交给 Agent；验证通过的序列可固化为回归脚本

**6.4 执行记录、带评估的结果与知识沉淀**

- **执行留痕**：每步记录"操作 + 控件快照 + 截图"三联；失败现场自动打包（轨迹 + 控件树 + 日志）供回喂修复
- **带评估的结果**：Agent 对失败预先分类——环境噪声 / 可自愈 / 真实缺陷；传统 UI 自动化 100 条失败需逐条人工排查，Agent 将需人工确认的比例大幅压缩，解除用例数量天花板
- **动态经验沉淀**：执行中发现的高效页面导航路径（菜单层级、入口控件）、不稳定控件、失败处置模式写入经验层；下次执行 Agent 优先查表按图索骥，省去逐步分析页面状态的推理开销；版本升级后控件树 diff 交 Agent 批量输出修改建议

**6.5 鲁棒性提升技术手段**

- 智能等待替代固定 sleep：以控件属性/状态变化触发代替硬编码延时
- 步骤级状态验证：每步执行前校验当前界面符合前置预期，支持从任意步骤续跑
- 幂等化前置：用例执行前重置到已知起始状态，消除用例间状态污染
- 经验驱动先验处理：已知不稳定点（慢渲染、动画页面）在 Skill 中预置针对性等待策略

**6.6 [演示 + 练习] 跑通最小 Windows 测试 Agent**

- [演示] 展示项目工程结构；加载参数编辑用例 → Agent 驱动执行 → 输出带评估的结果报告（截图 + 失败分类）
- [练习] 编写 Agent 定义与测试 Skill，改写一条用例并执行；人为制造控件变更，体验失败打包与回喂修复
- 产出：最小 Windows 测试 Agent（Agent 定义 + 测试 Skill + 驱动脚本 + 用例模板）

### 第七部分：Linux 桌面测试 Agent（VNC）（约 1.5h）

> **目标**：在只有像素流的约束下实现视觉驱动的测试 Agent，守住"真 Bug 不被自愈掩盖"的红线。

**7.1 视觉自动化手段与三档降级**

- 本质约束：无控件树、只有像素流；驱动层换为 vncdotool（键鼠注入与截图）；状态构造与故障注入优先走 CLI/Socket/API

**7.2 利于视觉断言的用例设计**

- 用例格式规范复用 6.2；视觉特有要求：预期结果写"可视觉判定"描述（指示灯颜色、列表行数、报警横幅），而非内部状态

**7.3 多模态 Agent 执行循环**

- 执行循环结构与 6.3 一致，差异在定位与断言手段：先查模板库，命中则执行；未命中则 OCR；都失败才调多模态

- **失败分类器（核心红线）**：区分"位置漂移"（可自愈）、"界面改版"（需人介入）、"真实缺陷"（**必须报 Bug，绝不能自愈掩盖**）——解除 UI 自动化规模天花板的关键

### 第八部分：日志分析与缺陷定位 — 诊断 Agent 实战（约 1.5h）

> **目标**：建立"先结构化、再推理"的 AI 日志分析流水线，设计缺陷定位诊断 Skill，把定位经验沉淀为团队故障模式库。

**8.1 设备日志体系与"先结构化、再推理"流水线**

- 典型日志源：主控日志、子系统/工艺日志、通信报文、报警历史、IO trace；根因往往跨源关联，直接投喂原始日志超出上下文
- 预处理（脚本完成）：时钟偏差校正 / 异常窗口截取（报警时刻 ±N 分钟）/ 事件抽取去重；模型只在压缩后事件序列上推理

**8.2 缺陷定位诊断 Skill 设计（单 Agent 与多 Agent 两档）**

- 知识层投喂（两档共用）：架构图（文本化）+ 日志格式说明 + 报警代码表
- 证据约束：每条假设必须引用日志行号/时间戳，无直接证据标 [推测]

- **单 Agent 快速诊断**：`/diagnose` 直接在压缩事件序列上推理，输出格式：现象 → 直接原因 → 根因假设（按概率排序）→ 验证手段；适合故障现象单一、日志量小的场景

- **多 Agent 深度并行诊断**（复杂故障）：
  - Orchestrator：读预处理摘要 → 生成 3–5 条根因假设 → 并行派发 InvestigatorAgent
  - InvestigatorAgent × N：每个 Agent 持一条假设，按需读取原始日志，输出 `findings/hypothesis_N.md`（假设 / 证据 / 置信度 / 裁定）
  - SynthesisAgent：读全部 findings，跨层关联，输出根因排序 + 验证手段 + 故障模式三元组
  - 状态只靠文件传递，各 Agent 独立 Session，无共享内存

**8.3 典型场景案例与故障模式库**

- 吞吐量下降：从调度日志中定位资源等待瓶颈
- 过程值报警：从控制 trace 中区分"传感器异常"与"控制逻辑缺陷"
- 通信超时：从报文日志中定位上位机侧、网络侧还是设备侧责任
- 故障模式库：定位后把"现象-证据-根因"三元组回填 experience/ 层，下次诊断自动 few-shot 注入

**8.4 [练习] 全流程定位实战（单 Agent）**

- 基于脱敏/模拟故障日志，跑完"窗口截取 → 事件抽取 → 因果推理 → 假设验证"全流程，结果写入故障模式库模板
- 产出：缺陷定位诊断 Skill + 故障模式库表结构与首批条目

**8.5 [演示] 多 Agent 并行诊断**

- 场景：通信超时（跨通信层、控制层、调度层，最能体现多 Agent 跨层关联价值）
- 演示流程：预处理摘要 → Orchestrator 生成 3 条假设（上位机侧 / 网络侧 / 设备侧） → 并行 InvestigatorAgent 各自取证 → findings 汇总 → SynthesisAgent 输出根因报告

### 第九部分：测试 Agent 规模化 — 场景与实现（约 1h）

> **目标**：打通从"1 人盯 1 个 Agent"到"1 人驱动多角色测试 Agent"的关键断点；核心不是"更多工具"，而是生成-评审分离的质量价值与回归的工程实现。

**9.1 规模化的核心洞察：生成与评审分离**

- 多数团队的瓶颈：单 Agent 自评估存在系统性缺陷——同一上下文自检的幻觉检出率显著低于独立评审；规模化缺的不是工具，是跨 Agent 的协作合同与状态载体
- 两角色最小可行模型：生成 Agent（注入规格+知识）+ 评审 Agent（独立上下文，只读用例+checklist）——独立 Verifier 是多 Agent 在测试场景的最大价值
- 协作合同：用例集、评审报告、执行结果、缺陷单——每份制品是上下游的唯一事实来源；Multi-Agent 无共享内存，状态只靠外部制品传递

**9.2 工程实现：工具组合与无人值守批跑**

- 工具组合：`claude -p` 无头执行升级为可重放流水线；Tmux 多会话隔离，窗口名即角色；Git Worktree 每个 Agent 独立目录防文件冲突；shell 脚本编排替代手工多终端操作
- 按模块扇出：N 个执行 Agent 并行跑 Mission，仿真器优先承接并发，真机串行 + 白名单；递进路径：单 Agent → 两角色 → 按模块扇出 → 夜间回归集群
- **人的监督带宽是硬约束**：汇总报告必须让人 10 分钟内判断是否有真 Bug；HITL 检查点：用例入库前终审、缺陷提交前确认、危险操作保持白名单串行
- 错误乘法效应：长链各步失败概率相乘——关键节点插 DoD 门禁，偏差早停；执行 Agent 用低成本模型，评审/诊断 Agent 用高能力模型

**9.3 [练习 + 研讨]**

- [练习] 跑通最小两角色流水线：生成 Agent 产出用例集 → 评审 Agent 独立评审，对比自检与独立评审的幻觉检出率
- [研讨] 公司内的规模化场景

### 第十部分：测试 Harness 的维护与刻意进化 — 让测试资产随软件版本共同生长（约 1h）

> **目标**：建立"干预即信号、纠正即 Harness 改进"的维护习惯，掌握版本迭代下测试资产的同步方法与防退化机制，并利用天然沉淀的失败/干预历史让 Harness 自动进化。

**10.1 测试维护的真问题 — 四类资产同时老化**

- 版本迭代带来四类老化：界面改版（模板/定位失效）、参数扩展（规格表过时）、报警代码新增（知识缺口）、需求变更（测试依据与用例失效）
- 两种团队的分野：路径 A 犯错→纠正→继续，每版本重复；路径 B 犯错→纠正→"教训编码进 Harness 哪一层？"

**10.2 干预即信号 — 测试场景的进化层级映射**

- AI 反复编造报警代码/参数值 → 表格化后入 device-knowledge/ 层
- 评审反复驳回同类用例 → 驳回案例入 test-patterns/ 层 + CLAUDE.md 补规则
- Agent 总忘记标注溯源 → 约束层 Hook 自动拦截，而非反复口头纠正
- 定位频繁失败 → 驱动脚本升级 + 知识库补条目；同一异常场景多次漏测 → 枚举框架补充到场景 Skill

**10.3 版本同步、防退化与刻意修剪**

- 发版触发资产 diff：新旧控件树/截图/参数规格 diff 交给 Agent，批量输出受影响资产清单；自愈修复经人工确认后回写知识库，形成"执行 → 自愈 → 资产更新"闭环
- 定期扫描蛀虫清单：过时参数规格、重叠/矛盾规则、经验噪音、失效图像模板；维护铁律：只保留不可替代的领域事实，每次只加一条规则、单独验证、无效回滚
- 退化先行指标：采纳率走低、自愈成功率走低、驳回原因重复出现

**10.4 自动进化 — 基于失败与干预历史的 Agentic Harness Engineering**

- 自动进化循环：采集失败轨迹（评审打标、自愈留痕、执行报告等已结构化沉淀）→ 聚类高频模式 → 归因到 Harness 层级 → 生成候选补丁 → 历史失败回归集验证 → 人工审批入库
- 安全护栏：每次只进化一条、可回滚；红线——绝不允许把"真缺陷"归因成"Harness 问题"而规则化掩盖
- [演示] 从评审驳回记录与自愈日志出发，聚类失败模式并生成候选规则补丁，跑回归集验证后提交审批
