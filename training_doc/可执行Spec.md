# 可执行 Spec：让 AI 和人都看得懂的需求文档

---

## 一、为什么 PRD 不够用？

**PRD 描述"做什么"——**  
*"用户可以登录"*

**开发需要"怎么做才算完成"——**  
*"邮箱不存在时返回 401，错误文案为'邮箱或密码错误'"*

这个 gap，在人工开发时靠沟通弥补。  
**在 AI 开发时，AI 没有机会问你。**

---

## 二、PRD vs SPEC：各司其职

| 维度 | PRD.md | SPEC.md |
|------|--------|---------|
| **读者** | PM、设计师、管理者 | 开发者、AI Agent |
| **粒度** | 功能列表、用户故事 | 领域名词、前置条件、主流程、异常处理、AC |
| **结构** | 按 Kano 优先级组织 | 五段式格式 |
| **是否可执行** | 否（意图层） | 是（验收层） |

> 核心原则：**PRD 定义"做什么"，SPEC 定义"怎么做才算对"**

## 三、五段式格式

```
领域名词 → 前置条件 → 主流程 → 异常处理 → 验收标准（AC）
```

### 1. 领域名词
统一概念定义，消除歧义。

```
| 术语          | 定义                              |
|--------------|----------------------------------|
| Access Token | 短期令牌（默认 2h），用于 API 请求鉴权 |
| Refresh Token| 长期令牌（默认 7d），用于静默续期     |
```

### 2. 前置条件
系统在此流程开始前必须满足的状态。

```
- SQLite 数据库和 User 表已初始化
- FastAPI 服务已配置 JWT 密钥和过期时间
```

### 3. 主流程
用户操作 + 系统响应，步骤化描述。

```
1. 用户输入邮箱 + 密码
2. 客户端提交 POST /api/auth/login
3. 服务端校验，通过 → 签发 Access Token + Refresh Token
4. 返回 200 OK + { access_token, refresh_token, user }
```

### 4. 异常处理
穷举边界情况，每种情况给出明确的错误响应。

```
| 异常场景      | 错误响应                         |
|-------------|--------------------------------|
| 邮箱不存在    | 401 + "邮箱或密码错误"            |
| 密码错误      | 401 + "邮箱或密码错误"            |
| 邮箱格式非法  | 422 + "邮箱格式不合法"            |
```

### 5. 验收标准（AC）

**这是最关键的一段。**  
每条 AC 必须是**可测试的**——开发者自测、AI 自检、自动化测试三路共用同一份标准。

```
AC-1：正确邮箱 + 正确密码 → 200 OK，响应体包含 access_token、refresh_token、user
AC-2：邮箱不存在 → 401，message 为"邮箱或密码错误"（不暴露具体原因）
AC-3：密码错误 → 同 AC-2
AC-4：邮箱格式非法 → 422
AC-5：勾选"记住我" → Token 写入 EncryptedSharedPreferences，重启 App 不需重新登录
```

## 四、SPEC 是唯一规则来源

**一份 SPEC，三方消费：**

```
                    SPEC.md（AC 是合同）
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
    开发者自检       AI Agent 自检    自动化测试生成
    （逐条对照）     （CLAUDE.md 约束） （pytest / Cypress / Espresso）
```

**AC 不只是验收条件，也是自动化测试的直接来源。**  
一条写得好的 AC，可以被 AI 直接翻译成测试用例：

```
AC-2：邮箱不存在 → 401，message 为"邮箱或密码错误"
```
↓ AI 生成
```python
def test_login_unknown_email(client):
    resp = client.post("/api/auth/login", json={"email": "x@x.com", "password": "abc"})
    assert resp.status_code == 401
    assert resp.json()["message"] == "邮箱或密码错误"
```

AC 写得模糊，测试就无法生成——或生成出来在测什么都不清楚。  
**AC 的质量 = 测试的质量 = 代码验收的质量。**

---

## 五、AI Agent 为什么需要 AC？

**SDD 约束（CLAUDE.md 中写明）：**

> 生成代码后，逐条自检 AC，确保所有验收标准被覆盖

没有 AC，AI 生成的代码"感觉对"但验收不了。  
有了 AC，AI 可以自检，人工只需抽查。

---

## 六、HITL 检查点

> **AC 的最终确认必须由人完成**

AI 可以从 PRD 草稿自动提取五段式 Spec 骨架——  
但 AC 是业务承诺，**人工审核不可跳过**。

```
PRD 草稿
   ↓ Claude 自动提取骨架
五段式 Spec 草案
   ↓ 人工确认 AC ← HITL 检查点
SPEC.md 定稿
   ├─ 开发/Agent 实现 → 逐条自检 AC
   └─ AI 生成自动化测试 → CI 持续守门
```
