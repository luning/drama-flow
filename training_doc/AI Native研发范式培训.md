# AI-Native 研发范式：从认知重构到全周期 Harness 工程深入实践

## 内容简介

随着推理与 Agent 能力的爆发，软件研发正从"AI 辅助编码"向"Agent 驱动研发"跨越。然而多数工程师面临同一困境：已经在用 AI，但提效始终有限 —— 需求越复杂 Agent 越容易跑偏、多轮纠正后效果还不如自己写、换一个 Session 之前的约定全部遗失、生成速度快但质量越来越难控制。

本课程围绕 **Harness Engineering（驾驭工程）** 这条主线，覆盖从需求到上线的完整软件生命周期实践。课程追求三个递进目标：第一，从"代码搬运工"转型为"Harness 建筑师"，设计让 Agent 精准执行的运行环境；第二，从"1 人 ↔ 1 Agent"跃迁到"1 人驱动 N 个角色化 Agent 并发"，以更少介入完成更大任务；第三，让团队的研发协作方式围绕 Agent 重组，将规范、经验、工具沉淀为持续进化的组织资产，而非停留在个人的使用技巧。

## 目标学员

1. **核心开发与架构师**：从手动编码转向 Harness 编排，设计 Agent 可高效理解的模块化系统
2. **研发效能负责人**：将 AI 深度注入全研发流程，构建团队级 AI 工作流
3. **产品负责人与设计师**：编写高质量可执行 Spec，以可执行设计系统驱动 Agent 精准交付
4. **测试与质量专家**：构建 AI 驱动的测试闭环与自动化验收

## 课程收益

1. **Harness 认知**：理解范式演进，掌握头部公司工程实践精华
2. **规格能力**：用可执行 Spec 缩短交付周期，告别多轮打地鼠
3. **项目空间建设**：将架构规范与开发经验结构化为 Agent 可理解的"项目大脑"
4. **工具系统设计**：掌握 Skills & MCP 设计方法论，沉淀可复用 AI 工具资产
5. **刻意进化**：建立"干预即信号、纠正即 Harness 改进"的习惯，甚至自动化改进的闭环
6. **质量闭环**：构建基于 Agent 的行为级测试与探索性验收闭环

## 授课方式

讲师讲授 + 现场演示 + 沙箱演练 + 主题研讨

## 课程大纲

### 第一部分：认知地图 — AI Native 的本质与 Harness Engineering（约 1h）

> **目标**：建立 AI Native 思维模型，理解 Harness Engineering 的概念与行业实践，明确"工程师能控制什么"。

**1.1 AI Native 的本质**

- 云原生类比：不是"把 AI 当 IDE 插件用"，而是围绕 Agent 能力重新设计研发架构
- AI Powered（人伺候 1-2 个 Agent）vs AI Native（1 人驱动 N 个 Agent 并发）的关键差距
- 影响 Agent 应用深度的三方面能力：模型内核、Harness 项目空间、项目架构

**1.2 Harness Engineering - 概念与行业实践**

- 三层范式演进：Prompt 工程（怎么问）→ Context 工程（给模型看什么）→ Harness 工程（模型在什么机制里干活）
- 词源："马具"把原始能力导向有用的工作；不是教模型怎么回答，而是设计模型怎么工作
- 头部公司实践精华：
  - Anthropic：双/三 Agent 架构，生成—评估分离，外部制品作为跨 Session 记忆
  - OpenAI：禁止手写代码实验，上下文工程 + 架构约束 + 定期"垃圾回收"
  - Google DeepMind：Generator-Verifier-Revisor 三角，独立 Verifier 解决自评估系统性缺陷
  - Vercel：移除 80% 工具后成功率反而上升——"约束解决空间以提升表现"
- Harness 六大核心模块：上下文管理、工具编排、验证机制、状态管理、可观测性、人类接管

**1.3 Agent 内核 vs 项目空间 - 工程师能控制什么**

- 内核（厂商提供）：LLM + 感知/规划/推理/上下文/工具调用/权限/记忆/子代理
- Claude Code 源码中内核复杂度远超写 Prompt
- 项目空间（工程师完全自主）：代码结构、文档、规则、工具、经验——Harness 工程主战场
- 工程师角色重塑：从"实现者"转向"Harness 设计师"
- [演示] 对比体验：空白 Harness 项目空间 vs 完善 Harness 下，Agent 完成任务的路径与幻觉率

### 第三部分：熟悉 Claude Code（约 0.5h）

> **目标**：掌握 Claude Code 的核心命令、配置体系与高级特性，为后续所有实践操作建立工具基础。

**3.1 核心工作流与日常命令**

- 核心交互：对话式任务、`/` 命令、`@` 文件引用
- 关键操作：`/compact`（压缩上下文）、Escape（打断）、逐文件 diff 审查
- 会话管理策略：何时 compact、何时开新 Session、何时 fork
- 安全习惯：大改前先 commit，改完逐文件确认，走偏立即回滚

**3.2 配置系统 - 让行为可预期**

- CLAUDE.md 层级结构：全局（`~/.claude`）→ 项目根 → 模块级，就近优先
- `settings.json` 核心配置：`allowedTools`（工具范围）、`permissions`（文件访问控制）
- Hooks 系统三类钩子：`PreToolUse`（拦截）/ `PostToolUse`（自动验证）/ `Stop`（完成触发）
- 典型 Hook 用例：提交前自动测试、危险操作强制确认、输出自动记录

**3.3 高级特性**

- Worktree 隔离：并行任务互不干扰的标准做法
- 子代理编排：主 Agent 委托子 Agent 完成独立模块，保持主上下文清洁
- 自定义 Slash Commands（Skills）的创建与加载机制

### 第四部分：规格工程 — 给 Agent 精确的任务边界和流程约束（约 2h）

> **目标**：掌握可执行 Spec 的编写方法，理解 SDD 工具生态与工作原理，从"描述需求"升级到"定义验收"。

**4.1 从 PRD 草稿到可执行 Spec**

- 场景：从一份模糊 PRD，提取五段式 Spec 骨架
- 逐条确认 AC，体验"合同"如何约束后续开发质量
- Prompt SDD 最小约束：接受任务前读 AC → 完成后逐条自检 → 变更时标注
- [练习] 模糊 PRD → 可执行 Spec 的全过程

**4.2 可执行 Spec - 格式与 AC 质量原则**

- 五段式：领域名词 → 前置条件 → 主流程 → 异常处理 → 验收标准（AC）
- 一份 Spec，三方消费：开发者自检、AI Agent 自检、自动化测试生成
- AC 质量标准：可验证、无歧义、无实现细节
- 失败模式：Agent 填充错误实现；约束在新 Session 中遗失；多 Agent 出现分歧

**4.3 SDD 工具生态 - 工作原理与选型**

- Prompt SDD 的规模瓶颈：约束易遗漏、AC 无法自动验证、变更无结构化追溯
- SDD 基本循环：讨论 → 规划 → 执行 → 验证 → 归档

**SDD 工具解构**

- 三种上下文策略的本质：新鲜上下文隔离 / 工件结构管理 / 变更隔离
- 工具骨架：变更目录结构 + Phase PLAN.md + 子代理执行 + Verification 关卡
- GSD 核心机制：波级并行执行 + 新鲜上下文隔离，适用长任务、跨模块重构

**OpenSpec 工作原理**

- 每个变更独立目录，`change.md` 是变更的单一真相源
- 核心工作流：Propose → Apply → Archive
- 优势：完整审计追踪、并行变更互不干扰，适用存量系统迭代
- [演示] 工作流程

**自定义 SDD**

- 核心要素：上下文加载策略 + 任务拆解规则 + 验证关卡 + 归档方式
- 从零构建实用 SDD ：PLAN.md 模板 + execute + subagent verify
- 何时自定义：为提升任务效果固化重复出现的步骤

### 第五部分：可执行设计系统 — 设计一处定义，人机共同执行（约 1h）

> **目标**：理解可执行设计系统，建立"代码即设计源"的工作流，将工程师的翻译工作降至最低。

**5.1 可执行设计系统的结构**

- 原型及设计系统演进：文档时代 → Figma时代 → 可执行设计系统时代
- AI 越能生成，设计约束越重要 —— 否则风格漂移、组件重复、UX 崩坏
- 设计系统五层结构：业务约束 → Design Token → 组件 Runtime → AI Generation Rules → Figma 协作层
- 原型生产方式：从 Figma 出发，从自然语言出发，从 Screen Spec 出发

**5.2 在设计系统约束下生成 UI**

- AI 读取设计系统文件后生成新页面，验证是否自动遵守 Token/组件/约束
- Prototype Skill 封装：将设计系统注入流程固化为 Skill
- [演示] 设计系统约束下的页面生成与约束验证

**5.3 三层视觉验收**

- 第一层（自动）：Skill 扫描 hardcoded 值 + ESLint/CI 拦截
- 第二层（工具辅助）：截图对比 + 像素级检查
- 第三层（人工）：视觉节奏、信息层级、交互情绪

### 第六部分：项目空间建设 — 让代码库成为 Agent 的操作系统（约 1.5h）

> **目标**：掌握 Harness 项目空间的四层架构，将项目改造成 Agent 可精准识别的数字基座。

**6.1 四层架构与即时可用的建设方法**

- 典型项目的完整 Harness 项目空间展示
- 文档层：全局行为规则 + 模块 README（Purpose / Interfaces / Dependencies / Constraints）
- 经验层（遇到问题后引入）：从历史提炼任务级变更模式，个人、项目、团队三级分层
- 约束层：import-linter / ArchUnit + pre-commit hooks 自动拦截架构违规
- 执行层：Skills + MCP + 自动化脚本

**6.2 四层建设前后 Agent 行为对比**

- 空白模块 vs 补充 README 后，定位修改文件的准确率对比
- Architecture as Code 拦截违规 → Agent 读取 CI 报错 → 自主修正全过程
- 有无经验文件时，Agent 是否重复踩同一个已知坑

**6.3 Harness 团队治理**

- Git 管理边界：哪些纳入版本控制哪些不纳入
- 经验文件质量管控：防止"越来越长、Agent 开始忽略"的退化模式
- CODEOWNERS 设置：Harness 文件有指定审阅者，防止质量腐化，Harness的补丁思维

**6.4 [练习] 为示例项目构建文档、经验及约束层**

- 为一个模块编写符合四段模板的 README.md，判断必要性

### 第八部分：测试与反馈体系 — 以 Agent 为中心的质量闭环（约 1h）

> **目标**：建立 AI 时代的行为验证闭环，防止"10 倍代码速度 = 10 倍技术债"。

**8.1 Spec-TDD - 以 AC 为起点的开发循环**

- [练习] 创建 spec-validate Skill：从 Spec 提取 AC → 对比测试覆盖 → 输出覆盖矩阵
- [演示] 核心流程：AC 写入 Spec → 行为级测试 → 实现 → spec-validate 确认覆盖 → 自愈
- AC 质量 = 测试质量 = 代码验收质量，AC 最终确认必须由人完成（HITL）

**8.2 Agent 驱动的探索性验收**

- 架构及框架：Claude → ADB/UI Automator → 设备
- Mission 文件直接对应 Spec AC；screen_knowledge/ 跨会话经验库避免重复踩坑
- [演示] 执行循环：案例应用的完整验收流程

**8.3 以 Agent 为中心的反馈体系**

- 让 Agent 能自己读懂结果（避免人肉搬运）：结构化日志（可观测性）+ 稳定自动化（可测试性）
- 让 Harness 从 Agent 行为中学习：失败模式 → Harness 迭代，而非靠感觉调
- 为什么选行为级测试

### 第九部分：工程师不可让渡的能力 — 设计力与代码审视非常重要（约 0.5h）

> **目标**：打破"AI 会写代码，工程师只需审批"的误区——AI 提速的是实现，加速暴露的是设计缺陷；代码品质守护、架构判断、职业心法，是工程师在 AI 时代的核心竞争力。

**9.1 AI 代码高频错误模式 + CR 策略**

- 五类高频错误：重复逻辑、状态泄漏、命名混乱、架构违规、冗余注释
- [练习] cr-refactor Skill：扫描 diff → 按五类错误输出优先级清单
- 重构铁律：不改功能只改结构；先计划再执行；每步运行 spec-validate，失败回滚
- 决策框架：逻辑正确但结构混乱 → 重构；逻辑本身有缺陷 → 重写

**9.2 AI 时代工程师心法**

- 架构不外包：约束、权衡、边界由人决定，实现交给 Agent
- 约束必须显式：CLAUDE.md + Spec 一次写入永久生效，不让 AI 猜
- 干预是信号：每次纠正后问一句"这需要编码进 Harness 吗"
- 小步拆解：任务越大，本质是约束越缺失
- Git 是后悔药：大改前 commit，改完逐文件 diff，走偏立即回滚
- 必须看代码：AI 加速生成也加速技术债，每迭代一次 CR + 重构
- 管理上下文窗口：主动 compact、善用新 Session、合理使用子代理
- 提升系统可观测性：结构化日志让 Agent 能自主定位问题，比每次手动整理日志更有杠杆
- 分清任务类型：目标明确可验证 → 放心给 AI；涉及权衡无唯一解 → 人来决策
- 保持 HITL：AC 确认、安全逻辑、数据模型重大变更、架构决策、合并前审阅——人工最终裁决

### 第十部分：刻意进化 — 让 Harness 越来越强（约 1.5h）

> **目标**：建立"干预是信号、纠正即 Harness 改进"的工程习惯，通过 Agentic Harness Engineering 让系统自主进化。

**9.1 两种工程师的分野**

- 路径 A：Agent 犯错 → 纠正 → 继续 → 等下一个模型。每月重复同样纠正
- 路径 B：Agent 犯错 → 纠正 → "这次教训，需要编码进 Harness 哪一层？"
- 核心认知：模型自然进步，Harness 不会——只在工程师主动决定时才进化

**9.2 六级进化场景**

每个场景：问题现象 → 应编码到的 Harness 层级

- L1 工具与权限：每次询问权限 → `allowedTools`；不询问删文件 → 危险操作安全规则
- L2 任务边界：直接写代码没澄清 → CLAUDE.md 任务启动规则；硬编码颜色 → 设计系统约束
- L3 微观决策：选了已排除的方案 → ADR；重复已知反模式 → EXPERIENCE.md
- L4 跨会话与完成验证：宣布完成但没验证 → DoD（完成定义）；长会话性能下降 → 上下文重置时机
- L5 经验沉淀：口头纠正但下次又犯 → 写入永久规则；经验文件过长被忽略 → 重组或封装为 Skill
- L6 高风险操作：两个 Agent 修改同一文件 → Worktree 隔离；不停重试浪费资源 → 最大重试 + 熔断器

**9.3 Agentic Harness Engineering**

- 人工 Harness Engineering 是瓶颈：模型更新，Agent迭代，手工优化的泥潭，自动化面临的障碍
- 可观测性驱动的自动演化：Agent组件，经验，决策的可观测性支柱
- 从失败轨迹到可验证改进：多步演化循环，分层映射约束，案例分析
- 关键发现和经验：哪些是有效模式，增益在哪里，归因的可靠性
- [演示] 在 Claude Code 中实现自动进化：Session JSONL是数据起点，分析高频失败模式，自动尝试并应用

**9.4 刻意进化的飞轮**

- 飞轮：干预 → Harness 改进 → 任务颗粒度增长 → 干预减少 → 更多 Agent
- 颗粒度路径：手动指导每步 → 指导方向自行拆解 → 给目标自行规划执行 → 一句话背景端到端
- 刻意修剪：定期清理过时规则，压缩 Harness，避免 Harness 腐化成负担
- [练习] 分析案例项目 Harness 的可优化内容

**9.5 从小范围到大范围的 Harness 突围路径**

- 区分任务的范围和难度，逐级扩大 Harness 的服务范围
- 小范围简单任务（如模块内 CRUD）：Harness 挑战低 → 立即可做
- 小范围复杂任务（如模块端到端需求）：Harness 挑战中 → 团队级 Spec 规范
- 大范围简单任务（如跨系统常规需求）：Harness 挑战高 → 先单系统，再跨系统
- 大范围复杂任务（如跨系统复杂故障）：Harness 挑战极高 → 隐性知识，长期目标

### 第十一部分：多 Agent 规模化 — 从单兵作战到 Agent 团队（约 1.5h）

> **目标**：掌握多智能体角色分工与并发编排，实现从"1 人 ↔ 1 Agent"到"1 人 ↔ N 角色化 Agent"的吞吐量跃迁。

**10.1 五角色模型与上下游合同**

- 五角色 Agent：PM Agent → Planner → Worker → Reviewer → QA
- 切换角色的方法：不同的 Agent.md 和 Skills
- 上下游合同：Spec，任务单，CR 报告作为合同
- HITL 检查点：PM 输出后确认 Spec；Planner 拆解后确认边界；合入前人工审阅

**10.2 三种并发编排模式**

- 扇出-扇入：N 个 Worker 并行 → 汇总（适用无依赖任务；HITL 在汇聚点）
- 流水线：阶段门禁式串行（适用有阶段分工；HITL 在各阶段入口）
- 竞合：同一问题多 Worker 独立求解择优（适用多解空间；HITL 在择优节点）

**10.3 工具组合 - 四件套驱动并发**

- Tmux：多终端会话隔离，窗口名即角色合同（PM / Planner / Worker）
- Git Worktree：每个 Worker 独立目录隔离爆炸半径；无文件重叠的 FD 可安全并行
- Markdown FD 文件：跨 Agent 共享状态的唯一事实来源，不依赖会话内存
- 斜杠命令：生命周期卡口，每阶段显式触发，防止 Agent 越级执行
- 空闲通知机制，让整体状态一目了然
- [演示] 用四件套实现 1 人驱动多 Agent 并行开发

**10.4 规模化节奏与挑战**

- 递进路径：单 Agent → 2 Agent 串行（跑通传递协议）→ 3-4 Agent 扇出（验证隔离）→ 8 Agent 全矩阵
- 模型分层：Worker 用低成本模型执行确定性任务，Planner / Reviewer 用高能力模型做推理判断
- 认知负荷极限：1–4 并发为高效区，8 为极限，超过 8 先完成一个再开新的；频繁要求 Agent 总结是过载信号
- 常见挑战：Token 放大（分层策略）、信息跨角色衰减（结构化传递载体）、并发文件冲突（Worktree 隔离）
- [练习] 设计 Agent 团队拓扑

### 第十二部分：Harness 工程诊断 — 识别症状、定位病因、选对层级修复（约 0.5h）

> **目标**：建立 Harness 问题诊断的系统性视角——区分"Agent 出了问题"与"Harness 配置长了蛀虫"，掌握修复层级决策树，让 Harness 持续健康而不是持续膨胀。

**12.1 高频失效模式**

- 遗留无测试，Agent 盲改：黄金大师模式打快照 + 两帽子原则（重构与开发严格分阶段）
- 跨端崩溃 / 数据污染：全栈遥测注入 + MCP 层强制 BEGIN/ROLLBACK
- 工具幻觉（Skills >50）：按目录动态注册，Pydantic 严格参数约束
- Agent 删关键旧代码：删前强制 `git blame` + CONSTRAINTS.md 圣牛清单
- 重构范围失控：PEV 循环（Plan 审批范围 → Execute 受限 → Verify）
- 多步骤成功率崩塌：错误乘法效应 → 关键步骤间插验证门禁 + 早停熔断
- 长会话规则逐渐失效：注意力衰减 → 核心约束紧贴最新输入 + 每 N 轮重注入
- [演示] 用 PEV 循环管控一次 AI 过度重构

**12.2 Harness Bad Smell**

定期扫描以下蛀虫：过时假设、重叠规则、防御性膨胀、硬编码工作流、万能 Prompt 补丁、经验噪音、推理替代脚本

**12.3 维护铁律**
- 只保留 A 类：设计约束 / ADR 不可替代；复述代码信息的 B 类随模型进化持续清退
- 实验驱动：每次只加一条规则，单独验证，无效回滚；换模型版本跑裸奔基线再决定去留
- 修复选对层级：Tool 实现 → Middleware → Skill → Tool Description → System Prompt

### 第十三部分：角色、组织与协作的进化（约 0.5h）

**13.1 各角色的定位演变**

Agent 接管大量执行性工作后，各角色的价值集中到 Agent 无法替代的部分：

- **PM** → 业务洞察 + 规格架构：用户价值判断与产品方向不变，新增将业务意图转化为可执行 Spec 的能力
- **设计师** → 体验判断 + 设计系统：交互体验与感知层审美判断不变，新增将设计约束系统化沉淀的能力
- **开发** → Harness 设计师，全栈化趋势与专业深度的平衡
- **测试** → 意图守护者——AC 最终确认、探索性验收策略、质量门禁设计
- **运维** → 可观测性基础设施设计者
- 新角色涌现：规格架构师、Harness 平台工程师、AI 质量工程师、设计系统工程师

**13.2 组织及协作的进化**

- 团队规模：减少的是执行实现类人手，判断类角色密度不变
- 组织形态：告别纯职能部门，双层模型——产品特性团队 + 平台 CoE
- 协作重构：从串行交接 → Spec 定稿后多角色并行，HITL 检查点是新的协作时刻
- 协作产物演变：SPEC、设计系统、ADR、Eval 体系、Harness 健康检查
