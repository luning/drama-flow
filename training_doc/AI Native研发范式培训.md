# AI-Native 研发范式：从认知重构到全生命周期工程实践 - 路宁

## 内容简介

随着 OpenAI o1/o3、Claude 4 等推理与 Agent 的爆发，软件研发正从"AI 辅助编码"向"AI 驱动研发（Agentic Workflow）"跨越。然而多数企业仍受困于三大挑战：AI 难以理解复杂存量系统、各环节工具孤岛、模型输出质量不可控。

本课程拒绝停留在 Prompt 技巧层面，围绕 **SDD（规格驱动开发）**、**Agent 友好型架构**、**Skills & MCP 工具系统** 等几条主线，覆盖从需求到落地的完整软件生命周期。核心目标是驱动工程师从"代码搬运工"转型为" **Agent 运行系统（Harness）的总建筑师**"，通过构建人机协同的标准化 SOP，实实在在地缩短产品交付周期。

本课程采用 **循序渐进讲解 + 现场演示 + 随堂练习** 的方式，体系化讲授 AI Native 研发的核心理念与方法论。

## 目标学员

1. **核心开发工程师与架构师**：希望从"手动编码"转向"Harness 编排"，掌握设计可被 Agent 高效理解的模块化系统
2. **研发效能负责人与技术经理**：寻求将 AI 深度注入研发全流程、构建团队级 AI 工作流的决策者
3. **产品负责人与 UI 设计师**：学习编写高质量可执行 Spec、掌握可执行设计系统驱动 Agent 精准交付的方法
4. **测试与质量保障专家**：关注 AI 驱动的测试闭环、自愈式质量保障与自动化验收落地的实践者


## 课程收益

1. **交付提速**：掌握 SDD 方法论，将核心业务模块交付周期从"天"缩短至"小时"
2. **质量自愈**：构建基于 Agent 的测试闭环，实现行为级测试自动覆盖与 Bug 自动修复
3. **知识资产化**：学会将架构规范与开发经验结构化为 Agent 可理解的"项目大脑"
4. **Agent 友好改造**：获得四层改造体系（架构/文档/经验/约束），让系统对 AI 如鱼得水
5. **工具系统构建**：掌握 Skills & MCP 设计方法论，为组织沉淀可复用的 AI 工具资产


## 授课方式

讲师讲授 + 现场演示 + 沙箱演练 + 主题研讨

---

> 本课程所有演示与练习均基于统一的业务代码仓库进行，确保上下文足够丰富且各环节紧密衔接，避免碎片化体验。你可以将方法论直接映射到自己日常工作的真实项目中。

# 第一部分：认知重构 — AI 能力演进与工程师角色转变（约 2h）

> **目标**：建立 AI Native 思维模型，理解从"辅助工具"到"协作实体"的范式跃迁。

**1.1 从补全到推理到 Agent 行动：能力跃迁时间线**

- 模型演进：GPT-3（概率补全）→ ChatGPT（对话理解）→ GPT-4（多步推理）→ o1/o3（思维链搜索）→ Claude 4（Agent 行动）
- 普通 LLM 调用 vs Agent：单轮响应 vs 多步推理多次行动、无工具 vs 自主调用 API、无状态 vs 有记忆上下文、人驱动 vs 自主决策
- Agent 四大能力：Planning（任务分解）、Tool Calling（工具调用）、Reflection（自我修正）、Multi-step Execution（多轮执行）

**1.2 Agent 技术栈五层架构：从推理引擎到自主行动**

- 五层架构：LLM Provider（推理引擎）→ Model Router（成本调度）→ Execution Runtime（执行治理）→ Context OS（记忆管理）→ Agent（思考行动）
- 同一架构两种形态：个人助手内嵌轻量，企业数字员工演化为独立共享服务
- Agent 层核心组件：Agent Runner、Skill 系统、Event 驱动
- 执行内循环：任务规划 → 工具调用 → 自主执行 → 自动修复
- [演示] 在真实业务项目上下文中，跟踪工具展示感知 → 思考 → 执行 → 观察 → 修正的完整轨迹

**1.3 Context OS：Agent 的记忆管理与上下文工程**

- 核心问题：Agent 如何按需获取正确信息，而非每次从头理解
- 交互模式：任务 → 查询（文档/约定/记忆）→ 片段注入 → 推理执行
- 三类分工：Agent 自身（当前 session）、企业平台（跨 Agent 共享及权限）、跨企业 infra（消除重复学习成本）
- 三级记忆：L1 上下文窗口（快，超 70% 遗忘）→ L2 外部存储（CLAUDE.md / SPEC.md）→ L3 参数记忆（固化权重，可能过时）
- CLAUDE.md：项目根目录下的 Agent 配置文件，承载架构约束、命名规范、常用命令与经验索引，是 Agent 进入项目后首先读取的"说明书"，后续各章节将从不同维度展开其用法

**1.4 工程师角色重塑：从"实现者"到"Harness 设计师"**

- 核心转变：设计 Agent 运行环境、校验逻辑与任务边界
- Harness 四维架构：环境隔离、知识地图、评估体系、自愈闭环
- Execution Runtime：个人场景轻量，组织场景必须独立管控五类风险
- 分享其他公司和团队在这方面的探索和实践

# 第二部分：规格驱动开发 (SDD) — 从需求描述到可执行验收（约 3h）

> **目标**：掌握用可执行 Spec 驱动 AI 开发的方法论与工具链，从"描述需求"升级到"定义验收"。

**2.1 Vibe Coding 的天花板：为什么"描述需求"不够**

- AI 不知道"做到什么程度算完成"，多轮对话变成打地鼠
- PRD 描述"做什么"，SPEC 定义"怎么做才算对"
- 核心原则：约束必须显式存在，不能让 AI 去猜

**2.2 可执行 Spec：五段式格式与演进策略**

- 领域名词 → 前置条件 → 主流程 → 异常处理 → 验收标准（AC）
- 一份 Spec，三方消费：开发者自检、AI Agent 自检、自动化测试生成
- 需求变更时三种处理方式：直接覆盖（推荐）/ 追加 / 废弃
- 原则：SPEC.md 只反映当前意图，历史由 git 记录
- 操作节奏：变更确认 → 定位受影响的 AC → 更新 Spec → 人工确认 → Agent 实现

**2.3 [练习] 从 PRD 到可执行 Spec**

- 任务：给定一份真实业务 PRD 草稿（如"新增优惠券模块"），让 Claude 提取五段式 Spec 骨架
- 人工逐条确认 AC，体验"合同"如何约束后续开发质量

**2.4 Prompt SDD：CLAUDE.md 最小约束**

- 零成本起步：接受任务前读 SPEC.md AC → 生成后逐条自检 → 修改已有 AC 标注变更
- 演示：以一个后台管理功能为例，对比"无 Spec" vs "有 Spec"的 AI 响应差异

**2.5 SDD 工具的必要性与设计原理 — 以 OpenSpec 为例**

- Prompt SDD 的三个规模瓶颈：约束易遗漏、AC 无法自动化验证、变更无结构化追溯
- SDD 工具基本循环（讨论→规划→执行→验证→归档）与三种上下文策略：新鲜上下文隔离、工件结构管理、变更隔离
- OpenSpec 结构：每个变更独立目录（proposal / design / tasks / specs），六步工作流（Explore → Propose → Spec → Apply → Verify → Archive），支持完整/快速前进双模式
- 核心机制：防串扰 + 审计追踪 + 渐进式采用

**2.6 [演示][练习] 工具化 SDD 生态：多款主流工具对比应用**

- SDD生态介绍
- GSD：执行优先的上下文工程，新鲜上下文隔离 + 波级并行，适用长任务跨模块重构
- OpenSpec：棕地优先的变更隔离（详见 2.5），适用存量系统迭代、需审计追踪的场景
- Spec Kit：企业级规格治理，宪法机制统一团队规范，8 步结构化闭环，适用大型企业跨团队协作
- Kiro：代理式 IDE，意图即代码，适用个人/小团队最快"想法→产品"路径
- 工具间的组合搭配建议

# 第三部分：Skills & MCP 工具系统 — 为 Agent 构建可控工具链（约 3h）

> **目标**：掌握为 Agent 构建可控工具系统的方法论，理解 Skills 与 MCP 的分工与组合。

**3.1 Skill 设计：四大原则**

- 参数最小化：让 Skill 自己从上下文推断，减少调用者出错
- 结构化反馈：输出包含状态（成功/失败）、变更明细、错误上下文、下一步提示
- 幂等性：可重复调用不产生副作用（`INSERT OR IGNORE`、`mkdir -p`）
- 错误恢复与降级：可恢复错误内部处理，需人工介入的清晰说明原因
- Skill 的四个核心价值：权限隔离、结构化输出、跨会话确定性、低频操作记忆消除
- 进阶：固定逻辑剥离——脚本做无需推理的固定操作，Skill 只负责调用、异常处理与结果解读

**3.2 [演示][练习] 创建 Skill**

以下三个 Skill 均以真实业务项目为上下文演示和练习
- `rebuild-deploy`：H5 编译 → 后端启动 → 模拟器安装，幂等性 + 结构化输出设计
- `spec-validate`：从 SPEC.md 提取 AC → 对比测试覆盖 → 自动生成缺失测试
- `cr-refactor`：CR 扫描 → 按优先级输出问题清单 → 可控分步重构

**3.3 MCP 三大能力 + 四大原则**

- Tools：可调用的有副作用函数，单一职责 + 权限最小化
- Resources：只读上下文注入，给 Claude 补充背景知识
- Prompts：固化高频诊断流程模板，一句话触发标准化分析
- 权限最小化：只读账号 + 视图隔离 + 参数白名单，绝不允许传原始 SQL
- 返回值可解析：结构化 JSON，让 Claude 可靠消费
- 错误信息面向 AI：语义化错误（`USER_NOT_FOUND`），而非技术栈
- 幂等性：只读 Tool 不触发业务逻辑，超时可安全重试
- MCP 的本质是给 Claude 的"工具箱"（确定性 API），Skill 是给 Claude 的"指令书"

**3.4 [演示][练习] 创建 MCP**

在给定项目代码下实现
- 四个只读 Tool：查积分、查流水、查库存、查订单（分别对接用户、订单、商品等核心业务域）
- 权限设计：只读账号 + IP 白名单 + 只暴露视图
- 用自然语言触发 MCP Tool 调用，运营查询无需接触数据库

**3.5 CLI Skill vs MCP Server：选型框架**

- Skill：流程编排、本地工具、Claude Code 独用、规范还在形成中
- MCP：系统集成、权限管控、跨平台复用、工具本身已稳定
- 两者不互斥：Skill 编排高层流程，MCP Tool 负责具体数据访问

**3.6 企业级 Skill / MCP 体系**

- 三层分级：个人级（本地，不纳入版本控制）→ 项目级（Git 管理，随项目演进）→ 企业级（独立仓库 + semver，跨项目共享）
- 版本管理：项目级随代码 commit、PR review；企业级 semver，接口变更升大版本并通知接入方
- Skill 共享：独立仓库维护 → install 脚本安装 → CLAUDE.md 注明版本，onboarding 时是规范传递的核心载体
- MCP 安全运营：只读账号 + IP 白名单 + 审计日志 + 敏感字段脱敏
- 选型口诀：流程编排/本地工具/Claude Code → Skill；系统集成/权限管控/跨平台 → MCP；两者可组合

# 第四部分：Agent 友好型系统设计 — 让代码仓库成为 Agent 的操作系统（约 2h）

> **目标**：掌握让代码仓库成为 Agent"操作系统"的四层改造方法。

**4.1 为什么需要 Agent 友好架构**

- Agent 表现上限取决于你提供的上下文质量
- 模糊项目中，Agent 需要大量推理才能定位任务边界——这是幻觉的温床
- 改造方向：将隐式知识显式化，让 Agent 直接查阅而非反复推断

**4.2 架构层：模块化与边界清晰化**

- DDD 限界上下文：将 Agent 任务限制在局部，压缩单次推理负担
- 接口契约标准化：OpenAPI / Protobuf 描述接口，减少通讯幻觉
- ADR 架构决策记录：让 Agent 不重蹈覆辙

**4.3 文档层：多层次上下文描述机制**

- 三层文档体系：系统级 MD（CLAUDE.md）→ 模块级 MD（README.md）→ 代码级辅助（Type Hints / JSDoc）
- 渐进披露原则：Agent 只需加载当前任务所需的层级信息，细节按需向下展开，推荐的层次结构
- 模块 README 标准模板：Purpose / Interfaces / Dependencies / Constraints

**4.4 经验层：知识注入与提炼**

- 重要前提：经验层是"遇到问题后才引入"的应对手段，不要提前过度建设
- 提炼来源：从 Git History 按任务聚合变更模式，识别每类任务的完整文件变更集
- 组织方式：CLAUDE.md → INDEX.md → 具体经验文件（渐进披露），或封装为 Skill（详见第三部分）
- 经验分层：Team 级 / Project 级 / Individual 级

**4.5 约束层：Architecture as Code**

- 核心思想：把架构规则写成可执行的代码，由 CI 替代人工审查
- 示例：import-linter 禁止 API 路由层直接操作数据库、ArchUnit 断言模块依赖规则

**4.6 [演示] 改造前后对比**

- 演示：以一个业务模块为例，对比无文档 vs 补充模块 README 后，Agent 定位修改文件的准确率差异
- 演示：Architecture as Code 拦截违规代码后，Agent 读取 CI 报错并自主修正

**4.7 [练习] Agent友好化改造**

- 任务：分析架构层改造点
- 任务：为项目补充文档层和约束层基本内容，识别哪些是必要的，哪些是负担
- 任务：为项目提炼经验层知识，注意识别其必要性

# 第五部分：行为验证与代码优化 — 测试、CR 与重构（约 2h）

> **目标**：建立 AI 时代的行为验证与持续改进闭环，防止"10 倍代码速度 = 10 倍技术债"。测试 + CR + 重构三板斧缺一不可。

**5.1 行为级测试策略**

- 为什么不选单元测试：测"用户可感知的行为"，不测"内部实现细节"
- 后端：API 行为级测试，测输入→输出契约，不测 Service 内部调用路径，技术方案
- 移动端：不测 ViewModel 内部状态，测用户可感知的 UI 流程，技术方案
- AI 生成测试场景矩阵（正常/异常/边界），人工筛选关键场景

**5.2 [演示] AC 是合同：从 AC 直接生成测试用例**

- 演示：以商品管理模块的一条 AC 为例，展示如何被 AI 直接翻译成 pytest 测试
- AC 的质量 = 测试的质量 = 代码验收的质量
- HITL 检查点：AC 的最终确认必须由人完成

**5.3 [练习] Spec-TDD：以验收标准为起点的开发**

- 核心流程：AC 写入 SPEC.md → 翻译成行为级测试（看红）→ 实现（看绿）→ spec-validate 确认覆盖
- 与经典 TDD 的关键差异：测试来源是 AC，不绑定实现，重构后测试保持绿色
- spec-validate Skill：SDD 验收门，自动检查 AC 覆盖率并补写缺失测试
- Skill 设计要点：输入 SPEC.md + 测试目录，输出覆盖矩阵及未覆盖 AC 清单；幂等——仅追加缺失测试，不修改已有用例
- 任务：基于 Spec 为项目补充行为测试

**5.4 [演示] RCA 框架与 Bug 自愈**

- 五步法：现象 → 证据 → 假设 → 验证 → 根因
- Bug 注入演练：在代码中故意引入 bug（字段名拼错/协程漏 await）→ Agent 读取错误日志 → 定位根因 → 修复 → 验证
- 提供 RCA 上下文 vs 直接说"帮我修"，AI 定位成功率的巨大差异
- 配套 Skill — `bug-diagnose`：封装五步 RCA 流程，自动收集日志/报错 → 生成假设 → 输出诊断报告，可流转至 Worker Agent 修复

**5.5 [演示] Agent 驱动探索性验收测试**

- 以移动端应用为例，架构：Claude（决策层）→ ADB/UI Automator（执行层）→ Android 设备
- 执行循环：截图 → 分析状态 → 定位元素 → 操作 → 记录 → 循环
- Mission 文件直接对应 SPEC.md AC
- screen_knowledge/ 跨会话经验库：避免重复踩坑
- 配套 Skill — `explore-accept`：将 AC 翻译为 Mission 文件 → 驱动 ADB MCP 探索循环 → 输出验收报告（通过/失败 + 截图）

**5.6 AI 代码高频错误模式**

- 重复逻辑：AI 不知道之前已经写过了
- 状态泄漏：跨请求的可变状态意外共享
- 命名混乱：同一概念不同叫法，或名字与行为不符
- 不遵循架构：如跳过 Service 层直接操作 ORM
- 啰嗦的注释或实现：名字即文档，只写"为什么"而非"是什么"
- 配套 Skill — `cr-scanner`：按 5 类错误模式扫描 diff，输出优先级问题清单（严重/建议/风格），标注文件路径与错误类别

**5.7 重构 vs 重写 + 技术债处置**

- 大量代码依赖AI生成时如何高效识别坏味道
- 重构铁律：不改功能，只改结构；先告诉计划再执行；一次只改一处
- 决策框架：逻辑正确但结构混乱→重构；逻辑本身有缺陷→重写
- 需求变更债（可标记延后）vs 新功能债（本迭代必须处理）
- 配套 Skill — `refactor-plan`：分析依赖与影响范围 → 输出分步重构计划 → 每步后自动运行 spec-validate，失败自动回滚

**5.8 [练习] CR + 可控重构**

- 任务：用 cr-scanner Skill 扫描 AI 生成的业务代码，识别高频错误模式，选择 2-3 条重构项
- 对比 SDD 工具内置的同类 Skill（如有），观察两者在问题发现维度和优先级判断上的差异
- 按"先报告计划 → 确认 → 执行 → 跑测试验证"的节奏完成重构

# 第六部分：多角色智能体规模协作 — 从单兵作战到 Agent 团队（约 2h）

> **目标**：掌握多智能体角色分工与并发编排的方法论，实现从"1 人 ↔ 1 Agent"到"1 人 ↔ N 个角色化 Agent"的吞吐量跃迁。

**6.1 [演示] 多角色协作全流程**

- 演示环境：Tmux 窗口矩阵分屏展示 PM / Planner / Worker × 3 / Reviewer / QA，空闲窗口反向高亮
- 第一段 — 正常流程：PM 澄清需求 → Planner 拆解 4 子任务 → 3 Worker 并行执行 + Reviewer 扫描 → QA 验收
- 第二段 — 异常应对：故意注入 Planner 遗漏约束 + Worker 死循环，对比展示问题表现与应对改进后的效果

**6.2 智能体角色矩阵**

- 五角色模型：PM Agent（需求澄清）→ Planner Agent（任务拆解）→ Worker Agent（隔离执行）→ Reviewer Agent（CR 扫描）→ QA Agent（行为级验证）
- 同一 Agent 加载不同 CLAUDE.md + Skills 即可切换角色，无需不同产品
- 上下游"合同"关系：Spec 文件是 PM → Planner 的合同，Task 拆解是 Planner → Worker 的任务单，CR 报告是 Reviewer → Worker 的修正指令
- HITL 检查点沿角色链分布：PM 输出需确认 Spec → Planner 拆解需确认任务边界 → 最终合入前人工审阅

**6.3 三种并发编排模式**

- 扇出-扇入：Planner 拆解 → N 个 Worker 并行执行 → 结果汇总（适用无依赖任务，不适合子任务有数据依赖的场景，HITL 在汇聚点）
- 流水线：Spec → 实现 → 测试 → CR → 合入，每阶段专属角色（适用有阶段门禁，不适合需求频繁变更的场景，HITL 在各阶段入口）
- 竞合：同一问题分派 2-3 个 Worker 独立求解择优合并（适用多解空间，不适合只有唯一正解且验证成本高的场景，HITL 在择优节点）

**6.4 规模化节奏**

- 递进路径：单 Agent → 2 Agent 串行（跑通传递协议）→ 3-4 Agent 扇出（验证隔离）→ 8 Agent 全矩阵
- 模型分层策略：Worker 用低成本模型执行确定性任务，Planner / Reviewer 用高能力模型做推理判断；优先 Subagent 隔离上下文
- 规模化中的常见挑战：Token 消耗放大、信息跨角色衰减、并发文件冲突 → 应对方向：模型分层 + 结构化传递载体 + Worktree 隔离 + CI 契约校验

**6.5 [练习] 设计 Agent 团队拓扑**

- 提供标准化拓扑模板（角色 / 输入 / 输出 / 并发模式 / HITL 检查点），降低启动成本
- 任务：选一个典型开发任务，设计角色分配与协作拓扑，标注并行/串行边界，小组交叉 Review Token 预算与信息传递链路
- 课后选做：实际运行验证

# 第七部分：经验总结与回顾 — AI 协作核心原则（约 1h）

> **目标**：回顾课程覆盖的关键方法论，提炼为一份可直接用于日常工作的 AI 协作实战清单。以下各条与前面各部分内容呼应，作为集中回顾而非全新知识。

**7.1 设计先行，架构不能外包**

- 人决定架构决策（成本约束、安全约束、团队约束），AI 执行实现
- 架构隐含了众多背景信息，不适合外包

**7.2 善用 CLAUDE.md / 知识沉淀 / SDD 固化约束**

- CLAUDE.md：命名规范、架构约束一次写入永久生效，是 Agent 的"宪法"
- 知识沉淀：bug 复盘、踩坑经验、最佳实践结构化存储，渐进披露，经验不随人走
- SDD 固化：利用 SDD 工具约束流程提升成功率，按任务复杂度判断是否启用，避免重而无效

**7.3 结构化 Prompt：把需求写成可执行指令**

- 明确输入/输出/成功标准/失败处理/约束，模型是概率机器，信息越完整猜错空间越小

**7.4 小步拆解，每步可验证**

- 一大步的本质问题是约束严重缺失；小步拆解是补足约束的手段
- 替代方案：先写详细 Spec 再统一开发——约束不在步骤里，就必须在 Spec 里

**7.5 Git 是后悔药：AI 时代的版本管理节奏**

- 每次 AI 大改前先 git stash/commit，改完逐文件 diff 确认
- 发现走偏了 git checkout 单文件回滚，或 Esc Esc 回滚整个对话

**7.6 必须看代码 + 及时重构**

- AI 加速了代码生成也加速了技术债积累，"每迭代一次 CR + 重构"是最低成本的路径
- 如何快速识别值得追问的异常，常见的模式
- 微观工程决策（错误码、字段设计、命名）AI 容易给出"合理但不符约定"的答案

**7.7 管理 Session 与上下文窗口**

- 积极考虑 compact 并提供方向说明，积极使用新 Session
- compact（压缩）/ fork（分叉）/ subagent（隔离）三者的配合使用

**7.8 熟悉 AI 不擅长的任务和容易犯的错误**

- 不擅长的任务：安全敏感逻辑、性能调优、有限状态机、架构重大决策、跨会话上下文、调试奇异 Bug
- 容易犯的错误：缺乏上下文时容易"瞎猜"——给日志、给截图、给具体现象，提供 RCA 上下文后定位成功率大幅提升

**7.9 分清执行类与架构类任务**

- 执行类（目标明确、结果可验证）：直接给 AI
- 架构类（涉及权衡、无唯一正解）：对比提问，"人"做决策

**7.10 对 Agent 保持高可观测性**

- 可观测性好的系统，Agent 可以自己读日志、定位问题、提出修复
- 提升系统可观测性，比每次 Debug 都手动整理上下文更有杠杆

**7.11 保持人类最终裁决权（HITL）**

- 必须人工确认：AC 最终确认、安全逻辑、数据模型重大变更、架构决策、合并前审阅
- 可以信任 AI：根据 AC 生成代码、跑测试+修复、生成 Spec 骨架、执行已定义的重构步骤

# 第八部分：原型与视觉验证 — AI 时代的设计系统（约 1h）

> **目标**：理解可执行设计系统，建立"代码即设计源"的新工作流。本专题适合产品负责人、UI 设计师及对设计系统感兴趣的开发工程师。

**8.1 原型四代演进：设计权力中心的迁移**

- 文档时代（Axure）：原型 = 沟通说明书
- 视觉时代（Figma）：原型 = 可复用设计组件
- 代码化时代（Storybook/shadcn）：原型 = 可运行组件
- AI 生成时代（v0/Bolt/Lovable）：原型 = 可执行产品
- 四个时代叠加积累而非依次替换，背后是"谁来定义 UI、控制一致性"的权力迁移，核心变化是 Figma 从"设计源文件"演化为"可视化协作 IDE"

**8.2 可执行设计系统的五层结构**

- Specification（业务约束）→ Design Token（品牌变量）→ Component Runtime（组件库）→ AI Generation（AI 规则）→ Visual Collaboration Layer（Figma 协作）
- AI 越能生成，设计系统的约束越重要——否则风格漂移、组件重复、UX 崩坏、状态不一致
- tokens.ts 是单一真相源：Figma 通过 Tokens Studio 同步消费，组件引用它驱动样式，AI 用它约束生成
- Figma 四个不可替代价值：人类可视化理解、UX 微调、AI Prompt 编辑、跨角色协作

**8.3 [练习] 为项目搭建可执行设计系统**

- 任务：从一个项目的原型或需求中提取设计系统，创建 tokens.ts + constraints.md + design-rules.md 等文件
- 推荐目录结构：design-system/（tokens.css / tokens.ts / constraints.md / design-rules.md / components/）
- 调优后让 AI 读取这些文件生成页面，验收其是否自动遵守设计约束
- 设计角色参与方式：GitLab 网页直接编辑 constraints.md（零门槛）、Tokens Studio 同步 Figma Token、CODEOWNERS 把关设计文件合并

**8.4 [练习] 在设计系统约束下创作原型**

- AI 读取设计系统文件后生成原型，自动遵守 Token 引用、组件调用、业务约束
- Prototype Skill 封装：将上下文注入流程固化为 Skill，设计系统遵守从"靠人记忆"变成"系统默认"
- 应用不同的原型生成工具：Claude Design，Claude Code，v0.dev

**8.5 三层视觉验收：从自动到人工**

- 第一层 — 代码合规（自动）：两道防线——生成时 Skill 扫描 hardcoded 色值；提交时 ESLint/CI 拦截
- 第二层 — 渲染正确（工具辅助）：主要方法、核心挑战及应对策略
- 第三层 — 体验质量（人工）：视觉节奏、信息层级、交互情绪感——前两层卸掉合规负担，人工走查才能专注这里
