# AI 新技术在测试的应用：大模型 Skill 能力建设与 Agent 驱动测试实践

## 内容简介

技术测试的核心挑战是：日志诊断依赖经验、性能问题难以定位、SQL 优化缺乏系统化方法——答案藏在数据里，但数据量太大、关联太复杂，人工处理效率极低。

AI 的价值是**知识驱动的自主测试能力**——把测试依据、领域知识、诊断经验沉淀为可版本化的 Harness，让 Agent 基于这套持久知识自主完成用例生成、执行与诊断。代价是大模型"可信但错"的输出识别难度高，必须有工程化对策。

本课程聚焦三类场景：功能测试、性能容量测试和 SQL 优化辅助。以**测试 Harness** 为工程基座，Skill / Agent / SDD 为实现手段，**Skill Hub** 为团队共建平台——帮助测试团队把 AI 能力从个人工具升级为可治理、可演进的团队基础设施。

## 目标学员

1. **技术测试工程师**：掌握用例设计、日志诊断、可观测性改进的 Skill 实现方法
2. **性能测试工程师**：掌握模拟数据生成、趋势诊断、容量预测的 Skill 构建方法
3. **测试自动化工程师**：掌握 Skill / Agent / SDD 的设计与工程化
4. **测试团队负责人**：建立 Skill Hub 治理体系与 Harness 持续进化路线图

## 课程收益

1. **测试 Harness 工程**：搭建项目测试空间，把知识、经验、约束和执行能力版本化沉淀
2. **Agent 驱动测试框架**：掌握从用例设计到执行自愈、诊断分析的完整能力体系
3. **三类场景 Skill 实现**：功能测试的用例生成与日志诊断、性能测试的数据生成与趋势诊断、SQL 优化辅助
4. **Skill 质量保障**：掌握 Skill 和 Agent 的测试方法与稳定性工程手段
5. **Skill Hub 与社区共建**：建立团队级共享体系，规划内外开源路径

## 课程大纲

### 第一部分：测试 Harness 结构与进化（约 30min）

> **目标**：建立"Harness 是测试能力的持久基座"的核心认知，理解项目测试空间的四层结构，掌握 Harness 随系统版本演进的方法。

**1.1 从散落 Skill 到持久 Harness**

- 散落 Skill 的四个退化点：无版本管理、约束跨会话消失、新人不知用哪个、知识与模板处处过时
- 三层范式演进：Prompt 工程（怎么问）→ Context 工程（给模型看什么）→ Harness 工程（模型在什么机制里干活）
- Harness 的一句话定义：**不是在教模型怎么回答，而是在设计模型怎么工作**
- [演示] 裸提问 vs 注入 Harness 知识后生成：用例覆盖深度与幻觉率对比

**1.2 项目测试空间：典型结构**

- 典型项目测试空间展示
- **知识层**（`knowledge/`）：接口契约、错误码表、系统领域规格；CLAUDE.md 渐进披露按需加载，Agent 推理的原材料
- **经验层**（`experience/`）：团队错题本；写"陷阱条件"不写"个人偏好"；任务关键词触发加载；少而精
- **约束层**（`hooks/`）：Hook 自动拦截不合规输出，DoD 门禁阻止未评审用例进入执行
- **执行层**（`skills/ / commands/`）：Skill 封装工作流，Agent 定义角色，SDD 命令串联流水线

**1.3 Harness 维护与进化**

- 干预即信号：AI 反复编造同类输出 → 补知识层；评审反复驳回 → 补经验层；Agent 总忘某规则 → 固化为 Hook
- 版本迭代后资产同步：系统接口 / 日志格式 diff 交给 Agent，批量输出受影响资产清单
- 维护铁律：每次只加一条规则、单独验证、无效回滚；采纳率走低是 Harness 老化先行信号
- **自动进化闭环**：采集评审驳回与执行失败轨迹 → 聚类高频模式 → 归因 Harness 层级 → 生成候选规则补丁 → 回归集验证 → 人工审批入库；**安全红线：禁止把"真缺陷"规则化掩盖**

### 第二部分：Agent 驱动测试的完整框架（约 50min）

> **目标**：建立 Agent 驱动测试的完整能力模型，理解 Skill / Agent / SDD 三者的分工，掌握生成-评审分离的质量保障机制——这是后续三类场景的共同方法论基础。

**2.1 四个能力维度**

- **用例设计**：基于测试依据、领域知识、历史缺陷生成可溯源的用例集
- **可测试性**：接缝设计、测试接口约定、环境构造——决定 Agent 能否可靠执行
- **可观测性**：结构化日志、状态事件埋点、指标采集——决定 Agent 能否读懂系统状态
- **执行 + 自愈 + 诊断**：Agent 驱动执行循环、失败分类与自愈、根因诊断
- 可测试性和可观测性是 Agent 的感知基础设施：两者不足，Agent 就只是代码生成器

**2.2 Skill / MCP / SDD / Agent / 多 Agent 的分工**

- **Skill** = 封装"怎么干这件测试活"：单职责、有明确完成标准、可跨 Agent 复用；步骤固定但需要 AI 推理的场景
- **MCP Server** = 外部服务集成接口：确定性 API，Agent 通过 Tool Call 调用；适合接入已有稳定工具（测试平台、缺陷系统、监控 API）
- **Agent** = 持角色、带工具白名单的自主执行者：驱动"观察-决策-行动"循环；单 Agent 负责一个明确角色
- **多 Agent 协作** = 分角色流水线：生成 / 评审 / 执行 / 诊断 Agent 各司其职，独立上下文防自评估污染；每个 Agent 有持久角色定义，不同于一次性子代理
- **SDD（Spec-Driven Development）** = 以结构化工件驱动的有状态流水线：Spec → 用例 → 评审 → 执行 → 诊断，每阶段输出是下阶段的输入；命令（`/gen-cases`、`/diagnose`）是流水线入口，每阶段起干净 Session 防上下文污染
- **自定义 SDD**：在 `commands/` 目录下为每个阶段编写命令文件，定义阶段角色、输入工件、输出工件、完成标准和 Hook 校验点；测试团队可按流程拆分阶段，将现有测试规范直接固化为可执行命令

**2.3 生成-评审分离：质量的核心保障**

- 自评估的系统性缺陷：同一上下文内 Agent 对自己输出的幻觉检出率显著低于独立评审
- 最小可行模型：生成 Agent（注入规格 + 知识）+ 评审 Agent（独立上下文，只读用例 + checklist）
- [演示] 自检 vs 独立评审的幻觉检出率对比

**2.4 领域知识决定输出质量上限**

- 无领域知识时只产出"通用软件"用例：格式正确、术语像样，工程上意义有限
- 知识注入四个来源：系统规格、接口契约、历史缺陷库、可观测性数据
- [演示] 裸问 vs 注入接口契约 + 错误码表后生成，覆盖深度与幻觉数量对比

**2.5 [演示] Agent 驱动 UI 验收：三要素缺一不可**

- **页面知识**：screen_knowledge/ 记录控件语义、已知坑、等待规则；跨会话积累，Agent 导航不依赖硬编码坐标
- **可测试性**：测试接口预置状态；操作后有稳定的完成标志；Mission 对应 Spec AC，意图可溯源
- **可观测性**：结构化留痕（动作-控件-结果 + 失败截图），诊断 Agent 可直接读懂，无需人工搬运

### 第三部分：常规功能测试的关键实现（约 30min）

> **目标**：掌握功能测试场景下的关键实现要点——用例溯源防幻觉、可观测性对诊断效率的影响、日志诊断的"先结构化再推理"流水线。

**3.1 API 测试 vs UI 测试**

- 优先走 API：稳定、可并发、Agent 消费成本低；UI 测试保留给"只能在界面验证"的场景
- 测试接口优先：推动开发侧提供测试接口绕过 UI，比视觉自动化稳定

**3.2 用例设计 Skill**

- 三类驱动输入：AC 条目（正向覆盖）/ 历史 Bug（补回归盲区）/ 接口文档（边界与异常）
- 溯源字段强制：每条用例携带"来源 AC 编号 / Bug ID"；Hook 拦截溯源字段为空的输出
- [待确认] 标记法：需求不清晰时主动标记而非编造

**3.3 可观测性设计：Agent 诊断的前提**

- 结构化日志：每条日志可独立被机器解析（时间戳 / 模块 / 事件 / 关键字段）
- 错误响应结构化：API 错误必须携带 error_code + 上下文字段，Agent 无法定位 "Internal Server Error"
- 状态转换必须记录：from / to / trigger，便于还原问题时序
- 可观测性成熟度阶梯 L0 → L4；**最小可行目标：L2**（结构化日志 + 稳定 API 测试）

**3.4 日志诊断 Skill**

- "先结构化、再推理"：脚本完成时间对齐 / 窗口截取 / 事件抽取，大模型只在压缩后事件序列上推理
- 输出格式：现象 → 根因假设（按概率排序）→ 验证手段；每条假设引用日志行号，无证据标 [推测]
- 故障模式库：诊断后把"现象-证据-根因"三元组写入经验层，下次自动 few-shot 注入
- [演示] 原始混杂日志 → 预处理 → 压缩事件序列 → 根因报告（含行号引用）

### 第四部分：性能容量测试的关键实现（约 30min）

> **目标**：掌握性能测试场景的 Skill 设计要点——数据代表性保障、时序数据结构化处理、趋势诊断的多因性推理。

**4.1 性能测试的特有挑战**

- 数据代表性：模拟数据必须覆盖真实负载分布（正常 / 峰值 / 容量边界），不能随机生成
- 时序关联：性能问题往往藏在时序关联里（A 指标先升，B 指标延迟跟升），单点阈值无法发现
- 瓶颈多因性：多指标同时异常时需多假设并行推理确定主因

**4.2 模拟数据生成 Skill**

- 参数化设计：负载模式（正常 / 峰值 / 容量边界）、时间粒度、业务场景权重
- 边界场景覆盖：满载、空载、冷启动、长时间跑批
- [演示] 生成三类负载模式的压测数据集

**4.3 性能趋势诊断 Skill**

- 时序预处理：归一化时间轴、填充缺失点、对齐多指标时间戳
- 拐点识别：区分噪声与真实退化；多指标关联推理，输出"主因假设 + 支撑证据 + 验证手段"
- 容量预测：基于历史趋势外推，输出"X 时间后触达水位边界"预警
- [演示] 从参数到诊断报告的完整 Skill 链（数据生成 → 压测执行 → 趋势诊断）

---

### 第五部分：SQL 优化辅助测试的关键实现（约 30min）

> **目标**：理解 SQL 优化辅助的场景定位差异，掌握慢查询结构化分析和改写建议 Skill 的设计要点与安全边界。

**5.1 场景定位：分析建议，不是执行验证**

- 核心差异：功能 / 性能测试是"执行 → 观察 → 判定"，SQL 优化辅助是"采集 → 分析 → 建议 → 人工决策"
- AI 的合理边界：**禁止自动执行 DDL / DML**；每条建议须附推理依据，不确定的标 [需人工验证]

**5.2 SQL 优化辅助 Skill 设计**

- 慢查询日志结构化：按问题类型分类（全表扫描 / 缺失索引 / N+1 / 锁等待）
- 改写建议：说明"为什么慢 + 改写后为什么快"；P0（线上已影响）/ P1（潜在风险）/ P2（优化空间）
- 安全约束：输出建议文档，不输出可直接执行的 SQL；附"预估影响"字段

**5.3 改写效果验证与知识沉淀**

- 对比链：原始 SQL + 执行计划 → 改写建议 → 测试环境执行 → 新执行计划 + 耗时对比
- 常见慢查询模式整理进 Harness 知识层，下次分析自动 few-shot 注入
- [演示] 慢查询日志 → 结构化分析 → 改写建议报告（含推理链 + 优先级）

### 第六部分：Skill 和 Agent 的测试与稳定性（约 20min）

> **目标**：掌握对 Skill 本身进行测试的方法，理解 Agent 稳定性的系统性来源。

**6.1 三类测试手段**

Skill 的特有风险是输出漂移——相同输入在不同上下文下输出不一致，且版本变更、模型升级都可能静默引入回归：

- **快照测试**：固定输入保存期望输出快照，变更后对比——检测格式与关键字段退化
- **边界输入测试**：空输入、异常格式、超长文本——验证 Skill 的降级处理
- **独立评审 Agent**：新鲜上下文只读输出 + checklist——检测语义质量，最接近真实使用

**6.2 稳定性工程手段**

- 约束 Hook：机器可查的 DoD 规则固化为自动拦截，不靠 Agent 自觉
- 幂等设计：同一 Skill 反复调用结果一致，不产生累积副作用
- 参数最小化：Skill 自己从上下文推断，减少调用者出错机会

**6.3 Agent 规模化视野**

- 多 Agent 协作流水线：生成 Agent + 评审 Agent + 执行 Agent 分角色运行
- 人工监督带宽是硬约束：汇总报告让人 10 分钟内判断是否有真问题
- 错误乘法效应：关键节点插 DoD 门禁，偏差早停；HITL 检查点控制危险操作

### 第七部分：Skill Hub 规划与社区共建（约 15min）

> **目标**：掌握团队级 Skill 库的分类规划与治理规范，建立从内部 Hub 走向对外开源的演进路径。

**7.1 三层分级与 Hub 分类**

- 个人层（本地）/ 项目层（Git 管理）/ 团队层（共享仓库 + 安装脚本）
- 按"测试类型 × 能力域"建目录：功能测试 / 性能测试 / 优化辅助 × 用例设计 / 诊断分析 / 数据生成
- 每个 Skill 必须有 README（用途 / 输入输出 Schema / 使用示例 / 限制说明）

**7.2 内部开源路径**

- 共享仓库 → 安装脚本（一键部署）→ 贡献规范（PR 模板 + Review checklist）
- Skill Hub 是团队规范传递的核心载体，新成员 Onboarding 的起点

**7.3 对外开源策略**

- 脱敏 + 通用化改造：去除业务特有名词，从"适用于本系统"升级为"适用于同类场景"
- 以"问题 + 解法"为单位贡献，比直接开放整个 Hub 更易获得社区反馈

### 第八部分：实践——Agent 驱动测试能力建设（约 3h）

以下三个案例**并列**，每个案例采用**递进约束场景**，从理想条件出发逐步引入真实障碍。学员选 1-2 个深入完成。

---

**案例一：应用日志诊断 Skill**

- **场景一（基线）**：结构化日志，字段完整 → 设计 `/diagnose-log` Skill，触发 Hook 拦截缺少行号引用的输出
- **场景二（噪音）**：日志混杂多服务，时间戳偏差，字段缺失 → 预处理脚本如何处理？Skill 如何标注证据不足？
- **场景三（知识缺口）**：日志含系统特有错误码，模型不识别 → 如何注入错误码表？对比注入前后诊断准确度
- **场景四（规模约束）**：日志超出上下文窗口 → 从"截取窗口"升级为"事件序列压缩"；诊断结论写入故障模式库
- **场景五（讨论）**：根因根本没有被日志记录——Skill 应该输出什么？如何沉淀可观测性改进建议？

---

**案例二：性能趋势诊断 Skill 链**

- **场景一（基线）**：指标完整，有明显拐点 → 设计 `/analyze-perf-trend` Skill，识别拐点输出瓶颈假设
- **场景二（缓慢退化）**：无明显峰值，持续缓慢劣化 → 如何区分噪声与真实退化？设计趋势外推与容量预警
- **场景三（数据缺失）**：指标时序有缺失段 → Skill 如何降级处理？何时必须标注"诊断不可信"？
- **场景四（多因瓶颈）**：CPU / 内存 / IO 同时异常 → 设计 `/gen-perf-data` Skill，链式组合进 SDD，验证幂等性

---

**案例三：SQL 优化辅助 Skill**

- **场景一（基线）**：明显缺失索引的慢查询 → 设计 `/sql-review` Skill，输出带推理链的 P0/P1/P2 建议
- **场景二（安全边界）**：复杂多表 JOIN，改写可能有副作用 → 如何加置信度标注和安全约束？
- **场景三（执行计划缺失）**：只有 SQL 和耗时，无执行计划 → Skill 如何降级？如何推动补充采集？
- **场景四（知识积累）**：同类问题反复出现 → 慢查询模式整理进知识层，验证 few-shot 自动注入效果

---

**综合练习：Skill 测试 + Hub 贡献**

- 对完成的 Skill 做边界输入测试（空输入、异常格式、超长文本）
- 按 Hub 规范补充 README，提交到模拟 Hub 仓库走 PR + 评审流程
- 复盘：各学员分享一个"在递进场景里发现的真实问题"
