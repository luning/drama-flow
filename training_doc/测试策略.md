# 测试策略与测试自愈

> **核心主张**：AI 加速了代码生成，也同步加速了技术债的积累。测试策略的选择不是技术偏好，而是决定"债还在哪里"——选错了，测试本身就变成了最难还的债。

---

## 一、为什么不选单元测试

单元测试绑定具体实现（函数名、类结构、调用签名）。在 AI Native 开发中，这个绑定代价极高：

**AI 生成代码的特点**：
- 内部实现路径不稳定——同一个功能，第二次生成可能重构了内部逻辑
- 重构频繁——CR + 重构是课程的常规节奏，不是偶发事件
- 命名容易漂移——跨轮迭代后函数名、模块分组都可能变化

**后果**：迭代 1 写的单元测试，到迭代 2 重构后，即使业务行为完全正确，测试也大面积报红。工程师花更多时间修测试而非改功能，投入产出完全倒置。

**结论**：不是不测，而是测"用户可感知的行为"，不测"内部实现的细节"。

## 二、DramaFlow 测试层级选择

### 后端：API 行为级测试（pytest）

测 API 的输入 → 输出契约，不测 Service / Repository 的内部调用路径。

```
# 好的测试：测 API 行为
def test_login_with_wrong_password_returns_401():
    response = client.post("/api/auth/login", json={
        "email": "user@test.com",
        "password": "wrong_password"
    })
    assert response.status_code == 401
    assert "detail" in response.json()

# 坏的测试：测内部实现
def test_auth_service_calls_hash_verify():
    with patch("app.services.auth.verify_password") as mock:
        ...  # 重构后必挂
```

**测什么**：

| 场景 | 测试重点 |
|------|---------|
| 正常流程 | 正确 HTTP 状态码 + 响应结构 |
| 认证/鉴权 | 无 Token / 过期 Token / 越权访问 |
| 数据边界 | 空字符串、超长字段、不合法格式 |
| 状态依赖 | 创建后读取、删除后再查 |

**不测什么**：SQL 查询语句、ORM 对象属性、Service 函数的调用次数。

---

### Android 端：两个维度的选择

Android 端测试有两个独立维度，组合出不同适用场景：

**驱动方式**——谁决定下一步操作：
- **脚本驱动**：开发者提前写死步骤和断言，每次行为确定 → 适合 CI 回归守门
- **Agent 驱动**：Claude 运行时看截图决策 → 适合探索性验收，能处理意外弹窗和 UI 变化

**执行工具**——怎么操控设备：

| | ADB | UI Automator | Espresso |
|---|---|---|---|
| **耦合度** | 零耦合，无需源码 | 零耦合，无需源码 | 需要 View ID，依赖源码 |
| **范围** | 黑盒，任意 App | 黑盒，支持跨 App | 白盒，单 App 内 |
| **上手难度** | 最低 | 中 | 中 |

这两个维度可以自由组合——Espresso / UI Automator / ADB 都能作为 Agent 驱动的执行层。

**测什么，不测什么**（与后端相同原则）：

```kotlin
// 好的测试：测用户流程（行为）
@Test
fun loginWithValidCredentials_navigatesToHome() {
    onView(withId(R.id.emailInput)).perform(typeText("user@test.com"))
    onView(withId(R.id.passwordInput)).perform(typeText("password123"))
    onView(withId(R.id.loginButton)).perform(click())
    
    onView(withId(R.id.homeFragment)).check(matches(isDisplayed()))
}

// 坏的测试：测 ViewModel 内部状态（实现）
@Test
fun loginSetsTokenInViewModel() {
    // ViewModel 内部状态变化对用户不可见，重构后必挂
}
```

**场景选型参考**：

| 场景 | 推荐方式 |
|------|---------|
| CI 每次 PR 回归，验证核心流程不挂 | 脚本驱动（Espresso）|
| 新功能上线前的视觉 + 交互验收 | Agent 驱动（test-agent）|
| 无源码的黑盒验收（测已发版 APK）| 脚本驱动（ADB / UI Automator）|
| 意外弹窗、未预期 UI 状态的处理 | Agent 驱动（Claude 实时决策）|

**Agent 驱动的核心架构**（test-agent）：

```
Claude Agent（看截图、决策下一步）
        │
        │ HTTP / ADB
        ▼
Android 设备执行层（点击、输入、截图、获取 UI 树）
```

执行循环：Observe（截图 + UI 树）→ Plan（Claude 分析状态）→ Locate（定位元素）→ Act（操作）→ Record → 循环

Mission 文件直接对应 SPEC.md 的 AC——AC 定义验收标准，mission 定义验收任务。`screen_knowledge/` 目录以页面名称为索引存储操作经验（已知陷阱、布局特殊性），跨会话复用，避免重复踩坑。

> 完整实现细节（执行工具对比、代码示例、screen_knowledge 格式、执行层演进路线）见 [探索性验收测试方案.md](探索性验收测试方案.md)

## 三、AI 生成测试场景矩阵

AI 擅长穷举边界条件，人擅长判断哪些有价值。标准协作模式：

**第一步：让 AI 推导测试矩阵**

```
给定这个 API Spec：
  POST /api/auth/login
  请求：{ email: string, password: string }
  响应：200 返回 token，401 密码错误，422 参数格式错误

请生成覆盖以下维度的测试场景矩阵：
- 正常流程（Happy Path）
- 异常输入（Error Path）
- 边界条件（Edge Cases）
- 安全场景（Security Cases）

每个场景用一行描述：输入 → 预期输出，不写代码
```

**第二步：人工筛选**

AI 会生成 20-30 条，但不需要全部写成测试。筛选标准：
- **必测**：P0 功能的 Happy Path + 最关键的 Error Path
- **选测**：高风险的边界条件（如 Token 过期的并发续期）
- **跳过**：纯格式校验（已有 Pydantic 覆盖）、极低概率场景

**第三步：让 AI 生成测试代码**

筛选后的场景，逐条让 AI 实现。场景描述越精确，生成质量越高。

**DramaFlow 示例矩阵节选**：

| 场景 | 输入 | 预期输出 | 优先级 |
|------|------|---------|--------|
| 正常登录 | 有效 email + password | 200 + token | P0 |
| 密码错误 | 有效 email + 错误 password | 401 | P0 |
| 不存在用户 | 未注册 email | 401 | P0 |
| 空 email | "" + password | 422 | P1 |
| Token 过期后调用接口 | 过期 token + 任意请求 | 401 | P0 |
| 重复注册 | 已存在 email | 409 | P1 |
| SQL 特殊字符注入 | email = "' OR 1=1--" | 422 或 401，不崩溃 | P0 |

## 四、spec-validate Skill：SDD 的验收门

每条 AC 写完，通过 `spec-validate` 检查测试覆盖率。这是 SDD 闭环的最后一关。

**工作原理**：
1. 读取 SPEC.md，提取所有 AC
2. 扫描测试文件，按关键词匹配 AC ↔ 测试
3. 输出覆盖报告：已覆盖 / 缺失 / 描述不匹配
4. 对缺失的 AC，自动生成测试骨架（可选自动补写）

**触发时机**：
- 每完成一个迭代的功能模块后跑一次
- CR 前确认没有 AC 遗漏
- Spec 有变更后重跑

**典型输出**：

```
✅ AC-AUTH-01: 注册成功返回 201 → test_register_success (line 23)
✅ AC-AUTH-02: 重复邮箱返回 409 → test_duplicate_email (line 45)
❌ AC-AUTH-03: Token 过期自动刷新 → 无对应测试 [已生成骨架至 tests/test_auth.py:89]
⚠️  AC-AUTH-04: 密码强度校验 → test_password_validation 存在但 AC 描述已更新，请确认
```

**"不脆弱"的测试写法原则**：

测试应该随业务行为稳定存在，而不是随实现细节漂移：

```python
# 脆弱：依赖具体返回字段名（内部字段随时可能重命名）
assert response.json()["access_token_value"] == "..."

# 稳定：只验证行为约束
assert response.status_code == 200
assert "token" in response.json()  # 存在性验证
assert len(response.json()["token"]) > 20  # 合理性验证，不验证具体值
```

## 五、基于 Spec 的 TDD 流程

经典 TDD 是"先写测试再写代码"。在 SDD 体系里，AC 已经是一份精确的行为规格——它天然就是测试的先验定义，只差翻译成可执行的测试代码。这让 Spec-TDD 成为比经典 TDD 更容易落地的流程选择。

### 流程对比

**经典 TDD**：
```
写单元测试（基于开发者对实现的预想）→ 看红 → 写实现 → 看绿 → 重构
```

**Spec-TDD（SDD 体系内）**：
```
AC 写入 SPEC.md → 翻译成行为级测试 → 看红 → 写实现 → 看绿 → spec-validate 确认覆盖
```

两者的关键差异：Spec-TDD 的测试来源是 AC，不是开发者对内部实现的预想，所以测试不绑定实现，重构时不会大面积挂红。

### 具体流程（DramaFlow 示例）

**Step 1：AC 定义（SPEC.md 中）**

```markdown
## AC-AUTH-03 Token 刷新
- 前提：用户已登录，access_token 已过期，refresh_token 有效
- 行为：调用任意需认证的接口时，自动使用 refresh_token 换取新 token
- 验收：
  - [ ] 新 token 在响应头 Authorization 中返回
  - [ ] 原请求正常返回数据（不返回 401）
  - [ ] refresh_token 过期时返回 401，不自动重试
```

**Step 2：AI 从 AC 生成测试骨架（此时实现还不存在）**

```python
# 提示词：根据以上 AC 生成 pytest 测试骨架，不要写实现逻辑，只写测试结构

def test_expired_access_token_auto_refreshes():
    # 前置：创建用户，生成已过期的 access_token + 有效 refresh_token
    ...
    response = client.get("/api/dramas", headers={"Authorization": f"Bearer {expired_token}"})
    
    assert response.status_code == 200                          # 原请求成功
    assert "Authorization" in response.headers                  # 新 token 在响应头
    assert response.headers["Authorization"] != expired_token   # token 已更新

def test_expired_refresh_token_returns_401():
    ...
    response = client.get("/api/dramas", headers={"Authorization": f"Bearer {expired_token}"})
    assert response.status_code == 401
```

**Step 3：运行测试，看红**

```
FAILED tests/test_auth.py::test_expired_access_token_auto_refreshes
  → 404: route not found  （中间件还没实现）

FAILED tests/test_auth.py::test_expired_refresh_token_returns_401
  → 404: route not found
```

**Step 4：让 AI 实现，目标是让测试变绿**

```
"这两个测试当前失败，请在 backend/app/middleware/auth.py 中实现
 JWT 自动刷新逻辑，让测试通过。已有的 refresh endpoint 在 /api/auth/refresh。"
```

AI 有明确的成功标准（测试绿），生成质量和迭代效率都比"让 AI 写个 token 刷新功能"高得多。

**Step 5：spec-validate 确认 AC 全部覆盖**

```
✅ AC-AUTH-03: Token 刷新 → test_expired_access_token_auto_refreshes (line 45)
✅ AC-AUTH-03: refresh 过期返回 401 → test_expired_refresh_token_returns_401 (line 58)
```

### 为什么 AI 场景下 Spec-TDD 更有效

| 维度 | 经典 TDD | Spec-TDD |
|------|---------|---------|
| 测试来源 | 开发者对实现的预想 | SPEC.md 的 AC（与实现无关）|
| 重构后测试状态 | 大面积挂红（绑定实现）| 保持绿（只绑定行为）|
| AI 的角色 | 写测试 + 写实现（容易自循环）| 从 AC 生成测试骨架，以测试为目标写实现 |
| 验收闭环 | 手动 code review | spec-validate 自动检查 AC 覆盖率 |

### 什么时候跳过 TDD 直接写实现

Spec-TDD 不是强制流程，以下场景可以先实现再补测试：

- **探索性代码**：不确定 API 设计是否合理，先跑通再定 AC
- **纯 UI 组件**：视觉层逻辑变化快，AC 难以提前稳定
- **原型阶段**：迭代 1 早期快速验证功能是否可行

原则：**AC 越稳定，越适合先写测试**。AC 还在变动的阶段，先实现再固化 AC 再补测试。

## 六、Bug 注入与 RCA 框架

### Bug 注入演练的目的

不是为了制造麻烦，而是在受控环境中练习"让 Agent 自主修复"的完整链路：
**错误日志 → Agent 读取 → 定位根因 → 修复 → 验证 → 提交**

这是生产环境最真实的问题处理场景。

### 典型 Bug 注入案例（DramaFlow）

**场景 1：后端接口 500**

```python
# 故意注入：watch_records 写入时 drama_id 字段名拼错
# 原本应该是 "drama_id"，改为 "dramaid"
watch_record = WatchRecord(
    user_id=user_id,
    dramaid=drama_id,  # ← 注入的 Bug
    episode=episode_number
)
```

让 Agent 读取 `uvicorn` 错误日志，观察其如何通过堆栈信息定位到 ORM 映射问题。

**场景 2：播放进度不保存**

```kotlin
// 故意注入：写入播放进度时漏掉 await
viewModel.saveProgress(episodeId, currentPosition)  // 应该是 suspend 函数
// 结果：不报错但进度静默丢失
```

这类"无报错的逻辑 Bug"是最难调的，让 Agent 通过日志对比"写入前 vs 读取后"的状态来定位。

---

### RCA 框架：现象 → 根因的五步法

当遇到 Bug 时，不要直接让 AI "帮我修这个 Bug"——那是最低效的方式。要走完整的 RCA 链路：

```
现象（Symptom）
    ↓ 观察并记录表现
证据（Evidence）
    ↓ 收集日志、截图、复现步骤
假设（Hypothesis）
    ↓ 根据证据推测可能原因（1-3个）
验证（Validation）
    ↓ 针对每个假设设计最小实验
根因（Root Cause）
    ↓ 确认根因并修复
```

**DramaFlow 实战示例**：

```
现象：播放进度存入后，重新进入剧集详情页，"继续观看"按钮不出现

证据：
  - API GET /api/watch-records/user/1 返回空数组 []
  - POST /api/watch-records 返回 200 且有 id 字段
  - SQLite 文件中手动查询 watch_records 表，数据存在

假设：
  1. 查询接口 SQL 条件写错（过滤条件有误）
  2. 写入和查询用的是不同 db 连接（路径不同）
  3. drama_id 字段类型不匹配导致查询匹配失败

验证假设 1：直接打印生成的 SQL 语句，检查 WHERE 子句
验证假设 2：在 POST 成功后立即 GET，看是否能查到

根因：验证发现 POST 写入用了临时 db session，commit 后 session 关闭
      但连接没有 flush，导致数据没有真正持久化到 SQLite 文件
```

**让 Agent 参与 RCA 的正确方式**：

```
不好的提问：
"帮我修播放进度不保存的 Bug"

好的提问（提供 RCA 上下文）：
"播放进度 POST 接口返回 200，但 GET 接口返回空数组。
 手动查 SQLite 文件数据存在。
 我怀疑是 SQLAlchemy session 的 commit/flush 问题。
 请检查 backend/app/services/watch_record_service.py 中的写入逻辑，
 定位是否存在 session 未正确 commit 的问题。"
```

提供 RCA 上下文后，AI 的定位成功率从"瞎猜"变为"精准"。

## 七、可观测性：让测试失败说清楚

AI 修复 Bug 的质量，80% 取决于你给它的错误信息质量。

**好的错误信息**（AI 能自修复）：
```
FAILED tests/test_watch_records.py::test_save_progress - AssertionError:
assert 404 == 200
 +  where 404 = <Response [404]>.status_code

Response body: {"detail": "Drama not found: id=999"}
Request: POST /api/watch-records {"drama_id": 999, "episode": 1, "position": 120}
```

**差的错误信息**（AI 只能猜）：
```
Error: Something went wrong
```

**提升测试可观测性的模式**：

```python
# 失败时打印完整响应，不只是状态码
def assert_success(response, expected_status=200):
    assert response.status_code == expected_status, (
        f"Expected {expected_status}, got {response.status_code}\n"
        f"Body: {response.json()}\n"
        f"URL: {response.url}"
    )
```

## 八、测试与 SDD 的关系

测试不是独立存在的，而是 SDD 闭环的组成部分：

```
SPEC.md (AC 定义)
    ↓
代码实现
    ↓
spec-validate（AC 覆盖检查 + 补测试）
    ↓
pytest / Espresso / Cypress（执行验证）
    ↓
CR 前确认：所有已通过的测试仍然绿色
    ↓
重构后重跑测试（行为不变 = 测试不挂）
```

**核心原则**：重构后测试不应该变。如果重构后必须大量修改测试，说明测试绑定了实现而不是行为——这是测试设计的问题，不是重构的问题。
