# AI 原生研发范式：重构产品、设计、开发和测试

AI 工具已经普及，但提效结果参差不齐——根本原因不在模型，在于研发流程中的产物和协作方式并不是为 Agent 设计的。本次分享围绕"AI 原生"这条主线，从需求、设计、开发到测试，逐环节探讨如何把现有工作流改造成 Agent 可直接消费的结构化资产，并结合案例介绍结构化需求、可执行 Spec、设计系统、SDD 工具和工程知识体系的实践，最终建立让 Harness 持续进化的工程基础。

---

## 从 AI 辅助到 AI 原生：围绕 Agent 重新设计研发要素

- 工具用上了，但提效结果参差不齐——提效天花板不是模型，是工程环境
- AI 辅助 vs AI 原生
- 现有工作流及产物并不是为 Agent 设计的，改进的原则和方向
- 工程师的主战场：项目空间（Harness）——代码结构、文档、规则、工具、经验

## 把需求文档升级为结构化的唯一事实来源

- 现有 PRD 不是为 Agent 设计的
- 参考业界实践的改造方案，一概念一文档、行内约束标记、Git 管理，成为唯一事实来源
- 实施中的现实难点及建议

## UX 原型要建立在可执行的设计系统之上

- 现有 UI/UX 的流程及产物并不是为 Agent 设计的
- 建立可执行设计系统，把颜色、组件、约束编码成代码，前端直接引用，Agent 直接消费
- 设计系统成为开发、Agent、验收的共同消费来源，减少人工翻译和视觉漂移

## 用 Spec 给 Agent 明确的任务边界

- Spec 五段式格式与 AC 质量标准
- AC 是三方合同：开发自检 / Agent 自检 / 自动化测试共用同一份
- Spec 的下游应用：开发执行、测试验收、变更追踪

## 用定制 SDD 和工程知识体系让 Agent 应对复杂系统开发

- 关键工程知识分在代码库之外的复杂系统面临的挑战
- 定制 SDD ，为项目注入领域知识和执行步骤约束
- 建立工程知识体系，将项目知识显式化、可路由

## Spec 驱动 + Agent 执行的测试体系

- AC 先行的 Spec 驱动测试：未覆盖 AC 自动补测试、再次验证（自愈循环）
- Agent 探索性验收测试
- 可观测性 + 可测试性是发挥 Agent 最大作用的前提

## 建立 Harness 进化飞轮

- 建立和维护 Harness 项目空间
- 干预即改进机会：每次纠正后问一句"需要编码进 Harness 哪一层"
- 工程师监督下的自动化演进路径
