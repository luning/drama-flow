# 讲师手册 - 第四部分：底层改造 —— 构建“Agent 友好型”软件系统

## 课程目标
探讨如何通过架构调整、文档结构化和流程规范，将现有的软件系统改造成 Agent 能够精准识别、高效协作的“数字基座”。

---

## 4.1 架构层：模块化与边界清晰化

### **要点 1：利用 DDD 划分限界上下文**
- **核心结论**：Agent 处理的任务规模应保持在模型推理能力的舒适区。
- **讲解内容**：
    - 过于庞杂的单体应用是 Agent 的噩梦。通过 DDD（领域驱动设计）划分微服务或明确的限界上下文，可以有效压缩 Agent 需要考虑的上下文空间。
- **举例细节**：
    - **逻辑演示**：将一个巨大的 `UserService` 拆分为 `ProfileService`、`AuthService` 和 `NotificationService`，当 Agent 处理“修改头像”任务时，其关注点仅局限在 `ProfileService`。

### **要点 2：接口契约标准化（OpenAPI / Protobuf）**
- **核心结论**：强类型协议比弱类型描述更能防止 Agent 产生通讯幻觉。
- **讲解内容**：
    - 强制使用 OpenAPI 或 Protobuf 描述所有内部和外部接口。
    - 给模型提供清晰的 Schema 描述，可以大幅提升 API 调用代码生成的成功率。
- **举例细节**：
    - **对比实验**：提供一段模糊的 API 文档（“传一个 id 给用户中心”） vs. 提供一份标准 OpenAPI JSON（明确 id 为 UUID 格式，包含 404 错误响应示例）。

## 4.2 文档层：多层次上下文描述机制（Standardized MD）

### **要点 1：系统级与模块级 MD**
- **核心结论**：Readme 驱动开发，将知识从工程师脑中同步到 Agent 磁盘。
- **讲解内容**：
    - **系统级 MD**：定义顶层架构、核心技术栈选型理由（Decision Log）。
    - **模块级 MD**：每个子目录必须包含 `README.md`，明确职责、依赖和关键逻辑流。
- **举例细节**：
    - **文档模板**：展示一个标准的模块级 README，包含：`Purpose` (定位), `Interfaces` (接口), `Dependencies` (依赖关系), `Constraints` (特殊约束)。

### **要点 2：代码级辅助与类型提示**
- **核心结论**：类型定义（Type Hints）是给 Agent 最直接的“强力暗示”。
- **讲解内容**：
    - 在 TS 中使用 `interface`，在 Python 中使用 `Pydantic` 或 `Type Hints`。
    - 详尽的 JSDoc/Docstrings，特别是在解释“为什么”而不是“是什么”。
- **举例细节**：
    - **代码片段**：展示一段没有类型的 Python 代码 vs. 加上详细 Type Hints 和 Docstrings 的代码，展示 Agent 对前者的迷茫与对后者的精准。

## 4.3 流程层：Architecture as Code

### **要点 1：用系统约束替代人工审查**
- **核心结论**：将架构规则编写为 Lint 规则或 CI 校验，由机器代替人进行监控。
- **讲解内容**：
    - 架构规则例如：模块 A 不得直接调用模块 C 的私有方法。
    - 使用工具（如 `ArchUnit`）在 CI 环节自动拦截不符合架构设计的 PR。
- **举例细节**：
    - **演示建议**：演示一个 Lint 报错如何引导 Agent 自主修正其生成的代码结构。

### **要点 2：自动化任务定位机制**
- **核心结论**：Agent 应具备在大型代码库中快速定位关联模块的能力。
- **讲解内容**：
    - 基于模块描述和代码索引建立检索系统。
    - 当任务到来时，先由定位 Agent 识别受影响的文件集。
- **举例细节**：
    - **实战流程**：任务“修改结算页折扣逻辑” -> 定位 Agent 查询索引 -> 锁定 `checkout/` 目录和 `discount-calculator.js` 文件。

### **要点 3：知识沉淀闭环（ADR）**
- **核心结论**：结构化的架构决策记录（ADR）是 Agent 进行长远演进的“营养来源”。
- **讲解内容**：
    - 将架构选型、弃用的方案和踩过的坑记录在 ADR 中。
    - 训练或微调 Agent 时，这些 ADR 是极佳的语料。
- **举例细节**：
    - **演示建议**：展示 Agent 在重构代码时，通过阅读 ADR 自动规避了 3 年前团队已经尝试并证伪的技术方案。

## 4.4 经验层：复杂任务的“知识注入”与提炼

### **要点 1：任务执行经验的显性化**
- **核心结论**：从 Git History 与 PR 记录中提炼出“实现模式（Patterns）”，变“推理”为“查表”。
- **讲解内容**：
    - 讲解如何使用 LLM 对历史提交记录进行聚类分析，识别出特定任务（如：增加一个新的 API 路由）通常涉及的文件变更集合。
    - 将零散的代码改动提炼为结构化的“任务笔记（Execution Notes）”。
- **举例细节**：
    - **演示建议**：展示一个名为 `NEW_API_ROUTE.md` 的经验文件，里面记录了必须修改的路由配置文件、权限中间件注入点以及日志打点位置。

### **要点 2：通过“注入经验”降低推理负担**
- **核心结论**：在高复杂度、长链路场景下，利用经验注入对抗 Agent 的“逻辑崩溃”与“幻觉”。
- **讲解内容**：
    - 讨论 Agent 在处理超过 10 个文件关联的任务时，为何容易顾此失彼。
    - “经验注入”本质上是提供了搜索空间的修剪（Pruning），让 Agent 直接跳过探索阶段，进入验证与执行阶段。
- **举例细节**：
    - **对比场景**：任务“重构全局状态管理”。如果不提供经验，Agent 可能尝试一次性修改所有组件导致崩溃；如果注入经验“采用分步替换策略，先替换根组件”，成功率将大幅提升。

### **要点 3：经验的分层管理与分级共享**
- **核心结论**：构建从“通用框架”到“项目特定”再到“个人风格”的多级经验库。
- **讲解内容**：
    - 讨论如何建立一个类似 `.gemini/experience/` 的目录，用于存放这些 Markdown 格式的经验。
    - 建立“动态提取”机制：当检测到任务关键词时，自动关联相关的经验文件。
- **举例细节**：
    - **分级架构**：
        - `Level 1 (Team)`：团队公认的代码风格与避坑指南。
        - `Level 2 (Project)`：特定老项目的业务逻辑陷阱。
        - `Level 3 (Individual)`：个人常用的代码片段与 IDE 习惯。

## 4.5 约束层：开发习惯与步骤的 SDD 固化

### **要点 1：SOP 即规格（Steps as Constraints）**
- **核心结论**：将团队的 SOP（标准作业程序）编写为 SDD 模版，强行规范 Agent 的行为轨迹。
- **讲解内容**：
    - 强调“过程正义”：代码写得对不够，过程必须符合规范。
    - 在 SDD 中硬编码 `Mandatory Steps`（如：先运行测试，失败则禁止提交）。
- **举例细节**：
    - **代码片段**：展示如何在 SDD 中通过 `## Implementation Protocol` 强制要求 Agent 每修改一个函数必须输出一行思考日志。

### **要点 2：定制化 SDD 的安装步骤与实现约束**
- **核心结论**：针对团队或个人偏好，设计差异化的“安装步骤（Installation Steps）”与“实现约束”。
- **讲解内容**：
    - 如何在 SDD 中描述“环境准备”：例如，要求 Agent 必须先启动一个 Docker 沙箱，或者先扫描本地 API 文档。
    - 实现约束：例如，“禁止使用外部库，仅限项目内置依赖”。
- **举例细节**：
    - **案例**：为一个注重性能的团队设计 SDD，约束其在生成循环逻辑时必须优先考虑 O(n) 的复杂度。

### **要点 3：高成功率 SDD 模板设计的案例分享**
- **核心结论**：分享一个经过实战检验、具备“自愈逻辑”的万能 SDD 模板。
- **讲解内容**：
    - 拆解一个高质量 SDD 的核心板块：Context -> Requirements -> Success Criteria -> Failure Recovery (自愈路径)。
    - 如何让 SDD 具备“自省”能力：在步骤末尾要求 Agent 检查自己的产出是否违反了约束。
- **举例细节**：
    - **实战演示**：演示一个带有 `Self-Correction` 环节的 SDD，当 Agent 忘记添加错误处理时，它如何根据 SDD 的约束自动识别并修正。
