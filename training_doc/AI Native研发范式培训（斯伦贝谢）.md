# AI-Native 研发范式：从认知重构到全周期 Harness 工程深入实践

## 内容简介

随着推理与 Agent 能力的爆发，软件研发正从"AI 辅助编码"向"Agent 驱动研发"跨越。然而多数团队面临同一困境：已经在用 AI，但提效始终有限 —— 需求越复杂 Agent 越容易跑偏、生成速度快但质量越来越难控制、个人产出翻倍但组织交付指标几乎没动。

本课程采用**三天制结构**：**第一天面向管理者**，建立 AI Native 认知，梳理 AI 在各研发环节的典型应用，结合行业实践与 ROI 数据，探讨角色、组织与效能度量的变化；**第二、三天面向各类工程师**，围绕 **Harness Engineering（驾驭工程）** 这条主线，覆盖从需求到上线的完整软件生命周期实践——从可执行 Spec、设计系统、项目空间，到质量闭环与多 Agent 并发编排。

## 目标学员

**第一天（管理者专场）**
1. **研发管理者与技术负责人**：理解 AI Native 转型方向，制定组织与效能度量策略
2. **产品负责人**：理解 AI 对研发全流程的重塑，调整协作方式与产出物

**第二、三天（工程师专场）**
1. **核心开发与架构师**：从手动编码转向 Harness 编排，设计 Agent 可高效理解的模块化系统
2. **研发效能负责人**：将 AI 深度注入全研发流程，构建团队级 AI 工作流
3. **产品负责人与设计师**：编写高质量可执行 Spec，以可执行设计系统驱动 Agent 精准交付
4. **测试与质量专家**：构建 AI 驱动的测试闭环与自动化验收

## 课程收益

1. **Harness 认知**：理解范式演进与行业实践规律，掌握 AI 在各研发环节的应用深度与 ROI 判断框架
2. **规格驱动**：用可执行 Spec 与结构化需求资产告别多轮打地鼠，深入掌握自定义 SDD 的设计与构建方法
3. **项目空间建设**：将设计系统、架构规范、开发经验结构化为 Agent 可精准消费的"项目大脑"，配合 Skills & MCP 沉淀可复用工具资产
4. **质量与进化闭环**：构建行为级测试、探索性验收与 AI 诊断流水线；建立"干预即信号"的 Harness 持续进化习惯
5. **Agent 规模化**：打通从 Subagent 到多 Agent 并发的断点，亲手跑通 1 人驱动 N Agent

## 授课方式

讲师讲授 + 现场演示 + 沙箱练习 + 主题研讨

### 第一天：AI Native 转型认知（面向管理者）

---

#### 第一部分：认知革新 — AI Native 的本质与 Harness Engineering（约 2h）

> **目标**：建立 AI Native 思维模型，理解 Harness Engineering 的概念与行业实践，明确"工程师能控制什么"。

**1.1 AI Native（AI 原生）的本质**

- 云原生类比：Agent 带来生产力跃升后，围绕它重新设计研发架构
- AI Powered（人伺候 1 个 Agent）vs AI Native（1 人驱动 N 个 Agent 并发）的差距
- 影响 Agent 应用深度的三方面能力：模型内核、Harness 项目空间、项目架构

**1.2 Harness Engineering — 概念与核心机制**

- 三层范式演进：Prompt 工程（怎么问）→ Context 工程（给模型看什么）→ Harness 工程（模型在什么机制里干活）
- Harness 六大核心模块：上下文管理、工具编排、验证机制、状态管理、可观测性、人类接管
- Harness 项目空间详解与演示
- 工程师角色重塑：从"实现者"转向"Harness 设计师"

**1.3 [演示] 一个需求的完整旅程**

直观体验—从一份 PRD 到功能实现的过程，Agent 在各环节如何工作，包括规格化、设计系统、开发/CR/测试等。

---

#### 第二部分：在研发各环节提升生产力 —— 典型应用、行业案例与分析框架（约 2h）

> **目标**：看清 AI 在各研发环节能替代哪些工作、做多深，以及什么投入能提高天花板。

**2.1 决定 Agent 应用深度的分析框架**

- **认知任务及其颗粒度**：模块级最成熟，系统级居中，跨系统级因隐性知识受限
- **Harness 依赖及其 ROI**：覆盖范围广、频率高的优先投入，不同建设项回报差异悬殊

**2.2 需求环节**

- **典型应用**：需求分析（识别歧义与缺口）、从文档到可执行 Spec 的结构化转换、一致性检查
- **关键 Harness**：需求代码化（PRD → 机器可消费格式），ROI 极高，是开发/测试/设计的上游输入
- 行业实践：GitHub 提出"规格即 Agent 编程接口"；国内头部互联网企业已有需求文档到代码的端到端 Agent 实践

**2.3 UI 设计环节**

- **典型应用**：Skill/脚本驱动设计规范合规检查、AI 辅助原型生成、批量生成符合 Design System 的 UI 草稿
- **关键 Harness**：Design System（Token + 组件规范 + 约束规则），ROI 高，同时约束开发阶段 UI 代码生成
- 设计工具厂商已明确将设计系统定位为"给 AI 的指令"而非"给开发者的文档"

**2.4 架构环节**

- **典型应用**：AI 辅助 ADR 编写（整理权衡点与决策依据）、脚本/CI 驱动架构违规检测
- **关键 Harness**：Architecture as Code（import-linter/ArchUnit + 约束文档）。ROI 中等；新架构合理性判断是当前天花板

**2.5 开发环节**

- **典型应用**：Agent 驱动功能实现（模块级已高度自主）、Skill 辅助代码审查、重构 Skill、各种 SDD 工具
- **关键 Harness**：Spec 质量 + 项目空间完整度 + 可测试性。ROI 极高，是 AI 应用深度最大的环节
- 行业数据：国内头部团队 AI 代码生成率 30%–50%，人均产出显著提升；GitClear 反面数据：代码克隆上升、重构占比下降，高接受率叠加低审查率加速积累技术债

**2.6 测试环节**

- **典型应用**：自动化脚本/CI 驱动回归测试、Skill 驱动测试用例生成、Agent 驱动探索性验收测试
- **关键 Harness**：可测试性工程（行为级测试架构、测试数据管理）+ 导航经验沉淀。ROI 高，同时支撑开发阶段
- 行业数据：智能测试选择执行时间缩减约一半；国内头部团队测试用例生成率、AI CR 参与度均大幅提升

**2.7 运维环节**

- **典型应用**：Skill 辅助日志分析（预处理 → 因果推理 → 根因排序）、多 Agent 并行取证
- **关键 Harness**：可观测性工程（结构化日志 + 调用链 trace + 故障模式库），ROI 高；隐性知识是当前天花板
- AIOps 已进入主流会议专项讨论，国内大厂在日志分析、故障诊断、成本优化等方向均有落地实践

**2.8 环节间的 Harness 依赖**

某些 Harness 建设产出本身就是其他阶段的输入，优先投入覆盖范围广的：

- **需求代码化**：开发、测试、UI 设计的上游输入
- **Design System**：开发阶段 UI 代码生成的约束基础
- **Architecture as Code**：开发阶段的架构约束层
- **可测试性工程**：开发、重构、测试三个环节的共同基础
- **可观测性工程**：运维、测试反馈闭环的共同基础

#### 第三部分：生产力跃升后的组织进化 —— 角色、协作、度量与行业案例（约 1.5h）

> **目标**：理解生产力跃升带来的深层矛盾，从角色、协作、组织形态、效能度量四个维度看变革方向，结合国内外企业案例理解转型路径与常见陷阱。

**3.1 生产力悖论**

- DORA 2025：个人产出翻倍，组织交付指标几乎没动——瓶颈从"写代码"转移到"审代码"与决策链条
- 核心结论：个人技巧必须沉淀为团队 Harness，才能转化为组织产能；提效必须带动协作重构

**3.2 各角色价值重心迁移**

- 转型结构：保留领域判断力、新学 Spec/Harness/度量、放下重复执行
- **PM** → 规格架构；**设计师** → 体验判断 + 设计系统；**开发** → Harness 设计师；**测试** → 意图守护者；**运维** → 可观测性设计者
- 角色融合：知识壁垒削薄后职能边界软化，全栈化靠 Harness 拉平门槛
- 新角色涌现：规格架构师、Harness 平台工程师、AI 质量工程师
- 行业案例：执行层与判断层的边界——某知名互联网金融企业的教训与修正

**3.3 协作与组织形态**

- 协作重构：串行交接 → Spec 驱动并行；HITL 检查点取代交接会议；协作产物转向 Spec/设计系统/ADR
- 组织形态：职能部门 → 双层模型（产品特性团队 + 平台 CoE）；人机配比成为组织设计参数
- 行业案例：Microsoft 协作单元重组；Duolingo AI-first 制度性重组；Moderna 人类员工与 AI Agent 统一编制规划
- 落地难点：AI 是放大器——工程成熟者获益，基础薄弱者放大技术债；隐性知识显式化是最难突破的天花板

**3.4 AI Native 效能度量**

- 度量核心：从"人完成了多少"到 **HAF**；警惕 Goodhart 定律——"AI 生成占比"当 KPI 驱动行为而非结果
- 五层指标：**AI 采纳程度** → **Agent 生产力** → **Harness 成熟度** → **工程质量** → **交付效率**
- 三个先行指标：人均管理 Agent 数、平均交付时间、线上缺陷率
- 落地原则：度量用于改进 Harness 而非考核个人；采纳与质量层联动，防止"快而烂"

### 第二天：AI Native 研发基础（面向工程师）

#### 第四部分：规格工程 — 给 Agent 精确的任务边界和流程约束（约 2h）

> **目标**：掌握可执行 Spec 编写方法，理解 SDD 工具生态，深入掌握自定义 SDD 的设计与构建，从"描述需求"升级到"定义流程"。

**4.1 可执行 Spec — 格式、AC 质量与失败模式**

- 五段式：领域名词 → 前置条件 → 主流程 → 异常处理 → 验收标准（AC）
- 三方消费：开发者自检、AI Agent 自检、自动化测试生成
- AC 质量标准：可验证、无歧义、无实现细节
- 失败模式：Agent 填充错误实现；约束在新 Session 中遗失；多 Agent 出现分歧
- [练习] 模糊 PRD → 可执行 Spec 全过程

**4.2 SDD 工具生态 — 原理与选型**

- Prompt SDD 最小约束：接受任务前读 AC → 完成后逐条自检 → 变更时标注
- Prompt SDD 的规模瓶颈：约束易遗漏、AC 无法自动验证、变更无结构化追溯
- SDD 基本循环：讨论 → 规划 → 执行 → 验证 → 归档
- 工具原理及选型：GSD、OpenSpec 等工具的设计原理与适用场景对比

**4.3 自定义 SDD — 定制你自己的 Agent 编排**

- SDD 本质是流程状态机：阶段定义 → 工件 Schema → 关卡条件 → 上下文加载策略
- 四要素设计：上下文加载策略、任务拆解规则、验证关卡、归档与变更追溯
- [演示] 从零构建最小可用 SDD：PLAN.md 模板 + /execute 命令 + subagent verify
- [练习] 为案例项目定制最小 SDD 流水线，跑通一个小需求

#### 第五部分：需求代码化 — 从增量 PRD 到唯一事实来源（约 1h）

> **目标**：掌握将散文 PRD 改造为 Agent 可直接消费的结构化资产：每个业务概念一份常青文档，唯一事实来源，Git 管理历史。

**5.1 核心问题：Agent 为什么读不懂 PRD**

- 增量文档：功能全貌散落在多份版本文件，Agent 无法主动追溯拼出当前状态
- 边界模糊：同一句自然语言让 Agent 实现三次，得到三种不同错误文案
- AC 不可执行：散文验收标准无法被 Agent 自检或测试工具直接提取

**5.2 改造方案（参考 OKF）**

- [演示] 散文 PRD vs 结构化需求，展示 Agent 消费差异
- 一概念一文档：每个功能一份常青文档，迭代时更新而非叠加版本文件
- YAML 文件头：声明 ID、状态（approved / deprecated）、关联 Spec
- 正文结构化：业务流程 + 异常处理表格 + AC 块
- 行内约束标记：`[MUST]` / `[MUST NOT]` / `[SHOULD]` / `[CONSTRAINT:类型]`
- Git 管理历史：变更有 diff、有 log，正文不维护"修改记录"

**5.3 实施建议**

- PM 友好：Agent 辅助维护（PM 描述 → Agent 更新 → PM 确认），可反向生成散文 PRD 供汇报
- 存量处理：新旧双轨，触碰则改，从核心链路开始
- 分级落地：最小（AC 块）→ 中等（+YAML+异常表）→ 完整（常青文档+Git+Agent 维护）

---

#### 第六部分：可执行设计系统 — 设计一处定义，人机共同执行（约 1h）

> **目标**：理解可执行设计系统，建立"代码即设计源"的工作流，将工程师的翻译工作降至最低。

**6.1 可执行设计系统的结构**

- 原型及设计系统演进：文档时代 → Figma时代 → 可执行设计系统时代
- AI 越能生成，设计约束越重要 —— 否则风格漂移、组件重复、UX 崩坏
- 设计系统五层结构：业务约束 → Design Token → 组件 Runtime → AI Generation Rules → Figma 协作层
- 原型生产方式：从 Figma 出发，从自然语言出发，从 Screen Spec 出发

**6.2 在设计系统约束下生成 UI**

- AI 读取设计系统文件后生成新页面，验证是否自动遵守 Token/组件/约束
- Prototype Skill 封装：将设计系统注入流程固化为 Skill
- [演示] 设计系统约束下的页面生成与约束验证

**6.3 三层视觉验收**

- 第一层（自动）：Skill 扫描 hardcoded 值 + ESLint/CI 拦截
- 第二层（工具辅助）：截图对比 + 像素级检查
- 第三层（人工）：视觉节奏、信息层级、交互情绪

---

#### 第七部分：项目空间建设 — 让代码库成为 Agent 的操作系统（约 1h）

> **目标**：掌握 Harness 项目空间的四层架构，将项目改造成 Agent 可精准识别的数字基座。

**7.1 四层架构与即时可用的建设方法**

- 典型项目的完整 Harness 项目空间展示
- 文档层：全局行为规则及索引 + 模块 README
- 经验层（遇到问题后引入）：从历史提炼任务级变更模式
- 约束层：import-linter / ArchUnit + pre-commit hooks 自动拦截架构违规；Hooks / Plugin 事件自动验证
- 执行层：Skills + MCP + 自动化脚本

**7.2 Harness 团队治理**

- Git 管理边界：哪些纳入版本控制哪些不纳入
- 经验文件质量管控：防止"越来越长、Agent 开始忽略"的退化模式
- CODEOWNERS 设置：Harness 文件有指定审阅者，防止质量腐化，Harness 的补丁思维

**7.3 [练习] 为示例项目构建文档、经验及约束层**

- 为一个模块编写符合四段模板的 README.md，判断必要性
- 补充一条 Architecture as Code 约束，验证 CI 能拦截违规代码
- 从 Git History 提炼一条有价值的经验，判断必要性

---

#### 第八部分：工具系统 — 为 Agent 构建可控工具链（约 1h）

> **目标**：掌握 Skills 与 MCP 的设计方法论，理解两者分工与组合，为组织沉淀可复用 AI 工具资产。

**8.1 创建第一个 Skill**

- Skill 的结构与设计原则
- 固定逻辑剥离：脚本承担确定性操作，Skill 只负责调用与结果解读
- 从日常重复操作出发，识别 Skill 化候选动作
- [演示] rebuild-deploy Skill 的完整创建过程

**8.2 MCP 工程设计**

- MCP 结构与设计原则
- 利用 MCP 接入外部服务
- [演示] 在示例项目中创建一个只读的 MCP Tool

**8.3 企业级工具体系**

- Skills vs MCP 选型框架
- 三层分级：个人级 → 项目级 → 企业级
- MCP 安全运营：只读账号 + IP 白名单 + 审计日志 + 敏感字段脱敏

### 第三天：质量闭环、规模化与工程心法（面向工程师）

---

#### 第九部分：测试与反馈体系 — 以 Agent 为中心的质量闭环（约 1h）

> **目标**：建立 AI 时代的行为验证闭环，防止"10 倍代码速度 = 10 倍技术债"。

**9.1 Spec-TDD - 以 AC 为起点的开发循环**

- [练习] 创建 spec-validate Skill：从 Spec 提取 AC → 对比测试覆盖 → 输出覆盖矩阵
- [演示] 核心流程：AC 写入 Spec → 行为级测试 → 实现 → spec-validate 确认覆盖 → 自愈
- AC 质量 = 测试质量 = 代码验收质量，AC 最终确认必须由人完成（HITL）

**9.2 Agent 驱动的探索性验收**

- 架构及框架：Agent CLI → ADB/UI Automator → 设备（无 Android 环境的学员使用 Web 版页面 + 浏览器自动化完成同等练习）
- Mission 文件直接对应 Spec AC；screen_knowledge/ 跨会话经验库避免重复踩坑
- [演示] 执行循环：案例应用的完整验收流程

**9.3 以 Agent 为中心的反馈体系**

- 让 Agent 能自己读懂结果（避免人肉搬运）：结构化日志（可观测性）+ 稳定自动化（可测试性）
- 让 Harness 从 Agent 行为中学习：失败模式 → Harness 迭代，而非靠感觉调

#### 第十部分：日志分析与缺陷定位 — 诊断 Agent 实战（约 1h）

> **目标**：建立"先结构化、再推理"的 AI 日志分析流水线，设计缺陷定位诊断 Skill，把定位经验沉淀为团队故障模式库。

**10.1 "先结构化、再推理"流水线**

- 日志源往往分散（应用日志、错误历史、调用链 trace），根因跨源关联，直接投喂原始日志超出上下文
- 预处理（脚本完成）：异常窗口截取（故障时刻 ±N 分钟）→ 事件抽取去重；模型只在压缩后事件序列上推理

**10.2 缺陷定位诊断 Skill 设计**

- 知识层注入：架构概述 + 日志格式说明；假设必须引用日志行号/时间戳，无直接证据标 [推测]
- **单 Agent**：`/diagnose` 输出：现象 → 直接原因 → 根因假设（按概率排序）→ 验证手段
- **多 Agent**（复杂故障）：Orchestrator 生成假设 → 并行 InvestigatorAgent 各自取证 → SynthesisAgent 跨层关联输出根因排序

**10.3 故障模式库**

- 定位后把"现象-证据-根因"三元组回填 experience/ 层，下次诊断自动 few-shot 注入

**10.4 [练习]**

- 基于模拟日志跑单 Agent 全流程：窗口截取 → 事件抽取 → 因果推理 → 假设验证

#### 第十一部分：工程师不可让渡的能力 — 设计力与代码审美非常重要（约 0.5h）

> **目标**：打破"AI 会写代码，工程师只需审批"的误区——AI 提速的是实现，加速暴露的是设计缺陷；代码品质守护、架构判断、职业心法，是工程师在 AI 时代的核心竞争力。

**11.1 AI 代码高频错误模式 + CR 策略**

- 五类高频错误：重复逻辑、状态泄漏、命名混乱、架构违规、冗余注释
- [练习] cr-refactor Skill：扫描 diff → 按五类错误输出优先级清单
- 重构铁律：不改功能只改结构；先计划再执行；每步运行 spec-validate，失败回滚
- 决策框架：逻辑正确但结构混乱 → 重构；逻辑本身有缺陷 → 重写

**11.2 AI 时代工程师心法**

- 架构不外包：约束、权衡、边界由人决定，实现交给 Agent
- 约束必须显式：CLAUDE.md / AGENTS.md + Spec 一次写入永久生效，不让 AI 猜
- 干预是信号：每次纠正后问一句"这需要编码进 Harness 吗"
- 小步拆解：任务越大，本质是约束越缺失
- Git 是后悔药：大改前 commit，改完逐文件 diff，走偏立即回滚
- 必须看代码：AI 加速生成也加速技术债，每迭代一次 CR + 重构
- 管理上下文窗口：主动 compact、何时开新 Session、何时 fork、合理使用子代理
- 提升系统可观测性：结构化日志让 Agent 能自主定位问题，比每次手动整理日志更有杠杆
- 分清任务类型：目标明确可验证 → 放心给 AI；涉及权衡无唯一解 → 人来决策
- 保持 HITL：AC 确认、安全逻辑、数据模型重大变更、架构决策、合并前审阅——人工最终裁决

#### 第十二部分：刻意进化 — 让 Harness 越来越强（约 1h）

> **目标**：建立"干预是信号、纠正即 Harness 改进"的工程习惯，通过 Agentic Harness Engineering 让系统自主进化。

**12.1 两种工程师的分野**

- 路径 A：Agent 犯错 → 纠正 → 继续 → 等下一个模型。每月重复同样纠正
- 路径 B：Agent 犯错 → 纠正 → "这次教训，需要编码进 Harness 哪一层？"
- 核心认知：模型自然进步，Harness 不会——只在工程师主动决定时才进化

**12.2 三类进化场景（问题现象 → Harness 层级）**

- 操作安全：每次询问权限 → 权限配置；不询问删文件 → 安全规则；多 Agent 改同一文件 → Worktree 隔离
- 任务边界：直接写代码没澄清 → CLAUDE.md 任务启动规则；宣布完成但没验证 → DoD；长会话性能下降 → 上下文重置时机
- 经验沉淀：选了已排除的方案 → ADR；口头纠正下次又犯 → 写入永久规则；规则文件过长被忽略 → 封装为 Skill

**12.3 Agentic Harness Engineering**

- 规模瓶颈：模型和 Agent 持续迭代，手工优化跟不上——自动化是唯一出路
- 数据基础：本地 Session 记录是起点，从中提取高频失败模式
- [演示] 失败轨迹 → 分层映射 → 自动生成规则 → 验证改进效果

**12.4 飞轮与突围路径**

- 飞轮：干预 → Harness 改进 → 任务颗粒度增长 → 干预减少 → 更多 Agent
- 刻意修剪：定期清理过时规则，避免 Harness 腐化成负担
- 突围路径（范围 × 难度）：小范围简单 → 立即可做；小范围复杂 → 团队级 Spec；大范围简单 → 先单系统再跨系统；大范围复杂 → 隐性知识，长期目标
- [练习] 分析案例项目 Harness 的可优化内容

#### 第十三部分：多 Agent 规模化 — 从单兵作战到 Agent 团队（约 1.5h）

> **目标**：掌握多智能体角色分工与并发编排，跑通"1 人 ↔ N 角色化 Agent"的吞吐量跃迁。

**13.1 Subagent vs Multi-Agent**

- Subagent：同会话内调度，并行度受限；适合独立子查询
- Multi-Agent：独立进程，无共享内存——靠外部制品（FD 文件、Git、任务单）+ 显式合同协作
- 跑不起来的根因：缺的不是工具，是跨 Agent 的协作合同与状态载体

**13.2 角色模型、编排模式与工具**

- 五角色链：PM → Planner → Worker → Reviewer → QA；合同载体：Spec、任务单、CR 报告
- 三种编排：扇出-扇入（无依赖并行）、流水线（阶段串行）、竞合（多解择优）；HITL 在各模式关键节点介入
- 四件套：Tmux（终端隔离）+ Git Worktree（目录隔离）+ FD 文件（共享状态）+ 斜杠命令（生命周期卡口）
- 进阶：`claude -p` / `opencode run` 脚本化编排
- [演示] 用四件套实现 1 人驱动多 Agent 并行开发

**13.3 规模化节奏与挑战**

- 递进：单 Agent → 2 串行 → 3-4 扇出 → 8 全矩阵
- [练习] ① 2 Agent + 1 FD 跑通传递协议；② Worktree 隔离下 3 Agent 扇出；③ 设计团队 Agent 拓扑
- 上限：1–4 并发为高效区，8 为极限；模型分层：Worker 低成本、Planner/Reviewer 高能力
- 常见挑战：Token 放大（分层）、信息衰减（结构化传递）、文件冲突（Worktree 隔离）

#### 第十四部分：Harness 工程诊断 — 识别症状、定位病因、选对层级修复（约 0.5h）

> **目标**：建立 Harness 问题诊断的系统性视角——区分"Agent 出了问题"与"Harness 配置长了蛀虫"，掌握修复层级决策树，让 Harness 持续健康而不是持续膨胀。

**14.1 高频失效模式**

- 遗留无测试，Agent 盲改：黄金大师模式打快照 + 两帽子原则（重构与开发严格分阶段）
- 跨端崩溃 / 数据污染：全栈遥测注入 + MCP 层强制 BEGIN/ROLLBACK
- 工具幻觉（Skills >50）：按目录动态注册，Pydantic 严格参数约束
- Agent 删关键旧代码：删前强制 `git blame` + CONSTRAINTS.md 圣牛清单
- 重构范围失控：PEV 循环（Plan 审批范围 → Execute 受限 → Verify）
- 多步骤成功率崩塌：错误乘法效应 → 关键步骤间插验证门禁 + 早停熔断
- 长会话规则逐渐失效：注意力衰减 → 核心约束紧贴最新输入 + 每 N 轮重注入
- [演示] 用 PEV 循环管控一次 AI 过度重构

**14.2 Harness Bad Smell**

定期扫描以下蛀虫：过时假设、重叠规则、防御性膨胀、硬编码工作流、万能 Prompt 补丁、经验噪音、推理替代脚本

**14.3 维护铁律**

- 只保留 A 类：设计约束 / ADR 不可替代；复述代码信息的 B 类随模型进化持续清退
- 实验驱动：每次只加一条规则，单独验证，无效回滚；换模型版本跑裸奔基线再决定去留
- 修复选对层级：Tool 实现 → Middleware → Skill → Tool Description → System Prompt
