# 全栈认知基础：vibe coding 时代的全栈基础课

## 内容简介

AI 编码工具已大幅降低写代码的门槛，但新问题随之而来：Agent 写出了前后端代码、数据库迁移、部署配置 —— 你看得懂吗？你敢上线吗？

本课程为不熟悉全栈技术的工程师设计，**不讲怎么造，教你怎么看懂 Agent 造出来的东西并判断对不对**。围绕 DramaFlow 短剧应用这个真实项目，跟着一个请求走完浏览器 → 前端 → 后端 → 数据库 → 容器部署的全链路，建立全栈全景认知。在此基础上，现场演示用 Agent 追加一个新功能，逐层拆解"diff 怎么看、改得对不对"，最终交付一张 A4 纸审查清单 —— 每次 Agent 交出代码，5 分钟快速判断质量。

## 目标学员

1. **后端工程师**：能写 Java，但不懂前端在干什么、代码怎么部署
2. **前端工程师**：能写页面，但不清楚后端如何处理请求、数据库长什么样
3. **产品经理**：能提需求，但看不懂 Agent 产出的技术方案是否合理
4. **运维 / 测试工程师**：懂部署和测试，但缺乏对全栈代码结构的整体理解

## 课程收益

1. **建立全栈全景认知**：能画出"一个请求走了哪些层、每层干了什么"的地图
2. **读懂 Agent 产出的代码**：看懂前端组件、后端接口、数据库迁移、部署配置各自在说什么
3. **理解各层技术选择**：知道前端框架、后端架构、数据库选型、部署方式的取舍逻辑
4. **掌握增改审查心法**：Agent 改代码后，能在 5 分钟内逐层判断改动是否正确
5. **学会分层定位 bug**：出问题时能快速判断"是哪一层的问题"，再看对应日志
6. **拿到可落地的审查清单**：一张 A4 纸，每次 Agent 交付代码后逐项对照

## 授课方式

讲师讲授 + 现场演示（Agent 实操）+ 案例研讨

## 课前准备

为保证课上能跟随讲师查看案例项目，建议提前准备：

- IDE（VS Code / IntelliJ IDEA）
- Git 客户端

（无需安装项目运行环境，课上以讲解和演示为主）

## 课程大纲

### 第一部分：全栈全景 —— 一次请求的完整旅程（约 45min）

> **目标**：建立全栈地图。不管之前懂多少，走出这一节后，每个人都能说出一次请求流经了哪些层、每层做什么。

**1.1 打开 DramaFlow 项目**

- 项目结构总览：前端（h5/）、后端（backend/）、数据库（SQLite）、部署配置
- 各目录的角色和关系

**1.2 一次"短剧列表加载"请求的全链路追踪**

- 现场用浏览器 DevTools Network 面板抓一次真实请求
- 从头到尾串起来：

```
用户打开 App / H5 页面
  → 浏览器发送 HTTP GET 请求（URL、方法、请求头）
  → 后端路由接收请求（哪个 Controller、哪个方法）
  → Service 层处理业务逻辑（过滤、排序、分页）
  → Repository 层查询数据库（SQL 生成与执行）
  → 数据库返回数据
  → 后端封装为 JSON 响应（状态码、响应体结构）
  → 浏览器接收 JSON
  → 前端组件渲染为 UI
```

- 每个环节只讲**它是什么、为什么放在这里**，不讲具体实现

**1.3 全栈地图输出**

- 讲师在白板上画出层与层之间的数据流向
- 学员形成自己的"全栈地图"笔记，后续每节都在这个地图上展开

### 第二部分：前端视角 —— 浏览器里发生了什么（约 45min）

> **目标**：打开前端代码不再眼晕。看懂组件树、状态管理、API 调用三件事，理解前端技术选型的取舍。

**2.1 打开 h5/ 目录，看一个页面的代码**

- 以 DramaFlow 首页（Home.vue）为例
- 三层结构：`<template>`（画什么）、`<script>`（逻辑）、`<style>`（长相）
- 组件树：页面 → 卡片组件 → 按钮组件，逐层嵌套
- 状态：`ref` / `reactive` 管什么数据、数据变化 UI 自动更新
- API 调用：`fetch('/api/dramas')` 在哪里发起、返回的 JSON 怎么绑定到模板上

**2.2 技术选型与要点**

- 主流框架对比：React vs Vue vs Angular —— 各自的哲学和适用场景
- SPA vs SSR：单页应用怎么做路由（vue-router），服务端渲染解决什么问题
- 状态管理：局部状态（组件内）vs 全局状态（Pinia），什么时候需要提到全局
- 构建工具：Vite 做了什么（打包、热更新、代码分割）

**2.3 从 vibe coding 角度看前端**

- Agent 改了组件代码，你该看什么：
  - props 定义和传参对不对
  - 状态（ref/reactive）有没有声明和正确更新
  - API 地址、方法、参数是否和后端匹配
  - 有没有处理加载中、加载失败、数据为空三种状态
- 看浏览器 Console：前端错误长什么样，和网络错误有什么区别

---

### 第三部分：后端视角 —— 服务端里发生了什么（约 45min）

> **目标**：看懂后端代码的分层结构，理解一个请求在后端走了哪几层、每层做什么。

**3.1 打开 backend/ 目录，跟着请求走**

- 以 DramaFlow 的短剧列表接口为例
- 分层追踪：

```
路由层（Router）  →  /api/dramas 这个 URL 映射到哪个函数
控制器层（Controller） → 接收请求参数，调用 Service，返回响应
服务层（Service）     → 业务逻辑所在：筛选、排序、分页、权限校验
数据访问层（Repository / DAO） → 与数据库交互，执行 SQL
模型层（Entity / Model） → 定义数据长什么样（字段、类型、关系）
```

- 每一层只做自己该做的事：Controller 不写 SQL，Service 不处理 HTTP

**3.2 技术选型与要点**

- 后端框架对比：Spring Boot vs Express vs FastAPI vs Django —— 各自定位
- API 风格：RESTful 约定（URL 用名词、方法决定操作、状态码表达结果）vs GraphQL
- 认证方式：JWT Token 是什么、怎么传递、过期怎么处理
- 错误处理：统一异常处理 vs 每个接口手动 try-catch，500 vs 4xx 的区别
- 日志：结构化日志长什么样，怎么读懂一条请求的完整日志轨迹

**3.3 从 vibe coding 角度看后端**

- Agent 加了一个接口，你该检查什么：
  - URL 和方法（GET/POST/PUT/DELETE）是否符合 REST 约定
  - 入参有没有校验（必填、类型、范围）
  - 返回值结构和已有接口是否一致
  - 异常有没有被 catch 后返回 null（吞掉错误）
  - 有没有跳过 Service 层直接在 Controller 写数据库操作

---

### 第四部分：数据视角 —— 数据如何存储和流动（约 30min）

> **目标**：看懂数据库表结构，理解 ORM 如何把代码和数据库连起来。

**4.1 打开数据库，看表结构**

- DramaFlow 有哪些表：dramas、users、watch_records 等
- 字段类型：INTEGER / VARCHAR / TEXT / DATETIME 各自存什么
- 表关系：一对一（用户 ↔ 用户详情）、一对多（用户 ↔ 观看记录）、多对多（用户 ↔ 收藏短剧）
- 用数据库工具（DBeaver / TablePlus）直观查看表和数据

**4.2 ORM：代码如何操作数据库**

- Object-Relational Mapping：Entity 类 → 数据库表，对象属性 → 表字段
- 增删改查对应的 ORM 写法：`.findAll()` / `.save()` / `.delete()`
- Migration 是什么：数据库的版本管理，每次改表结构都要有迁移脚本（up 创建 / down 回滚）

**4.3 技术选型与要点**

- 关系型 vs NoSQL：什么时候必须用关系型（数据一致性要求高），什么时候可以用 NoSQL（日志、缓存）
- ORM vs 原生 SQL：ORM 提升效率但可能生成低效查询，什么时候需要手写 SQL
- Migration 工具：Flyway / Liquibase 各自的风格

**4.4 从 vibe coding 角度看数据库**

- Agent 改了数据库，你该担心什么：
  - 字段类型是否合理（别拿 VARCHAR 存数值）
  - 有没有设置默认值和非空约束
  - 关联关系（外键）映射对不对
  - 迁移脚本有没有同时写 up 和 down
  - 会不会删表 / 删数据（危险操作）
  - N+1 查询：循环里发 SQL，看起来正常但性能很差

### 第五部分：部署视角 —— 代码如何变成可访问的服务（约 30min）

> **目标**：理解"本地能跑"和"线上能访问"之间的差距，看懂 Docker 和 CI/CD 配置文件在说什么。

**5.1 从本地到线上：中间发生了什么**

- 本地开发：一个命令启动（npm run dev / mvn spring-boot:run）
- 为什么需要容器：环境差异（"我电脑上能跑啊"→ 服务器上各种缺依赖）
- Docker 三步走：写 Dockerfile（定义镜像）→ 构建镜像 → 运行容器
- docker-compose：一键拉起前后端 + 数据库 + 其他服务

**5.2 打开 Dockerfile，逐行解读**

- 以 DramaFlow 的 Dockerfile 为例
- `FROM`：基础镜像，决定了运行环境（JDK 版本、操作系统）
- `COPY` / `ADD`：把代码放进容器
- `RUN`：构建时执行的命令（mvn package / npm build）
- `CMD` / `ENTRYPOINT`：容器启动时执行的命令
- `EXPOSE`：声明容器内部端口
- 环境变量：数据库地址、密钥等不能写死的东西，通过 env 文件 / 容器环境变量注入

**5.3 CI/CD：代码提交到自动部署的流水线**

- CI（持续集成）：每次 push 自动跑测试 → 构建 → 检查
- CD（持续部署）：构建通过后自动部署到测试 / 生产环境
- 看懂 CI 配置文件：GitHub Actions / Jenkins Pipeline 的关键步骤

**5.4 技术选型与要点**

- Docker vs 虚拟机：容器共享系统内核，轻量高效
- docker-compose vs Kubernetes：单机场景 vs 集群场景
- 环境分离：dev / staging / prod 各自独立的配置和数据库

**5.5 从 vibe coding 角度看部署**

- Agent 生成的 Dockerfile，你检查什么：
  - 基础镜像对不对（JDK 版本是否匹配）
  - 端口有没有暴露
  - 环境变量有没有写死（数据库密码 / API key 硬编码）
  - 构建过程是否完整（有没有漏了依赖安装）
- Agent 改了 CI 配置，检查什么：
  - 测试步骤有没有被意外删除
  - 部署目标环境是否正确

### 第六部分：现场演示 —— Agent 追加一个新功能（约 45min）

> **目标**：完整展示一次真实的 vibe coding 循环。从需求描述到 Agent 产出代码，再到逐层审查，最后跑起来验证。

**6.1 需求描述**

- 场景：DramaFlow 当前只有短剧浏览和播放，现在要加一个"搜索短剧"功能
- 用自然语言向 Agent 描述需求 —— 展示什么水平的 prompt 能得到更好的结果

**6.2 Agent 生成前端代码**

- Agent 在 h5/ 目录下改动：新增搜索输入框组件、搜索结果显示逻辑、API 调用
- 讲师逐段讲解 diff：哪些文件被改了、为什么加这些代码
- 对照第二部分的前端审查清单，逐项检查改得对不对

**6.3 Agent 生成后端代码**

- Agent 在 backend/ 目录下改动：新增搜索接口（Controller + Service + Repository）
- 讲师逐段讲解 diff：路由注册、参数接收、模糊查询逻辑、返回格式
- 对照第三部分的后端审查清单，逐项检查

**6.4 Agent 生成数据库迁移（如有）**

- 如果搜索需要索引优化，Agent 可能生成 migration
- 对照第四部分的数据库审查清单，检查迁移是否安全

**6.5 跑起来，发现 bug，指挥 Agent 修复**

- 如果是现场能跑的环境：启动服务，测试搜索功能
- 如果无法现场跑：在代码中找潜在 bug（典型的 Agent 失误），展示如何描述问题让 Agent 修复
- 展示调试决策树的使用

### 第七部分：增改代码的审查心法（约 45min）

> **目标**：本日核心章节。将上午各层的知识点浓缩为可操作的审查动作，Agent 每次交付代码后逐层检查。

**7.1 前端增改审查清单**

Agent 改了前端代码后，依次检查：

| 检查项 | 怎么看 | 高频错误 |
|--------|--------|----------|
| 路由注册 | 新页面有没有在 router 中注册路径 | 写组件忘了配路由，页面 404 |
| 组件嵌套 | 新组件是否放在了正确的父组件里 | 平级写成嵌套，布局错乱 |
| API 调用 | URL、方法、参数是否和后端接口一致 | 路径拼错、POST 写成 GET |
| 状态声明 | `ref` / `reactive` 是否声明且类型正确 | 没声明直接用，数据不更新 |
| 三态处理 | 是否处理了 loading / error / empty | 只有正常态，网络一慢就白屏 |
| 异步竞态 | 快速切换时是否取消了上一次请求 | 搜索结果闪烁、显示上一次的数据 |
| 复用检查 | 是否重复实现了已有的组件/工具函数 | 每个页面自己写一套卡片组件 |

**7.2 后端增改审查清单**

Agent 改了后端代码后，依次检查：

| 检查项 | 怎么看 | 高频错误 |
|--------|--------|----------|
| URL 和方法 | 路径命名是否符合 REST 约定、方法与操作匹配 | GET 接口改了数据、路径用动词 |
| 参数校验 | 入参是否校验了必填、类型、长度、范围 | 用户传 null 直接 500 |
| 返回值结构 | 和现有接口的响应格式是否一致 | 有的接口包 `{data: ...}`，有的裸返回 |
| 异常处理 | catch 块是否真的处理了错误 | `catch (e) { return null; }` 吞掉错误 |
| 分层穿透 | 是否跳过 Service 直写数据库 | Controller 里直接写 SQL |
| N+1 查询 | 循环里是否逐条查数据库 | for 循环里调 repository.findById() |
| 权限检查 | 接口是否校验了用户身份和权限 | 没登录也能调管理接口 |

**7.3 数据库增改审查清单**

Agent 改了数据库相关代码后，依次检查：

| 检查项 | 怎么看 | 高频错误 |
|--------|--------|----------|
| 字段类型 | 类型是否匹配数据语义 | VARCHAR 存金额/数量 |
| 默认值 | 有没有设置合理的默认值 | 新字段没默认值，老数据报错 |
| 非空约束 | 该必填的字段有没有 NOT NULL | 关键字段可以存 NULL |
| 索引 | 搜索/排序字段有没有加索引 | 表大了查询变慢 |
| 关联关系 | @OneToMany / @ManyToOne 方向对不对 | 关联方向写反 |
| Migration 完整性 | up 创建表/字段，有没有对应的 down 回滚 | 只能建不能回滚 |
| 危险操作 | 有没有 DROP TABLE / DELETE 无 WHERE | 误删全表数据 |

**7.4 部署配置审查清单**

Agent 改了部署相关文件后，依次检查：

| 检查项 | 怎么看 | 高频错误 |
|--------|--------|----------|
| 基础镜像 | JDK/Node 版本是否和项目匹配 | 用了不一样的 JDK 大版本 |
| 端口暴露 | EXPOSE 的端口和实际监听的是否一致 | 8080 监听了但 EXPOSE 是 3000 |
| 环境变量 | 数据库密码/API Key 是否硬编码 | `ENV DB_PASSWORD=123456` |
| 构建完整性 | 依赖安装、编译步骤是否完整 | 忘了 npm install 或 mvn package |
| CI 步骤 | 测试步骤有没有被删除或注释 | 为了"加速构建"删了测试 |

### 第八部分：调试心法 —— 出问题先问"哪一层"（约 30min）

> **目标**：出 bug 时不盲目。拿到一个现象，先判断是哪一层的问题，再看对应的日志或工具。

**8.1 分层定位决策树**

```
现象                                   → 优先排查层          → 看什么
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
页面白屏 / 样式错乱                     → 前端               → 浏览器 Console
点了按钮没反应 / 数据不对但后台有返回    → 前端               → Network 面板，看请求是否发出、响应是什么
接口返回 4xx（400/401/403/404）        → 前端 + 后端        → 前端看请求参数，后端看路由和校验
接口返回 5xx（500/502/503）            → 后端               → 后端日志，看异常堆栈
数据查出来不对 / 写不进去               → 数据库             → 直接查数据库，看表结构和数据
整个服务访问不了（502/504/拒绝连接）    → 部署 / 容器        → docker ps 看容器状态，看端口监听
环境变量 / 配置问题                     → 部署 / 容器        → env 文件，容器环境变量
```

**8.2 现场演练**

- 讲师在代码中故意引入 3 个典型 bug（前 / 后 / 数据库各一个）
- 带领学员用决策树定位：看现象 → 判断层级 → 看对应日志 → 找到根因
- 展示一个经验：**不要跳层猜原因，先确认是哪一层，再深入**

**8.3 日志阅读技巧**

- 前端 Console：红色错误 vs 黄色警告，Network 面板看状态码和 response
- 后端日志：如何从一堆日志中定位到自己的那条请求（traceId / requestId）
- 数据库：慢查询日志长什么样

### 第九部分：vibe coding 五大能力收官（约 45min）

> **目标**：回顾全天内容，将碎片化知识收敛为五大核心能力。输出一张可落地使用的 A4 审查清单。

**9.1 五大能力回顾**

| 能力 | 含义 | 对应的课程模块 |
|------|------|--------------|
| **追踪** | 能跟着一个请求从浏览器到数据库走完全链路 | 第一部分：全栈全景 |
| **读懂** | 能看懂前端组件、后端接口、数据库结构、部署配置 | 第二～第五部分：各层视角 |
| **识别模式** | 能认出 MVC、REST、ORM 等常见模式，发现 Agent 偏离 | 第二～第五部分：技术选型要点 |
| **定位问题** | 出 bug 能判断是哪一层的问题，再看对应日志 | 第八部分：调试决策树 |
