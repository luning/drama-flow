# 全栈认知基础：vibe coding 时代的全栈基础课

## 内容简介

AI 编码工具已让写代码的门槛大幅降低，但新问题随之而来：Agent 写出了前后端代码、数据库迁移、部署配置 —— 你看得懂吗？你敢上线吗？

本课程为不熟悉全栈技术的工程师设计，**不讲怎么造，教你怎么看懂 Agent 造出来的东西并判断对不对**。围绕 DramaFlow 短剧应用：先跟着一个请求走完全链路，建立全栈认知地图；再深入到各层核心知识——不只讲解 diff 怎么看、审查清单怎么用，更追问"为什么这么设计、不同选择有什么取舍"，让你真正理解技术栈的内在逻辑，有能力判断 Agent 产出代码的合理性。最终交付一张 A4 审查清单：Agent 交出代码，5 分钟快速判断质量。

## 目标学员

1. **后端工程师**：能写 Java，但不懂前端和 Android 在干什么、代码怎么部署
2. **前端工程师**：能写页面，但不清楚后端如何处理请求、数据库长什么样
3. **产品经理**：能提需求，但看不懂 Agent 产出的技术方案是否合理
4. **运维 / 测试工程师**：懂部署和测试，但缺乏对全栈代码结构的整体理解

## 课程收益

1. 能说出一次请求流经了哪些层、每层做什么、为什么这么分层
2. 看懂前端组件 / Android 页面 / 后端接口 / 数据库迁移 / 部署配置各自在说什么
3. 知道各层主流技术选项的取舍逻辑（React vs Vue、REST vs GraphQL、ORM vs 原生 SQL ……）
4. Agent 改代码后，能在 5 分钟内逐层判断改动是否正确
5. 出问题时快速判断"是哪一层的问题"，再看对应日志
6. 拿到一张可打印的 A4 审查清单，每次 Agent 交付代码后逐项对照

## 授课方式

讲师讲授 + 现场演示（Agent 实操）+ 案例研讨

## 课前准备

IDE + Git 客户端（无需安装项目运行环境，课上以讲解和演示为主）

## 课程大纲

### 第一部分：全栈全景 —— 一次请求的完整旅程（约 45min）

> **目标**：跟着一个请求从头走到尾，建立"全栈有哪些层、每层做什么、数据怎么流"的直觉认知。

**1.1 项目结构与全链路追踪**

- **请求发起**：浏览器 / App 发送 HTTP 请求 —— URL 结构（协议 + 域名 + 路径）、HTTP 方法（GET 读 / POST 写 / PUT 改 / DELETE 删）的含义；对比 Android 端 Retrofit / OkHttp 如何发起同样请求
- **路由分发**：Web 服务器（Nginx）将请求转发给后端；路由层根据 URL 和方法匹配到对应的 Controller 方法
- **分层处理**（Controller → Service → Repository）：Controller 接收参数、调用 Service、返回响应；Service 承载业务逻辑（筛选、排序、分页、权限）；Repository 封装数据库操作。为什么要分三层？—— 改业务不改接口，改数据库不影响业务，这是"关注点分离"
- **数据库查询**：ORM 把 Repository 方法调用翻译成 SQL 发给数据库，数据库返回行数据，ORM 再映射为 Java 对象。为什么需要 ORM？—— 避免手写 SQL 字符串的拼写错误和注入风险
- **响应返回**：后端把对象序列化为 JSON，设置 HTTP 状态码（200 成功 / 400 参数错 / 500 服务错），返回给客户端
- **客户端渲染**：前端解析 JSON → 更新组件状态（ref / reactive）→ 框架自动同步 DOM；Android 端：ViewModel 更新 LiveData / StateFlow → Compose / XML 自动刷新 UI

**1.2 理解技术选择背后的"为什么"**
- 每个环节都有多种技术选项：为什么用 REST 不用 GraphQL？为什么分三层而不是全写在一起？为什么用 ORM 而不是手写 SQL？—— 理解取舍比记住语法更重要，这是下午深入审查的基础

### 第二部分：客户端视角 —— 浏览器 / App 里发生了什么（约 45min）

> **目标**：打开前端和 Android 代码不再眼晕。看懂组件树、状态管理、API 调用，理解各自技术选型的取舍。

**2.1 Web 前端核心概念（Vue 3 / React）**

以 DramaFlow 首页为例：
- 三层结构：`<template>`（画什么）、`<script>`（逻辑）、`<style>`（长相）；组件树：页面 → 卡片 → 按钮，逐层嵌套，父传子 props、子通知父 emit
- 响应式状态：`ref` / `reactive` 管数据，数据变化 UI 自动更新——这是前端框架的核心价值
- 路由：vue-router 把 URL 路径映射到页面组件（hash vs history 模式）
- 构建：Vite 做了什么（打包、热更新、代码分割），为什么需要构建这一步（浏览器不认识 .vue 文件）
- 底线：任何数据加载必须处理 loading / error / empty 三种状态

**2.2 技术选型：React vs Vue vs Angular、SPA vs SSR、局部状态 vs 全局状态（Pinia / Redux）**

**2.3 Android 核心概念**

- 项目结构：`java/`（代码）、`res/layout/`（布局 XML）、`AndroidManifest.xml`（应用声明）、`build.gradle`（依赖和构建）
- Activity = 一个屏幕（类比 Web 的一个页面）；生命周期 6 个回调（onCreate → onStart → onResume → onPause → onStop → onDestroy）—— Agent 最容易在生命周期上犯错（如在 onStop 后还更新 UI → 崩溃）
- ViewModel + LiveData / StateFlow：Android 的"状态管理"，屏幕旋转数据不丢（类比 Pinia store），数据变化自动通知 UI
- 布局：XML + ViewBinding vs Jetpack Compose（声明式 UI，更接近 Vue/React 思维）
- 导航与网络：Navigation Component 管跳转（NavGraph，类比 vue-router）；Retrofit + OkHttp 发 HTTP 请求

**2.4 Agent 改了客户端代码，你该检查什么**
- Web：路由注册、props 正确性、状态声明、API 地址/方法是否匹配后端、三态处理
- Android：生命周期安全、ViewModel 数据流、Manifest 注册、Retrofit 接口匹配、权限声明/请求
- 附带讲解浏览器 Console 和 Android Logcat 的报错怎么看

### 第三部分：后端视角 —— 服务端里发生了什么（约 45min）

> **目标**：看懂后端的分层结构，理解每层为什么这样设计、不这样设计会怎样。

**3.1 以短剧列表接口为例，跟着请求走**

- 路由层：`@GetMapping("/api/dramas")` 把 URL 映射到方法
- Controller 层：`@RequestParam` / `@PathVariable` 接收参数，调用 Service，`ResponseEntity` 封装响应
- Service 层：业务逻辑（筛选、排序、分页、权限）。为什么需要 Service？——多个 Controller 可能用同一段逻辑，复用 + 统一事务边界
- Repository 层：Spring Data JPA 从方法名自动生成 SQL（`findByCategoryOrderByCreatedAtDesc`）。为什么不手写？——避免拼写错误、SQL 注入、数据库方言差异
- Entity 层：`@Entity` 标记持久化类，`@Column` 定义字段映射，`@OneToMany` / `@ManyToOne` 定义关联关系

**3.2 技术选型要点**
- Spring Boot vs Express vs FastAPI：企业级全栈 vs 轻量异步 vs 高性能 Python
- RESTful 约定：URL 用名词复数、方法决定操作、状态码表达结果（2xx/4xx/5xx）
- JWT 认证：Header.Payload.Signature 三段式、Bearer Token 传递方式、过期刷新机制
- 错误处理：为什么需要 @ControllerAdvice 统一处理而不是每个接口 try-catch
- 结构化日志：traceId 为什么至关重要（串联一次请求的所有日志，没有它排查问题如大海捞针）

**3.3 Agent 加了后端接口，你该检查什么**
- URL 和方法是否符合 REST 约定；入参是否校验（必填、类型、范围）；返回值结构是否和已有接口一致；异常是否被吞掉（catch 后 return null）；是否跳过 Service 在 Controller 写 SQL；循环里是否逐条查数据库（N+1 查询）；权限是否校验

### 第四部分：数据视角 —— 数据如何存储和流动（约 30min）

> **目标**：看懂数据库表结构，理解 ORM 如何连接代码和数据库。

**4.1 核心概念**
- 表结构：字段类型（INTEGER / VARCHAR / TEXT / DATETIME 各自存什么），表关系（一对一、一对多、多对多）
- ORM 原理：Entity 类 ↔ 表，属性 ↔ 字段。增删改查的 ORM 写法如何翻译为 SQL
- Migration：数据库版本管理，每次改表结构都要有迁移脚本（up 创建 / down 回滚），为什么不能直接改表（团队协作、可追溯、可回滚）
- 索引：搜索/排序字段不加索引为什么越来越慢（全表扫描 O(n) vs B+Tree 查找 O(log n)）

**4.2 技术选型：关系型 vs NoSQL、ORM vs 原生 SQL、Migration 工具比较**

**4.3 Agent 改了数据库，你该担心什么**
- 字段类型是否合理（VARCHAR 存金额 → 排序/计算错误）；有没有默认值和非空约束；关联关系方向对不对；migration 是否 up/down 都有；会不会误删表/数据；是否 N+1 查询

### 第五部分：部署视角 —— 代码如何变成可访问的服务（约 30min）

> **目标**：理解"本地能跑"和"线上能访问"的本质差距，看懂 Docker 和 CI/CD 配置。

**5.1 容器化的原理**
- "我电脑上能跑"为什么是谎言：Node/JDK 版本、系统库、环境变量各不相同
- Docker 三步：Dockerfile 定义环境（FROM + RUN + COPY + CMD）→ 构建成镜像（模板）→ 运行为容器（实例）
- docker-compose：编排多个容器（前端 + 后端 + 数据库），定义网络和启动顺序
- Docker vs 虚拟机：容器共享宿主机内核（启动秒级、MB 级），虚拟机独立 OS（启动分钟级、GB 级）

**5.2 CI/CD**
- CI：每次 push 自动跑测试、构建镜像；CD：通过后自动部署；环境分离（dev / staging / prod）各自独立配置
- docker-compose vs K8s：单机用 compose，多机集群用 K8s

**5.3 Agent 改了部署配置，你该检查什么**
- 基础镜像版本对不对；端口是否和监听一致；密码/密钥是否硬编码；构建步骤是否完整；CI 测试步骤是否被删除

### 第六部分：现场演示 —— Agent 追加一个新功能（约 30min）

> **目标**：完整展示一次真实的 vibe coding 循环，把前五部分的审查思维串联起来。

- 场景：在 DramaFlow 上增加"搜索短剧"功能，用自然语言向 Agent 描述需求
- Web 前端改动：搜索输入框、结果展示、API 调用 —— 讲师逐段讲解 diff，对照审查清单检查
- Android 改动：搜索入口、结果列表、网络请求 —— 对照生命周期和 ViewModel 审查
- 后端改动：搜索接口（Controller + Service + Repository）—— 讲解路由、参数校验、模糊查询、返回格式
- 数据库改动：如有加索引，对照迁移安全性检查
- 跑起来测，发现 bug（故意预留），展示如何描述问题让 Agent 精准修复；展示调试决策树实战应用

### 第七部分：增改代码的审查心法（约 45min）

> **目标**：本日核心章节。将各层知识点浓缩为可操作的审查清单，Agent 交付代码后逐层扫描。

**7.1 Web 前端** —— 路由忘配→404；嵌套错→布局乱；API 地址/方法错→调不通；状态没声明→不更新；缺三态→白屏；异步竞态→闪烁；重复造轮子

**7.2 Android** —— onStop 后更新 UI→崩溃；ViewModel 没绑 lifecycle→内存泄漏；Activity 忘在 Manifest 注册→启动崩溃；Retrofit 接口和后端不一致→调不通；忘声明/请求权限→功能异常

**7.3 后端** —— URL 不符合 REST；参数没校验→传 null 500；返回值格式不统一；catch 后 return null 吞错误；Controller 直接写 SQL；for 循环逐条查 DB（N+1）；没加权限校验

**7.4 数据库** —— VARCHAR 存金额→计算错；新字段没默认值→老数据报错；关联方向写反；migration 只有 up 没 down；DROP TABLE / DELETE 无 WHERE；搜索字段没索引→变慢

**7.5 部署** —— 镜像版本不匹配→构建失败；端口暴露和监听不一致→访问不了；密码硬编码（ENV DB_PASSWORD=123456）；忘装依赖或编译步骤；为了加速删了 CI 测试

### 第八部分：调试心法 —— 出问题先问"哪一层"（约 30min）

> **目标**：出 bug 时不盲目，先判断层级再看对应日志，形成肌肉记忆。

**8.1 分层定位决策树**（核心原则：不要跳层猜原因，先确认是哪一层，再深入）
- 页面白屏/样式错乱 → 浏览器 Console（Web）或 Logcat（Android）
- 点了没反应/数据不对 → Network 面板看请求和响应状态码
- 接口 4xx → 前端看参数，后端看路由和校验；5xx → 后端日志找异常堆栈，沿 traceId 追踪
- 数据不对/写不进 → 直接查数据库；服务 502/504 → docker ps + docker logs
- 配置问题 → 检查 .env 和 docker-compose 环境变量注入

**8.2 现场演练与日志阅读要点**
- 讲师故意引入 3 个典型 bug（前端/后端/数据库），带领用决策树定位：现象 → 层级 → 日志 → 根因
- 前端 Console 红色错误 vs 黄色警告，Network 面板状态码和 response body
- 后端 traceId 串联全链路日志；Android Logcat 按 tag 过滤，崩溃看 Stacktrace 第一行和最后一行

### 第九部分：vibe coding 五大能力收官（约 45min）

> **目标**：全天收敛为五大核心能力，输出可落地使用的 A4 审查清单。

**9.1 五大能力**
- **追踪**：跟着请求从客户端到数据库走完全链路（对应第一部分）
- **读懂**：看懂前端/Android/后端/数据库/部署代码（对应第二～第五部分）
- **识别模式**：认出 MVC、REST、ORM、响应式等模式，发现 Agent 偏离（对应各层技术选型）
- **定位问题**：出 bug 判断是哪一层，再看日志（对应第八部分）
- **表达清楚**：用 Agent 理解的术语描述需求，写有效 prompt（对应第六部分）

**9.2 审查清单（A4 打印版）**
```
□ Web前端: 路由配了没？三态全吗？API地址方法对吗？
□ Android: 生命周期安全吗？Manifest注册了吗？权限声明了吗？
□ 后端: URL REST合规？参数校验了？异常被吞了？越层写SQL了？
□ 数据库: 字段类型对？有默认值？migration有up和down？没危险操作？
□ 部署: 镜像版本对？端口对？密码没硬编码？CI测试还在？
□ 一致性: 前端调的接口存在吗？后端返回字段前端用了吗？Entity和表字段一致吗？
```
