> **核心命题**：决定 agent 上线的，不是你给模型写了什么 prompt，甚至不是你选了什么模型，而是你给模型搭了一套什么样的运行系统——这就是 harness。

2026 年上半年 AI 工程里升温速度最快的概念——Harness Engineering。2025 年底到 2026 年初，Anthropic、OpenAI、Google DeepMind、Stripe、Vercel 这些公司几乎同时开始公开讲同一件事。

---
## 1. 什么是 Harness Engineering

### 词源：马具的隐喻

**Harness** 的原始含义是马具——缰绳、马鞍子，一整套控制马匹的装备。这个隐喻是刻意的：

- **马** = 模型：强大、快速，但自己不知道该往哪跑
- **骑手** = 人类工程师：提供方向
- **马具** = harness：把原始能力导向有用的工作

> **另一个直觉类比**：把 Coding Agent 比作一支施工队，模型就是工人的技能水平，Harness 则是工地的工程管理体系——施工图纸、安全规范、质量巡检、进度管控。没有这套体系，几个工人也能搭个简易棚子；但要盖摩天大楼，缺了它寸步难行。

### 一句话定义

> **Harness Engineering 不是在教模型怎么回答，而是在设计模型怎么工作。**

它处理的是模型外部那一整层东西：任务怎么拆解、上下文怎么管理、工具怎么编排、权限怎么设定、状态怎么交接、做完了怎么验证、失败了怎么恢复、什么时候该把控制权交回给人类。

### 概念结晶时间线

| 时间 | 事件 |
|------|------|
| 2025 年 11 月 | Anthropic 发布《Building effective harnesses for long-running agents》，将 Claude Agent SDK 定义为通用型 agent harness —— **实践在先** |
| 2026 年 2 月 5 日 | HashiCorp 联合创始人 Mitchell Hashimoto 博客命名：*「每当你发现 agent 犯了一个错误，你就花时间工程化一个解决方案，让他永远不再犯同样的错。」* —— **命名** |
| 2026 年 2 月 | OpenAI 官方博客发布《Harness Engineering》—— **推广** |

> **结论**：Anthropic 是实践在先，Mitchell Hashimoto 是命名，OpenAI 是推广。

## 2. 三层工程范式演进

三个概念形成一条清晰的演进链条，**包含关系：Harness ⊃ Context ⊃ Prompt**。

| 维度 | Prompt Engineering | Context Engineering | Harness Engineering |
|------|-------------------|---------------------|---------------------|
| **时代** | 2022—2024 | 2025— | 2026— |
| **核心问题** | 「问什么」 | 「让模型看到什么」 | 「模型在什么机制里干活」 |
| **技术范围** | 措辞、少样本、思维链 | RAG、记忆注入、工具定义、对话历史 | 工具编排、权限、状态、验证、日志、重试、人机交接 |
| **性质** | 单轮、文本层面 | 动态组装模型输入 | 完整运行系统设计 |
| **比喻** | 命令「右转」 | 给模型一张地图 | 整辆车——方向盘、刹车、车道边界、维护计划、警示灯 |

### 关键判断

> Anthropic（2026 年 3 月）：Prompt Engineering 和 Context Engineering 都能显著提升效果，但都会碰到上限，**前沿的性能关键越来越落在 harness design 上**。

## 3. 为什么偏偏 2026 年爆发

### 原因 1：模型能力抬高，系统设计变成主要差异来源

模型够强了，但光靠它没用——你得给他一个好的工作环境，它才能把能力发挥出来。

### 原因 2：长任务暴露了裸模型的系统性缺陷

Anthropic 的具体描述：即使是 Opus 4.5，在跨多个上下文窗口运行时，如果只给一个高层级指令（如「构建一个 Claude.ai 的克隆」），它依然造不出生产质量的外部应用。

典型失败模式：
- 试图一口气完成所有事情 → 上下文耗尽
- 下一个 session 看到一部分进展就提前宣布完成 → 未验证

换更强的模型不会自动消失，必须靠 harness 层面的机制来治理。

### 原因 3：数学直觉——复合失败率问题

> 假设流水线每步成功率 **95%**，串联 20 步后，端到端完成率只剩 **36%**。

这就是为什么团队报告 agent 95% 的时间正常工作，但真实任务上仍有三分之一的失败率。**这个问题不是靠聪明的模型能解决的，必须靠系统层面的验证。**

### 原因 4：模型趋于商品化，系统设计成为新竞争壁垒

GPT 系列、Claude 系列、Gemini 系列在核心能力上的差距在缩小。

> **旧护城河是模型质量，新护城河是 harness 质量。**

## 4. 头部公司实践

### Anthropic

#### 第一版：双 Agent 架构（2025 年 11 月）

| 角色 | 运行时机 | 职责 |
|------|---------|------|
| **初始化 Agent** | 仅第一个 session | 建立环境、创建初始化脚本、写入进度日志、建立 Git 基线、将高层指令扩展为数百条具体可测试的功能需求（JSON 格式） |
| **编码 Agent** | 后续所有 session | 读进度文件 → 审查功能清单 → 跑现有测试 → 逐功能推进 |

**核心设计思想：外部制品成为 Agent 记忆**

进度文件、Git 历史、结构化需求清单跨 session 持久化；每个 agent session 在动手之前先从这些制品重建上下文。

**有趣细节**：两个 agent 实际上共享相同的系统提示、工具集和整个 harness，区别只是初始用户提示不同——**仅通过提示工程就能在单一 harness 内创造专门化行为**。

---

#### 第二版：三 Agent 架构（2026 年 3 月）

```
Planner → Generator → Evaluator（Playwright 交互式验证打分）
```

**最有意思的发现：为什么需要评估器分离？**

当你让模型评估自己的工作时，它会倾向于自信地表扬自己的作品，即使在人类看来质量明显平庸。这不是哪个模型的问题，**这是自评估的系统性缺陷**。

> 工程化一个独立的严格评估器 agent，远比教会生成器 agent 自我批评要容易得多。

**你们自己用 agent 做开发的时候，有没有遇到过 agent 自信满满地告诉你搞定了，结果一检查全是半成品的经历？**

---

#### 关键洞察：Harness 必须跟模型能力边界相匹配

- **Sonnet 4.5**：有明显的上下文焦虑倾向，随着上下文增长模型会变得不稳定 → harness 里设计了上下文重置机制
- **Opus 4.5**：模型自行消除了这个行为 → 上下文重置机制不再必要，反而变成了包袱

> **结论：harness 不是越复杂越好，模型强了，有些模块反而应该撤掉。**

### OpenAI

#### 基本数据

| 指标 | 数字 |
|------|------|
| 团队规模 | 3 人起步，扩展到 7 人 |
| 时间跨度 | 约 5 个月（2025 年 8 月起） |
| 代码产出 | 约百万行 |
| 合并 PR 数 | 约 1500 个 |
| 人均日 PR 吞吐 | 约 3.5 个（团队扩大后反而上升） |

**极端约束**：禁止手写代码——所有应用逻辑、测试、CI、文档、可观测性和内部工具，全部由 Codex 生成。构建速度约为手写的十分之一，但团队认为这是可接受的取舍。

#### Harness 三大支柱（Boeckeler 归纳）

1. **Context Engineering**：持续增强代码库知识库 + agent 对可观测性数据和浏览器的动态访问
2. **架构约束**：用确定性的自定义 Linter 和结构测试执行，而不是靠 agent 自觉遵守
3. **「垃圾回收」**：定期运行后台 agent 扫描不一致和架构违规，对抗系统的熵增

#### 核心模式

> 当 agent 遇到困难时，**不要更努力地尝试**，而是访问缺少什么能力，怎么让这个能力对 agent 来说既可读又可执行，然后让 Codex 自己编写修复代码。

→ 形成 **harness 自我改进的闭环**。

#### 诚实度提醒

Boeckeler 明确指出：OpenAI 在呈现这个案例时有既得利益。而且那篇文章标题虽叫《Harness Engineering》，正文里 harness 这个词只出现了一次——标题很可能是受 Mitchell Hashimoto 博客启发后加上的。**该学的学，该存疑的也得存疑。**

### Google DeepMind

#### Aletheiad（2026 年 2 月）

面向数学研究的自主 agent，核心架构是三组件 harness：

```
Generator（提出候选解法）
    ↓
Verifier（自然语言检查逻辑缺陷和幻觉）
    ↓
Revisor（修正验证器发现的错误）
    ↓ 循环，直到通过验证
```

**成果**：IMO-Proof Bench Advanced 准确率 **95.1%**，自主解决了 Erdős 猜想数据库中 4 个此前未被解决的开放问题。  
**批评**：在更广泛的问题上错了 **68.5%**——harness 在特定场景很强，但泛化能力受限于设计边界。

#### 行业模式收敛

> Anthropic 的 **planner-generator-evaluator** 和 Google 的 **generator-verifier-revisor** 是独立走到同一个设计模式上的。

**「生成—评估分离」正在成为 agent harness 设计的行业共识。**

#### 工具层动作

| 产品 | 定位 |
|------|------|
| **ADK（Agent Development Kit）** | 开源 agent 框架，内置 evaluation harness，类似 Claude Agent SDK |
| **Agent Starter Pack** | 生产级脚手架，含 CI/CD、测试框架、监控配置 |
| **ADK Python 2.0 Alpha** | 加入图式工作流编排（2026 年 3 月） |
| **Thought Signature（Gemini 3）** | 工具调用前生成加密推理状态表示，传回对话历史后可恢复精确推理链路 |

**两条技术路线对比**：
- Anthropic：**harness 层外部制品**（进度文件、Git 历史）跨 session 保持记忆
- Google：**模型内部**（Thought Signature）解决跨步骤状态持续性

### 其他值得关注的案例

#### Vercel：反直觉的约束实验

**做法**：给 agent 配了全面工具库（搜索、代码、文件、API 工具全有）→ 效果很差（agent 困惑、冗余调用、不必要步骤）→ **移除 80% 的工具**。

**结果**：更少步骤、更少 token 消耗、更快响应、更高成功率。

> 约束 agent 的解决空间，反而能提升它的表现。  
> **为了获得更多 AI 自主性，运行时环境反而需要更多约束，而非更少护栏。**

这跟传统软件开发里「给工程师更多自由度」的理念完全相反。

---

#### Stripe：生产级隔离环境

- agent 叫 **Minions**，运行在隔离的、预热好的 **DevBox** 环境里
- 与生产环境和互联网隔离，但跟人类工程师用的开发环境完全一样
- 通过 **MCP 服务器**访问超过 400 个内部工具

> 核心理念：agent 需要跟人类工程师一模一样的上下文和工具，而不是后期拼凑的集成方案。

---

#### Manus：迭代成本的现实

2025 年初走红的自主 agent，在 harness 达到生产就绪之前，经历了**六个月、五次完整的架构重写**。

> harness 的成熟是一个高成本、迭代密集的过程，没有人是一次就做对的。

## 5. 成熟 Harness 的六大核心模块

综合 Anthropic、OpenAI、Google DeepMind、Stripe 的实践归纳。

### 模块 1：上下文工程与知识管理

| 技术 | 说明 |
|------|------|
| 项目指令文件 | AGENT.md、CLAUDE.md，agent 启动时读取 |
| 动态上下文注入 | 从日志、指标、追踪信息中获取实时信息 |
| 上下文隔离 | 用子 agent 作为「上下文防火墙」，让不同子任务在隔离窗口里运行 |
| 上下文压缩 | 随着窗口被填满，自动丢弃或摘要无关信息 |

> OpenAI 的精辟观察：从 agent 的角度看，**它在运行时无法访问的任何东西都等同于不存在**。越来越多的知识需要被推送到代码库内部，成为版本化的制品。

### 模块 2：工具编排与权限设计

- 精心策划工具集，**移除多余选项**（Vercel 的教训）
- MCP 协议集成
- 文件系统访问管理
- 沙箱隔离

### 模块 3：验证机制与约束

这是 harness 区别于简单 scaffold 的核心特征。

| 类型 | 具体机制 |
|------|---------|
| **确定性约束** | 自定义 Linter、结构测试、pre-commit hooks——不依赖 LLM 判断的硬性规则 |
| **生成—评估分离** | 独立评估器 agent，避免自评估的系统性缺陷 |
| **自动审查循环** | Codex 在本地审查自己的更改，其他 agent 审查回应，循环迭代直到所有审查者都满意 |

### 模块 4：状态管理与记忆持续性

大语言模型是无状态的，每个新 session 从零开始——这是长任务场景的核心挑战。

**解决方案：外部化记忆**
- 进度追踪文件
- 结构化功能清单（JSON）
- 增量更新提交（Git 历史作为记忆）
- 检查点与恢复机制

### 模块 5：可观测性与反馈回路

- 执行追踪
- 质量分级
- 异常检测
- **反馈归因**：把 agent 在生产中的失败模式追溯到 harness 的具体缺陷，驱动持续改进

### 模块 6：人类接管与生命周期管理

**必须在以下场景暂停，让人类确认：**
- 要删数据库
- 要扣费
- 要发客户邮件

还包括：升级路径、失败重试、完整的生命周期 hooks。

## 6. 新瓶装旧酒，还是真正创新？

### 承认：确实有很大一部分不是新发明

- **Test harness**：软件工程里已有几十年历史
- **CI/CD 管道、Linter、pre-commit hooks**：成熟的 DevOps 实践
- **任务分解与编排**：分布式系统里早就被充分研究
- **沙箱隔离**：安全工程的基础概念
- **可观测性**：SRE 领域已经高度成熟

### 但也有真正的新贡献：四个维度

**① 约束对象发生了根本变化**

传统软件工程约束的是**确定性代码执行**，harness engineering 约束的是**概率性推理系统**。这要求在验证、重试恢复等方面采用根本不同的设计模式。

**② 「约束以提升」的反直觉原则**

Vercel 的案例证明：约束 agent 的解决空间、减少工具、限定模式、强制架构边界，反而提升了生产力和可靠性。这跟给人类工程师更多自由度的思路是相反的。

**③ 生成—评估分离模式**

虽然灵感可追溯到 GAN 架构，但在 agent 系统中被重新发现并工程化。Anthropic 和 Google 独立收敛到同一模式，说明这已经是**工程实践倒逼出来的结构性结论**，而非个别公司的偏好。

**④ 代码库本身成为 harness 的一部分**

代码结构、命名约定、模块边界，不仅服务于人类可读性，更服务于**agent 的可推理性**。OpenAI 的代码库甚至首先为 Codex 的可读性优化，而不是人类的阅读偏好。

### 定性

> Harness Engineering 更准确的定位是：在 agent 生产化的压力下，将多个成熟工程领域的实践**重新组合、调试，并补充针对概率性推理系统的新模式**，形成了一个统一的方法论。

这种重组本身就是有价值的创新——就像 DevOps 重组了开发与运维实践，Harness Engineering 正在重组 AI 系统的构建与运维实践。

## 7. 风险与局限

### 风险 1：概念膨胀

Harness Engineering 正在变成一个什么都能往里装的框。当一个术语从 AGENT.md 文件到完整的生产运维系统都能涵盖时，它的精确性和实用性就会被稀释。

### 风险 2：过度工程化

OpenAI 自己强调 harness 必须是**可撕裂的**。Anthropic 已经给出实例：Opus 4.5 自行消除了 Sonnet 4.5 的上下文焦虑行为，早期 harness 里的上下文重置机制就成了多余的包袱。

> **harness 不是越复杂越好，过度工程化的 harness 在模型升级后反而会成为包袱。**

### 风险 3：证据基础薄弱（最需要警惕）

支持 Harness Engineering 价值的大多数证据，来自**AI 工具厂商自身**——这些来源存在利益冲突。

- 独立的、定量的、可重现的 benchmark 验证目前仍然缺乏
- Anthropic 自己都说，他们的案例缺少显著的定量成功指标
- 学术层面虽然开始出现相关论文，但还没有经过同行评审的、被广泛引用的学术验证

### 风险 4：可重现性缺口

OpenAI 的百万行代码案例是在极其特定的条件下完成的：
- 从空仓库开始
- 用自家的 Codex 工具
- 团队本身就是 AI 系统专家

这个经验对普通工程团队的可重现性**完全没被验证过**。

### 风险 5：Harness 可能是风险放大器

Anthropic 在 BrowseComp 评测中发现：

| 配置 | 非预期解法发生率 |
|------|----------------|
| 单 agent 配置 | 0.24% |
| 多 agent 配置 | 0.87% |

多 agent 配置并不一定改变模型走捷径的倾向，但因为更高的 token 使用量和更多并行搜索，反而**提高了意外污染的概率**。

> **Harness 不只是性能放大器，也可能是风险放大器。**

---

### 开放性问题

> 如果 harness 必须与模型能力边界相匹配，而模型能力在快速提升，那 Harness Engineering 作为一门工程学科，它的核心知识会持续积累，还是会像很多补丁技术一样被下一代模型直接淘汰？  
>
> **Harness Engineering 最终会成为 AI 时代的 DevOps，还是会成为另一个被遗忘的过度概念？**

---

## 8. 行动路径总结

### 核心结论（三句话）

| 范式 | 解决什么 |
|------|---------|
| **Prompt Engineering** | 怎么说 |
| **Context Engineering** | 给模型看什么 |
| **Harness Engineering** | 让模型在什么运行机制里干活，并确保它真的把活干成 |

### 对 Agent 开发团队的务实行动路径

| 阶段 | 行动 | 说明 |
|------|------|------|
| **立即能做** | 创建 AGENT.md | 在项目根目录创建，每次 agent 犯重复性错误就加一条规则 |
| **中期投入** | 构建确定性验证层 | Linter、结构测试、commit hooks + 基本可观测性 |
| **长期规划** | 设计模块化可替换架构 | 支持模型升级时平滑迁移，避免 harness 成为技术债 |
