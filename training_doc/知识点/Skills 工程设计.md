## 什么是 Skill？

Skill 是 Claude Code 的功能扩展单元，将**特定领域的规则、上下文和工具**打包成可复用的模块。调用方式：在对话中输入 `/skill-name`，Skill 内容注入当前上下文，Claude 按其中的规则执行任务。

**何时封装成 Skill？**

| 适合 | 不适合 |
|------|--------|
| 步骤固定但需要 AI 推理的流程 | 纯机械操作（用 Shell 脚本更直接） |
| 需要专业上下文才能做对的任务 | 一次性任务，不会重复使用 |
| 团队希望标准化的操作规范 | 步骤每次都不同，无法归纳 |
| 跨会话需要一致行为的检查流程 | 简单到一句 prompt 就能描述清楚 |
| 当时不直觉、下次还会犯的判断 | 能用 linter/CI/脚本强制执行的约束 |

**粒度原则**：一个 Skill 对应一个有明确完成标准的任务。太宽（"做所有测试工作"）退化成 mega-prompt；太细（"运行一条命令"）不如直接写脚本。

### 为什么不直接问 Agent？

`/seed-data` 和直接说"添加测试数据"效果表面相似，但 Skill 的价值在四个更窄、更确定的场景：

**1. 权限隔离**：Skill 可以精确限定能做什么。`/seed-data` 只申请操作数据库的权限，不需要"Run Arbitrary Python"的全局权限。

**2. 结构化输出**：Agent 的自然语言回复不稳定——有时说"导入完成"，有时说"数据已存在"。Skill 输出固定格式，让 CI pipeline 或测试框架程序化消费结果。

**3. 跨会话的确定性**：在新会话里说"加测试数据"，Agent 的行为有方差——正确找到 seed.py、自己写 INSERT 语句、用 SQLite CLI 直接操作都有可能。Skill 消除这种方差。

**4. 低频操作者的记忆成本**：区分用户的不应是"非技术人员 vs 技术人员"，而是"天天用的人 vs 两周用一次的人"。Skill 为后者消除了每次重新摸索的成本。

## 选型决策

### Skill 类型

Skill 按内容性质分为三种，类型决定测试方式：

| 类型 | 定义 | 示例 | 如何测试 |
|------|------|------|---------|
| **Technique（技术）** | 有具体执行步骤的方法 | `rebuild-deploy`、`spec-validate` | 给一个应用场景，看 Claude 能否走完全部步骤 |
| **Pattern（模式）** | 解决某类问题的思考框架 | `cr-refactor`、`systematic-debugging` | 给反例和正例，看 Claude 能否正确判断何时使用 |
| **Reference（参考）** | API 文档、语法指南、工具手册 | OpenAPI schema、JSBridge 协议说明 | 给具体查询，看 Claude 能否准确检索并应用 |

### CLI Skill vs MCP Server

| 维度 | CLI Skill | MCP Server |
|------|-----------|------------|
| 适用场景 | 确定性流程，本地工具编排 | 外部服务集成，生态对接 |
| 推理介入程度 | 高（Claude 决策执行细节） | 低（确定性 API，Claude 只决定调用时机） |
| 适合团队 | 小团队，快速迭代，规范还在形成中 | 已有稳定服务需要接入的中大型团队 |

### Skill vs 脚本

**Skill 中不该有不需要推理的逻辑**。固定流程（检查端口、编译命令、文件路径拼接）用 Shell 脚本实现，Skill 调用脚本、处理异常、解读结果：

```
Skill（推理层）
  ├── 判断当前状态（需要 AI 读取上下文）
  ├── 调用 scripts/check-env.sh（固定检查逻辑）
  ├── 解读脚本输出，决定下一步（需要 AI 推理）
  └── 调用 scripts/deploy.sh（固定部署逻辑）
```

**判断标准**：这段逻辑用 `if/else` 写死能得到正确结果吗？能 → 脚本；需要读上下文、做判断 → Skill。

## 文件结构

```
.claude/commands/skill-name/
  SKILL.md          # 主文件：核心规则，Claude 优先读取
  references/       # 参考资料，按需读取
  scripts/          # 固定逻辑脚本，无需推理的部分
  examples/         # 示例代码
```

SKILL.md 只放核心规则，详细内容放子目录，控制单次注入的上下文量。

## 四大设计原则

### 参数最小化

每个额外参数都是一次出错机会。优先让 Skill 自己从上下文（当前目录、git 状态、已有文件）中推断所需信息：

```
# 差：需要调用者记住传参格式
/cr-refactor --path backend/app/api --depth 2 --format markdown

# 好：Skill 自己找
/cr-refactor
```

### 结构化反馈

Skill 的输出应该让 Claude 能够**自修复**——看到输出后能判断是否成功、哪里失败、下一步如何处理：

```bash
✅ H5 编译成功（dist/ 已更新）
✅ 后端启动（http://localhost:8000）
⚠️  模拟器未运行，请先启动 AVD 后重新执行
```

### 幂等性

同一个 Skill 反复调用，结果应该一致，不产生累积副作用：

- 创建资源前先检查是否已存在（`INSERT OR IGNORE`、`mkdir -p`）
- 数据导入用 upsert，不用 insert
- 临时文件写到固定路径，每次覆盖而非追加
- 启动服务前先检查端口是否已占用

### 错误恢复与降级

Skill 不应该在第一个错误处就停下来：

- **可恢复错误**：在 Skill 内部处理（例如依赖未安装，自动 pip install）
- **需要人工介入的错误**：清晰说明原因和恢复步骤，而非让 Claude 猜测
- **降级逻辑**：部分步骤失败时，哪些可以跳过继续，哪些必须中止

## 内容工程：让规则不被绕过

四大设计原则解决的是"做什么"；内容工程解决的是"如何让 Claude 真正执行到位"。

### 硬性门控（Hard Gate）

软性建议容易被跳过。当某个步骤至关重要时，用硬性门控标记它：

```markdown
<HARD-GATE>
在用户确认设计之前，禁止写任何代码、调用任何实现 Skill。
</HARD-GATE>
```

### 有序检查清单

流程叙述容易让执行顺序模糊。用编号 Checklist 代替段落描述：

```markdown
你必须按顺序完成以下步骤，每完成一步后继续下一步：
1. 探索项目上下文（检查文件、文档、近期提交）
2. 提问澄清需求（每次只问一个）
3. 提出 2-3 个方案及权衡
4. 展示设计，获得用户确认
5. 编写设计文档并提交
```

### 显式反模式

列出**常见错误路径**，让 Claude 主动识别自己是否正在走弯路：

```markdown
这些想法意味着你在自我合理化，立即停止：

| 想法 | 实际情况 |
|------|---------|
| "这太简单了，不需要设计" | 没有不需要设计的任务 |
| "先收集信息再说" | Skill 检查必须在任何行动之前 |
```

### 明确终止状态

好的 Skill 必须有清晰的"完成定义"，且明确说明完成后**只能**做什么：

```markdown
**终止状态**：调用 writing-plans skill。
禁止调用 frontend-design、mcp-builder 或任何其他实现 Skill。
只有 writing-plans 是合法的下一步。
```

### 内置自我审查

Skill 应在关键输出后内置验证循环，而不依赖用户发现错误：

```markdown
写完设计文档后，用新视角检查以下四点，发现问题直接修复：
1. **占位符扫描**：是否有 TBD、TODO、未完成的章节？
2. **内部一致性**：各章节是否互相矛盾？
3. **范围检查**：是否聚焦，还是需要拆分？
4. **歧义检查**：是否有可以被两种方式解读的要求？
```

关键是"**发现问题直接修复**，而不是再走一遍审查流程"。

### 上下文感知决策

避免给出"总是做 X"的绝对规则。好的 Skill 为每个决策点提供**判断标准**而非机械指令：

```markdown
❌ 机械规则：每个问题都通过浏览器展示
✅ 判断标准：这个问题用「展示」比「描述」更清楚吗？
  - 是（布局对比、架构图、UI 设计选项）→ 用浏览器
  - 否（需求澄清、概念选择、权衡列表）→ 用文字
```

### 选对指令形式

指令可以写成"禁止做 X"（约束），或"输出应该是 Y"（配方）。选错形式会让指令失效：

**场景 1：输出结构不对（太啰嗦、格式错）**

```markdown
❌ 禁止列表（Claude 会与"不要 X"协商，产出恰恰是你不想要的）：
不要复述问题背景，不要重申已知结论，不要铺垫上下文。

✅ 正向配方（直接约束结构，不留谈判空间）：
输出只包含三个部分，按此顺序：
1. 结论（1 句话）
2. 关键依据（不超过 3 条）
3. 下一步行动（如有）
```

**场景 2：漏掉必填项**

```markdown
❌ 散文提醒（容易被跳过）：
写完 PR 描述时，别忘了说明你的测试方案。

✅ 模板中设必填槽位（槽位存在就必须填，结构即约束）：
PR 描述格式（每项必填，不能留空）：
**变更说明**：
**影响范围**：
**测试方案**：
```

**场景 3：绝对规则在边缘场景产生荒谬行为**

```markdown
❌ 绝对规则 + 例外条款（无法穷举所有例外，Claude 遇到新情况还是不知道怎么办）：
所有错误必须报给用户。例外：编译警告可忽略，测试超时可忽略。

✅ 条件句 + 可观测的判断依据（给判断标准，而非例外清单）：
如果这个错误可以自动修复，修复后继续；
如果需要用户决策才能继续，才报给用户。
```

### 格式选择

| 内容类型 | 正确形式 |
|---------|---------|
| 参考资料、API 列表 | 表格或列表 |
| 代码示例 | Markdown 代码块（不要放进流程图节点） |
| 线性步骤（没有分支） | 编号列表 |
| 非显而易见的决策分支 | 流程图 |

流程图节点标签必须有语义：`step1`、`helper2` 是无效标签；应该用 `"检查端口是否已占用"` → `"启动服务"` → `"验证健康检查"` 这样的动作短语。

## 可发现性设计

### 描述字段：只写触发条件

**description 只描述"何时触发"，绝不描述"如何执行"。** 当描述包含流程摘要时，Claude 会直接按描述行动而不读完整 Skill——相当于 Skill 主体被绕过了：

```yaml
# ❌ 描述了执行流程，Claude 可能按描述行事而跳过 Skill 本体
description: 执行实现计划时使用——为每个任务分发子 Agent，任务之间做代码审查

# ✅ 只描述触发条件
description: 当会话中有需要独立执行的实现计划任务时使用
```

### 关键词覆盖

描述字段和 Skill 正文要覆盖 Claude 在遇到问题时会用到的词汇：

- **报错信息**："`Hook timed out`"、"`ENOTEMPTY`"——直接贴错误串
- **症状词**："`flaky`"、"`zombie`"、"`不稳定`"、"`偶发失败`"
- **同义词**："`timeout / hang / freeze`"、"`cleanup / teardown / afterEach`"

### 命名规范

Skill 名用**动词开头**，描述"在做什么"，而非"是什么工具"：`rebuild-deploy` ✅ vs `deploy-helper` ❌，`spec-validate` ✅ vs `testing-utils` ❌。

### Token 效率

Skill 被加载时注入上下文。高频加载的 Skill 目标 <200 词，专项 Skill <500 词。常见瘦身手段：参数说明放进脚本的 `--help`；用 Skill 名交叉引用而不是复制内容；每个模式只写一个高质量示例（Claude 擅长移植）。

## 验证：TDD 闭环

**Iron Law：没有跑过基线测试的 Skill，不能发布。**

必须先看到 Claude 在没有 Skill 时如何行动（测试失败），才知道 Skill 要纠正什么：

```
RED（基线）→ GREEN（写 Skill）→ REFACTOR（封堵漏洞）
```

**RED**：在没有 Skill 的情况下，给 Claude 一个会触发问题的压力场景。逐字记录 Claude 用了哪些借口（"太简单了不需要……"、"这次情况特殊……"）。如果没看到失败，说明这个 Skill 根本不需要写。

**GREEN**：只写能解决基线测试中观察到的具体失败的内容，不为假想场景添加内容。

**REFACTOR**：Claude 会找到新的合理化路径。每发现一个新借口，加进 Skill 的反模式表，再测试，循环直到没有新漏洞出现。

### 防合理化的四个具体技术

**1. 逐条封堵，不留余地**

```markdown
# ❌ 太宽松，Claude 有谈判空间
写代码前没写测试？重新来过。

# ✅ 逐条封堵
写代码前没写测试？删掉代码，重新来过。
**没有例外**：
- 不能留着"参考一下"
- 不能"边看着边写测试"
- 删掉的意思是真的删掉，不是注释掉
```

**2. 声明字面与精神一致**：在 Skill 开头加一句话截断辩解：

```markdown
违反规则的字面要求，就是违反规则的精神。
```

**3. 反模式表来自实测**：不要凭空想"Claude 可能会说什么"——从基线测试的实际记录里提取，真实的借口比想象的更有针对性。

**4. 微测试验证措辞**：每个变体跑 5 次以上，单次样本不可信；必须包含一组无指引的对照组；方差大说明措辞没有约束力，需要收紧。

## 边界设计

Skill 的纵向边界（与脚本的分工）见[选型决策](#选型决策)。横向边界的核心问题是**相同的推理模式被重复封装成了不同的 Skill**：

```
❌ 泛滥：三个 Skill，相同推理过程
/backend-code-review   → 读代码 → 找问题 → 分优先级
/frontend-code-review  → 读代码 → 找问题 → 分优先级

✅ 合并：一个 Skill，自动定位范围
/cr-refactor           → Skill 自己从 git diff 或当前目录推断范围
```

**识别合并机会**：先写触发描述。如果两个 Skill 的触发条件几乎一样，或者用户需要犹豫"该用哪个"，说明它们是同一个 Skill，只是参数不同。

**五条实操判断**：

| 判断 | 说明 |
|------|------|
| 3 次规则 | 同一个推理流程手动执行 3 次以上再封装，1 次是偶发 |
| 参数优先于复制 | 能用参数区分的变体，不应该建新 Skill |
| Description 唯一性 | 两个 Skill 的触发描述有重叠？有重叠就合并 |
| 完整任务边界 | Skill 要有明确的"完成状态"，片段任务留给 prompt |
| 一句话可描述 | 一句 prompt 说清楚的操作写进 CLAUDE.md，不用单独建 Skill |

## 团队级 Skill 库

### 三层分级

| 层级 | 位置 | 适用范围 | 管理方式 |
|------|------|---------|---------|
| 个人 | `~/.claude/commands/` | 个人习惯和偏好 | 本地，不纳入版本控制 |
| 项目 | `.claude/commands/`（项目根目录）| 当前项目规范 | Git 管理，随项目演进 |
| 团队 | 共享仓库 + 安装脚本 | 跨项目通用规范 | 独立版本管理，显式安装 |

### 版本管理与共享

- 项目级 Skill 随项目代码一起 commit，在 PR 中 review Skill 变更
- 团队级 Skill 用语义化版本号（semver），Breaking change 升大版本
- 团队 Skill 库作为独立 Git 仓库维护，通过 install 脚本（`cp -r skills/ .claude/commands/`）安装到项目；在 CLAUDE.md 中注明"已安装 XX 团队 Skill 库 vX.Y"，便于 onboarding
