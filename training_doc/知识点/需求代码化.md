## PRD 的设计意图与 Agent 的消费需求

PRD 的设计意图是为一次需求实现服务——描述这个版本要做什么、为什么做、优先级如何。它本来不负责管理功能的完整状态，每份 PRD 都是增量描述：v1.0 写了登录，v1.2 加了记住我，v2.0 改了 Token 策略。这三份文档拼在一起，才能还原登录功能的当前全貌。

这在人工研发时不是问题——开发者读完所有版本、问过 PM，脑子里能拼出全貌。但 Agent 没有这个能力。Agent 每次任务只能读它被给到的上下文，没法主动去追溯历史 PRD，也无法补全文档里没写的边界情况。

**需求代码化**要解决的不是"PRD 写得不好"，而是：**把为人准备的增量描述，改造成 Agent 能直接消费的、兼顾功能全貌的结构化资产。**

## Agent 消费 PRD 时面临的问题

### 问题一：找不到当前全貌

功能的完整状态散落在多份历史 PRD 里，没有一个地方能直接告诉 Agent：登录功能现在支持哪些场景、有哪些约束、AC 是什么。Agent 拿到最新一份 PRD，读到的只是上个迭代的变更，不是功能的全部。

```
登录功能的历史：
  PRD v1.0：邮箱密码登录，成功跳首页，失败提示错误
  PRD v1.2：增加"记住我"，Token 持久化 7 天
  PRD v2.0：密码安全升级，最少 8 位，失败 5 次锁定账号

Agent 拿到 PRD v2.0 → 知道"密码最少 8 位"
Agent 不知道 → "邮箱不存在时错误文案是什么"（PRD v1.0 的细节）
```

### 问题二：边界模糊，AI 补全不可控

PRD 里为了可读性，很多细节用自然语言概括：

> "错误情况下要有合适的提示，注意安全"

Agent 读到这句，会补全一个它认为合理的实现，但"合理"是不确定的：

- `"登录失败，请重试"` ← 太模糊
- `"邮箱不存在"` ← 暴露了账号信息，违反安全要求
- `"用户名或密码错误"` ← 文案对了，但你要的是"邮箱或密码错误"

这不是 AI 的问题，是边界没有写清楚。同一份 PRD 让 Agent 实现三次，会得到三种不同结果。

### 问题三：AC 无法被自动验证

传统 PRD 的验收标准往往写在描述里，散在各处，没有统一格式：

> "登录成功后跳转首页，失败时显示错误提示。密码长度不够要告知用户。"

这样的描述无法被 Agent 自检，也无法被测试工具直接提取。结构化的 AC 才能做到一对多消费：

```
AC-1: POST /api/auth/login，正确凭据 → 200 OK，响应含 access_token
AC-2: 邮箱不存在 → 401，message = "邮箱或密码错误"
AC-3: 密码少于 8 位 → 422，message = "密码至少 8 位"
```

同一份 AC，可以被开发自检、Agent 验证、pytest 自动执行，三方共用一份合同。

## 结构化格式参考：OKF 的启发

要让需求文档对 Agent 可消费，核心是**结构化表达**：把隐含在散文里的信息，用明确的格式写出来，让工具链能无歧义地提取。

OKF（Open Knowledge Format）是一种结构化知识管理的开源参考：以"概念"为文档单位，每个概念有稳定 ID，用 Git 管理变更历史，支持跨文档精确引用。它的设计恰好契合 Agent 消费的三个需求：

| OKF 特性 | Agent 消费收益 |
|---------|--------------|
| **以概念为单位**，一份文档覆盖一个功能的完整状态 | Agent 能从单一来源获得全貌，不需要跨文档拼合 |
| **稳定 ID**，每个需求有唯一标识 | Spec、测试、代码可以精确引用，变更影响范围可追踪 |
| **Git 管理**，变更有 diff、有历史 | Agent 能感知变更，工具链可以检测"哪些 Spec 需要跟着更新" |

大多数团队不会直接采用 OKF，但这三个特性可以用更轻量的方式在现有需求文档里实现。

## 改造方案：兼顾全貌的结构化表达

改造的核心原则是：**每个功能有且只有一份当前状态文档，覆盖完整行为，用 Git 记录演进历史。**

### 以功能为单位的结构化文档

不再用"v1.0 PRD"、"v1.2 PRD"这样的增量文档组织，而是用功能为单位，每个功能一份常青文档：

```
requirements/
├── auth/
│   ├── login.md          # 登录功能的当前完整状态（唯一来源）
│   ├── token-refresh.md  # Token 刷新
│   └── password-reset.md # 找回密码
└── drama/
    ├── browse.md
    └── playback.md
```

每次需求迭代，不是新建一份 PRD，而是更新 `login.md`，用 Git commit 记录这次变更是什么。文档始终反映当前全貌，历史通过 git log 查看。

### YAML 文件头

每份功能文档顶部声明元字段，提供稳定引用和状态标记：

```yaml
---
id: REQ-AUTH-001
title: 用户邮箱密码登录
status: approved          # draft | approved | deprecated
owner: pm-alice
updated: 2025-06-10
related:
  - REQ-AUTH-002          # Token 刷新（依赖关系）
  - SPEC.md#auth-login    # 对应的可执行 Spec
---
```

- `id` 提供稳定引用：SPEC、测试用例可以用 `REQ-AUTH-001` 精确指向这份需求
- `status: deprecated` 让 Agent 知道这份需求已下线，不应再实现
- `related` 把散落的关联文档显式连接，Agent 能沿链路找到完整上下文

脚本可以扫描所有文件头，自动生成需求索引，或检查"哪些 approved 需求还没有对应 SPEC"。

### 正文结构化

正文按职责分块，每块只做一件事：

```markdown
## 业务流程

1. 用户输入邮箱 + 密码，提交 POST /api/auth/login
2. 服务端校验：通过 → 签发 Access Token（2h）+ Refresh Token（7d）；失败 → 返回错误
3. 登录成功后跳转首页

## 异常处理

| 场景 | HTTP | 提示文案 |
|------|------|---------|
| 邮箱不存在 | 401 | "邮箱或密码错误" |
| 密码错误   | 401 | "邮箱或密码错误" |
| 密码少于 8 位 | 422 | "密码至少 8 位" |
| 账号被禁用 | 403 | "账号已停用，请联系客服" |
| 连续失败 5 次 | 429 | "账号已锁定，30 分钟后重试" |

## 验收标准

AC-1: 正确凭据 → 200 OK，响应含 access_token、refresh_token、user 对象
AC-2: 邮箱不存在 → 401，message = "邮箱或密码错误"（不得暴露"邮箱不存在"）
AC-3: 密码错误 → 同 AC-2
AC-4: 密码少于 8 位 → 422，message = "密码至少 8 位"
AC-5: 连续失败 5 次 → 429，账号锁定 30 分钟
```

异常处理单独列表，是因为这是最容易被散文略过的部分——"邮箱不存在"和"密码错误"返回同样的文案，这个安全决策在正文里只是一句话，但它会影响好几条 AC 的实现。表格格式让每个边界场景都显式可见。

### 行内约束标记

在正文中用标记区分规则的强制程度：

```markdown
- 错误提示 [MUST NOT] 区分"邮箱不存在"和"密码错误"，防止账号枚举攻击
- Token [MUST] 写入 EncryptedSharedPreferences，[MUST NOT] 明文存储
- 登录页 [SHOULD] 在请求期间显示加载状态
- [CONSTRAINT:security] 连续失败 5 次后锁定 30 分钟
- [CONSTRAINT:perf] 登录接口 P99 响应时间 < 500ms
```

| 标记 | 含义 | 强制程度 |
|------|------|---------|
| `[MUST]` | 必须实现 | 硬性要求，有 AC 覆盖 |
| `[MUST NOT]` | 明确禁止 | 安全/合规红线 |
| `[SHOULD]` | 建议实现 | 不做需说明原因 |
| `[CONSTRAINT:类型]` | 非功能约束 | 按性能/安全/合规分类 |

Agent 读到 `[MUST NOT]` 就知道这是红线，不会因为"看起来更简单"而绕过；读到 `[SHOULD]` 就知道时间紧时可以降级。

### Git 管理

需求文档纳入 Git 版本控制是结构化改造的关键一步。Git 提供的能力传统文档系统做不到：

```bash
# 查看登录需求的完整演进历史
git log --oneline requirements/auth/login.md

d4a83bc  增加账号锁定机制（连续失败 5 次）
a3f21bc  记住我：Token 持久化 7 天，写入 EncryptedSharedPreferences
b12f45a  初始版本：邮箱密码登录，JWT Token

# 查看某次迭代改了什么
git show a3f21bc -- requirements/auth/login.md
```

Git 管理还有一个关键好处：需求变更时，可以用 CI 脚本检测哪些 SPEC 引用了这份需求，提示"可能需要更新对应 Spec"，而不是等到开发发现不一致时再回头。

## 实施难点及建议

### 难点一：对 PM 不够友好

结构化 Markdown + Git 工作流对非技术 PM 有门槛。通常最先想到的解法是：

**方案 A — 工具包装：** 给 PM 提供填表单的界面（Notion Database、飞书多维表格、自研表单），后台自动生成结构化 Markdown 并提交 Git。PM 用熟悉的方式填写，不感知 Markdown 和 Git。

这个方案体感友好，但有持续的创建和维护成本：需要搭建同步脚本、处理字段变更、维护两套数据源（表单和 Markdown）的一致性。

**方案 B — Agent 辅助维护（推荐）：** 让 PM 直接通过 Agent 编辑和维护需求文档。PM 用自然语言描述需求或变更，Agent 更新结构化文档；PM 确认后由 Agent 提交 Git。不需要 PM 学 Markdown，不需要额外工具。

```
PM：登录失败 5 次后要锁定账号，锁定 30 分钟，提示"账号已锁定，请稍后重试"
  ↓ Agent 更新 login.md
  - 在异常处理表格中新增一行
  - 新增 AC-5
  - 更新 YAML 文件头的 updated 字段
  ↓ PM 确认 → Agent 提交 git commit
```

这个方案额外提供了一个能力：**从结构化需求反向生成传统 PRD 格式**。结构化文档是内部资产，而对齐评审、给业务方汇报时，仍然可以用 Agent 从结构化文档生成可读性强的散文 PRD，两者不冲突。结构化文档还可以包含更丰富的索引——相关 Spec、测试覆盖情况、变更历史摘要——这些在传统 PRD 里很难维护。

### 难点二：存量文档量大

已有大量历史 PRD 的团队，不可能全部改造。

**建议：新旧双轨，触碰则改。**

- 存量 PRD：保持现状，暂不动
- 新增功能：严格执行结构化格式，新建功能文档
- 迭代变更：触碰到哪个功能就补一份结构化文档，把该功能的当前全貌整理进去

优先级从影响面出发——核心流程（登录、支付、核心业务链路）先结构化，长尾功能后补。

### 难点三：方案调整幅度

不同团队的接受度不同，不一定要做完整的结构化改造。关键是找到 PM 能接受、又对 Agent 消费有实质帮助的方式：

**最小可行做法**：只要求每个功能文档末尾有明确的 AC 块，其余格式不作要求。哪怕其他内容还是散文，AC 结构化了，Agent 的输出质量就会有显著提升。

**中等做法**：AC 块 + YAML 文件头 + 异常处理表格。三个位置结构化，覆盖 Agent 最需要的信息。

**完整做法**：本文描述的全套方案——以功能为单位的常青文档 + 结构化正文 + Git 管理 + Agent 维护。

选哪种取决于团队节奏和 PM 配合度，不必强求一步到位。

## 与下游的关系

需求代码化不替代 SPEC.md，两者分工不同：

```
结构化需求文档（requirements/）    SPEC.md（可执行 Spec）
──────────────────────────         ─────────────────────
PM 主导，描述"做什么"              开发/AI 主导，描述"怎么做才算对"
以功能为单位，覆盖业务全貌          以模块/接口为单位，覆盖技术实现边界
包含背景、动机、优先级决策          只包含前置条件、流程、AC
AC 是业务层的验收意图              AC 是实现层的合同，可直接生成测试
```

结构化需求是上游，SPEC.md 从中提取业务 AC，技术细化后成为 Agent 直接消费的可执行工件：

```
结构化需求文档（业务 AC 意图）
    ↓ Agent 提取 + 技术细化
SPEC.md 草案
    ↓ 人工确认 AC
SPEC.md 定稿
    ↓
开发实现 → Agent 自检 AC → 自动化测试
```
