> **核心命题**：模型会自然进步，Harness 不会——它只在工程师主动决定"这次的教训不能白费"并付诸编码时才进化。  
> 每一次人类干预，都是一份等待被接收的 Harness 规格。**接不接收，是刻意的选择。**

## 1. 前言：刻意进化从哪里开始

### 1.1 两种工程师的分野

引入 Coding Agent 之后，工程师会走向两条截然不同的路：

**第一条路**：Agent 犯错，工程师纠正，继续使用，等下一个模型版本。  
逻辑是："模型在进步，再等等就好了。"  
结果是：每个月都在做同样的纠正，只是在不同功能上重复。

**第二条路**：Agent 犯错，工程师纠正，然后多问一句——"**这次纠正，我需要把什么编码进 Harness？**"  
逻辑是："干预是信号，不处理就是浪费。"  
结果是：同样的错误只发生一次，可管理的任务越来越大。

两条路的分叉点不是技术能力，而是一个**习惯性的追问**。

这个追问，就是刻意进化的起点。

### 1.2 干预是信号，编码是选择

换一个视角看"人类需要干预 Agent"这件事：**并不是模型不够强，而是 Harness 的某一层还没有覆盖到这个场景**——而这，恰恰是可以被工程化的。

| 人类干预的原因 | Harness 工程的对应动作 |
|--------------|----------------------|
| Agent 不知道能不能执行这个命令 | 权限配置（settings.json）|
| Agent 不知道这个架构决策的历史背景 | 架构决策记录（ADR）|
| Agent 没有上次踩坑的记忆 | 经验文件（EXPERIENCE.md）|
| Agent 宣布完成但没有验证 | 验收技能（Skill）|
| Agent 要执行不可逆操作 | 人机交接协议（Hooks + Human Approval）|

接收这个信号并编码，是工程师的主动选择——不是等工具进步，也不是等模型变强。

### 1.3 刻意进化也改变任务怎么被提出

以上讨论的都是"Agent 执行过程中需要干预"——这是事中和事后的刻意进化。  
但有一类干预，在任务还没开始之前就已经注定了：**因为任务本身定义得不够清晰。**

---

**场景：模糊任务引发的中途追问**

你告诉 Agent："优化一下登录页。"  
Agent 开始改，你看了之后说："不是这里，我是指错误提示文案。"  
Agent 改了文案，你又说："顺便也把加载状态修一下。"  
三轮之后，Agent 终于在做你脑子里的那件事。

但这三次干预，一次都不是因为 Agent 能力不足，而是因为**任务入口的信息就不足以支撑 Agent 做出正确的决策**。

---

**场景：执行中途追加需求**

你让 Agent 给短剧列表加搜索。做到一半，你想到搜索结果还需要支持筛选。于是你追加了需求。  
Agent 尝试把新需求整合进去，原来已经写好的部分要改，方向和原来的设计有些冲突。最终交付了一个勉强能用但结构乱的实现。

根本原因不是 Agent 协调能力差，而是**需求没有在执行前锁定**，让 Agent 在一个不断变化的目标上工作。

---

这两类场景有一个共同特征：干预发生在执行途中，但原因在任务定义阶段就埋下了。

刻意进化在这里的表现是**改变任务提出的方式**：

| 习惯 | 结果 |
|------|------|
| 任务描述：目标模糊，细节靠 Agent 猜 | 执行中多次追问和修正 |
| 任务描述：明确 AC，交付形式有范例 | Agent 可以独立执行到完成 |
| 需求在执行中追加 | Agent 在移动目标上工作，范围混乱 |
| 需求在启动前冻结，新需求另开任务 | 每个任务边界清晰，可独立验收 |

**具体做法**——每次给 Agent 分配任务前，主动回答三个问题：

1. **完成是什么样的？** 写出可以逐条验证的 AC，而不是目标描述
2. **边界在哪里？** 什么在范围内，什么不在，各举一个例子
3. **交付物是什么格式？** 代码变更、文档、还是 API 响应——有没有参考样本

这三个问题的答案，就是任务的 SPEC——它本身就是 Harness 的一部分。  
**写清楚任务 SPEC，是减少执行途中干预最直接、成本最低的刻意投入。**

---

### 1.4 推演的方式

本文通过六个递进层级的具体场景，从"工具能不能用"这样的基础控制，一路推演到"如何管理越来越大的任务颗粒度"这样的高阶问题。

每个场景的格式固定：

```
【场景】发生了什么 → 为什么需要人类干预
【根本原因】Harness 哪一层缺失
【引入】哪个 Harness 要素解决这个问题
【编码原则】以后怎么让 Agent 自己处理
```

## 2. L1 — 工具与权限：最基础的控制面

这一层的问题最简单，也最常被忽视：**Agent 连"能不能做"都不清楚。**

---

### 场景 1-A：Agent 每次都来问权限

**发生了什么**

你让 Agent 运行测试。它先问："我可以执行 `pytest` 吗？"你说可以。  
然后它问："我可以执行 `python -m pytest` 吗？"  
你再次批准。  
整个过程你批准了 12 次，大多数是同一类命令的变种。

**为什么需要人类干预**

因为 Agent 对"哪些操作是安全的、已被授权的"没有系统性认知，只能每次问。

**根本原因**：缺少权限白名单配置。

**引入**：`.claude/settings.json` 的 `allowedTools` 配置。

```json
{
  "allowedTools": [
    "Bash(pytest*)",
    "Bash(python -m pytest*)",
    "Bash(git status)",
    "Bash(git diff*)",
    "Read",
    "Edit"
  ]
}
```

**编码原则**：每次你批准一个"应当无需询问"的操作，就把它加进 allowlist。  
目标是：**日常开发的安全操作全部静默执行，只有高风险操作才弹出确认。**

---

### 场景 1-B：Agent 不经询问删除了文件

**发生了什么**

Agent 在重构时认为某个文件是临时文件，直接 `rm -rf` 了。那个文件恰好是你没提交的本地配置。

**为什么需要人类干预**

因为没有什么机制在 Agent 执行破坏性操作之前发出警告。

**根本原因**：缺少危险命令拦截中间件。

**引入**：`.claude/hooks/` 中的 PreToolUse 中间件。

```javascript
// .claude/hooks/dangerous-cmd-guard.js
// 拦截包含 rm -rf、DROP TABLE、truncate 等模式的命令
// 发现后暂停执行，要求人工确认
```

**编码原则**：把"哪些操作一旦执行就不可撤销"的直觉，翻译成 Hook 里的正则匹配规则。  
**确定性拦截 > 口头约束**——在 CLAUDE.md 里写"不要删文件"不如一个 Hook 可靠。

---

### 场景 1-C：Agent 用了不该用的工具

**发生了什么**

你有一个 `db-reset` skill 用于重置测试数据库。Agent 在排查一个数据问题时，直觉地调用了它——因为名字里有"db"和"reset"，它猜测这个工具能帮它查看数据库状态。结果测试数据被清空。

**为什么需要人类干预**

Agent 没有足够的语义信息来区分"查询"和"破坏性写入"操作。

**根本原因**：工具描述不精确，且破坏性工具没有访问控制。

**引入**：两个机制并用——
1. **工具描述精确化**：在 skill 的 description 里明确标注 `[DESTRUCTIVE]`、前置条件、使用场景。
2. **工具权限分级**：高风险 skill 要求显式调用意图，而不是靠 Agent 自动推断。

**编码原则**：**工具的命名和描述是 Agent 的判断依据。** 一个语义歧义的工具名，比一个有歧义的 API 更危险——因为 Agent 不会报编译错误，只会用错。

## 3. L2 — 任务边界：Agent 的工作范围从何而来

L1 解决了"能不能执行"，L2 要解决的是更深一层的问题：**Agent 知道自己在做什么、该做什么范围吗？**

---

### 场景 2-A：Agent 上来就开始写代码

**发生了什么**

你说"给短剧列表页加搜索功能"。Agent 直接开始改代码，没有读 SPEC.md，也没有看短剧列表的 UI 规格。  
写完后你发现：它实现了一个功能，但不是 AC（验收标准）里描述的那个功能。

**为什么需要人类干预**

因为 Agent 没有读过 SPEC，只是按自己对"搜索功能"的理解实现——做出来的东西不是 AC 定义的那个。

**根本原因**：缺少"任务前强制阅读上下文"的约束。

**引入**：CLAUDE.md 中的 **SDD 最小约束**——明确规定接受任务前必须读对应模块的 SPEC.md 和 AC。

```markdown
## SDD 最小约束
1. 接受任务前：先读对应模块的 SPEC.md AC，确认理解需求范围
2. 生成代码后：逐条自检 AC，确保所有验收标准被覆盖
```

**编码原则**：Agent 的"工作流纪律"不会凭空产生，必须在 CLAUDE.md 里明确写出。  
**预防性阅读 SPEC 的成本，远低于做完发现方向错了的返工成本。**

---

### 场景 2-B：Agent 修改了不该碰的模块

**发生了什么**

你让 Agent 修复 `auth` 模块的一个 bug。它不仅改了 `auth/`，还"顺便"修改了 `profile/` 里一个它认为有关联的函数。  
`profile/` 的修改虽然有道理，但破坏了一个你不知道的调用约定，CI 红了。

**为什么需要人类干预**

因为你需要 review 所有改动，撤销那个"顺便"的跨模块修改，并解释为什么不能这样做。

**根本原因**：模块边界对 Agent 不可见，没有机制阻止跨模块修改。

**引入**：两个机制——
1. **架构层**：模块目录 + 每个模块的 `README.md`（明确列出 Interfaces 和 Constraints）
2. **约束层**：`.importlinter` 配置模块依赖规则，违规则 CI 拦截

**编码原则**：**目录结构即边界，但边界对 Agent 不是自动可见的**——需要通过 README 声明"这个模块不对外暴露内部实现"，通过 import-linter 让违规有成本。

---

### 场景 2-C：Agent 硬编码了颜色值

**发生了什么**

Agent 新写了一个卡片组件，其中：
```css
background: #1a1a2e;
color: #6c5ce7;
```

你的设计系统里有 `--bg-card` 和 `--color-primary`，但 Agent 不知道。
你发现时，这个颜色值已经散落在三个文件里。

**为什么需要人类干预**

因为你得手动找出所有硬编码色值，替换为 CSS 变量，再解释为什么要这样做。

**根本原因**：设计系统规范对 Agent 来说只是文字建议，没有机制检测违规。

**引入**：  
1. **CLAUDE.md 明确设计系统引用规则**（颜色必须用 CSS 变量）  
2. **`scripts/check/check_tokens.py`**：可执行的 Token 合规检查脚本  
3. **CI 集成**：检查脚本接入 CI，违规则无法合入

**编码原则**：**把"应该用设计 Token"这个建议变成"不用就过不了 CI"这个约束。**  
建议靠 Agent 自觉遵守，约束靠机制强制执行——两者效果不在一个量级。

## 4. L3 — 微观工程决策：在对的轨道上

L2 解决了"做什么范围"，L3 要解决的是**在那个范围内，Agent 会做出什么设计决策，以及这些决策如何与团队已有的判断对齐**。

---

### 场景 3-A：Agent 选了团队明确排除过的方案

**发生了什么**

三个月前，你们评估过用 PostgreSQL 还是 SQLite，最终选了 SQLite（原因：部署简单，单机性能足够）。  
今天 Agent 在设计一个新模块时，看到数据量级，推断"应该用 PostgreSQL"，开始写 PG 的连接代码。

你看到的时候它已经写了 200 行。

**为什么需要人类干预**

因为 Agent 做的推断在技术上是合理的，但它不知道这个决定三个月前已经被团队否定过。

**根本原因**：架构决策的历史背景对 Agent 不可见。

**引入**：`docs/adr/`——架构决策记录（Architecture Decision Record）

```markdown
# ADR-001: 选择 SQLite 而非 PostgreSQL

## 状态：已采纳

## 背景
评估于 2025-11, 考虑了 PG 和 SQLite...

## 决策
使用 SQLite

## 理由
1. 单机部署，无需外部数据库服务
2. 当前用户规模下性能充分
3. 开发测试成本低

## 不选 PG 的理由
运维复杂度超出当前阶段价值。如规模超过 X，重新评估。
```

**编码原则**：ADR 不是写给人看的，是写给 Agent 看的。关键是记录**为什么不选另一个方案**——这部分是代码里看不出来的信息，也是 Agent 最容易走回头路的地方。

---

### 场景 3-B：Agent 写出的代码超出任务范围

**发生了什么**

你让 Agent 给一个接口加一个参数。它加了，但顺便：
- 重构了这个模块的错误处理逻辑
- 把三个相似的函数抽取成了一个
- 修改了函数命名

改动有道理，但都超出了"加一个参数"的任务范围。你现在需要 review 额外 300 行。

**为什么需要人类干预**

因为 Agent 没有"最小改动原则"的意识，它倾向于把"顺手能做的好事"都做了。

**根本原因**：SPEC.md 的 AC 是用来验收的，但没有变成 Agent 的**任务边界约束**。

**引入**：SPEC.md 的 AC 驱动自检机制

在 CLAUDE.md 里加入约束：
```markdown
生成代码后：
1. 逐条自检 AC，确保覆盖
2. 检查所有改动是否在 AC 范围内
3. 范围外的改动，无论是否合理，都单独提出供人类决策
```

**编码原则**：**SPEC 不仅是验收工具，也是任务范围的边界工具。** AC 里没有的，哪怕 Agent 有更好的做法，也应该标注"超出当前 AC 范围"而非直接实现。

---

### 场景 3-C：Agent 重复了一个已知的反模式

**发生了什么**

两个月前，你们发现在 `refresh_token()` 里当 token 为 `None` 时会抛未捕获异常。当时修复了，也在 code review 里提到了。  
今天 Agent 写了一个新的认证流程，同样的模式又出现了。

**为什么需要人类干预**

因为这个陷阱只存在于 code review 记录和人的记忆里，对 Agent 来说等于不存在。

**根本原因**：之前的教训只存在于 Git history 和人的记忆里，Agent 无法从中学习。

**引入**：`src/modules/auth/EXPERIENCE.md`——与模块代码 colocate 的经验文件

```markdown
## auth 模块经验陷阱（2025-11-12）

### refresh_token() 的 None 值陷阱
条件：token 参数为 None 时
症状：抛出未捕获的 AttributeError
修复：调用前必须显式检查 `if token is None: return None`
勿重现：新的认证流程中凡是调用 refresh 系列函数，都需要先做 None 检查
```

**编码原则**：**经验文件不是记录"最佳实践"的，是记录"踩过的坑"的。**  
格式要聚焦：触发条件 + 症状 + 修复 + 不重现的具体要求——而不是泛泛的"注意 None 值处理"。

---

## 5. L4 — 跨会话与自我验证：Agent 能相信自己吗

L4 要面对的是**长任务、多步骤、多会话**——这是 Agent 系统性失败最集中的地方。

---

### 场景 4-A：Agent "忘记"了上次做了什么

**发生了什么**

你在做一个需要多个会话才能完成的功能（比如完整的认证流程）。第一个会话完成了 API 设计和数据模型，下次会话你打开新对话，Agent 什么都不记得了。  
它的第一件事是重新分析代码库，然后开始……做了一些和上次重叠的事。

**为什么需要人类干预**

你需要手动告诉它"上次已经做了 A、B、C，今天要做 D、E"。

**根本原因**：LLM 是无状态的，每次会话从零开始。跨会话的任务状态没有被外部化。

**引入**：三种外部化状态机制（组合使用）

1. **进度追踪文件**：Agent 在每个会话结束时，把进展写入 `PROGRESS.md`，下次会话开始时先读它。
2. **Git 作为记忆**：每完成一个里程碑立即提交，提交信息即进度记录。
3. **Memory 机制**：`.claude/memory/project.md` 记录当前项目的关键决策和进度状态。

**编码原则**：**Agent 无法记住对话，但可以记住文件。** 外部制品（文件、Git 历史）就是 Agent 的跨会话记忆系统。把"应该被记住"的状态，变成"被写下来"的状态。

---

### 场景 4-B：Agent 宣布"已完成"但根本没验证

**发生了什么**

Agent 说"短剧列表功能已实现，测试通过"。  
你打开 App，列表加载正常，但搜索框根本没有出现——那是 AC 里的第 3 条。

**为什么需要人类干预**

因为 Agent 的"完成"只是"代码写完了"，不是"AC 逐条验证了"。

**根本原因**：没有强制的验收流程，Agent 依靠主观感受判断"完成"。

**引入**：**验收 Skill**——在 CLAUDE.md 里规定完成一个任务必须经过的工作流：

```markdown
## 任务完成流程
完成代码编写后，必须：
1. 逐条读 SPEC.md 中的 AC 列表
2. 对每条 AC，说明代码的哪个位置覆盖了它
3. 对无法通过代码 review 验证的 AC，必须运行 pytest 或启动服务验证
4. 在所有 AC 都被验证前，不允许宣布"完成"
```

还可以实现为一个独立的 `spec-validate` skill，专门做 AC 覆盖检查。

**编码原则**：**"完成"这个词在 Harness 里必须有操作定义。** 不定义"完成"意味着什么，Agent 会用最宽松的标准——代码存在 = 完成。

---

### 场景 4-C：长会话后期 Agent 性能明显下降

**发生了什么**

你和 Agent 在一个长会话里做了复杂的重构。到第 40 轮对话后，你发现 Agent 开始犯低级错误：忘了它两轮前才加的变量名，重复实现了已有的函数。

**为什么需要人类干预**

你需要频繁纠正这些"上下文衰减"导致的错误，或者被迫开启新会话重新铺垫所有背景。

**根本原因**：上下文窗口膨胀，早期信息的注意力权重衰减；大量历史代码占用窗口，有用信息被淹没。

**引入**：**子代理（Sub-Agents）——上下文隔离单元**

把大任务的独立子任务委派给子代理执行。子代理在独立的上下文窗口里工作，完成后只把结果返回主代理，不把中间过程的所有历史带入。

```
主代理（维持任务状态和决策）
   ├─ 子代理 A（隔离上下文）→ 实现 Feature X → 返回结果
   ├─ 子代理 B（隔离上下文）→ 实现 Feature Y → 返回结果
   └─ 子代理 C（隔离上下文）→ 代码 Review  → 返回结果
```

**编码原则**：**子代理不只是并行化工具，更是上下文防火墙。** 一个复杂任务超过 20 轮对话时，就应该考虑用子代理隔离子任务，防止上下文膨胀影响主代理的判断质量。

---

## 6. L5 — 经验沉淀：从纠正一次到永不再错

L3 引入了 EXPERIENCE.md 来记录模块级陷阱。L5 要深入讨论的是**经验如何产生、如何流转、如何保持质量**——这是 Harness 真正能实现"越用越聪明"的关键机制。

---

### 场景 5-A：你纠正了 Agent，但下次它又犯了

**发生了什么**

你告诉 Agent："在 DramaFlow 里，所有时间字段都必须用 UTC 存储，显示时再转本地时区。"  
Agent 道歉，修改了。  
三天后在另一个功能里，它又用了本地时间直接存储。

**为什么需要人类干预**

因为这次的纠正只发生在那次对话里，没有被写到任何地方。下次开新会话，这条规则又不存在了。

**根本原因**：纠正停留在对话层，没有被编码到 Harness 的任何持久层。

**引入**：**Memory → Experience 流水线**

```
场景：你纠正 Agent 某个行为
    ↓
Agent 的 memory/feedback.md 记录（个人层，不提交）
    ↓
验证这个教训是否普适（多个功能都遇到了同样问题）
    ↓
提炼到团队 EXPERIENCE.md（模块层，提交）
    ↓
如果影响所有模块，提升到 CLAUDE.md（全局层，严格 Review）
```

**编码原则**：**纠正 Agent 的那一刻，就是写经验文件的时机。** 不要等到"有空了再整理"——Agent 纠正和 Harness 更新应该是同一个动作，而不是两个分开的事。

---

### 场景 5-B：经验文件越来越长，Agent 开始忽略它

**发生了什么**

你的 `auth/EXPERIENCE.md` 已经有 80 条记录，包括一些"2024 年某次 bug"的流水账，还有"注意边界条件"这样的废话。  
Agent 读到中途就停了，后面的关键陷阱它没有遵守。

**为什么需要人类干预**

因为经验文件本身的质量问题，让它从"防坑指南"变成了"噪音源"。

**根本原因**：经验文件缺乏质量标准，写了太多不具可操作性的内容。

**引入**：**经验文件质量原则**（写入 CLAUDE.md 或 experience/ 的 README）

```markdown
经验文件写作标准：
✅ 写"陷阱条件"：token 为 None 时 refresh_token() 抛未捕获异常
✅ 标日期：每条记录标注日期，超过 6 个月标记待审查
✅ 少而精：5 条验证过的陷阱 > 50 条未经检验的"注意事项"

❌ 不写个人偏好："不要用 async/await"
❌ 不写废话："注意空值处理"
❌ 不写过时内容：已修复的 bug 如不涉及类似场景，直接删除
```

**编码原则**：**经验文件的价值不在于完整，而在于精准。** 一条有触发条件、有具体症状、有明确修复方向的陷阱记录，价值等于十条"要注意 X"。

---

### 场景 5-C：个人纠正 Agent 的经验没有流传到团队

**发生了什么**

A 工程师发现 Agent 在 profile 模块的一个陷阱并写了 memory。  
B 工程师两周后遇到了同样的问题，花了三小时 debug。

**为什么需要人类干预**

每个人都得自己踩一遍同样的坑，因为个人 memory 不会自动分享。

**根本原因**：经验的个人层（memory）和团队层（EXPERIENCE.md）之间，缺少流转机制。

**引入**：**`.claude/experience/INDEX.md`——跨模块经验索引**

这个文件不存储经验本身，而是建立**快速检索**的路由：

```markdown
# 经验索引

## 按关键词
- 时区 / UTC → src/modules/time/EXPERIENCE.md
- JWT / Token / 认证 → src/modules/auth/EXPERIENCE.md  
- SQLite / 事务 → src/modules/data/EXPERIENCE.md
- 设计 Token / CSS 变量 → design-system/EXPERIENCE.md
```

**团队治理**：当个人 memory 中的某条教训被验证是普适的，应当通过 PR 提炼到对应模块的 EXPERIENCE.md——这是 Harness 知识积累的完整闭环。

**编码原则**：**Memory 是个人草稿，EXPERIENCE.md 是团队定稿。** 一条个人 memory 如果三个月内被证明对其他成员也有用，它就应该成为团队经验。

---

## 7. L6 — 高风险操作与人机协作边界

前五层让 Agent 在正常任务流程中越来越自治。L6 要解决的是**哪些情况下 Agent 必须停下来，把控制权交还给人类**——以及怎么设计这个交接机制。

---

### 场景 6-A：Agent 向用户发送了一封错误邮件

**发生了什么**

Agent 在自动化一个通知任务。你以为它只是在测试环境验证，但它调用了生产环境的邮件 API，向 500 个用户发送了一封格式未确认的通知邮件。

**为什么需要人类干预**

因为发出去的邮件无法撤回，你需要紧急处理用户投诉。

**根本原因**：对外可见的副作用操作（发邮件、发推送、扣费）没有被标识为需要人类确认的高风险操作。

**引入**：**人机交接协议（Human-in-the-Loop）**

在 CLAUDE.md 中明确定义"必须暂停请人类确认"的操作类别：

```markdown
## 必须人类确认的操作
在执行以下任何操作前，必须展示操作详情并等待明确的人类确认：
- 向用户发送任何通知（邮件、推送、短信）
- 执行任何扣费或支付操作
- 删除数据库记录（非测试数据）
- 修改生产环境配置
- 对外发布任何公开内容
```

配合 Hook 实现：当 Agent 调用包含上述操作特征的工具时，中间件自动暂停并要求确认。

**编码原则**：**不可逆性和外部可见性是人类交接的核心判断标准。** 可以撤销、只影响本地的操作可以自动执行；一旦执行就无法完全还原、影响外部系统的操作，必须有人类确认门。

---

### 场景 6-B：Agent 在遇到困难时不停重试，浪费大量资源

**发生了什么**

Agent 在尝试安装一个依赖时失败了。它连续尝试了 15 次不同的安装方式，每次失败都推断一个新理由。整个过程用了 20 分钟，消耗了大量 token，最终还是没有解决——因为根本原因是网络访问被屏蔽，不是安装方式的问题。

**为什么需要人类干预**

因为 Agent 应该在多次失败后挂起任务，而不是无限重试。

**根本原因**：缺少**失败熔断机制**和**请求人类帮助的协议**。

**引入**：两个机制——

1. **熔断规则（在 CLAUDE.md 里）**：
```markdown
## 任务挂起协议
遇到以下情况时，立即停止重试，说明情况并请求人类判断：
- 同一类操作连续失败 3 次以上
- 遇到需要外部环境信息才能继续的阻塞（如网络配置、账号权限）
- 任务超出当前工具能力范围
```

2. **区分"应该挂起"和"应该继续尝试"的判断**：环境问题（需要人类解决）vs 逻辑问题（Agent 可以尝试不同方案）。

**编码原则**：**Agent 知道什么时候该"认输"，和 Agent 知道如何解决问题一样重要。** 无限重试消耗资源，也掩盖了真正需要人类介入的信号。

---

### 场景 6-C：两个并行 Agent 修改了同一个文件

**发生了什么**

你让两个 Agent 并行处理两个功能。它们分别修改了 `shared/types.py`，产生了冲突。合并时你需要手动解决，并确认两个 Agent 的改动哪些可以共存、哪些互相覆盖。

**为什么需要人类干预**

因为两个 Agent 不知道对方在干什么，没有协调机制。

**根本原因**：并行 Agent 缺少工作区隔离，共享文件没有独占锁机制。

**引入**：**Git Worktree 隔离**

每个并行 Agent 在独立的 git worktree 里工作，在隔离分支上进行修改，最终由主代理或人类协调合并：

```
main worktree（主线）
├─ worktree-feature-a（Agent A 的工作区）
└─ worktree-feature-b（Agent B 的工作区）
```

对于共享文件的修改，明确约定通过主代理统一处理，子代理不直接改共享基础设施。

**编码原则**：**并行不等于混乱。** 并行 Agent 的价值在于隔离上下文、提高吞吐量；但隔离的前提是有明确的工作区边界和共享资源协调机制。

---

## 8. 综合：场景 → Harness 要素映射表

以上六层场景推演出来的所有 Harness 要素，汇总如下：

| 人类干预的场景类型 | 触发层级 | Harness 要素 | Harness 层 |
|-----------------|---------|-------------|-----------|
| 重复权限询问 | L1 | `settings.json` allowlist | 执行层 |
| 不可逆命令无警告 | L1 | `hooks/` 危险命令拦截 | 约束层 |
| 工具语义混淆 | L1 | 工具描述精确化 + 权限分级 | 执行层 |
| Agent 不读 SPEC | L2 | CLAUDE.md SDD 约束 | 文档层 |
| 跨模块越权修改 | L2 | 模块 README + import-linter + CI | 架构层 + 约束层 |
| 硬编码设计值 | L2 | Token 检查脚本 + CI | 约束层 |
| 走架构回头路 | L3 | `docs/adr/` ADR | 文档层 |
| 超出任务范围 | L3 | SPEC.md AC 边界约束 | 文档层 |
| 重复已知反模式 | L3 | 模块 `EXPERIENCE.md` | 经验层 |
| 跨会话失忆 | L4 | 进度文件 + Memory | 执行层 |
| 假完成 | L4 | 验收 Skill + AC 自检 | 执行层（Skill）|
| 长会话性能衰减 | L4 | Sub-Agents 上下文隔离 | 执行层 |
| 纠正不持久化 | L5 | Memory → EXPERIENCE 流水线 | 经验层 |
| 经验文件退化 | L5 | 经验写作标准 | 经验层（治理）|
| 经验无法共享 | L5 | `.claude/experience/INDEX.md` | 经验层 |
| 不可逆副作用 | L6 | 人机交接协议 + Hooks | 约束层 + 执行层 |
| 无限重试浪费资源 | L6 | 失败熔断机制 | 约束层 |
| 并行 Agent 冲突 | L6 | Git Worktree 隔离 | 执行层 |

**与 Harness 五层对照**：

```
架构层（软约束）：模块边界可见性 → 防止 L2 跨模块越权
文档层（软约束）：CLAUDE.md / SPEC / ADR → 防止 L2-L3 方向偏差
经验层（软约束）：EXPERIENCE.md / INDEX → 防止 L3-L5 重复踩坑
约束层（硬约束）：import-linter / CI / Hooks → 强制拦截 L1-L6 违规
执行层（硬约束）：Skills / Sub-Agents / Worktrees → 规范 L4-L6 工作流
```

从上往下，约束力越来越强；从 L1 到 L6，场景越来越复杂。成熟的 Harness 在每一层都有覆盖，形成纵深防御。

---

## 9. 刻意进化的飞轮：让任务颗粒度持续增长

### 9.1 飞轮的驱动力：把每次干预变成 Harness 改进

干预本身不会让 Harness 进化——**飞轮需要工程师主动去推**。操作定义就两句话：

> **每次干预结束后，问自己：这次的纠正，我要把什么编码进 Harness 的哪一层？**  
> **每次分配任务前，问自己：AC 和边界清晰吗？还是在给 Agent 制造下一次干预的机会？**

飞轮的转速，一半取决于错误发生后的编码速度，另一半取决于能否从源头减少不必要的干预。

```
人类干预
    │
    ├─ 刻意分析：干预的根本原因是什么？
    │             Harness 的哪一层缺失？
    │             ↓
    ├─ 刻意编码：用最强约束的那一层修复
    │   （能用 Hook 就不用 Prompt，能用 Lint 就不用 Experience）
    │             ↓
    └─ 刻意验证：这次干预的情形，以后能自动处理吗？
                 能 → 飞轮转了一圈
                 否 → 找到遗漏，补上
```

### 9.2 任务颗粒度增长路径

刻意进化的成果是可见的——每覆盖一层，可以独立交给 Agent 的任务规模就扩大一级：

| Harness 成熟度 | 可独立处理的任务规模 | 典型任务 |
|-------------|------------------|---------|
| **L1 覆盖**（权限 + 危险拦截）| 单步工具调用 | 跑测试、格式化代码 |
| **L1-L2 覆盖**（+ 边界约束）| 单模块功能实现 | 给某 API 加一个字段 |
| **L1-L3 覆盖**（+ 工程决策对齐）| 跨模块功能 | 完整的认证流程 |
| **L1-L4 覆盖**（+ 跨会话验证）| 多日任务 | 完整的功能迭代（多会话）|
| **L1-L5 覆盖**（+ 经验沉淀）| 自我改进 | Agent 遇到新陷阱后自动记录，下次不再犯 |
| **L1-L6 覆盖**（+ 高风险协作）| 多 Agent 并行 | 同时推进多个功能，人类只 review 关键节点 |

这张表不是自动完成的。每一行都是团队刻意积累了对应层级的 Harness 覆盖之后才能解锁的能力。

### 9.3 刻意累积：一人管多 Agent 的真正前提

"一个工程师管理多个并行 Agent"听起来像是工具进步带来的红利。  
但实际上，它是**持续刻意投入 Harness 建设**的结果，而不是等来的。

当 Harness 覆盖了足够多的场景，人类的角色从"看护者"变成"架构决策者"：

- **L1-L3 成熟**：Agent 不再需要逐步骤确认，能独立执行单次任务
- **L4-L5 成熟**：Agent 能在多日任务里自我追踪进度，遇到问题有经验支撑
- **L6 成熟**：Agent 知道何时该停、何时该找人，不需要持续监控

一个人管理多个 Agent 的能力，**不是来自于对每个 Agent 的直接控制**，而是来自于 Harness 把大量"应该怎么做"的判断提前编码了进去。最终换来的是：
> **你批准任务，Agent 执行任务，结果符合预期——中间不需要你一直在场。**

### 9.4 刻意修剪：Harness 也会腐化

刻意进化不只是"加"——也包括"删"。

Harness 会随着模型升级、项目演进而腐化：

- **模型更强了**：某些经验文件里记录的陷阱，新模型已经能自动避免——继续保留反而是噪音
- **代码重构了**：某条 EXPERIENCE.md 记录的 bug 已在重构中消失——继续保留会误导 Agent
- **约束过时了**：ADR 里的"不选 PG"的理由已经不成立——继续保留会阻止合理的技术演进

腐化的 Harness 不会自动清理自己。需要工程师**主动**做基线测试：移除某条规则，观察 Agent 在新模型下是否仍会犯错。如果不会，这条规则可以退役。

> **Harness 治理的核心纪律**：每次模型版本升级，用裸奔基线测试审计一次 Harness——只保留仍产生显著价值的组件，退役其余部分。过时的 Harness 不是中立的，它是阻力。

---

> **结语**：Harness 不会因为时间流逝而进化，也不会因为模型变强而自动完善。  
> 它进化的每一步，都来自于某个工程师在某次干预之后，选择多做那一步——分析根本原因，找到对应的 Harness 层，把这次的判断编码进去，让它永远不再需要人来做第二遍。  
> 这就是刻意进化：不是等待，而是主动把人类的每一次判断，转化为系统永久的能力。
