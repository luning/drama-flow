# 结构化业务规则 — 从增量描述到唯一事实来源

---

## Agent 读 PRD 的三个盲区

PRD 天然是增量文档——v1.0 写登录，v1.2 加"记住我"，v2.0 改 Token 策略，三份拼起来才是当前全貌。人读完所有版本再问 PM，来脑补缺失部分；Agent 只读到被塞进上下文的那几份，无法主动追问。

**问题一：找不到当前全貌**

功能状态散落在多份历史 PRD，Agent 看到的永远是片段：

```
PRD v1.0：邮箱密码登录，成功跳首页，失败提示错误
PRD v1.2：增加"记住我"，Token 持久化 7 天
PRD v2.0：密码安全升级，最少 8 位，失败 5 次锁定

Agent 拿到 PRD v2.0 → 知道"密码最少 8 位"
Agent 不知道 → "邮箱不存在时错误文案是什么"（v1.0 的细节）
```

**问题二：边界模糊，AI 补全不可控**

自然语言概括留下歧义空间，同一句 PRD 让 Agent 实现三次会得到三种结果：

> "错误情况下要有合适的提示，注意安全"

- `"登录失败，请重试"` — 太模糊
- `"邮箱不存在"` — 暴露账号信息，违反安全要求
- `"邮箱或密码错误"` — 文案对了，但你要的可能是其他格式

**问题三：AC 无法被自动验证**

散文里的验收标准无法被 Agent 自检或测试工具提取：

> "登录成功后跳转首页，失败时显示错误提示。密码长度不够要告知用户。"

结构化 AC 可以被开发自检、Agent 验证、pytest 自动执行，三方共用一份合同：

```
AC-1: POST /api/auth/login，正确凭据 → 200 OK，响应含 access_token
AC-2: 邮箱不存在 → 401，message = "邮箱或密码错误"
AC-3: 密码少于 8 位 → 422，message = "密码至少 8 位"
```

**结构化业务规则的目标**：把为人准备的增量描述，改造成 Agent 能直接消费的结构化资产——让每个业务概念有且只有一个**唯一事实来源（Single Source of Truth）**。

## 哪种需求需要结构化？

不是所有产品知识都需要结构化。真正需要的是"业务规则"——逻辑密度高、边界清晰、错过就是线上事故。探索、流程、交互约定不需要。**共同特征：无法通过使用产品直观穷举，恰好是测试的重心。** 有的PM也已经在维护着这类文档，属于内在需要。

### 四种类型

| PRD 中的常见内容 | 现状 | 需要结构化？ |
|------|------|-------------|
| **规则判断**："失败 5 次锁定 30 分钟""优惠券与满减不可叠加""退款需先审核" | 散落在各版 PRD 里，逻辑密集、漏掉就是 bug | **是** |
| **探索方向**："要不要做社交？""先跑两周数据再看""等竞品发布再定" | 讨论性内容，方向未定，随时可能推翻 | 否 |
| **流程路径**："打开 App→首页→点短剧→播放""下单→支付→确认收货" | PRD 正文里已有完整表达，Agent 容易理解 | 否 |
| **界面调整**："按钮改成主色""间距加大 4px""标题字号调大一档" | 设计稿/代码里已有全貌，PRD 只描述改动增量 | 否 |

### 为什么 PM 需要专门维护全貌？

设计稿、代码、用例本身就是规范化的全貌产物——改一个按钮，Figma 里直接改，全貌自动更新。但 PRD 天然是增量叙事：v1.0 写登录，v1.2 加"记住我"，v2.0 改 Token 策略。PM 头脑中或散落在各版 PRD 里的完整规则，始终缺少一份"当前有效"的规范化表达。PM 不是没有全貌认知，而是没有把它规范化地沉淀下来——结构化就是把这份已经存在的全貌认知，用 Agent 能消费的格式落地。

### 测试视角

QA 的用例本质上就是校验业务规则——规则显式化后，AC 可被测试框架直接消费，这是 PM、开发、测试的三方对齐。

## PRD + 结构化业务规则如何协同

**双轨并存，互不替代。**

```
PM 写 PRD（变更叙事）
    ↓（1）Agent 提取规则变更 → 更新 business-rules/login.md（规则全貌）
    ↓（2）git commit + diff
    →（3）PRD 引用全貌链接 + 变更 diff
```

### PM 的维护方式

PM 可直接编辑 Markdown 文档，也可用自然语言描述变更，由 Agent 负责格式化、提交 git、生成 diff。

> **工作流示例：**
> ```
> PM：登录失败 5 次后要锁定账号，锁定 30 分钟，提示"账号已锁定，请稍后重试"
>   ↓ Agent 更新 login.md（新增异常行、新增 AC、更新文件头）
>   ↓ PM 确认 → Agent 提交 git commit
> ```
> 反向：结构化规则的变更也可逆向生成传统 PRD，对外汇报时由 Agent 转为散文。

### PRD 中引用规则的方式

- **全貌链接**：`详见 [登录规则](business-rules/auth/login.md)`，一键跳到完整规则
- **变更 diff**：`本次变更：新增账号锁定（连续失败 5 次 → 锁定 30 分钟）`，一眼看清改动

## 结构化原则参考：OKF

OKF（Open Knowledge Format）是 Google Cloud 2026 年发布的开放规范——Markdown + YAML 文件头，对人友好、对 Agent 友好，`cat` 即读、`git clone` 即分发。

OKF 本身为数据资产设计，三个结构原则恰好对应需求文档的核心问题：

| OKF 原则 | 解决的问题 |
|---------|----------------|
| **一个概念一份文档**，描述该资产的完整当前状态 | 功能全貌不再散落在多份增量 PRD 里 |
| **结构化 YAML 文件头**，字段无歧义、工具可提取 | 元信息机器可读，无需解析正文散文 |
| **Git 仓库管理**，变更有 diff、有 log | 演进历史自动留存，无需在正文里维护"修改记录" |

组织方式：一个概念一个文件，Concept ID = 文件路径去 `.md`；`index.md` 供 Agent 导航，`log.md` 记变更，概念间 Markdown 链接互连。

## 业务规则结构化方式

### 以业务概念为单位的文档

不用版本化 PRD，改为常青文档——文件路径即概念 ID：

```
business-rules/
├── auth/
│   ├── login.md          # 登录校验（字段、错误码、锁定策略）
│   └── token-refresh.md  # Token 刷新与过期规则
├── pricing/
│   └── coupon.md         # 优惠券规则（互斥、门槛、叠加）
└── order/
    └── state-machine.md  # 订单状态机（含退款条件）
```

每次迭代更新对应文档，git commit 记录变更，历史通过 git log 查看。

### 粒度如何选择？

"业务概念"的边界不绑定大小，判断原则：

- **独立覆盖一组完整规则，具有单一变更原因** — 核心 AC 在 5-15 条，总是一起改的不该拆，总是分开改的不该合
- **对 PM 有意义** — 对应一个能说清的完整规则点，而非技术实现细节

| 粒度 | 示例 | 问题 |
|------|------|------|
| 太粗 | `subscription.md`（覆盖定价、优惠、退款全部） | 变更原因不一致 |
| 太细 | `coupon-expiry.md`（仅券有效期） | 无法独立出有意义的 AC |

### YAML 文件头

```yaml
---
id: RULE-AUTH-001
title: 用户邮箱密码登录
status: approved          # draft | approved | deprecated
owner: pm-alice
updated: 2025-06-10
related:
  - RULE-AUTH-002          # Token 刷新
  - SPEC.md#auth-login     # 对应可执行 Spec
---
```

- `id`：稳定引用，SPEC 和测试用例可精确指向
- `status`：`deprecated` 告诉 Agent 规则已下线
- `related`：显式链接关联文档，Agent 沿链路找完整上下文
- 脚本可扫描文件头，自动检查 approved 规则是否有对应 SPEC

### 正文结构化

```markdown
## 异常处理

| 场景 | HTTP | 提示文案 |
|------|------|---------|
| 邮箱或密码不正确 | 401 | "邮箱或密码错误" |
| 密码少于 8 位 | 422 | "密码至少 8 位" |
| 连续失败 5 次 | 429 | "账号已锁定，30 分钟后重试" |

## 验收标准

AC-1: 正确凭据 → 200 OK，响应含 access_token、refresh_token、user 对象
AC-2: 邮箱不存在 → 401，message = "邮箱或密码错误"（不暴露"邮箱不存在"）
AC-3: 连续失败 5 次 → 429，账号锁定 30 分钟
```

异常处理单独列表：最容易被散文略过，表格让每个边界显式可见。

### 行内约束标记

```markdown
- 错误提示 [MUST NOT] 区分"邮箱不存在"和"密码错误"，防止账号枚举攻击
- Token [MUST] 写入 EncryptedSharedPreferences，[MUST NOT] 明文存储
- [CONSTRAINT:perf] 登录接口 P99 响应时间 < 500ms
```

| 标记 | 含义 | 强制程度 |
|------|------|---------|
| `[MUST]` | 必须实现 | 硬性要求，有 AC 覆盖 |
| `[MUST NOT]` | 明确禁止 | 安全/合规红线 |
| `[SHOULD]` | 建议实现 | 不做需说明原因 |
| `[CONSTRAINT:类型]` | 非功能约束 | 按性能/安全/合规分类 |

Agent 读到 `[MUST NOT]` 知道是红线，读到 `[SHOULD]` 知道时间紧时可以降级。

### Git 管理

```bash
# 查看登录规则的完整演进历史
git log --oneline business-rules/auth/login.md

d4a83bc  增加账号锁定机制（连续失败 5 次）
b12f45a  初始版本：邮箱密码登录，JWT Token
```

规则变更时，CI 可检测引用此规则的 SPEC，提示更新。

## 实施难点与建议

### 难点一：对 PM 不够友好

PM 可直接维护或通过 Agent 辅助（第三章已详述）。额外思路：md文件展示成wiki，支持通过wiki的编辑，类似LLM Wiki。

### 难点二：存量文档量大

**建议：新旧双轨，触碰则改。**

- 存量 PRD 保持现状，暂不动
- 新增功能严格执行结构化格式
- 迭代变更触碰到哪个功能，就补一份结构化文档整理当前全貌。优先从核心流程开始（登录、支付先行），长尾后补。

### 难点三：改造幅度选择

按团队接受度分级：

| 做法 | 内容 | 效果 |
|------|------|------|
| **最小可行** | 每个概念文档末尾有结构化 AC 块 | Agent 输出质量显著提升 |
| **中等** | AC 块 + YAML 文件头 + 异常处理表格 | 覆盖 Agent 最需要的信息 |
| **完整** | 常青文档 + 结构化正文 + Git + Agent 维护 | 完整的结构化资产体系 |

## 与下游的关系

|  | 结构化业务规则 | SPEC.md | 测试用例 |
|---|---|---|---|
| 主导方 | PM | 开发 / AI | QA |
| 描述对象 | "做什么"，业务全貌 | "怎么做对"，技术边界 | "做对没有"，可执行验证 |
| 包含内容 | 背景、动机、业务 AC 意图 | 前置条件、流程、可测试 AC | 具体输入、预期输出、执行方式 |

两者的 AC 是递进关系：业务规则 AC 是 PM 的 5-10 条业务意图，SPEC AC 是开发拆出的 20-50 条可验证技术预期。

### 三方 ID 引用联动

```
业务规则文档（PM）          SPEC.md（开发）            测试用例（QA）
  id: RULE-AUTH-001          references:                tc_id: TC-AUTH-002
                                   rule: RULE-AUTH-001    covers: RULE-AUTH-001
                              测试用例:                    / SPEC.md#AC-2
                                   AC-2 → TC-AUTH-002
```

### 流转路径

```
PRD（变更描述）
  ↓ Agent 读取 PRD + 对应业务规则文档（已有全貌）
  ↓ 生成 SPEC 草案
  ↓ 人工评审
  ↓ SPEC 定稿
  ↓ 开发实现
  ↓ 更新自动化测试
```

### 为什么不是三合一？

不是注定不能三合一。当前分立的根源更多是消费习惯差异：PM 维护规则时不想被技术 AC 细节淹没，开发写 SPEC 时不想在散文里翻找边界，QA 写用例时需要可执行的断言而非意图描述。三者共享同一套业务语义，但各自读取和编辑的节奏不同，强行合并会让各方工作都变沉。

ID 引用在保留分工舒适区的同时建立可追溯关联——这已经是轻量级的三合一。未来随着消费习惯演化和工具链成熟，结构化形式可以进一步收敛。
