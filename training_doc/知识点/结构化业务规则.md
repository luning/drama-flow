# 结构化业务规则 — 从增量描述到唯一事实来源

---

## PRD 天然描述增量

PRD 天然是增量文档——v1.0 写登录，v1.2 加"记住我"，v2.0 改 Token 策略。这是 PM 与下游协作的自然模式，下游消费增量信息最高效。

但这也意味着当前全貌散落在多份历史 PRD 中，没有一份文档直接呈现某功能此刻支持的所有场景和约束：

```
PRD v1.0：邮箱密码登录，成功跳首页，失败提示错误
PRD v1.2：增加"记住我"，Token 持久化 7 天
PRD v2.0：密码安全升级，最少 8 位，失败 5 次锁定

读到的 v2.0 → 知道"密码最少 8 位"
不知道 → "邮箱不存在时错误文案是什么"（v1.0 的细节）
```

人与增量 PRD 的协作没有大问题；但 Agent 只读到被塞进上下文的片段，无法主动追溯历史。

**结构化业务规则的目标**：把为增量协作准备的叙事，同步沉淀一份为 Agent 准备的常青文档——让每个业务概念有且只有一个**唯一事实来源（Single Source of Truth）**。

---

## 不是所有需求都需要结构化

不是所有产品知识都需要结构化。真正需要结构化管理的，是"业务规则"——那些逻辑密度高、边界清晰、错过就是线上事故的内容。**这类规则有两个共同特征：无法通过使用产品直观穷举，以及恰好是测试的重心。** 当你没法在页面上"点一圈"就看清所有分支，当 QA 的测试用例天然在覆盖这些边界——这就是该结构化的信号。

PRD 中常见的内容并非同一性质，是否结构化取决于内容本身：

| 类型 | 特征 | 示例 |
|------|------|------|
| **业务规则** | 边界清晰，逻辑密集，可穷举，漏掉就是 bug | 失败 5 次锁定 30 分钟、优惠券与满减不可叠加、退款需先审核 |
| **探索方向** | 方向未定，还在讨论，随时可能推翻 | "要不要做社交？""先跑两周数据再看" |
| **流程路径** | PRD 正文中已有完整表达，Agent 容易理解 | "打开 App → 首页 → 点短剧 → 播放" |
| **界面调整** | 设计稿/代码里已有全貌，PM 只描述改动增量 | "按钮改成主色""间距加大 4px" |

只有业务规则需要结构化，这部分内容很多PM也有维护全貌文档的内在需要，只是还不够规范化或范围不完整。

## PRD 与业务规则的协同

### 全景定位

结构化业务规则不替代 PRD、SPEC.md 和测试用例，四者各有分工：

| | PRD | 结构化业务规则 | SPEC.md | 测试用例 |
|---|---|---|---|---|
| 主导方 | PM | PM | 开发 / AI | QA |
| 描述对象 | "这次改什么"，变更叙事 | "当前规则是什么"，业务全貌 | "怎么做才算对"，技术边界 | "有没有做对"，可执行验证 |
| 包含内容 | 背景、动机、影响面 | 异常场景、业务 AC 意图 | 前置条件、流程、可测试的 AC | 具体输入、预期输出、执行方式 |

流转路径：

```
PRD（变更描述）
  ↓ Agent 读取 PRD + 对应业务规则文档（已有全貌）
  ↓ 生成 SPEC 草案
  ↓ 人工评审定稿
  ↓ 开发实现
  ↓ 更新测试用例
```

**为什么不是三合一？** PM 对规则正确性负责、开发对实现边界负责、QA 对覆盖充分性负责。合并为一份文档意味着三个角色的改动互相干扰。ID 引用在保留各方自治权的同时建立可追溯关联——工具可检测"规则变更后 SPEC 是否更新""AC 是否都有对应测试用例"，但不强制三方用同一个编辑器、同一套语法。

```
业务规则文档（PM）          SPEC.md（开发）            测试用例（QA）
  id: RULE-AUTH-001          references:                tc_id: TC-AUTH-002
                                    rule: RULE-AUTH-001    covers: RULE-AUTH-001
                               测试用例:                    / SPEC.md#AC-2
                                    AC-2 → TC-AUTH-002
```

### 双轨协作

```
PM 编写 PRD（变更叙事）
    │
    ├─→ 同步维护业务规则文档（规则全貌）
    │
    ↓
PRD 引用规则全貌链接 + 变更 diff
```

> **工作流示例：**
> ```
> PM 写 PRD v2.1："登录失败 5 次后锁定账号，锁定 30 分钟"
>   ↓ 同步更新 login.md，新增异常行、AC、更新文件头
>   ↓ 在 PRD 末尾附上：详见 [登录规则](business-rules/auth/login.md)
>   ↓ 本次变更：新增账号锁定（连续失败 5 次 → 锁定 30 分钟）
> ```
> Agent 可辅助格式化、提交 git，但 PM 主导规则内容的产出。

**PRD 中引用规则的方式：**
- **全貌链接**：`详见 [登录规则](business-rules/auth/login.md)`，一键跳到完整规则
- **变更 diff**：`本次变更：新增账号锁定（连续失败 5 次 → 锁定 30 分钟）`，一眼看清改动

**测试视角：** QA 的测试用例本质上就是在校验业务规则——一个场景有多少个 AC，测试就应该有多少条用例。结构化业务规则把规则显式化之后，AC 可以被测试框架直接消费。这不仅是 PM 和开发的对齐，也是 PM 和测试的对齐。

## 业务规则结构化实操指南

### 参考标准：OKF

OKF（Open Knowledge Format）是 Google Cloud 2026 年发布的开放规范——Markdown + YAML 文件头，`cat` 即读、`git clone` 即分发，对人友好、对 Agent 友好。

OKF 的三个结构原则恰好对应本文做法：

| OKF 原则 | 本文做法 |
|---------|----------------|
| **一个概念一份文档**，描述该资产的完整当前状态 | 一个业务概念一份文件 = SSoT |
| **结构化 YAML 文件头**，字段无歧义、工具可提取 | 元信息机器可读，无需解析正文散文 |
| **Git 仓库管理**，变更有 diff、有 log | 演进历史自动留存，无需在正文里维护"修改记录" |

### 核心原则

每个业务概念有且只有一份文档，作为该概念的唯一事实来源（SSoT），覆盖完整行为，用 Git 记录演进历史。

### 以业务概念为单位的文档

文件路径即概念 ID：

```
business-rules/
├── auth/
│   ├── login.md          # 邮箱密码登录的 SSoT
│   ├── token-refresh.md
│   └── password-reset.md
├── pricing/
│   └── coupon.md         # 优惠券规则（互斥、门槛、叠加）
└── order/
    └── state-machine.md  # 订单状态机（含退款条件）
```

每次迭代更新对应文档，git commit 记录变更，历史通过 `git log` 查看。

### 粒度如何选择？

"业务概念"的边界不绑定大小，判断原则：

- **独立覆盖一组完整规则，具有单一变更原因** — 核心 AC 在 5-15 条，总是一起改的不该拆，总是分开改的不该合
- **对 PM 有意义** — 对应一个能说清的完整规则点，而非技术实现细节

| 粒度 | 示例 | 问题 |
|------|------|------|
| 太粗 | `auth.md`（整个认证模块） | AC 太多太杂，变更原因不一致 |
| 合适 | `login.md`（邮箱密码登录） | 完整用户场景，AC 独立可验证 |
| 太细 | `password-validation.md`（密码格式校验） | 无法独立出有意义的 AC，是 login 的子逻辑 |

### YAML 文件头

```yaml
---
id: RULE-AUTH-001
title: 用户邮箱密码登录
status: approved          # draft | approved | deprecated
owner: pm-alice
updated: 2025-06-10
related:
  - RULE-AUTH-002          # Token 刷新
  - SPEC.md#auth-login     # 对应可执行 Spec
---
```

- `id`：稳定引用，SPEC 和测试用例可精确指向
- `status: deprecated`：告诉 Agent 规则已下线，不应实现
- `related`：显式链接关联文档，Agent 沿链路找完整上下文
- 脚本可扫描文件头，自动检查 approved 规则是否有对应 SPEC

### 正文结构

```markdown
## 业务流程

1. 用户输入邮箱 + 密码，提交 POST /api/auth/login
2. 服务端校验：通过 → 签发 Access Token（2h）+ Refresh Token（7d）；失败 → 返回错误
3. 登录成功后跳转首页

## 异常处理

| 场景 | HTTP | 提示文案 |
|------|------|---------|
| 邮箱或密码不正确 | 401 | "邮箱或密码错误" |
| 密码少于 8 位 | 422 | "密码至少 8 位" |
| 账号被禁用 | 403 | "账号已停用，请联系客服" |
| 连续失败 5 次 | 429 | "账号已锁定，30 分钟后重试" |

## 验收标准

AC-1: 正确凭据 → 200 OK，响应含 access_token、refresh_token、user 对象
AC-2: 邮箱不存在 → 401，message = "邮箱或密码错误"（不暴露"邮箱不存在"）
AC-3: 连续失败 5 次 → 429，账号锁定 30 分钟
```

异常处理单独列表：最容易被散文略过，表格让每个边界显式可见。

### 行内约束标记

```markdown
- 错误提示 [MUST NOT] 区分"邮箱不存在"和"密码错误"，防止账号枚举攻击
- Token [MUST] 写入 EncryptedSharedPreferences，[MUST NOT] 明文存储
- [CONSTRAINT:perf] 登录接口 P99 响应时间 < 500ms
```

| 标记 | 含义 | 强制程度 |
|------|------|---------|
| `[MUST]` | 必须实现 | 硬性要求，有 AC 覆盖 |
| `[MUST NOT]` | 明确禁止 | 安全/合规红线 |
| `[SHOULD]` | 建议实现 | 不做需说明原因 |
| `[CONSTRAINT:类型]` | 非功能约束 | 按性能/安全/合规分类 |

Agent 读到 `[MUST NOT]` 知道是红线，读到 `[SHOULD]` 知道时间紧时可以降级。

### Git 管理

```bash
# 查看登录规则的完整演进历史
git log --oneline business-rules/auth/login.md

d4a83bc  增加账号锁定机制（连续失败 5 次）
b12f45a  初始版本：邮箱密码登录，JWT Token
```

规则变更时，CI 可检测引用此规则的 SPEC，提示更新。

## 推行策略与常见难点

### 难点一：对 PM 不够友好

PM 可直接维护或通过 Agent 辅助（上一章已详述）。额外思路：md 文件展示成 Wiki，支持通过 Wiki 直接编辑。

### 难点二：存量文档量大

**新旧双轨，触碰则改。**

- 存量 PRD 保持现状，暂不动
- 新增功能严格执行结构化格式
- 迭代变更触碰到哪个功能，就补一份结构化文档整理当前全貌

优先级从核心流程出发（登录、支付、核心业务链路先行），长尾功能后补。

### 难点三：改造幅度选择

按团队接受度分级：

| 做法 | 内容 | 效果 |
|------|------|------|
| **最小可行** | 每个概念文档末尾有结构化 AC 块 | Agent 输出质量显著提升 |
| **中等** | AC 块 + YAML 文件头 + 异常处理表格 | 覆盖 Agent 最需要的信息 |
| **完整** | 常青文档 + 结构化正文 + Git + Agent 维护 | 完整的结构化资产体系 |
