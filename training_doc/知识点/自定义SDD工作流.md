---

> 标准 SDD 流程（Explore → Propose → Execute → Verify → Archive）解决的是"不忘记做什么"。  
> 它有意留白了很多判断——**它告诉 Agent 何时做，但没有告诉 Agent 怎么才算做好**。  
> 自定义的本质是：把你在口头上反复说的判断，变成工作流里的必经节点。

---
## 什么时候需要自定义

自定义有成本——写 Skill、维护状态机、调试检查点。判断是否值得，先问一个问题：

**这个判断需要持续执行，还是只是这次提醒一下？**  
如果只是提醒，写进 memory 或 CLAUDE.md 就够了。如果需要持续执行，才值得编码进工作流。

### 值得自定义的信号

**你在口头上重复说同一句话。**  
"你改完要自己跑一遍测试"、"CR 之前先过一下这个清单"——任何你说了超过三次的提醒，都是一个等待被编码的自定义节点。

**同类错误反复出现。**  
Agent 总是在同一个地方失败（实现完成但 AC 未完全覆盖，或 CR 总是漏看某类问题），说明标准流程在这里缺少一个强制检查。

**一个阶段的产出质量影响下游所有步骤。**  
设计文档写得模糊 → 实现偏了 → CR 发现 → 返工，整个链条重来。这类高代价的"质量门"值得在状态转移前加一道检查。

**多人协作时出现判断不一致。**  
不同的人触发同一个流程，产出标准不同。自定义可以把"我们团队认为合格的标准"写进工作流，而不是靠每次口头对齐。

## 自定义的三种方式

所有自定义，无论多复杂，都是在状态机的某条边上做文章。有三种基本操作：

### 方式一：插入前置门（Pre-condition Gate）

在状态 A → B 的转移前，插入一个必须通过的检查。检查不通过，状态不转移。

```
┌──────────┐              ┌──────────┐
│ EXECUTED │ ──[CR门]──▶  │ VERIFIED │
└──────────┘              └──────────┘
```

**适用场景**：下游步骤严重依赖上游质量，早发现比晚发现便宜得多。  
**典型例子**：独立 CR 通过前不能进入 Verified；设计文档完整才能开始实现。

### 方式二：插入反向弧（Feedback Arc）

检查发现问题时，把状态退回更早的阶段，而不是在当前阶段原地打转。

```
┌──────────┐    发现设计问题    ┌────────────────┐
│ EXECUTED │ ──────────────▶  │ DESIGN_BLOCKED │
└──────────┘                  └───────┬────────┘
                                      │ 人类决策
                                      ▼
                              返回 DESIGN 修改，
                              或缩小实现范围
```

**适用场景**：实现阶段才发现设计问题，需要明确的机制让 Agent 停下来，而不是带着问题硬做。  
**典型例子**：实现时发现 spec 有漏洞，写入 `design-blocker.md` 触发阻断状态，等人类决策后再继续。

### 方式三：旁路触发（Side Effect）

不阻塞主流程，但在特定事件后触发额外动作。

```
┌──────────┐
│ ARCHIVED │ ──▶ 主流程结束
└──────────┘
      │
      └──▶ [旁路] 对话提炼 → 更新 Harness
```

**适用场景**：记录、学习、持续改进类的动作——不应该阻塞任务交付，但每次执行都在积累价值。  
**典型例子**：Archive 后触发对话提炼，把这次学到的东西沉淀进 EXPERIENCE.md。

## 示例一：独立 CR Agent 作为合入门

### 问题

同一个 Agent 做实现，再做 CR，等于自己审自己。它倾向于为自己的设计决策辩护，而不是真的审视它们。表现症状：CR 总是通过，但合入后才发现问题。

### 自定义方案

在 EXECUTED → VERIFIED 之间插入一个**独立上下文的 CR Agent** 作为前置门。

关键设计原则：**CR Agent 不共享实现阶段的任何上下文**——它只拿 SPEC（验收标准）、CR Request（变更摘要）、核心 diff，不知道实现时做了哪些妥协，才能真正独立判断。CR Agent 的职责边界越清晰，它的输出越可信；不要因为"既然有 CR 了"就把所有质量检查都堆进去。

```
EXECUTED
    │
    ▼
生成 cr-request.md（实现 Agent 写：做了什么、为什么这样做、哪里不确定）
    │
    ▼
CR_PENDING → 独立 CR Agent 执行（新上下文窗口，只读 SPEC + cr-request + diff）
    │
    ├── 通过 ──────────────────────────▶ VERIFIED
    ├── 有条件通过（需 follow-up）──▶ VERIFIED（带待办）
    └── 不通过 ────────────────────────▶ NEEDS_REWORK → 返回 EXECUTED
```

### 实现

**状态感知**：

```bash
# cr-gate.sh <change-name>
CHANGE_DIR="openspec/changes/$1"

if [ -f "$CHANGE_DIR/cr-result.md" ]; then
  VERDICT=$(grep -m1 "^\*\*" "$CHANGE_DIR/cr-result.md" | tr -d '*')
  echo "{\"state\": \"cr_done\", \"verdict\": \"$VERDICT\"}"
elif [ -f "$CHANGE_DIR/cr-request.md" ]; then
  echo '{"state": "cr_pending", "next": "run independent CR agent"}'
else
  echo '{"state": "executed", "next": "generate cr-request.md"}'
fi
```

**CR Request 模板**（实现 Agent 填写）：

```markdown
# CR Request: <change-name>

## 变更摘要
<!-- 三句话：做了什么、为什么这样做、主要影响范围 -->

## 关键设计决策
<!-- 实现过程中做的 2-3 个非显而易见的选择，及选择理由 -->

## 重点关注区域
<!-- 你自己不确定的地方，主动列出来 -->

## diff 范围
<!-- git diff --stat 的输出 -->
```

**CR Agent Prompt 核心约束**：

```markdown
你是独立代码审查者，没有参与这次功能的设计和实现。

输入：SPEC.md、cr-request.md、核心 diff
不要读取：实现过程中的任何对话记录

检查两件事：
1. AC 覆盖：逐条对照 SPEC.md，标注覆盖状态和代码位置
2. 可疑设计：
   - 分层违规（Service 直接操作 DB？路由层含业务逻辑？）
   - 共享可变状态（绕过 Store/ViewModel 的全局变量？）
   - 接口向后兼容性
   - 未处理的 None/null 值
   - 单文件超 300 行、函数超 80 行、大段重复代码

结论：通过 / 有条件通过 / 不通过
写入：cr-result.md
```

## 示例二：对话提炼——把每次会话变成 Harness 优化机会

### 问题

每次会话结束，你脑子里都有几条"这次 Agent 不应该这样"或"这个方式很有效"的判断。但这些判断通常第二天就消失了，或者停在 memory 某个文件里再也没被用上。

结果是：每次对话学到东西，但 Harness 没有进化。同样的错误下次还会出现。

### 自定义方案

在 Archive 后或每天收工时，触发一个**对话提炼**旁路。由 Agent 主动回顾本次会话，按 Harness 层级提炼可编码的优化点，并**立即执行**"立即可做"的项。

这是旁路触发，不是强制门——不阻塞交付，但每次执行都在给 Harness 喂养原材料。

### 提炼 Skill

```markdown
---
name: extract-harness-insights
triggers: ["提炼", "回顾对话", "harness 优化"]
---

回顾本次对话，按以下层级扫描，找出**可被编码**进 Harness 的信号。

扫描原则：只提炼能写进 settings.json / CLAUDE.md / EXPERIENCE.md / Skill / Hook 的内容。
不记录这次任务特有的临时状态，不记录泛泛的"注意 X"。

**L1 权限与工具**
这次对话里，你反复询问某个操作权限（→ 加进 allowlist）？
你用错了某个工具（→ 需要优化工具描述）？

**L2 任务边界**
用户说"你改了不该改的地方"？
实现偏离了 AC 范围，导致返工（→ Execute Skill 加强制读 SPEC 步骤）？

**L3 工程决策**
用户纠正了一个有历史原因的设计决策（→ 写进 ADR 或 EXPERIENCE.md）？
你引入了团队明确排除过的方案（→ 补充 ADR）？

**L4 跨会话状态**
你"忘记"了上次会话的决策（→ 加收尾写进度的步骤）？
你宣布"完成"但 AC 未逐条验证（→ 加完成前的 AC 自检步骤）？

**L5 经验沉淀**
发现了新陷阱，用户确认是普适规律（→ 写进 EXPERIENCE.md）？
某种做法获得正面确认，值得推广（→ 写进 Skill 或 CLAUDE.md）？

输出格式：每条优化点注明"应改哪个文件"，并分类：
- **立即可做**（5 分钟内能改完）→ 当场执行，不只是记录
- **下次迭代**（需要设计，记录到 insights/）
- **暂时观察**（等第二次出现再编码）

写入：openspec/insights/YYYY-MM-DD-<change-name>.md
```

### 关键约束：提炼不执行等于没提炼

提炼出的优化点超过 5 条时，只执行影响最大的前 2 条。"立即可做"的项，提炼结束前必须改完对应文件——insights 文件不是记录"打算做"的地方。

**如果你发现自己从来不触发这个 Skill**，说明摩擦太高——把它加进 Archive Skill 的最后一步，变成弱强制（不阻塞，但提示"要不要提炼一下？"）。

## 示例三：跨会话握手——让长任务在会话切换时不丢状态

### 问题

标准 SDD 流程天然支持跨会话（工件存在就能恢复阶段）。但有一种失败模式它没有处理：

**Agent 知道自己在哪个阶段，但不知道这个阶段做到哪了。**

比如一个复杂功能的 Execute 阶段跨了三次会话。第二次会话打开，Agent 扫描目录，看到 `design.md` 存在、`cr-request.md` 不存在，判断"在 Execute 阶段"，然后从头重新分析代码——做了一堆上次已经做过的判断，甚至做出了和上次不同的决策。

根本原因：**阶段内的进度和决策没有被持久化**，只有阶段完成与否被持久化了。

这个问题在以下情况特别明显：
- Execute 阶段跨越多个会话（功能复杂、多日任务）
- 中途遇到阻塞，人类介入处理，然后 Agent 继续

### 自定义方案

在 Execute 阶段插入**会话握手**机制：每次会话结束前写 `handoff.md`，下次会话开始时强制读它。

这是两个旁路触发的组合——写（收工时）和读（开工时），形成一个跨会话的信息桥。

```
上次会话结束
      │
      ▼ [旁路：写 handoff.md]
   ┌────────────────────────────────────────┐
   │ 已完成：实现了 AC-001、AC-002           │
   │ 进行中：AC-003 的 DB query 写完了       │
   │         还差：Service 层调用 + 测试     │
   │ 关键决策：选了方案 B，原因是...          │
   │ 下一步：打开 service.py 第 42 行继续    │
   └────────────────────────────────────────┘
                     │ （会话切换）
                     ▼
下次会话开始：强制读 handoff.md，从上次停下的地方继续
```

### 握手文件格式

`handoff.md` 必须简短——超过 20 行就说明写的人在记流水账而不是提炼关键信息：

```markdown
# Handoff: <change-name> — <日期 时间>

## AC 进度
- [x] AC-001: 用户列表接口 ← service.py:58
- [x] AC-002: 分页参数校验 ← schema.py:23
- [ ] AC-003: 错误状态码映射 ← 进行中
- [ ] AC-004: 单元测试

## 进行中任务的确切位置
AC-003：service.py 的 get_drama_list() 写完了。
下一步：打开 api/drama.py，在 @router.get 函数里加 try/except，把 Service 异常映射成 HTTP 状态码。

## 本次会话的关键决策
- 错误处理选择在路由层统一捕获，理由：profile 模块用的同一个模式，保持一致

## 未解决的问题
- watch_record 表的索引暂时没加，等 AC-003 跑完测试再看性能
```

### Execute Skill 里的握手协议

```markdown
## 会话开始时

检查 handoff.md 是否存在：
- 存在 → 读取，从"进行中任务的确切位置"继续，不要重新分析代码
- 不存在 → 从 design.md 和 AC 列表重建上下文，然后继续

## 会话结束时（即使 Execute 没完成）

更新 handoff.md：
- 用 [x] 标注已完成的 AC
- 写清楚进行中任务的确切位置（文件名 + 行号 + 下一步要做什么）
- 记录本次会话的关键决策（不超过 3 条）
- 列出未解决的问题

不更新 handoff.md 就不允许关闭会话。
```

### 什么时候触发

这个机制对**单次会话能完成的任务没有价值**——会徒增摩擦。

| 情况 | 做法 |
|------|------|
| 预计 1 小时内能完成 Execute | 不写 handoff.md |
| Execute 开始后发现比预期复杂，本次无法完成 | 会话结束前补写 |
| 任务从一开始就预计跨多天 | Execute Skill 开头就写初版 handoff.md |
| 人类接手 Agent 处理阻塞后交还 | 人类在 handoff.md 里记录自己做了什么 |

最后一种情况是这个机制最有价值的地方——**人类的干预也能以同样的格式被 Agent 消费**。人类不需要在新会话里口头解释"我刚才做了什么"，只需要在 handoff.md 里写一行，Agent 就能接着做。

## 设计原则与避免过度工程

### 设计原则

**让检查点可以跳过，但跳过要留痕。**  
紧急修复、原型验证等情况下，允许绕过强制门——但跳过时必须写理由。跳过不等于没有记录；下次复盘时能看到"这次为什么跳过了 CR"，而不是完全不知道这里曾经有一个检查。

```bash
# 跳过 CR，但记录原因
bash cr-gate.sh my-feature --skip "hotfix: prod down, 用 pair programming 代替 CR"
# → 写入 cr-skipped.md，状态转移但留下可追溯的原因
```

**检查点的输出要比输入简单。**  
CR Agent 的输出（cr-result.md）应该比它的输入（SPEC + diff）更精炼、更可操作。衡量标准：读完输出，你能在 30 秒内判断"通过 / 不通过"吗？如果不能，输出格式需要优化。

**能用工具自动化的检查，不要变成工作流步骤。**

| 判断类型 | 正确的处理方式 |
|---------|-------------|
| 变量命名规范 | linter / pre-commit hook |
| 设计 Token 合规 | 检查脚本 + CI |
| AC 是否覆盖 | Skill（需要语义理解） |
| 架构决策是否合理 | 独立 CR Agent（需要上下文判断） |

工具比 Agent 更快、更稳定、更便宜。把语义判断留给 Agent，把机械检查交给工具。

### 避免过度工程

自定义 SDD 最常见的失败模式是**把所有"应该怎么做"都变成强制门**，最终工作流比直接做事还慢。

**判断一个检查点是否值得加，问三个问题：**

1. **这个检查的成本，比它能预防的返工小吗？**  
   CR 检查点：花 5 分钟，预防"实现完才发现方向错了"的 2 小时返工——值得。  
   "提交前确认变量名格式"：花 3 分钟，linter 1 秒能检查——不值得。

2. **这个判断需要 Agent 做，还是工具做？**  
   能自动化的，不要占用工作流节点。

3. **这个检查点，如果没有，会造成什么后果？**  
   "最多返工一次"→ 可选提醒，不需要强制门。  
   "浪费多人多天的工作"→ 值得是强制门。

**强制人类参与的节点，一个变更生命周期不应超过 3 个：**
1. 设计确认（方向对不对）
2. CR 决策（实现对不对）
3. Archive 确认（如果有不可逆操作）

超过 3 个，流程本身的摩擦会超过它带来的价值。

**识别过度工程的症状：**
- 每次任务都要经过 5 步以上的人类确认
- Skill 文件超过 300 行，Agent 开始"选择性阅读"
- insights 文件越积越多，但 Harness 本身没有变化
- 团队成员开始绕过流程"直接做"

最后一条是最清晰的信号——**如果人们在绕过你的工作流，说明摩擦已经超过了价值**。这时候应该精简，而不是补更多约束。

---

> **一句话总结**：自定义 SDD 工作流不是把流程做得更复杂，而是把你反复说的判断变成一次性编码。  
> 发现这个信号时，删比加更重要。
