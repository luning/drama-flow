> **Harness 是模型周围的工程组件集合（System Prompt、Tool、Middleware、Skill、Sub-Agent、Memory 等）。在复杂项目中应用 Harness Engineering 时，可能会遇到各种疑难问题，以下对部分疑难杂症做了总结。**

---

## 操作性问题

> 使用者视角——在项目中应用 Harness 时遇到的坑，每个问题按"症状 → 诊断 → 应对策略"展开。

---

### Q1：遗留代码没有测试，Agent 在"盲飞"

**症状**：遗留代码库完全没有单元测试，Agent 改一处不知道破坏了多少处，自我修复能力失效。

**诊断**：缺乏"安全网"——Agent 无法感知改动的影响范围，修改后的回归完全靠猜。

**应对策略**：

1. **黄金大师模式（Characterization Testing）**：在动刀前，先让 Agent 为旧函数写一组"快照测试"。记录下当前代码在 10 组不同输入下的输出——**即使输出是错的也记录下来**。这就是你的"黄金大师"——改动后任何快照变化都需要人类解释。
2. **两帽子原则（Two Hats）**：严禁重构与功能实现混在一起。
   - 阶段一：仅进行测试补全和微重构，验证通过。
   - 阶段二：进行需求开发。
   - 混在一起 → 出问题无法定位是谁的锅。

---

### Q2：后端单测全绿，但移动端崩溃

**症状**：Agent 修改了后端接口，后端单元测试全部通过，但移动端 App 崩溃或 CDN 缓存穿透。

**诊断**：跨层上下文盲区——Harness 只有局部观测能力，缺乏全栈视角。Agent 不知道自己的修改会影响哪些上游消费者。

**应对策略**：

1. **全栈遥测注入**：Harness 必须能够自动收集多端日志（Appium 崩溃日志、Nginx 报错日志）。当集成测试失败时，将这些日志"喂"给 Agent，提示其从全栈角度排查。
2. **状态挡板录制（VCR）**：对 CDN 和第三方服务使用流量录制工具。Agent 修改后，在模拟环境中回放流量，检测响应头（Headers）是否发生了非预期变更。

### Q3：Agent 污染数据库真实数据，测试环境不可复用

**症状**：测试过程中 Agent 修改了数据库中的真实遗留数据，后续测试结果不可信。

**诊断**：遗留系统难以彻底容器化，缺乏廉价的隔离沙盒。

**应对策略**：

1. **DB 事务拦截**：在 Harness 的 MCP Server 层，为 Agent 的写操作强制包装 `BEGIN` 和 `ROLLBACK`。所有测试运行结束必须回滚。
2. **数据影子表**：为高危表建立副本，让 Agent 仅在影子表上进行逻辑验证。

```
Agent 发 SQL 写操作
    → Harness 拦截，包装为：BEGIN → 原SQL → ROLLBACK
    → 结果返回给 Agent 用于验证
    → 真实数据零影响
```

### Q4：Skills 过多导致"工具幻觉"

**症状**：随着 Skills 越来越多（超过 50 个），Agent 开始出现工具选择错误——该查日志时调了删库工具，意图解析模糊。

**诊断**：工具集超过模型识别的临界值，选择空间过大导致意图匹配出错。

**应对策略**：

1. **动态工具注册**：根据 Agent 当前处理的文件目录（如 `android/` 或 `backend/`）动态加载对应的工具集，减少干扰项。不要一口气把所有工具都暴露。
2. **严格类型约束**：使用 Pydantic 或 TypeScript Interface 对所有 Skill 进行严格的参数限定——非法参数在调用前就被 Harness 拦截，不会到达 Agent。

### Q5：Agent 利用权限漏洞造成安全风险

**症状**：Agent 在处理遗留系统需求时，访问了不该访问的配置文件，泄露了敏感信息。

**诊断**：Agent 拥有过高的 Shell 权限或文件读写权限——默认给了太多。

**应对策略**：

1. **最小权限沙箱**：默认设置为只读。只有当 Agent 提出"由于需求需要，请求写权限"时，才通过 Harness 弹出人类审批。
2. **敏感信息过滤（Redaction）**：在 MCP Server 返回数据给 Agent 前，自动脱敏掉数据库密码、API Key 等字符串。

```
权限模型：
默认 → 只读（可以看代码、查日志）
请求写权限 → Harness 弹出审批 → 人确认 → 授权（有范围和时间限制）
敏感字段 → 永远不过 Agent 的手（在 Tool 层直接脱敏为 ***）
```

### Q6：Agent 删除了看起来没用但实际关键的旧代码

**症状**：Agent 为了满足新需求，删除了老代码里一行"看起来没用"但其实是处理特殊坏账逻辑的代码，导致旧功能静默出错。

**诊断**："部落知识"缺失——Agent 无法理解代码背后的历史背景。那行代码的存在理由不存在于代码本身，而存在于写它的人的记忆里。

**应对策略**：

1. **考古提示词策略**：要求 Agent 在删除任何存量代码前，必须先调用 `git blame` 溯源该行代码的原始 Commit ID 和关联任务。让 Agent 回答"这行为什么在这里"之后才能删。
2. **CONSTRAINTS.md 圣牛清单**：维护一份轻量级的约束文件，记录系统中不可触碰的"圣牛（Holy Cows）"逻辑——那些看起来怪但绝对不能改的业务规则。

### Q7：如何判断 Agent 的重构方案是合理还是过度？

**症状**：Agent 倾向于用现代写法完全覆盖掉稳定的旧逻辑，改动范围远超出需求本身，测试成本激增。

**诊断**：Agent 偏好"理想重构"而非"最小修改"——它不理解改动范围的隐性成本。本质上是因为 Agent 被允许在"生成"和"验证"之间一气呵成，没有中间检查点来限制其自由度。

**应对策略**：

1. **PEV 循环（Plan-Execute-Verify）**：将 Agent 的工作拆为三个阶段，每个阶段之间有显式门禁：
   - Plan：Agent 必须先写出修改计划（改哪些文件、改多少行），由 Harness 或人类审批范围。
   - Execute：执行被计划严格限定。Harness 层在每次 tool call 前检查——该操作是否在审批过的计划范围内？超出范围则拦截。
   - Verify：验证只检查计划中的验收标准是否达成。
   
   PEV 的核心是**在 Plan 阶段就压缩自由度**，而非在 Execute 阶段靠 prompt 劝 Agent"少改点"。

2. **方案 PK 机制**：强制 Agent 给出两份 Plan，而非两份代码：
   - 方案 A：最小入侵方案（加补丁），改动行数少
   - 方案 B：理想重构方案
   
   在 Plan 阶段由人类决策走哪条路，而非等代码写完了再比较。

### Q8：Agent 在遗留系统中找不到构建工具，陷入死循环

**症状**：Agent 反复尝试 `npm install` 但项目实际用 Ant 构建，连续失败浪费大量 token。

**诊断**：环境失配导致"Token 黑洞"——Agent 基于训练数据的默认假设（现代工具链）来处理老旧环境，屡试屡败。

**应对策略**：

1. **构建指令硬编码**：在 AGENTS.md 中明确屏蔽现代指令，强行指定 `./legacy_build.sh` 作为唯一构建入口。不让 Agent 自己猜。
2. **故障快速熔断**：设置 Harness 监控，如果 Agent 连续执行超过 3 次失败的 shell 命令，强制挂起任务并请求人工介入。

```
熔断规则：
shell 失败计数 > 3 次且相同命令
    → Harness 挂起任务
    → 通知人介入判断：环境问题？需求不清？工具不对？
```

### Q9：规范文档臃肿，Agent 选择性忽略规则

**症状**：随着项目推进，AGENTS.md 或 SDD 变得非常臃肿，Agent 开始选择性忽略某些规则。

**诊断**：上下文过载导致注意力弥散（Attention Drift）——长文档中关键规则被淹没在大量次要信息里。

**应对策略**：

1. **文档即地图（Maps, not Rules）**：减少长篇大论。将规范拆分为原子化的 Markdown 表格或 Mermaid 流程图。Agent 查表比读散文准确。
2. **上下文分区机制**：在 Harness 侧通过文件夹路由。例如，只有当 Agent 进入 `src/security/` 目录时，Harness 才把安全规范推送进上下文。

```
上下文按目录加载：
进入 backend/ → 注入后端规范
进入 android/ → 注入移动端规范
进入 src/security/ → 额外注入安全规范
→ 不在当前工作区的规范不占 token
```

### Q10：多步骤任务错误累积，最终成功率崩塌

**症状**：Agent 执行的每个步骤有 ~85% 的正确率，看起来"还行"，但 10 步整体任务只有 ~20% 的成功率。单个步骤检查都通过了，整体结果却一塌糊涂。

**诊断**：错误乘法效应（Compounding Error Cascade）——Agent 工作流缺少中间验证节点。前几步的小错误不被发现，后续步骤在错误基础上继续叠加，最终产出完全偏离。问题不在于单步准确率，而在于错误在步骤间被"保存"和"放大"。

**应对策略**：

1. **验证门禁（Validation Gates）**：在关键步骤之间插入自动化验证。每步输出经过校验后才进入下一步——这不是官僚流程，而是阻断错误滚雪球的工程手段。验证门禁可以是脚本断言、Schema 校验、或 LLM-as-Judge 的语义检查。
2. **早停熔断**：Harness 在检测到中间步骤的验证失败时，立即终止任务流并标记失败步骤，而非让 Agent 继续在脏数据上执行剩余步骤。避免"跑完才发现第一步就错了"的 token 浪费。

```
无门禁：Step1 → Step2 → Step3 → ... → Step10 → 最终验证（~20% 通过率）
有门禁：Step1 → [Gate] → Step2 → [Gate] → Step3 → ... → 最终验证（Gate 在早期就截断错误）
```

### Q11：长会话中初始规则逐渐失效

**症状**：会话开始时 Agent 严格遵守约束（如"必须用 TypeScript"），但到第 25 轮对话后，最近的 Python 代码 token 压过了初始 TypeScript 约束，Agent 开始悄悄输出 Python。

**诊断**：注意力衰减（Attention Decay）——在 Transformer 架构中，初始 system prompt 的注意力权重随对话增长而递减。当历史对话中出现了大量 Python 代码时，这些"近期的 Python token"在注意力机制中的权重远高于"远处的 TypeScript 规则"。Agent 并非"忘记"了规则，而是规则在注意力竞争中输了。

**应对策略**：

1. **上下文锚定（Context Pinning）**：不把关键约束只放在 system prompt 开头。将 prompt 结构化为：
   ```
   [System Prompt（角色定义）]
   → [历史对话]
   → [核心约束（Pinned，重复注入）]
   → [最新用户输入]
   ```
   核心约束紧贴在最新用户输入之前，利用近因效应（Recency Bias）确保约束始终处于注意力的高权重区。
2. **约束刷新**：Harness 每 N 轮自动将核心约束重新追加到上下文末尾，防止被不断增长的历史对话彻底淹没。与其靠初始位置争注意力，不如靠重复出现保持激活。

## Harness 设计反模式

> 维护者视角——Harness 配置本身的结构性问题。与操作性问题部分的区别：该部分是"Agent 出了什么问题"，这一部分是"你的 Harness 配置长了什么蛀虫"。定期用以下清单审计你的 Harness 配置。

---

### Bad Smell 自检清单

| Bad Smell | 症状 | 后果 | 怎么修 |
|-----------|------|------|--------|
| **过时假设（Stale Assumption）** | prompt 里写"模型不擅长 X，请先 Y"，但当前模型已能直接做 X | 增 token，可能误导模型绕远路 | 换模型版本时跑裸奔基线验证，确认规则是否仍有统计显著的提升 |
| **重叠规则（Rule Overlap）** | 同一约束同时出现在 system prompt、skill、hook 三层 | 难定位哪条真正生效，修改时容易遗漏层级，行为不一致 | 合并到约束最强的那一层，删除其余层级的重复 |
| **防御性膨胀（Defensive Bloat）** | 为防范罕见失败，规则列表越来越长 | prompt 臃肿，模型注意力分散，抓不住真正重要的约束 | 按实际频次统计，低频失败不加规则，宁缺毋滥 |
| **硬编码工作流（Hardcoded Workflow）** | "先读 A 再读 B 再改 C"写死，代码结构已变但流程未更新 | agent 按过时流程走，做无用功，浪费 token | 工作流写成意图描述而非步骤清单，让 agent 根据当前代码结构自行判断路径 |
| **万能 Prompt 补丁（Prompt-as-Duct-Tape）** | 遇到问题就往 prompt 加一句，而非在 tool/middleware 层修复 | prompt 越来越长，约束力没变强（论文证明 prompt-only 单独使用是退步的，-2.3 pp） | 优先在 tool/middleware 层做硬拦截，prompt 只作为最后手段 |
| **经验噪音（Experience Noise）** | 经验文件记录"曾有效但现在无效"的建议 | 误导 agent 采用过时方案，比没有经验更糟 | 每条经验标注时间戳和适用模型版本，定期清理失效条目 |
| **推理替代脚本（Reasoning-over-Scripting）** | prompt 里让 agent 推理校验"检查 X、Y、Z"，而 10 行脚本即可确定性完成 | 浪费 token 做编译器的事；推理有概率性可能漏检，脚本是确定性的不会漏 | 确定性校验交给脚本，推理能力留给真正需要判断的灰色地带 |

---

## Harness 维护原则

> Harness 不是在真空里运行的——它会老化、膨胀、被模型进化淘汰。这一章讨论 Harness 的本质特征和持续维护的方法论。

---

### 两类 Harness 内容

Harness 是在模型能力边界上的补丁，但并非所有补丁同质：

| 类型 | 特征 | 示例 | 可被模型进化替代？ |
|------|------|------|-------------------|
| **A. 架构/设计约束** | 代码分析不出来的决策理由、权衡、约定 | ADR（为什么选 SQLite 而非 PG）、模块边界约定、安全策略 | ❌ 不可。这些是"选择"，不是"推导"——代码只展示选了 SQLite，无法表达为什么不选 PG |
| **B. 代码重复型提示** | 复述代码已有的信息 | "调用 `get_user()` 传入 `user_id: int`"（函数签名已有类型标注）、"先读 A 再改 B"（import 关系已说明依赖） | ✅ 可以。随着模型搜索和理解能力提升，这类提示纯属冗余 |

A 类是 Harness 的价值所在——承载"为什么这么做"的设计知识。B 类是膨胀的主要来源——也是 Evolve Agent 最容易大量生成的内容（失败轨迹常表现为"agent 没找到某接口"）。

> Harness 的好坏不在于多全面，而在于多精准——每一行都是模型当前确实做不到的事。

### 生命周期与维护成本

Harness 的价值随模型能力提升而衰减：今天在 Harness 覆盖区里的内容，明天被模型内化后，就从"有用的补丁"变成"多余的噪音"。

所以 Harness 需要持续清理。但清理本身就是成本——而且容易被低估：

1. **生成容易，清理难**。模型几秒生成 hook，判断半年后是否仍有效却需要人类理解当时的上下文。
2. **缺乏所有权**。"谁加的这条规则？为什么加？还能删吗？"——三个问题常无人能答。
3. **没有测试保护**。代码有测试保护，改了会红；Harness 删一条规则，可能数天后才发现行为退化。

> Harness 需要和代码一样的维护纪律，但多数团队对它的维护投入远低于代码。

实践做法：

- **每次换模型版本，跑裸奔基线**。只保留仍产生统计显著提升的组件，退役其余部分。
- **把 Harness 组件设计成"可退役"的**。标注创建时间和触发条件，定期审查"当前模型下还成立吗？"

### 实验驱动，而非经验预设

> **Harness 的存在依据是"实验证明有效"，而不是"工程师觉得应该有"。**

| 不该做的 | 应该做的 |
|----------|---------|
| 因"模型常犯这类错"就预设性加 hook | 先统计实际频次，确认是真实问题再动手 |
| 一次性加一整套规则 | 每次只加一条，单独验证效果，无效回滚 |
| 因 Harness 有效就一直保留 | 定期用新模型跑裸奔基线，判断边际价值 |

> 把每个 Harness 组件当作**可证伪的实验假设**。加之前问"证据在哪"，加之后问"效果怎么验证"，效果消退后问"能不能删"。

### 修复层级决策树

> 遇到问题时选哪一层修？按约束强度从强到弱：

```
问题出现
│
├─ 能用 Tool Implementation 拦截吗？
│   → 是：改工具执行逻辑（强约束，不容商量）
│   → 否：继续
│
├─ 能用 Middleware 拦截吗？
│   → 是：加 PreToolUse / PostToolUse hook
│   → 否：继续
│
├─ 能用 Skill 注入工作流吗？
│   → 是：写按需加载的 skill
│   → 否：继续
│
├─ 能改 Tool Description 说清楚吗？
│   → 是：优化工具文档
│   → 否：继续
│
└─ 最后手段：改 System Prompt
    → 仅当前面所有层级都不适用时
```

**典型案例**：

| 遇到的情况 | ❌ 错误做法 | ✅ 正确做法 |
|-----------|-----------|-----------|
| Agent 验收后误删交付物 | 在 prompt 加"别删文件" | 在 tool 实现中做硬拦截 |
| Agent 忽略 risk 警告 | 在 output 后追加警告 | 在 before_model middleware 注入到 reasoning context |
| Agent 用行数检查替代字段断言 | 在 prompt 加"仔细检查" | 加 middleware 做跨步骤状态追踪 |

> 口诀：**Prompt 讲道理，Tool 做执行，Middleware 做拦截**——能硬拦截的不靠建议。
