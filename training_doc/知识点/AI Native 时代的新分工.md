# AI Native 时代的新分工 - 围绕 Agent 的角色、组织与流程重构

> 当 Agent 成为研发的核心生产力，围绕"有认知约束的人"设计的分工体系就不再合理。本文从角色、组织、协作三个层次分析这场重构：每个角色的价值重心在哪里，团队应该怎么组合，协作流程如何重新设计。

## 1. 根源：为什么必须重构

传统研发模式围绕一个核心假设：**个体认知是有约束的**——工程师只能聚焦少数领域，由此产生了专业分工、职能团队、跨角色协作、流程规范这整套体系。

Agent 打破了这个假设。它能跨越认知约束，快速理解多个领域的上下文。当 Agent 开始胜任"多领域认知任务"，**围绕人的认知约束设计出来的分工方式就失去了存在的理由**。

```
传统研发的设计逻辑              AI Native 的设计逻辑
════════════════════            ════════════════════════
人的认知约束                     Agent 的算力约束
    │                                │
    ▼                                ▼
专业分工（减少认知负担）           规格质量（决定 Agent 工作质量）
角色协作（弥补个体边界）           Harness 建设（扩展 Agent 工作范围）
流程规范（多人协作的质量保障）     HITL 检查点（关键节点保留人的判断）
```

这不是工具升级，而是生产力结构的改变——就像云原生不只是把服务器搬到云上，而是围绕弹性能力重新设计架构和运维。**三个成熟度决定 Agent 能走多远**：模型内核（不可控）、Harness 项目空间（团队可控的新增部分）、项目架构与可观测性（持续优化的工程基础）。后两者越成熟，Agent 需要人介入的频率越低。

## 2. 角色重定义

每个角色从"执行认知任务"转向**判断、守护、设计**——这些是 Agent 真正做不到的事。

### 2.1 产品经理：从需求描述者到规格架构师

传统 PM 靠人与人的沟通弥补需求模糊。开发读到"用户可以登录"，会追问边界，PM 澄清后实现。Agent 没有这个追问机会——**PRD 里的每一处模糊，都会被 Agent 自信地填充成某种具体实现，而且还会通过测试**。

```
PRD："用户可以登录"
  ↓ Agent 自行决定：邮箱不存在时返回"用户不存在"
  ↓ 实现完成，Agent 写测试验证这个行为
  ↓ 测试通过 ✅  ←  安全漏洞（用户枚举）悄然存在
```

**核心职责一：从 PRD 到可执行 Spec**

PRD 定义"做什么"，Spec 定义"怎么做才算对"。PM 需要主导 Spec 的生产。

```
传统 PM 工件          AI Native PM 工件
════════════          ══════════════════════════════
用户故事              五段式 Spec：
功能列表                领域名词（统一概念，消除歧义）
流程图                  前置条件（系统初始状态）
优先级矩阵              主流程（用户操作 + 系统响应）
                        异常处理（穷举边界情况）
                        验收标准 AC（可测试的业务合同）
```

**核心职责二：AC 质量守护（核心 HITL 检查点）**

AI 可以从 PRD 草稿提取 Spec 骨架，但 AC 是业务承诺，人工确认不可跳过。PM 需要识别"Agent 容易误解的 AC"：

| 歧义类型 | 问题示例 | 修正方向 |
|---------|---------|---------|
| 前置状态缺失 | "Token 自动刷新" | 什么状态下的 Token？已过期？快过期？ |
| 模糊词汇 | "友好的错误提示" | 是哪几种文案？分别对应什么场景？ |
| 隐含业务规则 | 不能同时在两个设备播放 | 这条约束在 AC 的哪里明确写出？ |
| 边界条件不完整 | "超过限制" | 等于限制算不算超过？临界行为是什么？ |

**核心职责三：Spec 的持续维护**

需求演变时，PM 直接更新 SPEC.md，而不是只更新 PRD 等开发消化。Spec 只反映当前意图，历史意图交给 git。

### 2.2 设计师：从像素创作者到设计系统守护者

当 Agent 可以直接生成前端代码，**设计稿作为"人翻译给开发"的中介价值大幅下降**。取而代之的是设计系统作为人机共用的唯一真相源——Agent 生成代码必须遵循它，CI 校验代码是否引用了它。

```
传统设计权力链               AI Native 设计权力链
══════════════               ═══════════════════════════
设计师画 Figma               设计系统（tokens + components）
  ↓                               │
前端开发实现                 ┌────┼────┐
  ↓                          ▼    ▼    ▼
每次改动重新沟通           设计师  Agent  CI 检查
                           创作  生成代码 合规守门
```

**核心职责一：维护可执行设计系统**

主要产出从 Figma 页面转向设计系统核心文件：`tokens.css`（颜色、间距、字体的唯一真相）、`components.yaml`（组件规格）、`design-rules.md`（约束规则，Agent 生成时必须遵循）。

**核心职责二：视觉验收的重心转移**

| 验收层次 | 执行者 | 变化方向 |
|---------|--------|---------|
| 代码合规（有无硬编码色值）| 工具自动（CI/lint）| 人工 → 自动 |
| 渲染正确（布局是否符合设计）| 截图对比工具 | 人工 → 半自动 |
| 体验质量（节奏感、情绪、完成感）| 设计师人工走查 | 不变，更聚焦 |

设计师从"盯像素差异"解放出来，集中在**体验质量判断**——这是 Agent 无法替代的感知层。

**核心职责三：设计约束的显式化**

以往靠设计师逐一 review 的规范，现在要写成可执行约束：

```css
color: #6c5ce7;           /* ❌ 硬编码，CI 拦截 */
color: var(--color-primary); /* ✅ 引用 token */
```

### 2.3 开发：全栈化趋势与专业深度的平衡

前后端的边界在 AI Native 时代面临根本性压力，但结论不是"什么都要会"。

**全栈化的驱动力**

Agent 不尊重前后端边界，实现一个完整功能会自然跨越 API、业务逻辑、UI 三层。更根本的是：**Spec 是端到端的**——把一条 AC 拆成前端 ticket 和后端 ticket，制造了人为的认知割裂，Agent 也无法在两个上下文间保持一致。

**全栈化的现实约束**

Android + iOS + Web + 后端是四个独立生态，平台特有知识（Audio Focus、生命周期、内存管理）需要专业积累。架构决策（数据库设计、并发处理、渲染性能）仍然需要专业深度，Agent 给出的是"合理但通用"的方案。

**合理解法：领域全栈，而非技术全栈**

不是"什么都懂"，而是围绕产品的**垂直切片**覆盖，而非技术层的水平分层：

```
传统分法（按技术层）         AI Native 分法（按产品领域）
══════════════════          ════════════════════════════
前端工程师                   Web 产品工程师 = H5 + API
后端工程师                   App 核心工程师 = Android + API 协作层
移动端工程师                 平台工程师 = API 设计 + 数据层 + 基础设施
```

小团队（5 人以下）真正的技术全栈可行——Agent 处理大部分实现，专业深度要求相对下降。中大型产品，领域全栈是现实，纯技术层分工是负担。

**核心职责一：架构决策（不可外包给 Agent）**

人必须决策：技术选型、模块边界、状态机完整设计、安全相关逻辑。Agent 不了解团队约束和历史负债。

**核心职责二：用设计语言精确引导 Agent**

```
低效引导                         高效引导（用设计模式命名）
════════════                     ══════════════════════════════════
"注意别影响原有逻辑"              "使用适配器模式，写 ExportAdapter
"要注意这个、那个..."             包装原有 ExportService，
                                 不直接修改旧的 exportData 方法"
```

设计能力在 AI 时代是与 Agent 沟通的精确语言，不会用模式名称引导 Agent，只能靠啰嗦的约束文字——效率和准确率都低。

**核心职责三：主动 CR 节奏**

AI 生成代码速度是传统的 10 倍，技术债积累速度也是 10 倍。优先扫描 AI 高频错误：重复逻辑、状态泄漏、命名漂移、违反约定架构。把规律性错误写回 CLAUDE.md，让同类问题不再重犯。

**核心职责四：系统可信赖性建设**

可观测性决定 Agent 改完代码后能不能自主知道对不对。最小目标是 L2：结构化日志（Agent 能读懂系统状态）+ 明确错误码（Agent 能定位根因）+ 稳定 API 测试（Agent 能自证修复正确）。测试接缝同样是开发的责任：清晰模块边界、可替换的外部依赖，让每一层独立可测。

### 2.4 测试：意图守护者，而非执行者

传统测试守的是"实现是否符合需求"——代码崩了、边界没处理、功能缺失，都能发现。AI Native 时代出现了新的失效模式，传统测试守不住：

```
新失效模式：合理化的偏差

Agent 对需求有偏差理解
  ↓ 实现了"合理的错误行为"
  ↓ Agent 还写了测试来验证这个错误行为
  ↓ spec-validate 显示 AC 已覆盖
  ↓ 测试全部通过 ✅  ←  用户体验始终不对，没有人发现
```

因此，测试角色需要**双向延伸**：

```
传统：  需求 → 设计 → 开发 → [测试] → 上线

AI Native：[前置：Spec 质量审查] → 开发 → [后置：Agent 盲区探测] → 上线
                ↑ 意图守护（源头）              ↑ 探测 Agent 守不住的地方
```

**测试职责的重新分配**

| 已向 Agent + 开发转移 | 留在测试 / 质量工程师 |
|---------------------|---------------------|
| 从 AC 自动生成测试（spec-validate）| AC 歧义审查（上游介入）|
| CI 回归测试执行 | Agent 生成测试的质量审查 |
| 开发自测和修复 failing 测试 | 探索性测试（盲区地图驱动）|
| API 行为验证（开发负责）| Eval 体系设计与维护 |

**关键风险**：测试职责完全转移给开发后，**独立视角丢失**。开发写测试天然倾向"证明我的实现对了"，而测试人员的价值在于"找实现哪里不对"——这是两种根本不同的思维姿势。测试角色不是消失，而是升级。

**核心职责一：Spec 质量审查（前置防线）**

在 AC 进入开发前，像"攻击者"一样审视 AC，找出 Agent 可能的合理误解路径。

**核心职责二：评审 Agent 生成的测试**

四类常见问题：自我循环验证（测试验证的是 Agent 的错误理解）、覆盖幻觉（AC 显示已覆盖但只测了最简单路径）、断言过宽（只验证状态码不验证响应体）、负向测试缺失（Agent 倾向于写 happy path）。

**核心职责三：面向 Agent 盲区的探索性测试**

Agent 的系统性盲区有规律，探索性测试优先覆盖：

```
并发类                     状态恢复类
──────────────────         ─────────────────────────
Token 并发刷新             异常状态后能否正常恢复
同一用户多端同时操作        播放失败 → 重试 → 再失败
列表加载中同时下拉刷新      App 被系统 Kill 后重新进入

上下文丢失类               隐性约束类
──────────────────         ─────────────────────────
多步流程中途退出再进入       未写进 Spec 的业务"常识"
跨会话状态是否正确保留       新功能对老功能的隐性影响
跳转链路中途中断后恢复       功能之间的隐性耦合
```

**核心职责四：Eval 体系建设**

从"执行测试"延伸到"设计评估体系"：行为契约（这个场景下系统应该怎样）、Golden Dataset（真实场景与期望输出的对照集）、Drift Detection（Agent 每次输出的行为漂移监测）。

### 2.5 运维：Agent 驱动的线上运营

传统运维：感知问题 → 人工分析 → 执行操作。Agent 带来的改变是：**信息聚合和分析可以自动化，人的注意力集中到判断和决策上**。同时职责向两个方向扩展：向应用层建设 Agent 可访问的可观测性基础设施，向 Harness 层分析 Agent 行为记录驱动持续进化。

**场景一：告警响应自动化**

```
传统：告警触发 → on-call 登录 → 查日志 → 猜原因（15-30 分钟）

AI Native：
  告警触发
    ↓ Agent 自动执行（只读，< 2 分钟）
      聚合日志 → 分析异常维度 → 追踪链路 → 对比历史事件
    ↓ 推送摘要给 on-call
      "现象：API 错误率 10:23 从 0.1% 升至 12%
       根因假设：drama_id=999 查询触发 N+1 问题
       证据：drama_service.py:89，查询时间超过 5s
       建议：禁用该 drama（feature flag）/ 回滚上次部署
       影响：约 3% 用户"
    ↓ 人工决策（30 秒）：批准 / 调整 / 自己处理
```

前提是**结构化日志 + 明确的错误码**（可观测性 L2 以上）——没有这个基础，Agent 的分析是在噪音里猜测。

**场景二：Runbook Agent 化**

传统 Runbook 是给人读的文档，执行靠人逐步操作。AI Native 的 Runbook 变成 Agent 可执行的 Skill：每个有副作用的操作之前是一个 HITL 检查点，Agent 执行只读步骤、汇报状态、提议写操作，人工批准后 Agent 执行并记录。

**场景三：持续健康监控（从被动告警到主动预判）**

Agent 周期性读取关键指标，与历史基线对比，在问题触达告警阈值之前推送洞察：

> "API 响应时间在过去 2 小时从 120ms 升至 350ms，按当前趋势预计 30 分钟后触发告警阈值。可能原因：18:00 上线的新查询逻辑在高峰流量下存在 N+1 问题。建议现在介入。"

**场景四：变更影响预评估**

部署前 Agent 分析历史相似变更的影响，提醒关注点和回滚方案。

**Agent 运维的权限边界**

必须明确定义，否则"自主"会变成风险：

| 区域 | 操作类型 | 执行方式 |
|------|---------|---------|
| 绿色 | 读取日志/指标/配置，生成报告，发送通知 | Agent 自主执行 |
| 黄色 | 重启无状态服务，切换 feature flag，调整限流 | Agent 提议，人工一次确认 |
| 橙色 | 数据库配置变更，调整实例规模，部署新版本 | Agent 提议，人工二次确认 + 记录 |
| 红色 | 删除生产数据，撤销用户权限，跨系统连锁操作 | 永远人工，Agent 只提供分析 |

**核心职责**：可观测性基础设施建设（既给人用也给 Agent 用，一次投入双倍收益）、Harness 平台工程（分析 session 记录，驱动 Skill/Prompt 优化）、Agent 化 CI/CD（新增设计规范合规、AC 覆盖检查等节点）、幂等测试环境管理（Agent 频繁运行需要稳定的环境基础）。

## 3. 组织重组

### 3.1 团队规模：多小才合理

直觉上 AI Native 意味着"更少人做更多事"，但规模决策比这复杂。

**规模下限**由 HITL 检查点的密度决定。AC 确认、架构决策、安全逻辑审阅、体验验收——这些判断节点必须有人在场。**Agent 越快，每个判断节点的影响面越大，人工判断反而更贵重，不是更廉价**。盲目压缩人数，压掉的可能正是关键判断节点。

**规模上限**由 Harness 成熟度决定。成熟度越低，需要越多人工补位；过多的人引入协调成本，而协调成本在 AI Native 时代是稀缺资源。

```
规模参考（同等业务产出）
════════════════════════════════════════════════════════

功能特性团队
  传统：PM×1 + 设计×1 + 前端×2 + 后端×2 + 测试×1 = 7 人
  AI Native：PM×1 + 设计×1 + 全栈×2 + 质量工程师×1 = 5 人
  减少的是执行实现类人手，不减少的是判断类角色密度

平台 / 基础设施团队（新增）
  Harness 平台 + 设计系统工程 + 工具链
  规模：2-4 人（中小公司可以跨团队共享）
  不是压缩，是新投入
```

### 3.2 组织形态：告别纯职能部门

职能部门（前端部、后端部、测试部）存在的理由是降低专业知识的复制成本。这个理由在 AI Native 时代被部分削弱，但并非完全消失：

| | 职能组织 | AI Native 时代 |
|-|---------|---------------|
| 专业人手稀缺性 | 是分工的核心理由 | Agent 跨越认知约束，稀缺性下降 |
| 标准制定与知识沉淀 | 靠职能部门积累 | 仍然需要，以 CoE 形式存在 |
| 串行交接 | 靠流程规范 | Spec 驱动并行，交接成本大幅下降 |
| 技术层划分 | 前端/后端边界清晰 | 应该按产品领域划分，而非技术层 |

**推荐结构：双层模型**

```
平台层（小型 CoE，跨业务共享）
┌────────────────────────────────────────────────────┐
│  Harness 平台工程：Skill / Tool / Workflow 标准化   │
│  设计系统工程：Token + Component 的 owner           │
│  质量标准：Eval 体系模板，AC 规范，测试工具链        │
└────────────────────────────────────────────────────┘
            ↕ 提供标准 + 工具 + 咨询

产品层（自包含特性团队）
┌────────────┐  ┌────────────┐  ┌────────────┐
│   Team A   │  │   Team B   │  │   Team C   │
│ PM+全栈+QE │  │ PM+全栈+QE │  │ PM+全栈+QE │
│ 自己的 Spec│  │ 自己的 Spec│  │ 自己的 Spec│
│ 自己的     │  │ 自己的     │  │ 自己的     │
│ Harness    │  │ Harness    │  │ Harness    │
└────────────┘  └────────────┘  └────────────┘
```

"前端部门/后端部门/测试部门"在这个结构里不再有意义。"设计系统组"、"平台工程组"作为 CoE 依然有价值——它们提供标准和工具，而不是提供人手。

### 3.3 新角色的涌现

以下角色不一定是新的 headcount，更多是现有角色职责的升级演化：

| 新角色 | 从哪里演化 | 核心职责 |
|--------|-----------|---------|
| 规格架构师 | 高级产品经理 | 设计可执行 Spec 体系，定义 AC 规范 |
| Harness 平台工程师 | 运维 / 平台工程师 | 构建和维护 Agent 运行的基础设施 |
| AI 质量工程师 | 高级测试工程师 | 设计 Eval 体系，审查 Agent 行为质量 |
| 设计系统工程师 | 高级设计师 + 前端 | 维护可执行设计系统，Token/Component 的 owner |

## 4. 协作重构

### 从串行交接到规格驱动并行

```
传统串行流程
PRD → 设计稿 → 开发 → 测试 → 上线
 ↕     ↕       ↕      ↕
沟通  评审    联调   报告（每个箭头都是等待和信息损耗）

AI Native 规格驱动流程
              SPEC.md 定稿（HITL：PM + 测试共同确认 AC）
                    │
    ┌───────────────┼───────────────┐
    ▼               ▼               ▼
设计系统更新    Agent 实现      Eval 体系 + 盲区地图
（设计师）     （开发引导）    （质量工程师）
    │               │               │
    └───────────────┼───────────────┘
                    ▼
            spec-validate（自动）
            体验质量验收（设计师）
            Agent 盲区探测（QE）
                    │
                   上线
```

### HITL 检查点：新的协作时刻

以往协作靠会议对齐信息。AI Native 的协作围绕 HITL 检查点——人在关键节点介入做决策，不是为了传递信息。

| HITL 检查点 | 参与角色 | 通过标准 |
|------------|---------|---------|
| AC 最终确认 | PM + 测试 | 测试人员找不到可被误解的 AC |
| 架构决策 | 开发（领域负责人）| 决策有 ADR 记录，理由清晰 |
| 安全逻辑审阅 | 开发 | 逐行 review 通过 |
| 体验质量验收 | 设计师 + PM | 设计师判断通过 |
| 代码合并 | 开发（非 Agent 独自）| git diff 确认，spec-validate 绿色 |
| 运维操作审批 | 运维 / on-call | 逐操作人工批准 |

### 协作产物的演变

| 传统产物 | AI Native 产物 | 变化方向 |
|---------|--------------|---------|
| PRD | PRD + SPEC.md（可执行 AC）| Spec 是新增核心产物 |
| 设计稿 | 设计系统更新 + 必要新页面稿 | 系统性 > 一次性 |
| 技术方案文档 | ADR + CLAUDE.md 约束 | 决策留档，约束可执行 |
| 测试用例 | 测试用例 + Eval 体系 + 盲区地图 | 增加 Eval 维度 |
| 上线检查单 | 上线检查单 + Harness 健康检查 | 增加 Agent 运行环境验证 |

### 两层反馈回路

```
对象层（应用系统 → Agent）
  结构化日志 + 测试结果 → Agent 自主感知 → 定位修复 → 验证
  目标：Agent 不需要人来描述现象、搬运信息

元层（Agent 行为 → Harness）
  session 记录 → 失败模式分析 → Skill/Prompt 优化 → 下一轮验证
  目标：Harness 不断进化，Agent 能力边界持续扩大
```

Agent 频繁需要人介入时的快速诊断：读不懂报错 / 测试结果不可信 → 对象层问题，优先改应用；反复犯同一类错误 / Skill 失效 → 元层问题，分析 session 日志。两层同时失效时，优先修对象层——没有可靠信号，元层分析是沙上建塔。

## 5. 过渡路径

**分阶段推进，不要期望一步到位**

```
阶段 1：小范围简单任务（模块内 CRUD）
  目标：个人建立 Harness 闭环
  关键行动：CLAUDE.md + SPEC.md + 基础测试接缝

阶段 2：模块端到端需求（跨前后端）
  目标：特性团队建立可执行 Spec 机制
  关键行动：PM/测试参与 AC 定稿，spec-validate 守门，领域全栈

阶段 3：跨系统常规需求
  目标：Harness 跨团队标准化，平台层建立
  关键行动：双层组织结构落地，Harness 平台工程师角色明确

阶段 4：跨系统复杂任务
  目标：Agent 能自主处理复杂多步问题
  关键行动：完整可观测性体系，元层反馈自动化，Agent 化运维落地
```

**各角色的优先行动**

| 角色 | 最高优先级行动 | 预期效果 |
|------|--------------|---------|
| 产品经理 | 写五段式 Spec，重点是 AC 的清晰度 | Agent 实现质量从"猜需求"变为"遵守合同" |
| 设计师 | 建立 tokens.css 为核心的可执行设计系统 | 视觉规范 Agent 可遵循，验收可自动化 |
| 开发 | 主动 CR 节奏 + 可观测性到 L2 | 技术债不积累，Agent 能自主感知和验证 |
| 测试 | 介入 AC 评审（前置）+ 建立盲区探测清单（后置）| 覆盖传统测试守不住的新失效模式 |
| 运维 | 结构化日志 + Agent 化 Runbook + 权限边界定义 | Agent 辅助告警响应，on-call 从查日志转向决策 |

**需要避免的误区**

| 误区 | 后果 |
|------|------|
| "让 AI 做所有事，人只看结果" | HITL 节点被跳过，系统性偏差积累 |
| "工具换了，流程不变" | Agent 在模糊需求上快速生成错误代码 |
| "测试让 AI 自动覆盖就好" | Agent 用自己的理解写测试，测试绿色行为却始终不对 |
| "Harness 建设是运维的事" | 产品、测试的知识无法沉淀，Agent 能力上限受限 |
| "AI Native = 减人" | 判断节点被当成成本优化，关键质量机制失守 |

## 总结

| 角色 | 价值重心 |
|------|---------|
| 产品经理 | 意图的精确定义者——AC 质量决定 Agent 实现质量的上限 |
| 设计师 | 设计约束的系统化守护者——设计系统是 Agent 的设计宪法 |
| 开发 | 架构引导者——用设计语言精确引导 Agent，主动守住质量 |
| 测试 | 意图守护者——守住 Spec 质量，探测 Agent 系统性盲区 |
| 运维 | Harness 平台工程师——让 Agent 运行的基础设施持续进化 |

**核心原则：AI 越快，人的判断越贵重。自动化执行层，人工决策层。**
