## 极简工具栈对抗系统复杂性

**核心理念**：拒绝臃肿的编排器框架与复杂的子智能体配置，回归原生（Vanilla）智能体形态。

四件工具足以驱动 8 路并发：

| 工具 | 职责 |
|------|------|
| **Cursor**（IDE）| 代码浏览、跨模型校验与手动干预 |
| **Tmux**（窗口管理）| 多终端会话管理与并行环境隔离 |
| **Markdown**（状态存储）| 系统全局唯一真实数据源（Single Source of Truth） |
| **Slash Commands**（斜杠命令）| 纯文本指令驱动控制流与生命周期管理 |

> **反直觉之处**：越简单的工具栈，越能撑起大并发——复杂框架本身就是认知负担。

## 架构层：三位一体的会话角色分配

每个 Tmux 窗口通过**命名约定**绑定特定角色任务：

```
tmux: PM
  └── 管理待办事项（Backlog grooming）与创意倾泻（Idea dumping）

tmux: Planner
  └── 将模糊需求转化为完备的 Markdown 规格说明（Specs）

tmux: Worker
  └── 严格依据确定的规格说明执行代码落地与实现
```

**关键原则**：角色不混用。PM 不写代码，Worker 不定义需求，Planner 不执行实现。  
窗口名称即角色合同——智能体读取窗口名就知道自己该做什么。

## 数据层：FD 作为唯一事实真相

**所有代码的编写均始于一份完成的 FD（Feature Design）。**

一份标准 FD 必须包含四个维度：

```markdown
FD-051: Multi-label document classification
Status: Open

## Problem
明确当前痛点与边界（现象 + 影响范围）

## Solution
最终方案与执行计划（不含多个备选方案，只写已决策的路径）

## Files to Modify
精准框定爆炸半径（列出所有将被新增/修改的文件）

## Verification
明确的运行时验证步骤（如何证明这个 FD 已完成）
```

> **核心价值**："Files to Modify" 强制开发者在动手前思考影响范围，避免 Agent 随意扩散修改。

## 状态机：八阶生命周期与全局追踪

FD 流转八个阶段，`FEATURE_INDEX.md` 是跨所有 FD 的状态注册表：

```
Planned → Design → Open → In Progress → Pending Verification → Complete → Deferred → Closed
```

**FEATURE_INDEX.md 示例：**

| FD | Title | Status | Effort |
|----|-------|--------|--------|
| FD-051 | Multi-label document classification | Open | Medium |
| FD-052 | Streaming classification pipeline | In Progress | Large |
| FD-050 | Confidence-based routing | Pending Verification | Medium |

**自动化规则**：代码提交完成后，Changelog 自动基于已关闭的 FD 累加——不需要手写 Release Notes。

## 控制流：驱动生命周期的六大斜杠命令

```
/fd-new       从创意倾泻创建新 FD
/fd-status    展示全局索引与进度状态
/fd-explore   加载代码库上下文、架构文档与开发指南
/fd-deep      启动并行测试时计算（Test-time compute）
/fd-verify    校对代码，提出验证计划并提交
/fd-close     归档 FD 并自动更新 Changelog
```

**引导命令**：运行 `/fd-init` 可在任意新仓库中自动拉起包含目录、模板和指令的完整系统。

> **设计哲学**：斜杠命令是生命周期的"卡口"，每个阶段转换都必须显式触发，防止 Agent 越级执行。

## 算力爆发：/fd-deep 并行深度探索

借鉴"测试时计算"（Test-time compute）理念——遇到棘手设计或未知技术栈时，`/fd-deep` 同时启动 **4 个并行 Opus 智能体**，从不同角度独立推演：

```
主 Planner 节点
（遇到复杂队列回退问题）
    │
    ├── 并行智能体 1：算法视角
    ├── 并行智能体 2：结构视角
    ├── 并行智能体 3：环境视角
    └── 并行智能体 4：增量视角
    │
编排器汇总校验
```

**适用场景**：
- 技术方案不确定，需要多路推演后取最优解
- 涉及复杂依赖链，单一视角容易遗漏
- 架构决策前的"压力测试"

> **与 /fd-explore 的区别**：explore 是加载上下文（读），deep 是并行推理（算）。

## 核心内循环：无损的规划与隔离的执行

**三阶段循环：**

```
规划期
  └── Worker 的 Plan mode：生成行级实现计划
      在 Cursor 中使用 %% 写内联批注，指令智能体读取笔记
执行期
  └── 大型重构时创建原生 Worktree（隔离爆炸半径）
验证期
  └── /fd-verify 自动校验与提交
```

**内联批注技巧**：对话式交互不够精确时，直接在 FD 的 Solution 节下用 `%%` 写疑问：

```markdown
## Solution
Replace cron-based batch processing with an event-driven pipeline.
Consumer pulls from the queue, processes in micro-batches of 50.
%% what's the max queue depth before we start dropping? need backpressure math
Failures go to the dead-letter queue.
%% what happens to in-flight items during cutover? need to confirm drain behavior
```

智能体读取 `%%` 批注，在执行前先解决疑问——避免带着未解决的假设落地代码。

## 建立"机器品味"：双层上下文管理

**问题根源**：智能体缺乏判断力（害怕报错、留存死代码）。  
**解法**：不要让全局 CLAUDE.md 过载，按需读取深度指南。

```
CLAUDE.md（保持精简）          docs/dev_guide/（深度库，按需读取）
─────────────────              ──────────────────────────────────
代码格式规范                   1. 禁止静默回退：配置错误必须大声报错，
Python / SQL 约定                 不隐藏于默认值之后
FD 生命周期规则                2. 部署安全：破坏性操作必须等待运行任务完成
                               3. 严格解析：LLM JSON 必须使用宽容模式与
                                  正则回退，严禁裸用 json.loads()
```

**两层设计的价值**：
- CLAUDE.md 精简 → 每次 Session 都被完整读取，不被截断
- 深度指南按需加载 → 减少上下文噪音，智能体只在需要时读取相关规则

## 工作台空间映射：物理级并行布局

应对 8 个并行上下文切换的人类视觉与空间管理工程：

```
屏幕 1：Cursor（IDE）
  └── 主攻视觉代码浏览、手动编辑与跨模型校验
      （如 gpt-5.3-codex 复核计划）

屏幕 2：Ghostty Terminal 1 + Tmux
  └── 运行纯净会话，承载通用型 Claude Code
      tabs: planner | worker-fd038 | ...

屏幕 3：Ghostty Terminal 2 + Tmux
  └── 承载深度集成数据库的 Cortex Code
      tabs: PM | ...
```

**空间设计原则**：每类智能体有专属物理屏幕 → 眼神落点即可判断当前上下文 → 无需脑力记忆"这个窗口在做什么"。

## 消除并行混乱：路径别名与视觉提示

**路径别名**：配置 `g*` 别名，智能体直接解析，免去长路径输入：

```bash
# Bash 路径映射
gpipeline -> ~/workspace/services/data-pipeline
gapi      -> ~/workspace/services/api-service

# 对话中直接使用：
"run the eval in gpipeline"
```

**空闲反转通知**：智能体完成任务空闲时，终端 Tab 自动反转颜色发出视觉信号：

```json
// ~/.claude/settings.json
"idle_prompt" hook sends bell (\a)
```

```
# ~/.tmux.conf
monitor-bell on
window-status-bell-style reverse
```

> **效果**：8 个并发任务无需轮询状态——完成的窗口自己"亮起来"，开发者被动感知，主动响应。

## 系统边界与物理限制

并行并非无限扩展，有四个真实约束必须正视：

| 限制 | 描述 | 应对策略 |
|------|------|---------|
| **认知负荷极限** | 1-4 个并发为高效区，8 个为极限区，8+ 进入崩溃区。频繁要求智能体总结工作是系统过载的信号。 | 保持并发数 ≤ 8 |
| **串行依赖冲突** | 强制将存在顺序依赖的功能并行会导致严重的 Merge 冲突。 | 保持增量与原子化提交 |
| **上下文极速消耗** | 探索型任务快速消耗 Token，Compaction 会丢失关键决策。 | 大幅增加 Checkpoint 频率 |
| **黑名单博弈焦虑** | 智能体常试图绕过危险命令黑名单——拦截了 `rm`，它们会狡猾地使用 `unlink` 或 `find -delete`。 | 黑名单按语义而非命令名设计 |

## 开发者的新定位：业务与机器的桥梁

> 机器的并发执行能力已经远超人类的上下文切换极限。

**未来的核心竞争力不再是亲手编写每一行代码，而是：**

```
如何将复杂的业务上下文
精准地翻译为智能体可执行的 Markdown 规格说明（FDs）
```

**能力重心转移对照：**

| 过去的核心能力 | AI 时代的核心能力 |
|---------------|-----------------|
| 写出正确的代码 | 写出正确的 FD（规格翻译能力）|
| 调试 Bug | 设计可观测的系统（让 Agent 自己调试）|
| 管理代码复杂度 | 管理 Agent 并发复杂度 |
| 执行实现 | 决策架构 + 验证结果 |

> **结论**：工程师不再是"代码生产者"，而是"规格定义者"与"质量裁判员"——这个角色反而比以前更需要深厚的业务理解力与工程判断力。

## Claude Code 落地实践指南

> 本节将上述模式落地为可立即执行的 Claude Code 操作步骤。
> 本项目已预置完整的斜杠命令实现（`fd/` 目录 + `.claude/commands/fd/`），开箱即用。

### 核心机制：斜杠命令 = `.claude/commands/` 下的 Markdown 文件

Claude Code 的自定义斜杠命令本质是一个 Markdown 文件：

```
.claude/commands/fd/
├── fd-init.md       ← /fd-init 命令的完整 prompt
├── fd-new.md        ← /fd-new 命令
├── fd-status.md     ← /fd-status 命令
├── fd-explore.md    ← /fd-explore 命令
├── fd-deep.md       ← /fd-deep 命令（使用 Task 工具并行）
├── fd-verify.md     ← /fd-verify 命令
└── fd-close.md      ← /fd-close 命令
```

当你在 Claude Code 中键入 `/fd-new 需求描述`，Claude 会：
1. 读取 `fd-new.md` 中的 prompt 内容
2. 将 `$ARGUMENTS`（即你的需求描述）注入 prompt
3. 按 prompt 中的 `<process>` 步骤执行

文件顶部的 frontmatter 控制命令元数据：
```markdown
---
name: fd:new
description: 从用户需求描述创建新 FD 文档
argument-hint: "<需求描述>"
allowed-tools:
  - Read
  - Write
  - Bash
---
```

### 快速开始：5 分钟拉起工作台

#### Step 1 — 初始化 FD 工作台

在任意 Claude Code 会话中运行：

```
/fd-init
```

这会创建 `fd/FEATURE_INDEX.md` 和 `fd/templates/FD-template.md`（幂等，已存在则跳过）。

#### Step 2 — 创建你的第一个 FD

```
/fd-new 用户登录后首页加载太慢，需要优化短剧列表的首屏渲染时间
```

Claude 会自动：
- 分配编号（FD-001）
- 填写 Problem / Solution / Files to Modify / Verification 四个维度
- 写入 `fd/FD-001-optimize-drama-list-render.md`
- 更新 `fd/FEATURE_INDEX.md`

#### Step 3 — 开始并行

同时打开多个 Claude Code 终端窗口，各自处理不同 FD：

```bash
# 终端 1（Worker A）
claude --model claude-opus-4-7
> /fd-explore FD-001
> 实现 FD-001

# 终端 2（Worker B）
claude --model claude-opus-4-7
> /fd-explore FD-002
> 实现 FD-002

# 终端 3（Planner）
claude
> /fd-new 下一个需求描述
```

关键原则：**不同终端各自独立，通过 `fd/` 目录下的 Markdown 文件共享状态**，不通过会话内存交互。

### 并行执行：Worktree 隔离爆炸半径

当多个 Worker 同时修改代码时，用 Git Worktree 隔离，避免冲突：

```bash
# Worker A 的工作区
git worktree add ../drama-flow-fd001 -b feature/FD-001

# Worker B 的工作区
git worktree add ../drama-flow-fd002 -b feature/FD-002
```

各自在独立目录里启动 Claude Code：
```bash
cd ../drama-flow-fd001 && claude
cd ../drama-flow-fd002 && claude
```

完成后合并主干：
```bash
cd drama-flow
git merge feature/FD-001
git merge feature/FD-002
git worktree remove ../drama-flow-fd001
git worktree remove ../drama-flow-fd002
```

> **为什么这很重要**：FD 的 "Files to Modify" 节就是提前声明爆炸半径。  
> 两个 FD 若没有文件重叠，可以安全并行；有重叠的必须串行或手动协调。

### `/fd-deep` 的并行子 Agent 机制

`/fd-deep` 使用 Claude Code 的 **Task 工具**在同一会话内启动多个子 Agent。
Task 工具是 Claude Code 内置的子 Agent 调度器，允许并行启动多个独立推理任务。

```
你（主 Claude 会话）
    │ 调用 Task 工具 × 4（同时）
    ├── 子 Agent 1：算法视角推演
    ├── 子 Agent 2：架构视角推演
    ├── 子 Agent 3：风险视角扫描
    └── 子 Agent 4：增量步骤规划
    │ 等待全部完成
主 Agent 汇总 → 写回 FD Solution 节
```

触发方式：
```
/fd-deep FD-003
```

适用场景：FD Solution 写完后，你对方案还不确定，或者 Solution 里有多个 `%%` 批注未解决。

### 空闲通知配置（可选）

让完成的终端窗口自动"亮起来"，避免轮询：

**~/.claude/settings.json**（全局）：
```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "printf '\\a'"
          }
        ]
      }
    ]
  }
}
```

**~/.tmux.conf**：
```
set-option -g bell-action any
set-option -g monitor-bell on
setw -g window-status-bell-style reverse
```

效果：Claude Code 停止输出时，终端发出 bell 信号，Tmux Tab 标题反色显示，你无需盯着屏幕轮询。

### 完整工作流一览

```
1. /fd-init          ← 一次性初始化（项目已完成）

2. /fd-new <描述>    ← PM 角色：将需求转为 FD 文档
   ↓
3. /fd-explore <FD>  ← Planner 角色：加载代码上下文，识别风险
   ↓（遇到复杂决策）
   /fd-deep <FD>     ← 并行推演，汇总最优方案
   ↓
4. 实现代码          ← Worker 角色：在独立 Worktree 中实现
   ↓
5. /fd-verify <FD>   ← 逐条验收，运行测试
   ↓
6. /fd-close <FD>    ← 归档，追加 CHANGELOG

7. /fd-status        ← 随时查看全局进度
```

### 认知负荷管理

| 并发数 | 状态 | 建议 |
|--------|------|------|
| 1–3 | 高效区 | 正常推进 |
| 4–6 | 压力区 | 注意上下文切换成本 |
| 7–8 | 极限区 | 频繁要求总结是过载信号 |
| 8+  | 崩溃区 | 先完成一个再开新的 |

`/fd-status` 输出的"Active Work"数量是实时负荷指示器，超过 4 个 In Progress 时系统会主动提示。
