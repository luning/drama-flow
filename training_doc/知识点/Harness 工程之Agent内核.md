## 1. 内核与项目空间的分工

Harness 由两部分构成：

```
┌──────────────────────────────────────────┐
│               Harness                    │
│                                          │
│   ┌──────────────┐  ┌──────────────────┐ │
│   │  Agent 内核  │  │    项目空间       │ │
│   │  (厂商提供)  │  │  (工程师构建)     │ │
│   └──────────────┘  └──────────────────┘ │
└──────────────────────────────────────────┘
```

| 维度 | Agent 内核 | 项目空间 |
|------|-----------|---------|
| **谁构建** | AI 工具厂商（Anthropic、OpenAI、Google…） | 工程师和团队 |
| **能否干预** | 不能直接修改，只能通过接口影响 | 完全自主管理 |
| **包含内容** | 模型、推理机制、工具调用框架、上下文压缩 | 代码库结构、文档、约束规则、经验沉淀、工具配置 |
| **决定什么** | Agent 能做什么、能做多好 | Agent 知道什么、被允许做什么、如何验收 |

**核心认知**：工程师的工作不是改造内核，而是通过精心建设项目空间，让内核充分发挥潜力。

## 2. 内核的九大组件

综合学术研究（LLM Agent 系统综述）与工程实践（Claude Code 架构论文 arxiv:2604.14228），成熟 Agent 内核由九个组件构成。

> **关键数据**：对 Claude Code 源码的深度分析发现，**仅 1.6% 的代码是 AI 决策逻辑**，其余 98.4% 是纯粹的操作基础设施——上下文管理、工具路由、权限控制、恢复逻辑。这意味着内核的工程复杂度远超"给模型写 prompt"。

**组件全景**：

| 组件 | 类别 | 核心职责 |
|------|------|---------|
| ① LLM（推理引擎） | 认知核心 | 文本理解、推理规划、代码生成 |
| ② 感知层（Perception） | 认知核心 | 处理外部输入，将环境状态转化为 LLM 可理解表示 |
| ③ 规划与反思（Planning & Reflection） | 认知核心 | 任务分解、路径规划、自我批评修正 |
| ④ 推理循环（Agentic Loop） | 运行时 | 驱动多步骤持续执行的控制流 |
| ⑤ 上下文管理（Context Management） | 运行时 | 窗口装配 + 长任务的上下文压缩 |
| ⑥ 工具调用引擎（Tool Engine） | 交互层 | 执行操作，将结果反馈进推理循环 |
| ⑦ 权限与安全（Permission & Safety） | 交互层 | 操作边界控制，人机交接触发点 |
| ⑧ 记忆系统（Memory） | 持久化 | 跨 session 状态保存与恢复 |
| ⑨ 子代理编排（Sub-Agent Orchestration） | 扩展层 | 并行子任务委派，角色专化 |

**组件关系图**：

```
外部输入
    ↓
② 感知层（Perception）── 结构化处理 ──→ ⑤ 上下文管理
                                         ↑ ← ⑧ 记忆系统（session 启动时注入）
                                         ↓
                                    ① LLM（推理引擎）
                                    ③ 规划与反思
                                         ↓
                               ④ 推理循环（Agentic Loop）
                                    ↙         ↘
                         ⑦ 权限与安全      ⑨ 子代理编排
                               ↓（通过）          ↓（派发）
                         ⑥ 工具调用引擎      子 Agent 实例
                               ↓ 结果 ←←←←←←←← ↙（汇报）
                          感知层处理结果 → 追加入上下文管理
```

---

### 组件 ① LLM（推理引擎）

**是什么**：内核的认知底座，真正产生"智能"的部分。

**作用**：文本理解、推理规划、代码生成。所有思考、判断、输出，最终都由 LLM 完成。

**关键特性**：

| 特性 | 说明 |
|------|------|
| 概率性输出 | 不是确定性代码，相同输入可能产生不同输出 |
| 上下文窗口限制 | 每次推理只能看到有限的信息（详见组件⑤） |
| 跨 session 无状态 | 新 session 开始时不记得上次做了什么 |
| 能力由厂商决定 | 推理质量、代码能力、多语言支持——外部无法干预 |

**代表厂商**：Anthropic（Claude）· OpenAI（GPT）· Google（Gemini）· Meta（Llama）

LLM 的能力上限决定了 Agent 能做多好，而它的系统性局限决定了项目空间需要往哪里补（详见第 3 节）。

---

### 组件 ② 感知层（Perception）

**是什么**：Agent 处理外部输入、将环境状态转化为 LLM 可理解表示的入口层。

**作用**：把文件内容、命令输出、用户消息、API 响应、截图等异构数据，转化为结构化的上下文表示，注入推理循环。

**处理的输入类型**：

| 输入类型 | 来源 | 处理方式 |
|---------|------|---------|
| 文本指令 | 用户消息、CLAUDE.md | 直接装入 System Prompt / 对话上下文 |
| 工具返回结果 | 命令输出、API 响应 | 格式化后追加进上下文窗口 |
| 多模态输入 | 截图、图表、PDF | 通过视觉编码器转化为文本描述 |
| 环境状态 | 目录结构、git 状态、测试结果 | 结构化摘要后注入 |

**工程含义**：Agent "看到"什么决定它"想到"什么。**结构化输出（JSON、明确的状态码）是为感知层优化的，不是为人类可读性优化的**——脚本输出"已重置，导入 42 条"而非退出码 0，就是在为感知层服务。

---

### 组件 ③ 规划与反思（Planning & Reflection）

**是什么**：LLM 在推理过程中主动进行任务分解、路径规划和自我批评修正的认知机制，发生在推理循环每一轮的"Think"阶段内部。

**作用**：将高层任务拆解为可执行步骤；执行过程中持续自我评估；发现偏差时修正方向而非盲目继续。

**关键推理机制**：

| 机制 | 说明 | 适用场景 |
|------|------|---------|
| **Chain-of-Thought（CoT）** | 逐步推理，而非直接跳到结论 | 降低幻觉率，提升逻辑准确性 |
| **Extended Thinking** | 回应前进行深度隐式推理（Claude 3.7+） | 复杂决策、需要权衡多个方案 |
| **Tree-of-Thought（ToT）** | 同时探索多条执行路径，择优继续 | 有多种解法时的最优路径选择 |
| **Reflection（自我反思）** | 观察执行结果后主动质疑"是否真的完成了" | 防止 Agent 自信宣布完成但实为半成品 |
| **ReAct 模式** | 推理（Reason）与行动（Act）交替 | 每步推理紧跟工具调用，保持推理-验证闭环 |

**规划 vs 反思的分工**：
- **规划**：任务开始时分解步骤，决定"先做什么后做什么"
- **反思**：每次行动后评估结果，决定"上一步是否真的成功了"

**核心洞察**：Anthropic 发现模型有系统性的乐观偏差——Agent 评估自己的输出时会高估质量。反思机制只能缓解，无法根治。这正是独立评估器子代理（⑨）作为架构解法存在的原因：**工程化外部评估比训练内部自我批评更可靠**。

---

### 组件 ④ 推理循环（Agentic Loop）

**是什么**：驱动 Agent 持续工作的控制流机制，把单次 LLM 推理扩展为多步骤自主执行。它是整个内核的"发动机"。

**作用**：不断循环"思考—行动—观察"，直到任务完成或无法继续。

**循环结构**：

```
接收任务
    ↓
装载上下文（System Prompt + 记忆注入 + 动态内容）
    ↓
┌──────────────────────────────────────────┐
│               推理循环                    │
│                                          │
│  Think：规划与反思（组件③）               │
│     ↓                                    │
│  Act：发出工具调用请求                    │
│     ↓                                    │
│  Permission Check：权限与安全（组件⑦）   │
│     ↓（通过）                             │
│  Execute：工具调用引擎（组件⑥）执行      │
│     ↓                                    │
│  Observe：感知层（组件②）处理结果        │
│     ↓ 追加入上下文                        │
│  Loop or Done？                          │
└──────────────────────────────────────────┘
    ↓（完成 / 无法继续 / 需要人工确认）
输出结果
```

**终止条件**：

| 类型 | 触发原因 |
|------|---------|
| 正常完成 | LLM 判断任务已达成预期 |
| 人工确认暂停 | 危险操作、关键决策点，等待用户输入 |
| 上下文压缩触发 | 窗口接近上限，执行压缩后继续 |
| 异常终止 | 连续工具调用失败、达到最大步骤数 |

---

### 组件 ⑤ 上下文管理（Context Management）

**是什么**：管理上下文窗口内容的装配、优先级排序，以及长任务中的自动压缩（Compaction）机制。

**作用**：在有限的窗口空间内，始终保证最关键的信息被 LLM 看到；当窗口即将耗尽时，通过压缩而非截断来保持任务连续性。

**窗口内容的分层构成**：

```
┌────────────────────────────────────────────┐
│             上下文窗口（有限空间）            │
├────────────────────────────────────────────┤
│ System Prompt（固定区）                     │
│   └─ CLAUDE.md 规则 + 架构约束              │
├────────────────────────────────────────────┤
│ 任务描述 + 动态注入（启动时装载）             │
│   └─ Skills 工作流 / 记忆文件 / 文档片段     │
├────────────────────────────────────────────┤
│ 推理轨迹（持续增长）                         │
│   └─ Think → 工具调用 → 工具结果 → Think... │
└────────────────────────────────────────────┘
              ↑ 填至约 95% 时触发压缩
```

**上下文压缩（Context Compaction）**：

长任务场景的关键机制。Claude Code 的实现：当上下文使用量达到 **95%** 时，自动将推理轨迹摘要压缩，保留关键发现，丢弃中间步骤细节，腾出空间继续执行。

```
正常执行阶段                     压缩触发
──────────────────               ──────────────────────────
推理轨迹不断追加         →  窗口至 95% → 自动压缩推理历史
                                              ↓
                              保留：关键发现、当前任务状态
                              丢弃：中间步骤的详细日志
                                              ↓
                                         继续执行
```

> **2026 年的生产警告**：研究发现 2025 年约 65% 的企业级 AI 失败案例源于上下文漂移（context drift）——关键约束信息在压缩过程中被误丢，而非上下文耗尽本身。这是为什么 System Prompt 中的核心规则需要"锚定"不可被压缩掉。

### 组件 ⑥ 工具调用引擎（Tool Calling Engine）

**是什么**：Agent 与外部世界交互的桥梁，让 LLM 突破"只会说话"的限制，真正执行操作。

**作用**：接收 LLM 发出的结构化工具调用请求，通过权限检查（组件⑦），执行操作，将结果交给感知层（组件②）处理后追加入上下文。

**内置工具分类（以 Claude Code 为例）**：

| 类别 | 工具 | 作用 |
|------|------|------|
| 文件操作 | Read / Write / Edit | 读写代码文件 |
| Shell 执行 | Bash | 运行命令、脚本、测试 |
| 代码搜索 | Grep / Glob | 在代码库中查找内容 |
| 网络 | WebSearch / WebFetch | 获取外部信息 |
| 人机交互 | AskUserQuestion | 关键决策点暂停请求确认 |
| 子代理 | Agent / Task | 派发子任务（详见组件⑨） |
| 状态管理 | TodoWrite | 追踪任务进度 |

**扩展机制**：通过 MCP（Model Context Protocol）注册自定义工具。MCP 在 2025 年底被 Anthropic 捐赠给 Linux 基金会下的 AAIF，已成为 Agent 工具扩展的行业标准协议。

---

### 组件 ⑦ 权限与安全（Permission & Safety）

**是什么**：在每次工具调用前后执行的访问控制与安全审查层，是内核内置的安全边界。

**作用**：决定"这个操作是否被允许执行"，在关键节点触发人机交接（HITL），记录操作审计日志。

**拦截位置（PreToolUse / PostToolUse）**：

```
LLM 决定调用工具
        ↓
PreToolUse 检查
  ├─ 此工具是否在 allowlist？
  ├─ 命令是否匹配危险模式（rm -rf / DROP TABLE...）？
  └─ 是否需要人工确认（数据删除、生产环境操作）？
        ↓（通过）
工具执行
        ↓
PostToolUse 审查
  ├─ 结果中是否包含密钥/敏感信息？
  └─ 记录操作日志（谁、何时、做了什么）
```

**三类控制机制**：

| 类型 | 实现 | 约束强度 |
|------|------|---------|
| 静态 allowlist | `.claude/settings.json` 预声明允许的工具和命令 | 硬约束，声明外一律拒绝 |
| 动态拦截 hooks | `.claude/hooks/` PreToolUse / PostToolUse 脚本 | 硬约束，机器强制执行 |
| 人机交接 | `AskUserQuestion` 工具暂停循环等待确认 | 软约束，人工判断后继续 |

**组织级 vs 个人级的设计差异**：个人使用时（Claude Code），权限层很轻量——它在执行危险命令前弹出确认框，就是最简单的 HITL。组织级 Agent 需要更完整的权限体系：基于身份的权限控制、操作范围隔离（测试库 vs 生产库）、强制审计日志。

> **架构洞察**：权限系统的设计不应基于"Agent 足够聪明会自己判断"，而应基于"**Agent 一旦误判，谁来承担后果**"。这个问题的答案，决定了权限层该有多厚。

---

### 组件 ⑧ 记忆系统（Memory System）

**是什么**：Agent 自己维护的跨 session 持久化机制，解决 LLM 跨 session 无状态的根本问题。

**作用**：将当前 session 学到的东西写入文件，下次 session 启动时重新注入上下文，实现跨会话的状态延续。

**记忆的四种存储形态**（学术分类）：

| 类型 | 存储介质 | 内容 | 类比 |
|------|---------|------|------|
| **工作记忆** | 上下文窗口（运行时） | 当前任务状态、推理轨迹 | 短期工作台 |
| **情景记忆** | memory 文件（持久化） | 过去的交互历史、用户习惯 | 日记本 |
| **语义记忆** | 向量数据库（企业级） | 组织知识库、文档索引 | 知识图谱 |
| **程序记忆** | Skills / EXPERIENCE.md | 已学会的操作流程、避坑经验 | 操作手册 |

**Claude Code 的记忆文件类型**：

| 文件 | 存储内容 | 举例 |
|------|---------|------|
| `user.md` | 用户偏好、技能背景 | "用户是 Go 专家，React 新手" |
| `project.md` | 项目约定、在途决策 | "正在迁移认证模块，截止本周五" |
| `feedback.md` | 用户对 Agent 行为的纠正 | "不要在响应末尾加总结段落" |
| `reference.md` | 外部系统的访问路径 | "Bug 追踪在 Linear 项目 INGEST" |

> **人写 vs Agent 写**：`EXPERIENCE.md` 是人写的陷阱预判（预防），Memory 是 Agent 自己踩坑后记的教训（复盘）。都服务于"下次不踩坑"，但主体不同。

### 组件 ⑨ 子代理编排（Sub-Agent Orchestration）

**是什么**：主 Agent 将子任务委派给独立 Agent 实例执行的机制。每个子代理拥有完全隔离的上下文窗口和推理循环，与主代理互不干扰。

**作用**：解决单 Agent 在面对复杂任务时的两个根本瓶颈——上下文容量不足、无法并行处理。

**核心机制**：

```
主 Agent 推理循环
  判断："这个任务有三个独立部分，可以并行"
         ↓ 分别调用 Agent 工具（可同步或后台并行）
         ├──→ 子 Agent A（独立内核）── 执行子任务 A ──→ 返回结果 A
         ├──→ 子 Agent B（独立内核）── 执行子任务 B ──→ 返回结果 B
         └──→ 子 Agent C（独立内核）── 执行子任务 C ──→ 返回结果 C
         ↓ 三个结果作为工具返回值，经感知层处理后追加入主上下文
主 Agent 汇总结果，完成整体任务
```

**四大价值**：

| 价值 | 说明 |
|------|------|
| **上下文隔离** | 子代理的大量探索不消耗主代理的窗口空间 |
| **并行执行** | 多个子代理同时运行，复杂任务耗时大幅压缩 |
| **角色专化** | 不同子代理配置不同系统提示，扮演规划师、执行者、评估者 |
| **防上下文污染** | 子代理的探索"噪音"不会污染主代理的推理质量 |

**与 Anthropic 三 Agent 架构的对应**：

```
Planner（规划师子代理）── 任务分解 ──→ 结构化计划
    ↓ 派发
Generator（生成器子代理）── 编写代码 ──→ 产出物
    ↓ 派发
Evaluator（评估器子代理）── 独立验收 ──→ 评分 + 问题报告
```

Anthropic 和 Google DeepMind 独立收敛到相同结论：**工程化外部评估器，比训练模型自我批评要容易得多**——这是自评估乐观偏差的架构解法，而非某个模型的问题。

**与 Skills 的关键区别**：

| 维度 | Sub-Agent | Skill |
|------|----------|-------|
| 执行上下文 | 独立隔离（全新内核实例） | 主 Agent 当前上下文内 |
| 并行能力 | 支持（多个同时派发） | 不支持（串行注入） |
| 适合场景 | 重型子任务、大量探索、需要上下文隔离 | 标准工作流指引、步骤提示 |
| 上下文消耗 | 不消耗主 Agent 窗口 | 消耗主 Agent 窗口 |

## 3. 内核与项目空间的接口

内核无法直接干预，但项目空间通过四个接口影响内核行为：

```
项目空间                            Agent 内核
──────────                          ──────────

CLAUDE.md ──────────────────────→  System Prompt
（全局规则、架构约束）               （Agent启动时读入，全程有效）

.claude/skills/ ────────────────→  工作流注入
（按需激活的操作规程）               （识别任务意图后动态追加进上下文）

.mcp.json + MCP Server ─────────→  工具扩展
（工具声明与实现）                   （Agent可调用的能力集扩大）

.claude/memory/ ────────────────→  跨会话持久化
（用户偏好、项目约定、历史教训）      （新session启动时注入，恢复跨会话状态）
```

**每个接口的设计原则**：

| 接口 | 关键设计原则 |
|------|------------|
| **System Prompt（CLAUDE.md）** | 精简为最重要的规则和约束，其余通过渐进披露按需加载；每加一条都占窗口空间 |
| **Skills** | 把"加载经验 + 执行任务"打包成工作流，比依赖 Agent 自觉查文档更可靠 |
| **MCP 工具** | 精心策划工具集，移除多余选项——Vercel 的案例证明：更少工具 → 更高成功率 |
| **Memory** | Agent 自己写、自己维护；人写的经验放 EXPERIENCE.md，Agent 自己踩坑后记的教训放 memory |

---

## 4. 关键结论：理解内核是为了建设项目空间

内核的每一条局限，都直接对应一类项目空间的建设方向：

| 内核局限 | 根本原因 | 项目空间的对应建设 |
|---------|---------|-----------------|
| 上下文窗口有限 | Agent 只能看到主动注入的部分，无关内容永远不存在 | 文档层渐进披露 + 经验文件精简 |
| 跨 session 无状态 | 每个 session 从零开始，进度与记忆全部消失 | Memory 文件 + 进度追踪文件 + Git 历史 |
| 概率性推理，行为不可保证 | 反思机制能缓解乐观偏差但无法根治 | 机器强制约束层（CI / Linter / hooks）+ 独立评估器子代理 |
| 工具调用受限于内置工具 | 内核工具集由厂商预定义 | MCP 扩展自定义工具 + Skills 工作流注入 |
| 感知能力受限于输出格式 | 感知层依赖结构化输入才能准确理解 | 脚本和 API 输出结构化结果（JSON、明确状态描述）|
| 单 Agent 处理复杂任务能力有限 | 窗口容量和串行执行的物理上限 | 子代理编排（主代理 + 专化子代理分工）|

内核提供原始能力，项目空间决定这些能力能不能被稳定、可治理地用于真实任务。一个粗糙的项目空间，再强的模型也只能低效试探；一个精心建设的项目空间，普通模型也能稳定完成复杂任务。

> **Harness Engineering 的核心价值：不是在教模型怎么回答，而是在设计模型怎么工作。**
