## 应用反馈层：应用给 Agent 的反馈

**信号方向**：应用系统 → Agent

**核心问题**：Agent 改了代码之后，它能不能自己知道对不对？

依赖两个条件：

- **可观测性**：系统能表达自身状态——结构化日志、有上下文的错误信息、状态机转换记录
- **可测试性**：行为能被可靠验证——清晰的测试接缝、稳定的自动化、明确的测试范围边界

两者缺一不可。可观测性差，Agent 读不懂现象；可测试性差，Agent 改完无法自证正确。

失效症状相同：人被迫成为信息中转站——粘贴日志、描述复现步骤、手动联调确认效果。

→ 详见《对象层反馈：可观测性与可测试性》

## 框架演化层：LLM 行为数据驱动 Harness 改进

**信号方向**：LLM 行为记录 → Harness

**核心问题**：Harness 如何基于 LLM 实际运行的数据持续进化，而不是靠人的经验拍脑袋调整？

AHE（Agentic Harness Engineering）用三个可观测性支柱来驱动这个演化循环：

| 支柱 | 观测对象 | 作用 |
|------|---------|------|
| **组件可观测性** | Skill / Prompt / 工具定义以文件形式存在，git diff 即变更记录 | 让每次 Harness 修改都可追溯 |
| **经验可观测性** | session JSONL → 失败模式 → 跨任务基准 | 从海量轨迹中蒸馏出有效信号 |
| **决策可观测性** | 每次修改附带"预测效果"，下一轮验证是否兑现 | 让演化有方向，而不是随机试错 |

失效症状：Harness 靠感觉调、调了不知道好没好、好了不知道为什么好——演化退化为 trial-and-error。

→ 详见《Agentic Harness Engineering》

## 两层的关系

两层是独立的反馈循环，但互相影响：

- **应用反馈层的信号质量，决定了框架演化层能分析什么。** 如果测试抖动、日志模糊，session 记录里充满噪声，从中提取的"失败模式"就是假信号。举个例子：某接口测试偶发超时，Agent 每次失败的 session 记录里原因各不相同——有时归咎于代码逻辑、有时怀疑环境。这种噪声进入框架演化层后，会导致 Skill 朝错误方向优化，越调越乱。
- **框架演化层的优化，反过来改善 Agent 在应用反馈层的工作方式。** 更好的 Skill 让 Agent 更准确地使用测试工具，更好的上下文注入让 Agent 更快读懂日志。

**一个实用的优先级判断**：

如果 Agent 频繁需要人介入——先看是哪一层的问题：

```
Agent 读不懂报错 / 测试结果不可信  →  应用反馈层问题，优先改应用
Agent 反复犯同一类错误 / Skill 失效  →  框架演化层问题，优先分析 session 日志、优化 Harness
```

两层同时失效时，优先修应用反馈层——没有可靠的信号，框架演化也是沙上建塔。
