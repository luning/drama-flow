## 从"云原生"理解"AI 原生"

Native 是"原生"的意思。要理解 AI 原生，先看我们熟悉的**云原生**。

早年服务是单体应用，后来演进为微服务：无状态、注册发现、容量缩放，大幅缓解了容量、成本和运维难题。微服务相比单体是巨大的技术进步，大到需要**围绕它来重新看服务如何架构、构建和运维**，甚至围绕它来划分组织（康威定律），决定分工协作模式。

> **核心判断**：巨大的技术进步，导致必须围绕它来重新组织各要素——这才算是"技术原生"的改变。

## 现有研发模式的根本假设

目前的研发模式是围绕**"有认知约束的人"**来设计的：

- 个体难以长期高效处理多个复杂领域的问题
- 大部分工程师只能聚焦少数领域高效工作
- 由此产生了：专业分工 → 职能团队 → 角色协作 → 流程规范

工程师作为知识工作者，最重要的工作是完成**"认知任务"**——需要收集信息、结合专业知识分析规划并执行的任务，其余任务大多已被自动化。

---

## Agent 打破认知约束

Agent 不仅能完成认知任务，还能快速理解多个领域的上下文，**突破了普通个体的认知约束**，分工协调的必要性也因此大幅降低。

当 Agent 开始胜任"多领域认知任务"后，一个朴素的想法便会产生：

> 给予足够的算力，就能指数级提升生产力。

如果指数级提升可行，就不再值得围绕"有认知约束的人"来设计开发模式，而是**围绕"有充足算力的 Agent"**——因为它完成的认知任务会比人多得多。

**围绕新的生产力来组织开发要素，这便是 AI"原生"。**

## AI Powered vs AI Native

### 现状：AI Powered

一个人能伺候一两个 Agent 就比较吃力，虽然有价值，但远未达到预期。这只能算 **AI Powered**，远没到 AI Native 该有的样子。

### 为什么还没到 AI Native？

认知任务可从两个维度区分：

|          | 简单任务         | 复杂任务               |
|----------|------------------|------------------------|
| **小范围** | 模块内 CRUD      | 模块性能优化           |
| **大范围** | 跨系统常规需求   | 跨系统偶现故障排查     |

---

## 影响 Agent 能力的三大成熟度

伺候 Agent 完成认知任务面临挑战，应对这些挑战依赖**三个方面的能力成熟度**：

### 1. 模型及 Agent 内核成熟度
包括模型能力（上下文窗口、推理质量）和 Harness 中的 Agent 内核部分，这部分是团队不可直接控制的外部能力。模型强大、窗口大、Agent 内核聪明 → 成熟度高

### 2. Harness 项目空间成熟度
Harness 中项目空间/工程空间的成熟度，是**研发团队可控**的部分，也是 AI 流行之前项目不会包含的**新增部分**。包括：
- 系统知识简洁完备
- 隐性知识被充分刻画
- 规格及约束充分可执行化
- 工具及流程完备
- 如何充分利用 Agent 内核能力

### 3. 项目架构与可观测性成熟度
原始项目本身需要持续优化的部分，即使没有 AI 支持也应坚持推进：
- 架构清晰，符合共识
- 自动稳定的端到端运行调试
- 环境及数据隔离
- 日志规范清晰

> 三方面成熟度越高，Agent 完成任务越如鱼得水，对工程师指导或信息搬运的依赖越少。

---

## 从小范围到大范围的演进路径

不同任务维度对三大成熟度的挑战完全不同：

| 任务类型 | 挑战程度 | 说明 |
|----------|----------|------|
| 模块内 CRUD（小范围简单） | 低 | 个人即可建立高成熟度 Harness，闭环容易 |
| 模块端到端需求（小范围复杂） | 中 | 需跨角色（产品/设计/开发/测试）建立可执行 Spec 机制 |
| 跨系统常规需求（大范围简单） | 高 | Harness 建设涉及多组织架构师，联调自动化难度大 |
| 跨系统复杂故障（大范围复杂） | 极高 | 当前条件下极难全面覆盖 |

**合理路径**：从小范围到大范围，从简单到复杂，逐步推进。

---

## 从 AI Powered 到 AI Native 的过渡

当上述改变逐步推进并取得成效后，从**以 Agent 为中心**的视角看：

- 现有的角色定位
- 分工方式
- 协作范围
- 团队边界

……都将显得不合时宜，需要相应调整。

**至此，AI Powered 就正式过渡到了 AI Native。**
