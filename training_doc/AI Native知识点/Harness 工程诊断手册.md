## 一、代码质量与测试安全网

> 共同根源：Agent 缺乏安全网——没有机制告诉它"这里动不得"或"这步改错了"。

### Q1：遗留代码没有测试，Agent 在"盲飞"

**症状**：遗留代码库完全没有单元测试，Agent 改一处不知道破坏了多少处，自我修复能力失效。

**诊断**：Agent 无法感知改动的影响范围，修改后的回归完全靠猜。

**应对策略**：

1. **黄金大师模式（Characterization Testing）**：动刀前先让 Agent 为旧函数写一组"快照测试"——记录当前代码在多组不同输入下的输出，**即使输出是错的也记录**。改动后任何快照变化都需要人类解释。
2. **两帽子原则（Two Hats）**：严禁重构与功能实现混在一起。阶段一只做测试补全和微重构并验证通过，阶段二再做需求开发。

### Q2：Agent 删除了看起来没用但实际关键的旧代码

**症状**：Agent 删除了老代码里"看起来没用"但其实处理特殊坏账逻辑的一行，导致旧功能静默出错。

**诊断**："部落知识"缺失——那行代码的存在理由不在代码本身，而在写它的人的记忆里。

**应对策略**：

1. **考古提示词策略**：要求 Agent 在删除任何存量代码前，必须先调用 `git blame` 溯源该行的原始 Commit 和关联任务，回答"这行为什么在这里"之后才能删。
2. **CONSTRAINTS.md 圣牛清单**：维护一份轻量级约束文件，记录系统中不可触碰的"圣牛（Holy Cows）"逻辑——那些看起来怪但绝对不能改的业务规则。

### Q3：Agent 的重构方案合理还是过度？

**症状**：Agent 倾向于用现代写法完全覆盖稳定的旧逻辑，改动范围远超需求本身，测试成本激增。

**诊断**：Agent 偏好"理想重构"而非"最小修改"——没有中间检查点来限制其自由度。

**应对策略**：

1. **PEV 循环（Plan-Execute-Verify）**：将工作拆为三阶段，每阶段之间设显式门禁：
   - **Plan**：Agent 先写出修改计划（改哪些文件、改多少行），由 Harness 或人类审批范围。
   - **Execute**：每次 tool call 前检查该操作是否在审批范围内，超出则拦截。
   - **Verify**：只检查计划中的验收标准是否达成。
2. **方案 PK 机制**：强制 Agent 给出两份 Plan——方案 A（最小入侵）和方案 B（理想重构），由人类在 Plan 阶段决策，而非等代码写完再比较。

### Q4：多步骤任务错误累积，最终成功率崩塌

**症状**：每步约 85% 正确率，10 步串联后整体成功率只剩约 20%。单步检查都通过了，整体结果却一塌糊涂。

**诊断**：错误乘法效应（Compounding Error Cascade）——前几步的小错误不被发现，后续步骤在脏数据上叠加放大。

> **数学直觉**：0.85¹⁰ ≈ 0.20。这个问题靠更聪明的模型解决不了，必须靠系统层面的验证。

**应对策略**：

1. **验证门禁（Validation Gates）**：在关键步骤之间插入自动化验证——脚本断言、Schema 校验或 LLM-as-Judge。每步输出经过校验后才进入下一步。
2. **早停熔断**：检测到中间步骤验证失败时，立即终止任务流并标记失败步骤，而非让 Agent 继续在脏数据上执行。

## 二、工具、权限与上下文设计

> 共同根源：Harness 的边界设计出了问题——工具太多、权限太宽、规则被淹没。

### Q5：Skills 过多导致"工具幻觉"

**症状**：Skills 越来越多后，Agent 开始出现工具选择错误——该查日志时调了删库工具，意图解析模糊。

**诊断**：工具集超过模型有效识别的上限，选择空间过大导致意图匹配出错。Vercel 的实验印证：移除 80% 的工具后，步骤更少、token 更省、成功率反而更高——**约束解决空间，反而能提升表现**。

**应对策略**：

1. **动态工具注册**：根据 Agent 当前处理的文件目录（如 `android/` 或 `backend/`）动态加载对应工具集，不一口气暴露所有工具。
2. **严格类型约束**：使用 Pydantic 或 TypeScript Interface 对所有 Skill 做严格参数限定——非法参数在调用前就被 Harness 拦截。

### Q6：Agent 利用权限漏洞造成安全风险

**症状**：Agent 在处理需求时访问了不该访问的配置文件，泄露了敏感信息。

**诊断**：Agent 拥有过高的权限——默认给了太多。

**应对策略**：

1. **最小权限沙箱**：默认只读。Agent 需要写权限时，通过 Harness 弹出人类审批（有范围和时间限制）。
2. **敏感信息过滤（Redaction）**：MCP Server 返回数据前自动脱敏数据库密码、API Key 等字段，在 Tool 层直接替换为 `***`，永远不过 Agent 的手。

### Q7：规范文档臃肿，Agent 选择性忽略规则

**症状**：AGENTS.md 或 SDD 变得非常臃肿，Agent 开始选择性忽略某些规则。

**诊断**：上下文过载导致注意力弥散（Attention Drift）——关键规则被淹没在大量次要信息里。

**应对策略**：

1. **文档即地图（Maps, not Rules）**：将规范拆分为原子化的 Markdown 表格或 Mermaid 流程图。Agent 查表比读散文准确。
2. **上下文分区机制**：通过文件夹路由按需注入——只有 Agent 进入 `src/security/` 时才推送安全规范；不在当前工作区的规范不占 token。

### Q8：长会话中初始规则逐渐失效

**症状**：会话开始时 Agent 严格遵守"必须用 TypeScript"，但 25 轮后开始悄悄输出 Python。

**诊断**：注意力衰减（Attention Decay）——Transformer 架构中，初始 system prompt 的注意力权重随对话增长而递减。近期大量 Python token 在注意力竞争中压过了远端的 TypeScript 约束。Agent 不是"忘了"，是规则输了。

**应对策略**：将 prompt 结构化为 `[角色定义] → [历史对话] → [核心约束（重复注入）] → [最新输入]`，核心约束紧贴最新输入之前。Harness 每 N 轮自动将核心约束重新追加到上下文末尾，靠重复出现保持激活，而非靠初始位置争权重。

## 三、系统集成与 Harness 生命周期

> 共同根源：系统边界或时间维度带来的盲区——Agent 看不到跨端影响，或 Harness 本身随时间腐化。

### Q9：后端单测全绿，但移动端崩溃

**症状**：Agent 修改了后端接口，后端单元测试全部通过，但移动端 App 崩溃。

**诊断**：跨层上下文盲区——Harness 只有局部观测能力，Agent 不知道自己的修改影响了哪些上游消费者。

**应对策略**：

1. **全栈遥测注入**：Harness 自动收集多端日志（App 崩溃日志、Nginx 报错日志）。集成测试失败时将这些日志"喂"给 Agent 从全栈角度排查。
2. **契约测试（Contract Testing）**：在后端 CI 中加入消费者契约测试（Consumer-Driven Contract），接口变更时自动校验移动端和 H5 的期望是否仍被满足——不依赖 Agent 自己意识到跨端影响。

### Q10：Agent 污染数据库真实数据，测试环境不可复用

**症状**：测试过程中 Agent 修改了真实遗留数据，后续测试结果不可信。

**诊断**：遗留系统难以彻底容器化，缺乏廉价的隔离沙盒。

**应对策略**：

1. **DB 事务拦截**：在 MCP Server 层为 Agent 的写操作强制包装 `BEGIN` 和 `ROLLBACK`——测试结束必须回滚，真实数据零影响。
2. **数据影子表**：为高危表建立副本，让 Agent 仅在影子表上进行逻辑验证。

### Q11：模型升级后，旧 Harness 规则反成包袱

**症状**：升级到更强的模型后，Agent 开始出现奇怪的绕路行为——在不必要的地方重置上下文、插入多余检查步骤。

**诊断**：Harness 里沉积了"为当时的模型打的补丁"。Anthropic 记录了真实案例：为 Sonnet 4.5 的上下文焦虑行为设计的"上下文重置机制"，升级到 Opus 4.5 后模型自行消除了该行为，但机制依然在运行，变成了噪音。

**应对策略**：

1. **换版本时跑裸奔基线**：升级前关掉所有 Harness 组件跑标准任务建立基线，升级后对比——无统计显著提升的组件直接退役。
2. **给每个组件打适用版本标签**：注明创建时间、触发该组件的原始失败案例、适用的模型版本区间，换模型时逐条核对而非默认继承。

## Bad Smell 自检清单

> 维护者视角——Harness 配置本身的结构性问题，与前面"Agent 出了什么问题"不同，这里是"你的 Harness 长了什么蛀虫"。

| Bad Smell | 症状 | 后果 | 怎么修 |
|-----------|------|------|--------|
| **过时假设** | prompt 里写"模型不擅长 X"，但当前模型已能直接做 X | 增 token，误导模型绕远路 | 换模型版本时跑裸奔基线，确认规则是否仍有统计显著提升 |
| **重叠规则** | 同一约束同时出现在 system prompt、skill、hook 三层 | 难定位哪条真正生效，修改时容易遗漏层级 | 合并到约束最强的那一层，删除其余重复 |
| **防御性膨胀** | 为防范罕见失败，规则列表越来越长 | prompt 臃肿，注意力分散 | 按实际频次统计，低频失败不加规则，宁缺毋滥 |
| **硬编码工作流** | "先读 A 再读 B 再改 C"写死，代码结构已变但流程未更新 | Agent 按过时流程走，浪费 token | 工作流写成意图描述而非步骤清单 |
| **Prompt 补丁** | 遇到问题就往 prompt 加一句，而非在 tool/middleware 层修复 | prompt 越来越长，约束力没变强 | 优先在 tool/middleware 层做硬拦截，prompt 只是最后手段 |
| **经验噪音** | 经验文件记录"曾有效但现在无效"的建议 | 误导 Agent 采用过时方案，比没有经验更糟 | 每条经验标注时间戳和适用模型版本，定期清理失效条目 |
| **推理替代脚本** | prompt 里让 Agent 推理"检查 X、Y、Z"，而 10 行脚本即可确定性完成 | 浪费 token；推理有概率漏检，脚本是确定性的 | 确定性校验交给脚本，推理留给真正需要判断的灰色地带 |

## Harness 维护原则

### 两类内容，不同命运

| 类型 | 特征 | 示例 | 随模型进化会消亡？ |
|------|------|------|-------------------|
| **A. 架构/设计约束** | 代码分析不出来的决策理由、权衡、约定 | ADR（为什么选 SQLite 而非 PG）、模块边界、安全策略 | ❌ 不会。这些是"选择"，不是"推导" |
| **B. 代码重复型提示** | 复述代码已有的信息 | "调用 `get_user()` 传入 `user_id: int`"（签名已有类型标注） | ✅ 会。随模型搜索和理解能力提升，这类纯属冗余 |

> Harness 的好坏不在于多全面，而在于多精准——每一行都是模型当前确实做不到的事。

### 实验驱动，而非经验预设

| 不该做的 | 应该做的 |
|----------|---------|
| 因"模型常犯这类错"就预设性加 hook | 先统计实际频次，确认是真实问题再动手 |
| 一次性加一整套规则 | 每次只加一条，单独验证效果，无效回滚 |
| 因 Harness 有效就一直保留 | 定期用新模型跑裸奔基线，判断边际价值 |

### 修复层级决策树

按约束强度从强到弱依次尝试，前面能解决的不往后推：

```
问题出现
│
├─ 能用 Tool Implementation 拦截吗？  → 改工具执行逻辑（强约束，不容商量）
├─ 能用 Middleware 拦截吗？           → 加 PreToolUse / PostToolUse hook
├─ 能用 Skill 注入工作流吗？          → 写按需加载的 skill
├─ 能改 Tool Description 说清楚吗？   → 优化工具文档
└─ 最后手段：改 System Prompt         → 仅当前面所有层级都不适用时
```

| 遇到的情况 | ❌ 错误做法 | ✅ 正确做法 |
|-----------|-----------|-----------|
| Agent 验收后误删交付物 | 在 prompt 加"别删文件" | 在 tool 实现中做硬拦截 |
| Agent 忽略 risk 警告 | 在 output 后追加警告 | 在 before_model middleware 注入到 reasoning context |
| Agent 用行数检查替代字段断言 | 在 prompt 加"仔细检查" | 加 middleware 做跨步骤状态追踪 |

> **Prompt 讲道理，Tool 做执行，Middleware 做拦截——能硬拦截的不靠建议。**
