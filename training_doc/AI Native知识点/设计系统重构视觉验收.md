可执行设计系统并不消除视觉验收，而是**重构它的层次**，让每层都有更合适的工具负责。

| 验收层次 | 核心问题 | 主要方式 | 执行者 |
|---------|---------|---------|-------|
| 代码合规层 | 代码是否使用了设计系统？ | Skill 审查 + ESLint/CI 拦截 | 工具自动 |
| 渲染正确层 | 正确代码是否正确渲染？ | 截图对比（H5 有成熟工具，移动端需自研） | 工具为主，人工兜底 |
| 体验质量层 | 渲染正确，体验是否好？ | 人工走查，关注节奏与情绪 | **人工（核心价值）** |

前两层的人工成本由工具承接，人工验收的精力才能集中在真正需要判断的地方。

## 第一层：代码合规

设计系统建得再好，如果开发（或 AI）绕过它写了 hardcoded 值，后面两层的保障都会失效。这层是前置检查，也是最容易被忽视的。

**典型问题：**

```tsx
// 违规：绕过 Token 直接写值
<div style={{ color: '#6C5CE7', padding: '16px' }}>

// 合规：通过 Token 引用
<div style={{ color: tokens.color.primary, padding: tokens.spacing.md }}>
```

**两道防线：**

**防线一：生成时拦截（Skill）**

在 AI 生成原型的 Skill 中增加审查步骤——生成代码后自动扫描 hardcoded 色值或裸 px 值，发现即要求重新生成：

```
AI 生成页面代码
    ↓ Skill 审查步骤
扫描 hardcoded 色值（正则匹配 #[0-9a-fA-F]{3,6}）
扫描裸 px 值（非来自 tokens.* 的间距）
    ↓ 发现违规
要求 AI 修正，重新引用 Token
    ↓ 通过
提交代码
```

**防线二：提交时拦截（CI）**

在 ESLint 和 Stylelint 中配置规则，无论人工还是 AI 写的代码，一旦含 hardcoded 色值，CI 直接报错：

```js
// .eslintrc 规则示例
'no-restricted-syntax': ['error', {
  selector: 'Literal[value=/^#[0-9a-fA-F]{3,6}$/]',
  message: '禁止硬编码色值，请使用 tokens.color.*'
}]
```

## 第二层：渲染正确（H5/Web）

代码正确使用了设计系统，不代表页面渲染就正确。布局在特定内容下可能被压缩变形，flex/grid 在某些数据边界下可能错乱，组件在真实 viewport 下可能溢出或遮挡——这些是**运行时问题**，代码审查发现不了。

**典型问题：**

- 剧集标题超过两行时，卡片高度撑开，破坏网格对齐
- 按钮文字过长时，padding 被压缩，不再符合设计规范
- 在小屏设备上，两栏布局因内容宽度挤成一栏

**H5/Web 场景有成熟工具链：**

| 工具 | 适用场景 |
|------|---------|
| **Storybook + Chromatic** | 组件级别：各种 props 组合的视觉快照，PR 合并前自动对比 |
| **Playwright / Cypress** | 页面级别：真实浏览器截图，对比基准快照，捕获整页布局变化 |
| **人工走查** | 边界内容（极长文本、零条目、大量条目）、真实设备 viewport |

核心思路是建立**基准快照**：第一次验收通过后保存截图，后续改动自动对比，有视觉差异才进入人工判断。

## 移动端渲染验收的技术挑战

第二层在移动端 App 场景情况复杂得多——目前没有任何一个现成工具能开箱解决，几乎必然走向自研或深度组合。

### 根本难点：三类不可忽视的噪音

移动端视觉验收的核心挑战不是"怎么对比"，而是**怎么区分"真正的回归"和"正常的差异"**。

| 噪音类型 | 具体表现 | 为什么不能简单过滤 |
|---------|---------|-----------------|
| 动态内容 | 用户名、剧名、时间戳每次不同 | 过滤太宽 → 漏掉真实文案错误 |
| CDN 图片 | 封面图 URL 一致但渲染结果可能因缓存、解码差异而不同 | 无法依赖内容 hash |
| 平台渲染差异 | 抗锯齿、字体 fallback、GPU 合成层差异 | 不同设备/API level 表现不一致 |

### 为什么现有工具不够

H5 有 DOM 可以拿，能做结构化对比；Android 原生 App 通过 UI Automator 能拿到 ViewTree（XML 结构），但存在关键限制：

- **ViewTree 能告诉你布局，告诉不了你渲染**——颜色、渐变、字体替换、裂图，XML 里看不出来
- **WebView 内部 UI Automator 进不去**——H5 页面的内部结构对 Android 测试框架完全不透明，只能靠截图
- **动态区域识别没有标准答案**——哪些区域应该被忽略，每个项目不同，现成工具要么全比要么手工配

任何单一方案都有盲区，必须**分层叠加、互补覆盖**。

### 分层叠加的应对思路

```
高信号/低噪音  ┌──────────────────┐
               │ 布局树语义对比    │  能覆盖：元素偏移、缺失、文案错误
               ├──────────────────┤  抓不到：颜色/字体/渲染异常
               │ 区域 ROI 像素检查 │  能覆盖：关键区域颜色、图标、背景
               ├──────────────────┤  抓不到：H5 内部、动态区域误报
               │ AI 视觉评估       │  兜底：裂图、字体替换、H5 CSS 异常
               └──────────────────┘
 低信号/高噪音
```

**布局树语义对比**：不碰像素，比较 UI Automator XML 的结构化语义。核心是不比"树的形状"，比"用户可感知的语义特征"——容器类型互认、子节点排序归一、bounds 差异 ≤ 2px 容忍、纯容器层变化忽略。真正触发报警的差异：resource-id 增删、交互元素偏移 > 8px、静态文本变化、可点击区域数量变化、visibility 变化。

**区域 ROI 像素检查（需自研）**：布局树覆盖不到的颜色、图标、背景渐变，需要按区域做像素级检查。动态区域自动识别是核心工程问题——推荐**多 baseline 消噪**：同一页面跑 3 次，自动 diff 各次截图，反复出现差异的区域标记为 IGNORE，稳定区域出 diff 才报警，3 次运行后自动收敛。不同组件差异化策略：ImageView 只查 bounds、动态 TextView 忽略 text 只查 bounds、Button 查 text + bounds + 可点击态、分隔线/背景只查颜色和尺寸。

**AI 视觉兜底**：前两层都通过，渲染仍可能异常——字体替换、H5 CSS 渲染异常、裂图、颜色编译错误。让 AI（Claude）看截图评估，前两层已过滤掉布局噪音，AI 可聚焦真正的渲染问题，判断质量和 token 成本都更可控。

### 三层串联流水线

```
布局树对比 ──pass──→ ROI diff ──pass──→ AI 看图评估 ──pass──→ ✅ 通过
   │ fail                 │ fail                 │ fail
   ↓                     ↓                     ↓
报具体错误            标记可疑区域                输出差异描述
（哪个元素偏移/缺失）  （截图 + 热力图）          （自然语言报告）
```

### 建设路线与上限

| 阶段 | 能力 | 投入 | 覆盖范围 |
|------|------|------|---------|
| P0 基线 | 多 baseline 消噪 + 布局树语义对比 | ~2 天 | 原生页面 70% 视觉回归 |
| P1 增强 | ROI 像素 diff + H5 CDP DOM 对比 | +2 天 | 关键区域颜色/图标 + H5 布局 |
| P2 AI 兜底 | Claude 看图评估接入 | +1 天 | 剩下 30% 渲染/样式异常 |
| P3 设计稿校验 | 设计稿 → baseline 的一次性 AI 评估 | +1 天 | 新功能首次上线前的设计还原度检查 |

需要承认的上限：

1. **Golden image 不应是设计稿，而是真机 baseline。** 设计稿只在新功能首次上线前做一次性 AI 对比评估，之后转为真机自动化对比，设计稿 diff 噪音太大不适合持续回归。
2. **三层叠加仍有约 30% 的盲区。** 主要集中在 H5 WebView 内部渲染、跨设备字体差异、GPU 合成层异常——剩余部分由人工走查兜底。
3. **H5 是结构性难点，不是方案问题。** WebView 内部对测试框架不透明是平台限制，精度天然低于原生，无法通过工程手段消除。

## 第三层：体验质量

这是目前最难自动化的层次，也是设计师最核心的判断价值所在：

- 页面的视觉节奏和呼吸感
- 信息层级是否清晰，阅读路径是否自然
- 交互动效是否流畅，情绪传达是否到位
- 跨页面的一致性感受

**这一层的验收方法不变，但精力得以集中。** 因为前两层的合规问题已由工具负责，设计师在走查时不再需要分心核对色值和间距，可以把全部注意力放在体验判断上。
