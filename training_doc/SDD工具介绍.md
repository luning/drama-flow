# SDD 工具全景 —— 从 Prompt SDD 到工具化 Spec-Driven Development

## 一、为什么需要 SDD 工具？

### 1.1 从 Vibe Coding 到 SDD

2025 年 AI 辅助编码已成为主流，但一个残酷的现实浮出水面：**62% 的 AI 输出代码需要大量人工修正**。单纯依赖"聊天式编程"（Vibe Coding）在小型 Demo 或一次性脚本中效率惊人，但在以下场景中迅速失效：

- **跨模块改造**：改一个 API 涉及前端、后端、数据模型，AI 容易遗漏依赖
- **存量系统维护**："不要破坏已有功能"的约束比"实现新功能"更难传达
- **团队协作**：不同开发者用不同的 Prompt 风格，产出质量方差极大
- **长上下文衰减**：多轮对话后 AI 忘记早期决策，产生不一致代码

**Spec-Driven Development（SDD）** 的核心思想是：**在编码之前，先把"怎么做才算完成"写清楚**。这一思想并不新——BDD、TDD、ATDD 都是它的前身。SDD 的不同之处在于，规格不再仅仅是供人阅读的文档，而是**直接驱动 AI Agent 行为的可执行工件**。

### 1.2 为什么需要工具？

早期团队的"Prompt SDD"做法是：在 CLAUDE.md 中写一段约束，要求 Agent 每次任务前阅读 SPEC.md。这种做法有效，但有三个局限：

| 局限 | 表现 | 后果 |
|------|------|------|
| **约束易遗漏** | 只靠 Prompt 提醒，Agent 可能在复杂任务中跳过自检 | AC 覆盖率下降 |
| **AC 无法自动化验证** | 人工逐条对照，耗时且容易疲劳 | 验收流于形式 |
| **Traceability 缺失** | 做了哪些变更、对应哪个 AC、是谁批准的，没有记录 | 审计困难 |

SDD 工具正是为解决这些问题而生——它们将规格从**文本**升级为**可执行的流程单元**，提供结构化的变更管理、自动化验证和上下文隔离。

## 二、SDD 工具的核心能力框架

所有 SDD 工具都围绕一个基本循环构建：

```
讨论/探索 → 规划 → 执行 → 验证 → 归档
```

在这个循环基础上，不同工具在以下维度上产生分化：

### 2.1 规格管理

规格是 SDD 工具的核心资产，不同工具在规格管理上的取舍：

| 维度 | GSD | OpenSpec | Spec Kit | Kiro | Taskmaster |
|------|-----|----------|----------|------|------------|
| 编写格式 | 对话驱动 | Markdown 目录 | Markdown + YAML | 自然语言 | PRD → 任务树 |
| 版本追踪 | Git | 变更目录 | Git + Constitution | IDE 历史 | Git |
| 规格粒度 | 功能级 | 变更级 | 功能级 | 意图级 | Story 级 |

### 2.2 上下文策略

这是 SDD 工具最核心的技术差异，也是区分工具能力的关键指标：

- **新鲜上下文隔离**（GSD 代表）：每次执行从项目工件重新构建上下文，而非累积聊天历史。解决"上下文腐烂"问题——执行到第 10 个任务时，Agent 对前 9 个的记忆仍然清晰一致，不会出现"忘记早期决策"的情况。
- **工件结构管理**（Spec Kit / OpenSpec 代表）：通过级联文件（spec → plan → task → research）创建隐式上下文边界。Agent 在规格阶段加载宪法和功能规格，计划阶段只看到计划相关文件，执行阶段聚焦实现。每个阶段的上下文被精准控制在当前所需的范围内。
- **变更隔离**（OpenSpec 特有）：每个变更拥有独立目录，防止跨变更污染。存量系统上同时进行两个功能开发时，各自的 spec、task、design 互不干扰。
- **持久化上下文**（Taskmaster AI 代表）：维持长期持久化上下文，通过结构化提示词和多模型路由管理，无显式隔离机制。

### 2.3 执行深度

- **编排型**（GSD）：工具管理任务的并行执行、代理调度、依赖追踪。GSD 的波级并行是代表——4 个研究器可同时工作，独立任务并行执行，依赖任务自动等待。
- **委托型**（Taskmaster AI）：工具负责规划和分解，实际编码交给 Cursor / Claude Code 等外部代理执行。
- **中间态**（OpenSpec / Spec Kit）：工具管理"构建什么"（spec + task），不管理"如何构建"（执行交给底层 AI 代理）。

### 2.4 平台集成

- **广度型**：OpenSpec 支持 20+ 工具、Spec Kit 支持 18+ 代理——使用跨平台斜杠命令，不绑定特定 IDE
- **深度型**：Taskmaster AI 通过 MCP 与 Cursor 深度集成、Kiro 自建 IDE——提供第一类体验但锁定平台
- **中间态**：GSD 支持 Claude Code / OpenCode / Gemini CLI 三个运行时，有深度适配层但数量有限

## 三、主流 SDD 工具详解

### 3.1 GSD（Get Shit Done）

| 属性 | 详情 |
|------|------|
| **GitHub** | 16.7k stars, MIT |
| **平台** | Claude Code, OpenCode, Gemini CLI |
| **定位** | 执行优先的上下文工程系统 |

GSD 不追求流程仪式感，核心解决两个问题：**上下文腐烂**和**执行效率**。其哲学是交付结果，而不是流程文档。

**四阶段流程**：讨论（/gsd:discuss）→ 计划（/gsd:plan）→ 执行（/gsd:execute）→ 验证（/gsd:verify）。其中执行阶段将任务拆分为"波"（Wave），独立波并行执行，依赖波串行等待，同时调度 4 个研究器 + 规划器 + 执行器 + 验证器 + 调试器的多代理架构。

**新鲜上下文隔离**是 GSD 最核心的技术点：每个执行单元拥有独立的上下文窗口（Claude Code 上接近 200K tokens），从项目工件构建而非累积聊天历史。执行 10 个任务不会出现早期决策被遗忘的问题，上下文不会随时间线性膨胀。

**适用场景**：长任务（跨半天或数天）、跨模块改造（涉及 3+ 模块）、复杂重构。在 DramaFlow 课程的迭代 3（需求演进）中引入——存量改造最大的挑战不是"改哪里"，而是"让 Agent 理解上下文不丢失"。

---

### 3.2 OpenSpec（Fission AI）

| 属性 | 详情 |
|------|------|
| **GitHub** | 24.9k stars, MIT |
| **平台** | 20+ AI 工具（Claude Code, Cursor, Windsurf 等）|
| **定位** | 棕地优先的变更隔离框架 |

OpenSpec 自称**"棕地优先"**——专为已有代码库的团队设计。其切入点是**变更隔离**：在存量系统上，最怕的不是改不动，而是改 A 的时候破坏了 B。

**变更隔离结构**：每个变更拥有独立目录 `openspec/changes/<name>/`，内含 `proposal.md`（为什么改）、`design.md`（怎么改）、`tasks.md`（拆解步骤）、`specs/`（验收标准）。这种结构让更改不串扰、提供完整审计追踪、支持渐进式采用。

**核心命令**：`/opsx:new` 创建提案、`/opsx:ff` 快速前进（一步生成所有规划工件）、`/opsx:explore` 探索模式、`/opsx:apply` 执行、`/opsx:verify` 验证、`/opsx:archive` 归档。支持双模式：完整模式适合复杂变更，快速前进模式适合中等复杂度变更。

**适用场景**：存量系统迭代、需要审计追踪的合规场景、多人并行变更。在 DramaFlow 课程的迭代 2 中替代纯 Prompt SDD，解决约束遗漏率高、AC 自动化验证困难、跨变更追溯缺失三个问题。

---

### 3.3 Spec Kit（GitHub）

| 属性 | 详情 |
|------|------|
| **GitHub** | 70.8k stars, MIT |
| **平台** | 18+ AI 编码代理（Claude Code, Cursor, Copilot 等）|
| **定位** | 企业级规格治理工具 |

Spec Kit 来自 GitHub 官方，强调**"规格不服务于代码；代码服务于规格"**。通过"项目宪法"机制确保团队规范。

**项目宪法**：`.specify/constitution.md` 定义团队规则（如"所有 API 必须包含 OpenAPI 文档"），每次任务执行时被加载，确保 AI 生成代码遵循团队标准。

**8 步结构化闭环**：初始化 → 定义宪法 → 编写功能规格 → 返回澄清（循环）→ 生成实现计划 → 分解任务 → AI 执行实现 → 验证分析。生成丰富的工件集：`spec.md`、`plan.md`、`research.md`、`data-model.md`、`contracts/` 等。

**适用场景**：大型企业项目、跨团队协作、需要向上汇报和审计的团队。弱点在于**流程较重**——8 步闭环在大型项目中提供必要治理，但在快速原型迭代中显得笨重。

### 3.4 Kiro（AWS）

| 属性 | 详情 |
|------|------|
| **平台** | 独立 IDE（桌面应用）|
| **定位** | 代理式 IDE，个人/小团队加速器 |
| **集成** | MCP 插件生态 |

Kiro 是一个**代理式 IDE**，将 AI 代理内置为 IDE 的一等公民。口号是"意图即代码"。

**代理驱动闭环**：输入意图 → 代理规划 → 执行前置钩子 → AI 生成代码 → 执行后置钩子（测试/lint）→ 审查/转向 → 一键部署。通过 `steering.md` 控制 AI 行为。支持三种 Workflow：Kiro Design（设计优先）、Kiro Build（构建优先）、Kiro Bugfix（修复优先）。

**适用场景**：个人独立开发者（最快"想法→产品"路径）、小团队早期原型验证。局限在于限定在桌面 IDE 内，无法作为 CLI 集成到 CI/CD 流程，规格追踪能力较弱。

---

### 3.5 Taskmaster AI

| 属性 | 详情 |
|------|------|
| **GitHub** | 25.5k stars, MIT + Commons Clause |
| **平台** | Cursor（第一类）、Windsurf、VS Code、Claude Code |
| **定位** | 将 AI 视为项目经理，专注任务分解 |

Taskmaster AI 的独特切入点是：**AI 不是开发者，而是项目经理**。将 PRD 解析为分层的、感知依赖关系的任务列表，再交给编码代理执行。

**多模型架构**：主模型（核心操作）+ 研究模型（获取最新信息）+ 后备模型（降级兜底）。PRD 被解析为依赖感知任务图，阻塞任务先执行，独立任务并行。与 Cursor IDE 深度 MCP 集成，在 Cursor 内部直接操控编辑器。

**适用场景**：以 Cursor 为主要 IDE 的团队、从 PRD 出发的完整项目管理。需注意许可证为 MIT + Commons Clause，限制将软件作为服务销售。

### 3.6 快速上手指南对比

各工具的安装与首次使用路径对比：

| 工具 | 安装方式 | 初始化步骤 | 第一个命令 | 首个任务完成时间 |
|------|----------|-----------|-----------|----------------|
| **GSD** | 复制 Skill 文件到项目 | 将 GSD 文件放入 `.claude/skills/` | `/gsd:discuss-phase` | 视任务复杂度 |
| **OpenSpec** | `npm install -g @fission-ai/openspec` | `openspec init` | `/opsx:new my-change` | 10-20 分钟 |
| **Spec Kit** | `pip install specify-cli` | `specify init my-app --ai claude` | `/speckit.specify` | 30-60 分钟 |
| **Kiro** | 官网下载安装包 | 安装即用 | `/kiro:init` 生成 steering.md | 5-10 分钟 |
| **Taskmaster AI** | npm 安装 + Cursor 配置 | 在 Cursor 中启用扩展 | 输入 PRD 文本 | 15-30 分钟 |
| **Trellis** | `npm install -g @trellis/cli` | `trellis init` | `trellis spec create` | 15-30 分钟 |
| **Superpowers** | 复制 Skill 文件到项目（与 GSD 同源） | 放入 `.claude/skills/` | 无需显式触发，自动生效 | 即装即用 |

### 3.7 SDD 生态中的其他代表性工具

除了上述 5 款主流 SDD 框架，社区中还涌现了一批专注特定环节的工具，以下两款值得关注：

#### Trellis

| 属性 | 详情 |
|------|------|
| **定位** | 跨平台工作流与项目记忆组织 |
| **核心理念** | 用 Specs / Tasks / Workspace 三层结构组织跨平台工作流 |

Trellis 的切入点是：当你同时在 Claude Code、Cursor、GitHub Copilot 等多个 AI 工具间切换时，如何保持上下文和工作流的连续性？它通过三层抽象来解耦：**Workspace** 定义项目全景，**Specs** 定义功能规格，**Tasks** 定义执行单元。Trellis 的设计哲学是"工具无关"——你的 Spec 和 Task 可以在任何 AI 工具中加载执行，不绑定特定平台。适合在多人多工具环境中需要统一工作流定义的团队。

#### Superpowers（GSD 作者）

| 属性 | 详情 |
|------|------|
| **定位** | 方法论与技能增强层 |
| **关联** | 与 GSD 同作者，可配合使用 |

Superpowers 不做完整的 SDD 流程编排，而是专注于一件事：**把 TDD、Code Review、调试等传统工程习惯编码为 Agent 的默认动作**。它是一组可复用的 Agent Skills，安装后 Claude Code 会在日常开发中自动执行测试驱动、审查代码质量、定位 Bug 根因。适合已经有一套成熟 SDD 工具、希望补充工程纪律的团队。

安装方法：在cli中运行`/plugin install superpowers@claude-plugins-official`，然后重启vs code就可以在claude code插件中使用了。

## 五、从 Prompt SDD 到工具化 SDD 的演进路径

根据 DramaFlow 课程的设计经验，SDD 的引入可以分为三个渐进层次：

### 层次一：Prompt SDD（零成本切入）

**做法**：在 CLAUDE.md 中写入 SDD 约束

```markdown
## SDD 最小约束
1. 接受任务前，先阅读对应模块的 SPEC.md 中的验收标准
2. 生成代码后，逐条自检 AC，确保所有验收标准被覆盖
3. 修改已有 AC 时标注变更记录，保留历史意图
```

**适合**：小团队、早期项目、单人或双人协作

**局限**：依赖 Agent 自觉性，缺乏强制力和自动化。DramaFlow 课程的迭代 1 使用此方式，迭代 2 复杂度上升后转向工具化 SDD。

**效果对比**：

| 维度 | Prompt SDD | 工具化 SDD |
|------|-----------|-----------|
| AC 自检 | 依赖 Agent 自觉 | 工具强制检查 |
| 变更管理 | 靠开发者记忆 | 结构化目录归档 |
| 上下文策略 | 累积聊天历史 | 新鲜隔离 / 工件边界 |
| 协作方式 | 顺序依赖 | 变更级并行 |
| 审计能力 | Git log | 变更目录 + 归档记录 |
| 自动化验证 | 无 | spec-validate 等专用命令 |

### 层次二：轻量工具 SDD（推荐入门）

**做法**：引入 OpenSpec 或 GSD

OpenSpec 适合存量系统——变更隔离结构能从第一个变更开始就建立正确的工作习惯。在 DramaFlow 课程的迭代 2 引入，效果显著：AC 覆盖检查从"人工逐条对照"变为 `/opsx:verify` 一键扫描。

GSD 适合复杂开发任务——新鲜上下文隔离在长任务中效果显著。在 DramaFlow 课程的迭代 3（需求演进改造）引入。

**适合**：复杂项目、需要多人并行、存量改造。建议从 OpenSpec 开始，遇到长任务上下文衰减问题时补充 GSD。

**收益**：AC 自动化验证、变更追踪、上下文管理

### 层次三：完整 SDD 工具链

**做法**：根据场景组合工具

- 规划：OpenSpec（change proposal）
- 执行：GSD（波级并行 + 上下文隔离）
- 测试：spec-validate（AC 覆盖检查）
- 治理：Spec Kit（宪法 + 规范）
- 原型：Kiro（快速验证）

**适合**：大型团队、企业级项目、需要完整 SDLC 治理。需注意工具链本身的学习成本，建议分阶段引入而非一次性搭建。

---

## 六、选型决策指南

### 6.1 快速决策树

```
你的项目是存量系统还是绿地项目？
├── 存量系统 → OpenSpec（变更隔离是刚需）
│
└── 绿地项目 → 团队规模和协作模式？
    ├── 独立开发者 → Kiro（最低摩擦）
    ├── 小团队（2-5人） → GSD（执行效率优先）
    ├── 大团队（5+人） → Spec Kit（治理优先）
    └── 多工具混合团队 → Trellis（工作流统一）
```

### 6.2 场景推荐

| 场景 | 推荐工具 | 核心理由 |
|------|----------|----------|
| 维护一个 5 年老的 Java 项目，持续迭代 | **OpenSpec** | 变更隔离防止改 A 坏 B |
| 从零开始做一个新产品 MVP | **Kiro** | 最快的"想法→可运行产品"路径 |
| 复杂重构，涉及 5+ 模块 | **GSD** | 上下文隔离 + 波级并行 |
| 企业团队，需要统一开发规范 | **Spec Kit** | 宪法 + 8 步闭环 = 可治理 |
| 在 Cursor / Claude Code / Copilot 之间切换 | **Trellis** | 跨平台 Spec/Task 同步 |
| 已有 SDD 工具，想强化 TDD 和 CR 纪律 | **Superpowers** | 工程习惯自动化 |
| 混合场景：原型 + 正式开发 | **Kiro + OpenSpec** | Kiro 快速验证，OpenSpec 正式集成 |

### 6.3 不需要 SDD 工具的信号

- 你是一个人在做一次性脚本或工具
- 项目只有 2-3 个文件，预计 1 周内完成
- 你已经很满意当前的 AI 编码效果，没有遇到上下文衰减或质量方差问题
- 团队对引入新工具流程的接受度较低

在这些情况下，Prompt SDD 已经足够。工具化 SDD 解决的是**复杂度带来的问题**——如果你的项目还没有这个复杂度，不必提前引入。

---

## 七、SDD 工具的未来趋势

### 7.1 核心循环的收敛

所有主流 SDD 工具在**Spec → Plan → Execute → Verify**的核心循环上已经趋同，说明这个基本模式已被验证。未来的分化将集中在：

- **上下文管理技术**：新鲜窗口 vs 结构化工件 vs 持久化记忆
- **多代理编排**：如何让多个 Agent 协同执行一个大规模任务
- **与 CI/CD 的集成**：SDD 工件的自动化验证融入部署流水线
- **企业治理**：合规、审计、权限管理的能力增强

### 7.2 对团队的启示

1. **不要被工具绑架**：SDD 的本质是"先想清楚再动手"，工具只是手段
2. **渐进式引入**：从 Prompt SDD 开始，遇到具体痛点后再引入工具
3. **组合优于统一**：没有万能的 SDD 工具，场景化的工具组合更有效
4. **节奏比工具更重要**：保持"思考→规格→编码→验证"的节奏，比使用什么工具更关键

---

## 八、总结

SDD 工具的涌现是 AI 辅助编程走向成熟化的必然结果。当"让 AI 写出代码"不再是问题时，行业的下一个核心挑战变成了**"如何确保 AI 写出的代码是正确、一致、可维护的"**。

从 Prompt SDD 到工具化 SDD，本质上是**把规范和约束从人脑/文字中提取出来，编码为可执行的系统**。这个过程与软件工程过去几十年走过的路如出一辙：从个人手艺→口头约定→文档规范→代码化/自动化。

选择 SDD 工具的关键不在于哪个工具最流行，而在于：

1. **你的痛点是什么？**（上下文衰减？变更串扰？验收流于形式？）
2. **你的团队状态如何？**（个人/小团队/大团队/企业？）
3. **你的项目阶段？**（绿地/棕地？维护/迭代/重构？）

回答好这三个问题，SDD 工具选型就是一门清晰的科学。

### 一个实用的起步策略

如果你的团队正在考虑引入 SDD 工具，推荐以下渐进路径：

1. **第一周**：在 CLAUDE.md 中写入 Prompt SDD 约束（零成本，立即生效）
2. **遇到第一个"改了 A 忘了 B"的 bug 后**：引入 OpenSpec，从 `/opsx:new` 开始
3. **遇到长任务上下文衰减后**：引入 GSD 的讨论→计划→执行流程
4. **团队扩展到 5 人以上**：考虑 Spec Kit 的宪法机制统一规范
5. **持续审视**：定期回顾工具引入后是否真正提升了交付质量，而非增加了流程负担
