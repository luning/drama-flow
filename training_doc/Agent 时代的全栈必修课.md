# Agent 时代的全栈必修课

## 内容简介

AI 编码工具已经把"写出能跑的代码"的门槛大幅拉低，功能实现类问题 Agent 反复调试基本能自己收敛。真正拉开差距的，是能不能看出"这个做法不对""这里设计有问题"——原生前端工程师看后端代码、后端工程师看前端代码，往往只能判断"功能跑起来了没有"，看不出对方那端的设计是否合理。这是全栈化转型最难补的一块。

本课程**不讲怎么造，教你在不擅长的那一端也能看出不合理的设计和不符合规范的写法**。能跑通不代表适合——全表扫描代替分页、单文件塞所有逻辑代替分层，这些做法在练手项目里无伤大雅，放进真实多人协作项目就是隐患，也恰恰是 Agent 最容易给出的方案。围绕 DramaFlow 短剧应用：

- 先走一遍请求全链路建立全栈认知地图，再对前端、后端、数据三层分别按认知顺序展开——不熟悉的技术栈没法一下子全懂，得先弄清楚几个有依赖关系的核心概念（比如后端：路由机制 → 三层结构 → 持久化 → 可观测性）；同时讲规范、练挑错，聚焦方案选择、分层是否合理这类只有理解项目语境才能识别的问题
- 讲清楚用 SDD 工具（OpenSpec / Superpowers）驱动 Agent 开发的实操方法


## 目标学员

1. **后端工程师**：能判断后端设计规范，但看不出前端 / Android 代码的设计是否合理
2. **前端工程师**：能判断前端设计规范，但看不出后端分层、事务边界是否合理
3. **运维 / 测试工程师**：懂部署和测试，但缺乏全栈代码结构的整体判断力

## 课程收益

1. **补齐跨端设计判断力**：不用精通实现细节，也能看出方案选择、分层是否配得上项目真实规模
2. **建立全栈认知地图**：讲清一次请求流经哪些层、为什么这样设计、技术选型的取舍
3. **掌握 SDD 工具实操**：用 OpenSpec / Superpowers 管理 Agent 开发中间产物，扩展项目专属检查点
4. **建立全栈判断力框架**：需求怎么拆到前后端各层、契约怎么跨端对齐、架构类任务什么时候必须加倍 review

## 授课方式

讲师讲授 + 现场演示 + 代码练习 + 案例研讨

## 课前准备

- AI 编码工具（Claude Code / Cursor / OpenCode，至少装一种）+ IDE（VS Code 或 IntelliJ IDEA）
- 课程涉及技术栈：Vue 3、Android（Kotlin）、Java Spring Boot、SQLite、Docker（无需安装运行环境，课上看懂即可）
- 课程涉及 SDD 工具：OpenSpec、Superpowers（讲师机演示为主，学员机器可选装）

## 课程大纲

> 内容总量对应约 2 天课程，各部分时长可根据学员背景灵活调整，此处不做精确到分钟的标注。

### 第一部分：全栈全景 —— 一次请求的完整旅程

> **目标**：跟着一个请求从头走到尾，建立"全栈有哪些层、每层程序怎么组织、数据怎么流"的直觉认知。

以 DramaFlow "短剧列表加载"为例，现场用 DevTools Network 抓请求，逐环节展开：

- **请求发起**：浏览器 / App 发 HTTP 请求，讲清 URL 结构和方法含义（GET/POST/PUT/DELETE）；对比 Android 端如何发起请求
- **路由分发**：Web 服务器转发给后端，路由层根据 URL 和方法匹配到 Controller
- **分层处理**（Controller→Service→Repository）：改业务不改接口，改数据库不影响业务
- **数据库查询**：ORM 把方法调用翻译成 SQL，避免手写 SQL 的拼写错误和注入风险
- **响应返回与客户端渲染**：对象序列化为 JSON、设状态码返回客户端；前端解析 JSON 更新组件状态、框架同步 DOM，Android 端 ViewModel 更新 LiveData 刷新 UI

### 第二部分：善用 SDD 工具适配全栈开发

> **目标**：用 OpenSpec / Superpowers 管理 Agent 开发的中间产物，把评审提前到写代码之前，并把项目专属检查点扩展进工具里。

**2.1 为什么中间产物才是评审的关键点**：Agent 写代码前先产出 proposal / design，描述前后端各做什么；等代码写完再挑错成本远高于方案阶段，且审方案不需要精通对方那端的实现细节

**2.2 OpenSpec 实操流程**：`explore`（可选）→ `propose`（产出 proposal.md/specs/design.md/tasks.md）→ `apply`（照 tasks.md 实现）→ `archive`（归档）；现场演示一次真实小变更的 propose，看 proposal.md 怎么描述前后端改动范围

**2.3 Superpowers 实操流程**：brainstorming（design.md）→ writing-plans（plan.md）→ 执行（subagent-driven 最常用）→ finishing；design.md / plan.md 和 OpenSpec 的 proposal / specs 起同样的评审作用

**2.4 SDD 工具里的 Review 机制**：OpenSpec 靠状态机防止任务带着缺失工件往下推进，归档前强制检查工件完整性；Superpowers 的 subagent-driven 执行默认双重审查（implementer + 独立 reviewer）；人可以借这些天然关卡把 review 精力集中在中间产物上

**2.5 把全栈关注点注入 SDD 工具**

- 核心动作：把前后端各自的专属检查点（踩过的坑、分层禁区）通过扩展工具本身注入 SDD 流程，而不是每次口头提醒 Agent
- 路径一：扩展 OpenSpec 自定义 Schema——DramaFlow 的 `dramaflow` schema（标注 Scope/Endpoint、Scenario 用 4 个 `#`）就是一个实例
- 路径二：引入独立的 Router 层——不改通用 Skill 本身，用映射层按任务所属层加载检查点，换项目不用碰 Skill

**2.6 【练习】审 proposal.md，挑出方案层面的问题**：给一份 DramaFlow 的 proposal.md 摘录，练习识别方案和需求匹配吗、有没有顺手重构不相关模块、前后端改动范围分工写清楚了吗

### 第三部分：后端视角 —— 服务端的程序结构

> **目标**：按认知顺序建立后端完整理解——路由 → 分层 → 持久化 → 可观测性；重点补齐前端 / 运维背景学员的判断力，不是教语法。

**3.1 后端认知顺序**

- 请求进来 → 代码分层：① 路由机制（URL→方法）→ ② 三层结构（Controller→Service→Repository，改业务不改接口）
- 数据读写 → 契约与安全：③ 持久化与 ORM（Entity↔表→SQL）→ ④ 请求/响应契约（RESTful、状态码、JSON）→ ⑤ 认证鉴权（JWT）
- 出问题怎么办：⑥ 异常处理（统一兜底）→ ⑦ 可观测性（traceId 贯穿全链路）

**3.2 后端基础编码规范清单**

- 状态码规范：200 成功、400 参数错误、401 未认证、403 无权限、404 不存在、500 服务端错误
- 日志规范：统一日志级别，不能用 `System.out.println`
- 安全规范：密码类字段不能明文落库、不能出现在日志里；Token 不能硬编码
- 这些规范模型很熟悉、Agent 一般不会写错——但转型工程师不认识的话，写对了也看不出"为什么对"

**3.3 AI 协作要点：后端专属 checkpoint**

- 接口契约测试：Request/Response 字段类型和约定一致吗？Service 业务规则有单测兜底吗？
- traceId 核验：日志贯穿三层吗？"新增路由容易漏注册"这类项目坑要写进 skill 固化
- 规模适配核验：列表接口做分页了吗？连接复用了吗？

**3.4 【练习】挑一段后端 diff 的方案问题**

- 给一段 AI 生成的后端 diff，练习识别：业务逻辑该不该下沉到 Service？是不是和已有方法重复该复用却新写？改动量超出需求了吗？是不是"能跑但只适合玩具项目"的做法（没分页、异常吞掉、配置写死）？

### 第四部分：客户端视角 —— 浏览器 / App 的程序结构

> **目标**：按认知顺序建立 Web 和 Android 完整理解——组件 → 响应式 → 路由 → 状态共享；重点补齐后端 / 运维背景学员的判断力，不是教语法。

**4.1 Web 认知顺序**（以 DramaFlow 首页为例）

- 页面搭起来：① 组件组织（template/script/style，逐层嵌套）→ ② 组件通信（props/emit）
- 数据驱动界面：③ 响应式（ref/reactive——和后端"请求-响应"模型差异最大的一环）→ ④ 路由（vue-router）→ ⑤ 跨组件状态共享（组件内 state vs 全局 Store/Pinia）
- 工程规范：⑥ 三态处理（loading/error/empty）→ ⑦ 视觉一致性（Design Token，不硬编码）

**4.2 Web 技术选型**：React vs Vue、SPA vs SSR

**4.3 Android 认知顺序**

- ① 项目结构（java/res/layout/Manifest/gradle）→ ② 生命周期（Activity/Fragment，不同状态能做什么）
- ③ 布局（XML+ViewBinding vs Jetpack Compose，声明式思维接近 Vue/React）→ ④ 状态管理（ViewModel+LiveData，类比 Pinia）
- ⑤ 跳转（Navigation/NavGraph）→ ⑥ 发请求（Retrofit + OkHttp）

**4.4 前端 / Android 基础编码规范清单**

- 目录规范：pages/ 放页面组件、components/ 放复用组件、stores/ 放跨组件状态，不能都塞一个文件
- Token 规范：色值 / 间距 / 字体禁止硬编码，必须引用 tokens.css
- 三态规范：异步数据加载必须处理 loading/error/empty，只写成功路径不算完成

**4.5 AI 协作要点：前端专属 checkpoint**

- 三态检查 + Design Token 合规（结合项目 `design-check` 脚本演示）
- 视觉核对：截图比对设计稿，评估组件树改动的影响范围
- 规模适配核验：状态塞进大组件了吗？没走 Store 直接组件间传值吗？

**4.6 【练习】挑一段前端 diff 的方案问题**

- 给一段 AI 生成的前端 diff，练习识别：多个组件是不是各自重复实现了请求封装，没复用 Store/API 层？本该放 Store 的状态写进组件内部了吗？这种写法是不是"页面简单时能跑，放到实际组件规模下会失控"的临时做法？

### 第五部分：数据视角 —— 数据如何存储和流动

> **目标**：按认知顺序建立数据层完整理解——表结构 → 关系 → ORM → 演进 → 性能；这层不分前后端背景，都容易只看"数据存进去了没有"，看不出设计是否合理。

**5.1 数据层认知顺序**

- 怎么建模：① 表结构与字段类型 → ② 表关系（一对一、一对多、多对多）→ ③ ORM 映射原理（Entity↔表，增删改查→SQL）
- 怎么演进与保性能：④ 约束与默认值（nullable、有没有默认值，决定能不能安全加字段）→ ⑤ Migration（up 创建/down 回滚，不直接改线上表）→ ⑥ 索引（不加全表扫描，加多了拖慢写入）

**5.2 技术选型**：关系型 vs NoSQL、ORM vs 原生 SQL

**5.3 数据层基础编码规范清单**

- Migration 规范：改表结构必须配 up/down 脚本，不能手动改线上表
- 字段设计规范：nullable 显式声明；新增字段避免直接 NOT NULL 且无默认值
- 索引规范：搜索 / 排序 / 外键字段该加索引，但不是都要加

**5.4 AI 协作要点：数据层专属 checkpoint**

- Migration 完整性：up/down 都生成了吗？down 验证过能回滚吗？
- 破坏性变更识别：NOT NULL 无默认值、删字段、改类型对现有数据的影响评估过吗？——典型必须人工确认（HITL）的节点
- 规模适配核验：该建索引的建了吗？该拆表的是不是偷懒塞进大 JSON 字段？

**5.5 【练习】判断 migration 方案是否合理**

- 给一个 migration 方案（如"加字段" vs "建关联表"），判断方案是否匹配需求复杂度——是不是为了"更完整"过度设计出不必要的关联表，或者该拆表却偷懒加了个大字段

### 第六部分：部署视角 —— 代码如何变成可访问的服务

> **目标**：理解容器化和 CI/CD 的基本概念。

- Docker：把应用和依赖打包成可运行的"容器"，解决"我电脑能跑、你电脑不行"的问题；docker-compose 一条命令编排前端、后端、数据库多个容器
- CI/CD：每次 push 代码自动跑测试、构建镜像，通过后自动部署到 dev/staging/prod 各自独立的环境
- 人需要判断什么：部署配置有没有把密码写死？环境变量对不对？

### 第七部分：【练习】Agent 追加一个新功能

> **目标**：完整走一遍真实的 vibe coding 循环，综合运用第二部分的 SDD 流程和第三 / 四 / 五部分讲的各层 checkpoint，练习人在每个环节的判断和决策。

- 场景：在 DramaFlow 上增加"搜索短剧"功能，涉及前端（搜索框+结果页）、后端（搜索接口）、数据库（可能加索引）
- **第一步：自己做需求拆解** —— 判断涉及哪些层、要不要新建接口/页面/表，用 SDD 工具产出 proposal/design
- **第二步：审查 Agent 生成的代码** —— 对照第三 / 四 / 五部分讲的 checkpoint，逐段判断"方案合理吗？有没有更简单的做法？"
- **第三步：集成验证** —— 前后端连起来测，正常路径和异常路径（搜不到、空关键词）都要走一遍
- **第四步：修复讲师预留的 bug** —— 练习怎么描述问题、怎么给 Agent 正确上下文让它修复

### 第八部分：AI 工作心法与核心判断力

> **目标**：本日核心章节，讲清哪些能力不能让渡给 Agent、全栈判断力落在哪几个点上，以及怎么按任务类型分配 review 力度。

**8.1 为什么判断力比以前更值钱**

- Agent 写代码快了，但架构、契约、验收必须人来把关——错误发现得越晚代价越高
- 技术债积累速度和代码生成速度成正比
- 对转型工程师尤其关键：本职那端天然有判断力，看陌生那端往往只剩"功能对不对"

**8.2 不能让渡的能力清单**

- 架构决策权：SQLite 还是 PostgreSQL、WebView 还是原生页面，AI 建议、人拍板
- 微观代码审阅：架构类改动必须逐行看，不能只看"功能好像跑起来了"
- HITL 最终裁决：验收标准、安全逻辑、数据模型变更、合并主分支前必须人工过一遍
- 可观测性建设：结构化日志、明确错误码、精确的测试失败定位——这是人要主动建的基础设施

**8.3 主动区分架构类 vs 执行类任务**

- 执行类：目标明确、结果可验证，直接交给 Agent 看结果
- 架构类：涉及权衡、无唯一正解，对比提问让 Agent 摆权衡、人来决策（如问"offset/limit 和 cursor-based 哪个更合适"，而不是直接问"怎么设计"）
- 先标注类型再定 review 力度：架构类加倍看，执行类放心收

**8.4 全栈判断细则（四个关键判断点）**

- **需求拆解** —— 涉及哪些层？新做还是扩展？小需求别大动干戈
- **接口契约** —— 参数、字段、类型、异常情况约定了吗？前后端各写各的会导致联调时字段名对不上
- **设计评估** —— 呼应第三 / 四 / 五部分练习：改动量匹配需求吗？风格一致吗？问一句"能不能少改几个文件"
- **集成验证与反馈引导** —— 正常 / 异常路径都跑了吗？Agent 跑偏了先判断原因，给具体信息："期望返回 A，实际返回了 B"

**8.5 【练习】判断任务类型**

- 给几张任务卡片（如"给短剧列表加个搜索接口" vs "把认证方式从 Session 换成 JWT"），当场判断执行类 / 架构类，说明对应的 review 力度该怎么调整
