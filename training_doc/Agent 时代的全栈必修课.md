# Agent 时代的全栈必修课

## 内容简介

AI 编码工具已让写代码的门槛大幅降低，但新问题随之而来：Agent 写出了前后端代码、数据库迁移、部署配置 —— 你看得懂吗？你敢上线吗？

本课程为不熟悉全栈技术的工程师设计，**不讲怎么造，教你怎么看懂 Agent 造出来的东西并判断对不对**。围绕 DramaFlow 短剧应用：先跟着一个请求走完全链路，建立全栈认知地图——理解各层程序结构是怎么组织的、为什么要这样组织；在此基础上，聚焦人在 Agent 开发中真正要做的判断：需求怎么拆到各层、接口契约怎么定、Agent 的方案怎么评估、集成怎么验证、出问题怎么引导 Agent 回到正轨。最终交付一张判断清单。

## 目标学员

1. **后端工程师**：能写 Java，但不懂前端和 Android 在干什么、代码怎么部署
2. **前端工程师**：能写页面，但不清楚后端如何处理请求、数据库长什么样
3. **产品经理**：能提需求，但看不懂 Agent 产出的技术方案是否合理
4. **运维 / 测试工程师**：懂部署和测试，但缺乏对全栈代码结构的整体理解

## 课程收益

1. **建立全栈认知地图**：能说出一次请求流经了哪些层、每层程序结构怎么组织、为什么这样设计
2. **理解技术选型逻辑**：知道各层主流技术选项的取舍，不只知其然
3. **掌握 Agent 场景的判断力**：需求怎么拆到各层、接口契约怎么定、Agent 的方案怎么评估、集成怎么验证
4. **拿到可落地的判断清单**：每次 Agent 交付代码后对照检查，而不是盲目信任

## 授课方式

讲师讲授 + 现场演示（Agent 实操）+ 案例研讨

## 课前准备

- AI 编码工具（Claude Code / Cursor / OpenCode，至少装一种）+ IDE（VS Code 或 IntelliJ IDEA）
- 课程涉及技术栈：Vue 3、Android（Kotlin）、Java Spring Boot、SQLite、Docker（无需安装运行环境，课上看懂即可）

## 课程大纲

### 第一部分：全栈全景 —— 一次请求的完整旅程（约 45min）

> **目标**：跟着一个请求从头走到尾，建立"全栈有哪些层、每层程序怎么组织、数据怎么流"的直觉认知。

以 DramaFlow "短剧列表加载"为例，现场用 DevTools Network 抓请求，逐环节展开：

- **请求发起**：浏览器 / App 发 HTTP 请求，讲清 URL 结构和方法含义（GET/POST/PUT/DELETE）；对比 Android 端如何发起请求
- **路由分发**：Web 服务器转发给后端，路由层根据 URL 和方法匹配到 Controller
- **分层处理**（Controller→Service→Repository）：Controller 接参数调 Service 返响应；Service 承载业务逻辑；Repository 封装数据库操作。分三层的理由：改业务不改接口，改数据库不影响业务
- **数据库查询**：ORM 把方法调用翻译成 SQL，数据库返回数据映射为 Java 对象。用 ORM 的理由：避免手写 SQL 的拼写错误和注入风险
- **响应返回**：对象序列化为 JSON，设状态码（200/400/500），返回客户端
- **客户端渲染**：前端解析 JSON → 更新组件状态 → 框架同步 DOM；Android 端 ViewModel 更新 LiveData → Compose/XML 刷新 UI

### 第二部分：客户端视角 —— 浏览器 / App 的程序结构（约 45min）

> **目标**：看懂 Web 和 Android 的代码是怎么组织的，理解组件树、状态管理、路由这些基本程序结构。

**2.1 Web 前端程序结构**

以 DramaFlow 首页为例，讲清四个核心结构：
- 组件怎么组织：template（画）、script（逻辑）、style（长相）三层结构；组件逐层嵌套，父传子 props、子通知父 emit
- 数据怎么驱动 UI：ref/reactive 管数据，数据变 UI 自动变——响应式的核心
- 页面怎么跳转：vue-router 把 URL 映射到组件
- 代码怎么跑：Vite 构建打包、热更新
- 底线：任何数据加载必须考虑 loading/error/empty 三种状态

**2.2 Web 技术选型**：React vs Vue、SPA vs SSR、局部状态 vs 全局状态

**2.3 Android 程序结构**
- 项目结构：java/（代码）、res/layout/（布局）、AndroidManifest.xml（声明）、build.gradle（依赖）
- Activity = 一个屏幕；生命周期回调 —— 理解"屏幕在不同状态下能做什么"
- ViewModel + LiveData：Android 的状态管理，屏幕旋转数据不丢（类比 Pinia）
- 布局：XML + ViewBinding vs Jetpack Compose（声明式 UI，接近 Vue/React 思维）
- Navigation Component 管跳转（NavGraph，类比 vue-router）；Retrofit + OkHttp 发 HTTP 请求

**2.4 人需要判断什么**
- 这个功能需要新页面还是改现有页面？涉及哪些组件？
- 页面需要哪些数据？这些数据从哪个接口来？

### 第三部分：后端视角 —— 服务端的程序结构（约 45min）

> **目标**：看懂后端代码的分层结构，理解每层为什么这样设计。

**3.1 后端的五层结构**

- 路由层：@GetMapping 把 URL 映射到方法
- Controller：接收参数，调用 Service，封装响应
- Service：业务逻辑（筛选、排序、分页、权限）—— 多 Controller 复用 + 统一事务边界
- Repository：Spring Data JPA 从方法名自动生成 SQL —— 避免手写 SQL 的拼写错误和注入风险
- Entity：标记 Java 类与数据库表的对应关系，定义字段和表关联

**3.2 技术选型要点**
- 框架：Spring Boot（主流企业级框架）
- RESTful 约定：URL 用名词、方法决定操作、状态码表达结果
- JWT 认证：Token 传递、过期刷新机制
- 错误处理与日志：统一异常处理 vs 逐个 try-catch；traceId 串联全链路日志

**3.3 人需要判断什么**
- 一个需求需要新接口还是扩展现有接口？接口的 URL、参数、返回值怎么定？
- 业务逻辑放在 Service 层的哪个方法？需要改几个文件？

### 第四部分：数据视角 —— 数据如何存储和流动（约 30min）

> **目标**：看懂数据库表结构，理解 ORM 如何连接代码和数据库。

**4.1 核心概念**
- 表结构：字段类型各自存什么，表关系（一对一、一对多、多对多）
- ORM 原理：Entity 类 ↔ 表，属性 ↔ 字段，增删改查写法如何翻译为 SQL
- Migration：数据库版本管理，每次改表结构都要迁移脚本（up 创建/down 回滚），不能直接改表
- 索引：搜索/排序字段不加索引为什么越来越慢（全表扫描 vs 索引查找）

**4.2 技术选型**：关系型 vs NoSQL、ORM vs 原生 SQL

**4.3 人需要判断什么**
- 这个功能需要新表还是加字段？字段类型和关系怎么定？
- 改了表结构，migration 怎么写？对现有数据有什么影响？

### 第五部分：部署视角 —— 代码如何变成可访问的服务（约 30min）

> **目标**：理解容器化和 CI/CD 的基本概念。

**5.1 核心概念**
- Docker 是什么：把应用和它的依赖打包成一个可运行的"容器"，解决"我电脑能跑，你电脑不行"的问题。Dockerfile 定义环境（基础镜像 + 装依赖 + 放代码 + 启动命令）→ 构建镜像 → 运行容器
- docker-compose：把前端、后端、数据库等多个容器编排在一起，一条命令全部启动
- CI/CD：每次 push 代码，自动跑测试、构建镜像（CI），通过后自动部署到对应环境（CD）；dev/staging/prod 三套环境各自独立

**5.2 人需要判断什么** —— 部署配置有没有把密码写死？环境变量对不对？

### 第六部分：现场演示 —— Agent 追加一个新功能（约 45min）

> **目标**：完整展示一次真实的 vibe coding 循环，重点展现人在每个环节的判断和决策。

- 场景：在 DramaFlow 上增加"搜索短剧"功能
- **第一步：人做需求拆解** —— 这个功能涉及前端（搜索框+结果页）、后端（搜索接口）、数据库（可能加索引）。讲师展示拆解思路，然后写 prompt 给 Agent
- **第二步：Agent 生成代码，人审查** —— 前端改了哪些文件、后端改了哪些、数据库改了哪些。讲师逐段讲解 diff，重点不是语法，而是"Agent 的方案合理吗？有没有更简单的做法？"
- **第三步：集成验证** —— 前后端连起来测，正常路径和异常路径（搜不到、空关键词）都走一遍
- **第四步：出问题，引导 Agent 修复** —— 故意预留 bug，展示人怎么描述问题、怎么给 Agent 正确的上下文让它修复

### 第七部分：人在 Agent 开发中的核心判断力（约 45min）

> **目标**：本日核心章节。Agent 能写代码，但设计、契约、验收这些事必须人来做。聚焦五个关键判断。

**7.1 需求拆解** —— 拿到一个需求，先拆到各层
- 这个功能涉及哪些层？前端改什么、后端改什么、数据库改什么？
- 是新页面还是改现有页面？是新接口还是扩展现有？是新表还是加字段？
- 原则：小需求不要大动干戈，优先扩展现有而非新建

**7.2 接口契约** —— 前后端之间的数据协议，人必须拍板
- 需要传哪些参数？返回哪些字段？字段叫什么、什么类型？
- 异常情况怎么约定？搜不到返回空列表还是报错？参数不合法返回什么？
- 前后端各写各的，没人定契约 → 联调时才发现字段名对不上

**7.3 设计评估** —— Agent 给的实现方案，人判断对不对
- 改动量和需求匹配吗？Agent 有时候会过度设计（小功能大重构）
- 和已有代码风格一致吗？Agent 可能用不同的模式实现同一类功能
- 有没有更简单的做法？问一句"能不能少改几个文件"往往能得到更好方案

**7.4 集成验证** —— Agent 说做完了，人怎么验证
- 前端和后端连起来对吗？数据能正常展示吗？
- 正常路径跑一遍，异常路径跑一遍（空数据、错误输入、网络断开）
- 有没有破坏已有功能？改了 A 功能，B 功能还能用吗？

**7.5 反馈引导** —— Agent 跑偏了，人怎么把它拉回来
- 先判断原因：是需求没描述清楚？还是上下文不够？还是 Agent 真的理解错了？
- 重新描述问题时给具体信息：不是"不对"，而是"期望返回 A，实际返回了 B"
- 必要时缩小范围：把大需求拆成小步骤，一步步引导

### 第八部分：收官 —— 判断清单与 Q&A（约 30min）

> **目标**：全天收敛，输出可落地使用的判断清单。

**8.1 判断清单（A4 打印版）**
- 拆解：需求涉及哪些层？新做还是扩展？小需求是否小改动？
- 契约：接口参数和返回值定了吗？异常情况约定了吗？前后端字段名一致吗？
- 设计：Agent 的方案和现有风格一致吗？改动量合理吗？有更简单做法吗？
- 验证：正常路径跑了吗？异常路径跑了吗？有没有破坏已有功能？
- 引导：出问题时，现象描述具体吗？期望说清楚了吗？需要缩小范围吗？

**8.2 Q&A 与反馈**
