# Agent 时代的全栈必修课

## 内容简介

AI 编码工具已经把"写出能跑的代码"的门槛大幅拉低，功能实现类问题 Agent 反复调试基本能自己收敛。真正拉开差距的是能不能看出"这里设计有问题"——原生前端工程师看后端代码、后端工程师看前端代码，往往只能判断"功能跑起来了没有"，看不出对方那端的设计是否合理，这是全栈化转型最难补的一块。

本课程**不讲怎么造，教你在不擅长的那一端也能看出不合理的设计和不符合规范的写法**。能跑通不代表适合——全表扫描代替分页、单文件塞所有逻辑代替分层，这些做法在练手项目里无伤大雅，放进多人协作项目就是隐患，也恰恰是 Agent 最容易给出的方案。内容上：

- 先走一遍请求全链路建立全栈认知地图，再对后端、Web、App（Android）、数据四层展开——每层先给知识全貌（语言/主框架/各类库/代码设计/契约与集成/安全/性能与扩展性/可观测性/测试九层，标注本课程覆盖到哪层），再进入认知顺序，只学"覆盖"项里的骨架概念（如后端：路由机制 → 三层结构 → 持久化）和横切关注点（如契约、安全、可观测性）；同时讲规范、练挑错，聚焦方案选择、分层是否合理这类只有理解项目语境才能识别的问题
- 各端讲完之后，讲清楚怎么用 SDD 工具和知识工程固化这些跨端经验，而不是每次口头提醒 Agent

## 目标学员

1. **后端工程师**：能判断后端设计规范，但看不出前端 / Android 代码的设计是否合理
2. **前端工程师**：能判断前端设计规范，但看不出后端分层、事务边界是否合理
3. **运维 / 测试工程师**：懂部署和测试，但缺乏全栈代码结构的整体判断力

## 课程收益

1. **补齐跨端设计判断力**：不用精通实现细节，也能看出方案选择、分层是否配得上项目真实规模
2. **建立全栈认知地图**：讲清一次请求流经哪些层、为什么这样设计、技术选型的取舍
3. **建立判断力框架**：区分硬技术决策（决定系统能力边界）和代码设计判断（决定可读可维护性），各自的判断依据来自哪里
4. **掌握 SDD + 知识工程实操**：用 SDD 工具管理 Agent 开发中间产物，并把跨端经验转化为 Agent 可加载的知识

## 授课方式

讲师讲授 + 现场演示 + 代码练习 + 案例研讨

## 课前准备

- AI 编码工具（Claude Code / Cursor / OpenCode，至少装一种）+ IDE（VS Code 或 IntelliJ IDEA）
- 课程涉及技术栈：主流前端框架（Vue/React 任一）、Android（Kotlin）、后端框架（Spring Boot/FastAPI 任一）、关系型数据库、Docker
- 课程涉及 SDD 工具

## 课程大纲（共 1 天，约 7.5h）

- 一、全栈全景——一次请求的完整旅程（0.5h）
- 二、后端视角（2h）
- 三、Web 视角（1h）
- 四、App（Android）视角（1h）
- 五、数据视角（0.5h）
- 六、部署视角（0.5h）
- 七、利用 SDD 和知识工程适配全栈开发（1h）
- 八、【练习】Agent 追加一个新功能（0.5h）
- 九、AI 工作心法与核心判断力（0.5h）

### 一、全栈全景 —— 一次请求的完整旅程（约 0.5h）

> **目标**：跟着一个请求从头走到尾，建立"全栈有哪些层、每层程序怎么组织、数据怎么流"的直觉认知。

以一个典型的"列表加载"请求为例，现场用 DevTools Network 抓请求：

- **请求发起**：浏览器 / App 发 HTTP 请求（URL 结构、GET/POST/PUT/DELETE）
- **路由分发**：路由层根据 URL 和方法匹配到 Controller
- **分层处理**（Controller→Service→Repository）：改业务不改接口，改数据库不影响业务
- **数据库查询**：ORM 把方法调用翻译成 SQL，避免手写 SQL 的拼写错误和注入风险
- **响应返回与客户端渲染**：JSON 序列化+状态码返回；前端更新组件状态、Android 端 ViewModel 更新 LiveData

### 二、后端视角 —— 服务端的程序结构（约 2h）

> **目标**：先建立后端的知识全貌和掌握路径，再按认知顺序展开学习，重点补齐前端 / 运维背景学员的判断力，不是教语法。

**2.1 后端知识全貌**（本课程只覆盖其中几层，其余留给日常工作积累，对应第九部分的隐性知识五维度）

- 语言（Python 语法、类型系统、同步/异步）——不覆盖，默认已掌握
- 主框架（FastAPI：路由注册、依赖注入、请求生命周期）——覆盖，骨架起点
- 各类库（SQLAlchemy ORM、Pydantic 数据校验）——覆盖，骨架终点
- 代码设计（三层结构 Controller→Service→Repository）——覆盖，骨架核心
- 契约与集成（RESTful、状态码、JSON 序列化）——覆盖，横切关注点
- 安全（认证鉴权 JWT、Token 存储、敏感字段处理）——覆盖，横切关注点
- 性能与扩展性 / 测试——不覆盖
- 可观测性（日志规范、异常兜底、traceId）——覆盖，横切关注点

**掌握路径**：阶段1 看得懂改得动（本课程全覆盖）→ 阶段2 能独立做方案判断（本课程覆盖入门/练习）→ 阶段3 主导架构演进（不涉及，留给日常积累）

**2.2 认知顺序**：① 路由机制 → ② 三层结构 → ③ 持久化与 ORM；横切关注点（读到哪层顺手认）：契约、安全、可观测性

**2.3 技术决策判断力**

- **硬技术决策**（决定系统能力边界，通常有对错）：例如 Token 有效期与刷新策略——内部管理后台可以宽松处理，涉及支付或敏感数据的系统里泄露窗口就是安全红线；判断依据来自项目的非功能需求（是否对外、合规要求、并发规模）
- **代码设计判断**（决定可读可维护性，没有绝对对错）：例如业务规则放 Controller 还是 Service——依据单一职责原则和项目已有分层惯例；重复逻辑要不要抽公共方法——依据"重复次数 vs 抽象成本"，练手 Demo 和多人协作项目的容忍阈值完全不同
- 判断依据 = 项目的设计规范和已沉淀的设计决策，不是抽象的"好不好"（第七部分讲怎么固化、怎么喂给 Agent）

**2.4 规范清单**：状态码规范（200/400/401/403/404/500）；日志规范（不能裸标准输出）；安全规范（密码类字段不落库、不进日志，Token 不硬编码）——这些模型很熟悉、Agent 一般不会写错，但转型工程师不认识的话，写对了也看不出"为什么对"

**2.5 【练习】挑一段后端 diff 的方案问题**：业务逻辑该不该下沉到 Service？该复用却新写了吗？是不是"能跑但只适合玩具项目"的做法（没分页、异常吞掉、配置写死）？属于硬技术决策还是代码设计判断？

### 三、Web 视角 —— 浏览器端的程序结构（约 1h）

> **目标**：先建立 Web 端的知识全貌，再按认知顺序展开学习，补齐后端 / 运维背景学员的判断力；额外讲清怎么借 Agent 把需求快速变成可视化原型。

**3.1 Web 知识全貌**

- 语言（TypeScript 类型系统）——不覆盖，默认已掌握
- 主框架（Vue3：组件组织、响应式、生命周期钩子）——覆盖，骨架核心
- 各类库（Vite、Pinia、Vue Router）——覆盖，骨架延伸
- 代码设计（组件拆分粒度、目录规范、Design Token）——覆盖，骨架核心
- 契约与集成（props/emit、JSBridge 协议）——覆盖，横切关注点
- 安全（登录态存储、XSS/CSRF 防护）——覆盖，横切关注点
- 性能与扩展性 / 测试——不覆盖
- 可观测性（三态处理 loading/error/empty）——部分覆盖

**3.2 认知顺序**：① 组件组织 → ② 组件通信（props/emit）→ ③ 响应式 → ④ 路由 → ⑤ 跨组件状态共享；横切关注点：契约、安全、可观测性

**3.3 技术决策判断力**

- **硬技术决策**：登录态存 Cookie 还是 LocalStorage——纯展示型站点影响有限，涉及用户身份或支付信息的系统里选错就是 XSS/CSRF 风险的直接来源；判断依据来自安全模型和数据敏感级别
- **代码设计判断**：状态放组件内部还是全局 Store——依据是否跨组件消费；要不要抽公共 API 层——单页原型和十几个页面共存的长期项目，抽象必要性完全不同

**3.4 规范清单**：目录规范（页面组件/复用组件/跨组件状态分目录）；Token 规范（色值/间距/字体禁止硬编码，必须引用设计 Token）；三态规范（loading/error/empty 必须处理，只写成功路径不算完成）

**3.5 【练习】挑一段 Web diff 的方案问题**：多个组件是不是各自重复实现了请求封装，没复用 Store/API 层？该放 Store 的状态写进组件内部了吗？这是不是"页面简单时能跑，组件规模上去就会失控"的做法？

**3.6 【新增】需求到原型：用 Agent + Design System 快速出图**

- 核心思路：原型页面的色值、间距、组件不是 Agent 凭记忆生成，而是先把设计系统（Token、约束、页面规则）作为上下文注入，再让 Agent 在约束内生成，从源头避免"能看但不合规"的原型
- 现场演示：给 Agent 一句模糊需求（如"加一个收藏列表页"），走一遍完整流程：
  1. Agent 先读 `design-system/tokens/`（可用色值/间距/动效变量）、`design-system/specs/constraints.md`（业务约束，如每页只能有一个 Primary CTA）、`design-system/specs/design-rules.md`（页面结构模板）
  2. 需求模糊时，Agent 应先追问核心功能、展示数据、关键交互，而不是直接猜着生成
  3. 生成时强制引用 `var(--color-primary)` 等 Token，禁止硬编码色值；复用已有组件 class（如 `.drama-grid`），不重写样式
  4. 生成后跑 `check_tokens.py` / `check_constraints.py` 做合规校验，而不是靠肉眼看像不像
- 人的判断点：Agent 生成的原型是复用了已有页面模式，还是重新发明了一套？新增的约束该不该反哺进 design-system，让下一次生成自动遵守？

### 四、App（Android）视角 —— 客户端的程序结构（约 1h）

> **目标**：先建立 Android 端的知识全貌，再按认知顺序展开学习，补齐 Web / 后端背景学员的判断力。

**4.1 App 知识全貌**

| 层级 | 覆盖情况 |
|------|------|
| 语言（Kotlin 语法、协程） | 不覆盖，默认已掌握 |
| 主框架（Activity/Fragment 生命周期、ViewModel+LiveData、Navigation） | 覆盖，骨架核心 |
| 各类库（ExoPlayer、网络请求库） | 部分覆盖（网络层讲，播放器内部机制不深入） |
| 代码设计（Fragment/ViewModel/Repository 分层） | 覆盖，骨架核心 |
| 契约与集成（与 H5 的 JSBridge 协议、网络接口契约） | 覆盖，横切关注点 |
| 安全（EncryptedSharedPreferences、敏感凭证处理） | 覆盖，横切关注点 |
| 性能与扩展性 / 测试 | 不覆盖 |
| 可观测性（网络异常处理、崩溃监控） | 部分覆盖 |

**4.2 认知顺序**：① 项目结构 → ② 布局 → ③ 状态管理（ViewModel+LiveData）→ ④ 跳转（Navigation）→ ⑤ 发请求；横切关注点：生命周期、契约（JSBridge）、安全（加密存储）

**4.3 技术决策判断力**

- **硬技术决策**：敏感数据用明文 SharedPreferences 还是加密存储——内部测试 App 可能被忽略，涉及账号或支付凭证的正式产品里这直接决定能否通过安全合规审查
- **代码设计判断**：跳转逻辑放 Fragment 还是 ViewModel——依据是"UI 决策"还是"业务决策"的边界；用 Navigation 还是裸 Intent——Demo 和多模块协作长期项目对可维护性的要求不同

**4.4 规范清单**：分层规范（Fragment 只做 UI 绑定、ViewModel 管理状态和业务逻辑、Repository 封装数据源）；生命周期规范（避免错误阶段持有 Context 导致内存泄漏）；安全存储规范（Token 等敏感信息禁止明文存储）

**4.5 【练习】挑一段 App diff 的方案问题**：业务逻辑是不是写进了 Fragment？跳转是不是绕过 Navigation 直接用 Intent？敏感信息存储方式对吗？

### 五、数据视角 —— 数据如何存储和流动（约 0.5h）

> **目标**：不分前后端背景，这层都容易只看"数据存进去了没有"，看不出设计是否合理。

**5.1 数据层知识全貌**：语言（SQL，不覆盖）；主框架（SQLAlchemy 2.0 ORM 映射，覆盖）；各类库（Migration 工具，覆盖）；代码设计（表结构/表关系设计，覆盖）；契约与集成（Entity 与 API 响应模型映射，部分覆盖）；性能与可观测性（索引策略、约束校验，部分覆盖）；安全已在后端层讲过，此处不重复；测试不覆盖

数据层没有独立的三阶段掌握路径，判断力随后端 / App 的进阶阶段同步积累。

**5.2 认知顺序**：① 表结构与字段类型 → ② 表关系 → ③ ORM 映射原理；横切关注点：约束与默认值、Migration、索引

**5.3 技术决策判断力**

- **硬技术决策**：给已有大量数据的表加 NOT NULL 且无默认值的字段——原型验证阶段可以直接改，承载生产流量的表这么改会锁表或写入报错
- **代码设计判断**：关联关系建独立表还是塞进大 JSON 字段——依据这个关系未来会不会被单独查询/索引，不是"看起来更完整"就该建关联表

**5.4 规范清单**：Migration 规范（改表结构必须配 up/down 脚本，不能手动改线上表）；字段设计（nullable 显式声明，新增字段避免直接 NOT NULL 无默认值）；索引规范（搜索/排序/外键字段该加，但不是都要加）

**5.5 【练习】判断 migration 方案是否合理**：给一个方案（如"加字段" vs "建关联表"），判断是否匹配需求复杂度——是否为了"更完整"过度设计，或该拆表却偷懒加了个大字段

### 六、部署视角 —— 代码如何变成可访问的服务（约 0.5h）

> **目标**：理解容器化和 CI/CD 的基本概念。

- 容器化：把应用和依赖打包成可运行的"容器"，解决"我电脑能跑、你电脑不行"的问题；编排工具一条命令拉起前端、后端、数据库多个容器
- CI/CD：每次提交自动跑测试、构建镜像，通过后自动部署到 dev/staging/prod 各自独立的环境
- 人需要判断什么：部署配置有没有把密码写死？环境变量对不对？

### 七、利用 SDD 和知识工程适配全栈开发（约 1h）

> **目标**：讲清楚"精通一个端"背后到底积累了哪些隐性知识，以及怎么把这些知识变成 Agent 可加载的上下文，而不是每次口头提醒。

**7.1 隐性知识的五个维度**

- 前面几部分的判断力练习本质上都在练"识别项目专属的隐性知识"——路由容易漏注册、状态该不该上提、字段该不该建关联表，都不是语法问题，是经验问题
- 一个端的专家和新手的差距，体现在是否系统性掌握以下五类隐性知识：
  - **结构知识**：这个端的模块怎么组织、入口在哪、谁负责哪块
  - **编码规范**：命名、日志、错误处理这类每次都要遵守的硬性规则
  - **设计决策**：为什么这么设计、否决过哪些方案、项目形成了哪些设计惯例
  - **任务经验**：反复做同类任务时踩过的坑、容易漏掉的步骤
  - **领域知识**：该端相关但不在代码库里的外部规范（浏览器兼容性、平台生命周期机制等）
- 这五类知识直接对应各端进阶路线图的阶段3——主导架构演进、反哺知识库；转型工程师要在陌生端补判断力，缺的正是这五类，可按这个清单主动查漏补缺

**7.2 把隐性知识变成 Agent 能用的上下文**

- Agent 执行时只看得到 Context 和 Instructions，Skill 只定义推理模式（怎么做），不该塞领域内容（做什么）——领域内容属于上面五类知识，需单独存放
- Router 负责把"当前任务属于哪个端、该加载哪些知识"映射起来：自定义 schema 用字段标注端归属，用固定格式约束场景描述；不用 schema 机制时，也可以用一份路由文件手动维护映射关系

**7.3 全栈自定义 SDD Skill 举例**

- 这类适配不必等工具厂商提供，思路是把反复出现的检查动作固化成可复用的 Skill，例如："审 diff 是否符合项目分层惯例"（检查改动是否越层、该复用却新写）、"新增接口检查清单"（按分层规范提示容易漏掉的注册/测试步骤）、"三态检查"（扫描新增的异步数据加载是否处理了 loading/error/empty）
- 价值在于把口头反复提醒的内容变成 Agent 每次都会执行的动作，且和具体项目的知识内容解耦，换项目只需换知识，不用重写 Skill

**7.4 【练习】给一个项目陷阱归类**：给一个具体案例（如"新增路由容易忘记注册"），讨论它属于五类知识里的哪一类、该存放在什么位置、什么时机该被加载给 Agent

### 八、【练习】Agent 追加一个新功能（约 0.5h）

> **目标**：压缩版的完整 vibe coding 循环，综合运用第二至第五部分的判断力和第七部分的知识固化思路。

- 场景：给内容类应用增加"搜索"功能，涉及前端（搜索框+结果页）、后端（搜索接口）、数据库（可能加索引）
- 时间盒流程（合并原本的需求拆解/审查/验证/修复/沉淀五步，压缩执行）：
  1. **需求拆解 + 生成**（约 10min）：判断涉及哪些层，用 SDD 工具产出简要 proposal，Agent 出代码
  2. **审查 + 修 bug**（约 15min）：对照判断力框架挑方案问题；修复讲师预留的一个 bug，练习怎么给 Agent 正确上下文
  3. **验证 + 沉淀**（约 5min）：正常/异常路径各跑一次；这次踩的坑按五类知识框架判断该记录成哪一类

### 九、AI 工作心法与核心判断力（约 0.5h）

> **目标**：本课程收尾章节，讲清哪些能力不能让渡给 Agent、全栈判断力落在哪几个点上，以及怎么按任务类型分配 review 力度。

- **判断力比以前更值钱**：Agent 写代码快了，但架构、契约、验收必须人来把关，错误发现得越晚代价越高，技术债积累速度和代码生成速度成正比；对转型工程师尤其关键，本职那端天然有判断力，看陌生那端往往只剩"功能对不对"
- **不能让渡的能力**：架构决策权（AI 建议、人拍板）；微观代码审阅（架构类改动必须逐行看）；HITL 最终裁决（验收标准、安全逻辑、数据模型变更、合并主分支前必须人工过一遍）；可观测性建设（结构化日志、明确错误码、精确的测试失败定位，这是人要主动建的基础设施）
- **区分架构类 vs 执行类任务**：执行类目标明确、结果可验证，直接交给 Agent 看结果；架构类涉及权衡、无唯一正解，对比提问让 Agent 摆权衡、人来决策（如问"两种方案哪个更合适"，而不是直接问"怎么设计"）；先标注类型再定 review 力度
- **判断力的两个维度收口**：硬技术决策决定系统能力边界，通常有对错，判断依据来自项目的非功能需求、合规要求、规模预期；代码设计判断决定可读可维护性，没有绝对对错，判断依据来自设计原则和项目已沉淀的设计惯例；核心方法是把项目已有规范作为上下文判断方案适不适合本项目，而不是脱离语境抽象评判"对不对"
- **用判断力框架优化 SDD 工作步骤**：① 让 Agent 先解释这一步的技术决策和权衡点，而不是直接出代码 → ② 主动提问权衡的关键分歧点（尤其硬技术决策）→ ③ 对照第七部分固化的设计规范判断方案是否适合当前项目 → ④ 选最适合当前项目语境的方案，而不是"看起来更完整/更通用"的方案 → ⑤ 把决策沉淀回知识库，形成闭环
- **全栈判断细则**：需求拆解（涉及哪些层？新做还是扩展？小需求别大动干戈）；接口契约（参数/字段/类型/异常情况约定了吗？）；设计评估（改动量匹配需求吗？能不能少改几个文件？）；集成验证与反馈引导（正常/异常路径都跑了吗？Agent 跑偏了先判断原因，给具体信息："期望返回 A，实际返回了 B"）
